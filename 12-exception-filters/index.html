12. 异常过滤器 ​

对应漫画

本章配套四格漫画：EP.12 异常过滤器（含剧情回顾、知识点拆解、坑点清单与自测题）

本章示例：server/src/ch12-exception-filters（npm run start:ch12 → http://localhost:3012）

异常过滤器是什么 ​

异常过滤器（Exception Filter）是请求处理管线的最后兜底：任何一层（守卫、拦截器、管道、控制器、服务）抛出的异常，最终都会到达这里，由它决定给客户端返回什么。

Nest 内置一个全局异常过滤器：能识别 HttpException（按其状态码响应），其余一律 500。但真实项目需要统一的错误响应结构与业务错误码体系——这正是自定义过滤器的价值。

本章搭建两层防线：

text
异常抛出
  ├── HttpException（含 BizException）→ HttpExceptionFilter → 统一结构 + 业务错误码
  └── 其他（代码 bug 的 Error 等）      → AllExceptionsFilter → 500 + 不泄露堆栈

代码实现 ​

业务异常体系 ​

BizException 在 HTTP 状态码之外携带业务错误码（前端按码做分支处理，比解析文案可靠得多）：

ts
// 文件: server/src/ch12-exception-filters/exceptions/biz.exception.ts
// 业务异常基类：携带业务错误码，与 HTTP 状态码解耦
import { HttpException, HttpStatus } from '@nestjs/common';

export class BizException extends HttpException {
    constructor(
        public readonly code: string, // 业务错误码，如 USER_NOT_FOUND
        message: string,
        status: HttpStatus = HttpStatus.BAD_REQUEST,
    ) {
        super(message, status);
    }
}

HTTP 异常过滤器 ​

@Catch(HttpException) 只捕获 HttpException 及其子类：

ts
// 文件: server/src/ch12-exception-filters/filters/http-exception.filter.ts
// HTTP 异常过滤器：把 HttpException（含 BizException）统一成一致的响应结构
import { ArgumentsHost, Catch, ExceptionFilter, HttpException } from '@nestjs/common';
import type { Request, Response } from 'express';
import { BizException } from '../exceptions/biz.exception';

@Catch(HttpException) // 只捕获 HttpException 及其子类
export class HttpExceptionFilter implements ExceptionFilter {
    catch(exception: HttpException, host: ArgumentsHost) {
        const ctx = host.switchToHttp();
        const response = ctx.getResponse<Response>();
        const request = ctx.getRequest<Request>();
        const status = exception.getStatus();

        response.status(status).json({
            statusCode: status,
            // BizException 带业务错误码；普通 HttpException 用通用码
            code: exception instanceof BizException ? exception.code : 'HTTP_ERROR',
            message: exception.message,
            path: request.url,
            timestamp: new Date().toISOString(),
        });
    }
}

兜底过滤器 ​

@Catch() 不带参数 = 捕获一切。它存在的意义：非 HTTP 异常（代码 bug）绝不把堆栈泄露给客户端——堆栈留在服务端日志，客户端只收到通用文案：

ts
// 文件: server/src/ch12-exception-filters/filters/all-exceptions.filter.ts
// 兜底过滤器：@Catch() 不带参数 = 捕获所有未被更具体过滤器接住的异常
// 兜底存在的意义：非 HTTP 异常（如代码 bug 抛出的 Error）绝不把堆栈泄露给客户端
import { ArgumentsHost, Catch, ExceptionFilter, HttpStatus } from '@nestjs/common';
import type { Request, Response } from 'express';

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
    catch(exception: unknown, host: ArgumentsHost) {
        const ctx = host.switchToHttp();
        const response = ctx.getResponse<Response>();
        const request = ctx.getRequest<Request>();

        // 服务端保留完整堆栈便于排查
        console.error('[ch12] 未预期异常:', exception);

        response.status(HttpStatus.INTERNAL_SERVER_ERROR).json({
            statusCode: HttpStatus.INTERNAL_SERVER_ERROR,
            code: 'INTERNAL_ERROR',
            message: '服务器内部错误',
            path: request.url,
            timestamp: new Date().toISOString(),
        });
    }
}

注册 ​

APP_FILTER 注册全局过滤器。匹配规则是「最具体的优先」，所以两层过滤器同时存在不冲突：

ts
// 文件: server/src/ch12-exception-filters/app.module.ts
// APP_FILTER 注册全局过滤器；匹配规则是「最具体的优先」，
// 因此 HttpExceptionFilter 与 AllExceptionsFilter 同时存在时不冲突
import { Module } from '@nestjs/common';
import { APP_FILTER } from '@nestjs/core';
import { HttpExceptionFilter } from './filters/http-exception.filter';
import { AllExceptionsFilter } from './filters/all-exceptions.filter';
import { UsersController } from './users.controller';

@Module({
    controllers: [UsersController],
    providers: [
        { provide: APP_FILTER, useClass: AllExceptionsFilter },
        { provide: APP_FILTER, useClass: HttpExceptionFilter },
    ],
})
export class AppModule {}

抛出异常的演示控制器 ​

ts
// 文件: server/src/ch12-exception-filters/users.controller.ts
import { Controller, ForbiddenException, Get, Param, ParseIntPipe } from '@nestjs/common';
import { UserNotFoundException } from './exceptions/user-not-found.exception';

@Controller()
export class UsersController {
    // GET /users/1 → 正常；GET /users/999 → 抛业务异常（404 + USER_NOT_FOUND）
    @Get('users/:id')
    findOne(@Param('id', ParseIntPipe) id: number) {
        if (id !== 1) {
            throw new UserNotFoundException(id);
        }
        return { id: 1, name: '张三' };
    }

    // GET /forbidden —— 内置 HttpException 也走统一响应结构（code: HTTP_ERROR）
    @Get('forbidden')
    forbidden() {
        throw new ForbiddenException('没有访问权限');
    }

    // GET /boom —— 普通 Error：被兜底过滤器接住，返回 500 + INTERNAL_ERROR
    @Get('boom')
    boom() {
        throw new Error('模拟代码 bug：Something went wrong');
    }
}

最佳实践与坑点 ​

  1. 业务码与 HTTP 状态码解耦：HTTP 码给网关/中间层看，业务码（USER_NOT_FOUND）给前端逻辑看；同一个 404 可能对应多种业务场景；
  2. 业务异常集中在 exceptions/ 目录：继承 BizException 基类，一处定义、全站复用；
  3. 兜底过滤器里必须 console.error 保留堆栈：否则线上 bug 无从排查；推荐接入结构化日志（如 winston、pino）；
  4. @Catch() 参数决定捕获范围：@Catch(HttpException) 精确匹配子类树；@Catch() 全捕获；@Catch(BadRequestException) 只匹配单一类型；
  5. 过滤器中拿不到响应后要自己 response.json()：此时脱离了 Nest 的标准响应流程，拦截器的响应包装也不会再执行——所以错误结构要在过滤器里一次性写完整。
