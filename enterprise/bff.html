BFF：聚合、裁剪、降级 ​

BFF 聚合、裁剪、缓存与超时降级的企业级实现。

apps/api/src/bff 里有可运行的聚合接口、下游 mock 服务、按端裁剪、聚合缓存与超时降级，聚合块包括用户、审计、订单摘要与下游通知，并有单测与 e2e 覆盖。GraphQL、熔断器、跨服务追踪透传未实现，在文末单独列出。

业务背景 ​

客户端直连多个下游会带来三件事：请求数爆炸、字段冗余、端上拼装逻辑重复。BFF（Backend For Frontend）把「取数、裁剪、兜底」收敛到服务端一层：

  • Web、管理后台、移动端各要一份结构不同的数据，而不是同一份大 JSON 各自过滤；
  • 某个下游慢了，页面不应该整屏白掉；
  • 下游地址、超时、降级值属于服务端决策，不该下发到客户端。

本页对应的问题是：一个聚合接口在部分下游故障时，怎么仍然给出可用、可解释的响应。

数据模型 ​

聚合视图不落库，只定义「返回什么」：

缓存键bff:dashboard:{client}:{userId}:{simulate|live}同上

两条设计约束：

  1. 裁剪是白名单不是黑名单。实体新增字段时默认不出现在任何端，漏配的后果是「前端看不到」，而不是「内部字段泄漏」。
  2. 块结构永远一致。降级块也返回 data: []（订单块是 { scope, total: 0, items: [] }），前端只写一套渲染分支，靠 status 展示「暂时没有加载出来」。

订单块还多一层语义：scope 区分 self 与 all。admin 端看全量摘要，web / mobile 只看当前用户；即使是 admin 角色，用 web 端时也会显式带上 userId 过滤（不能靠「admin 默认全量」的默认值）。

关键流程与时序 ​

text
客户端 GET /api/bff/dashboard?client=web
  │
  ├─ 鉴权（全局 JWT Guard）
  ├─ 端与角色校验：client=admin 只允许 admin
  ├─ 查聚合缓存 ──命中──→ 直接返回（x-cache: hit）
  │
  └─ 未命中：并行取块（受总预算约束）
       ├─ profile   ← UsersService（关键块，失败即整体失败）
       ├─ audits    ← AuditService（仅 admin 端）
       ├─ orders    ← OrdersService（web/mobile 只看自己，admin 看全量摘要）
       ├─ catalog   ← OrdersService.listProducts（公开数据，但内部字段按端裁剪）
       └─ notifications ← HTTP 调下游 mock（单块超时 400ms）
            └─ 失败 → 该块 degraded，其余照常返回
  │
  ├─ 按端裁剪字段
  ├─ 写聚合缓存（10s，降级结果也缓存，避免失败风暴重复打下游）
  └─ 200 + { data, meta }，meta 里标记 partial / blocks / errors

入口只做三件事：拿身份、拿 origin、把 x-cache 写回响应头。

ts
/**
 * 按端聚合的首屏接口。
 *
 * 下游地址未配置时（示例默认），`BFF_NOTIFICATIONS_BASE_URL` 为空，
 * 用当前请求的 origin 去访问同进程的 mock 服务；
 * 真实部署时把它指向内部服务地址，BFF 代码不需要改。
 */
@Get('dashboard')
async dashboard(
  @Query() query: DashboardQueryDto,
  @CurrentUser() actor: AuthenticatedUser,
  @Req() request: Request,
  @Res({ passthrough: true }) response: Response,
): Promise<DashboardView> {
  const origin = `${request.protocol}://${request.get('host') ?? 'localhost'}`;
  const { view, cacheHit } = await this.bffService.dashboard({
    actor,
    client: query.client,
    simulate: query.simulate,
    origin,
  });

  // 与其它接口保持同一个观测口径：x-cache 表示聚合结果是否来自缓存
  response.setHeader('x-cache', cacheHit ? 'hit' : 'miss');
  return view;
}

聚合服务先做两道边界校验，再进入缓存与并行取块：

ts
async dashboard(input: DashboardInput): Promise<{ view: DashboardView; cacheHit: boolean }> {
  const { actor, client, simulate, origin } = input;

  // 端与角色是两层不同的边界：admin 端会返回审计与邮箱，
  // 只靠前端的「隐藏菜单」不算权限控制。
  if (client === 'admin' && actor.role !== 'admin') {
    throw new ForbiddenException({
      code: 'BFF_CLIENT_FORBIDDEN',
      message: '当前角色不能使用 admin 端聚合',
      details: { requiredRole: 'admin', actualRole: actor.role },
    });
  }

  // simulate 是演示开关；生产环境必须关闭，否则任何人都能制造降级
  if (simulate && this.nodeEnv === 'production') {
    throw new ForbiddenException({
      code: 'BFF_SIMULATE_FORBIDDEN',
      message: '生产环境不允许使用故障注入参数',
    });
  }

  const startedAt = Date.now();
  // 键里必须带身份与端：不同用户数据不同、不同端裁剪后的字段不同
  const cacheKey = `bff:dashboard:${client}:${actor.id}:${simulate ?? 'live'}`;
  const cached = await this.cache.getOrSet(
    cacheKey,
    () => this.aggregate({ actor, client, simulate, origin }),
    this.config.cacheTtlSeconds,
  );

  return {
    view: {
      ...cached.value,
      // 这两个字段每次请求重新计算，不能跟着缓存一起变旧
      generatedAt: new Date().toISOString(),
      meta: {
        ...cached.value.meta,
        elapsedMs: Date.now() - startedAt,
        cache: cached.hit ? 'hit' : 'miss',
      },
    },
    cacheHit: cached.hit,
  };
}

// 审计块、订单块与通知块没有依赖关系，并行发起，总耗时取决于最慢的一块；

订单块不直接返回订单明细，而是先压成摘要；scope 与字段白名单一起决定客户端最终看到什么：

ts
/**
 * 订单块：web/mobile 只取当前用户，admin 端取全量摘要。
 *
 * 注意 admin 用户也可能用 web 端登录，所以这里显式传 userId 而不是依赖
 * OrdersService.list 里「admin 不传就全量」的默认行为。
 */
private async fetchOrders(
  actor: AuthenticatedUser,
  client: BffClient,
): Promise<OrdersSummary> {
  const query = new ListOrdersQueryDto();
  query.page = 1;
  query.pageSize = ORDER_LIMITS[client];
  if (client !== 'admin') {
    query.userId = actor.id;
  }

  const page = await this.orders.list(query, actor);
  return {
    scope: client === 'admin' ? 'all' : 'self',
    total: page.total,
    items: page.items.map(toOrderSummary),
  };
}

商品块的数据源是公开目录，但内部字段同样要按端取舍；裁剪放在聚合层，而不是让领域服务删字段：

ts
/**
 * 商品块：目录本身是公开数据，裁剪的是「内部字段」而不是「谁能看」。
 *
 * sku 与 updatedAt 只给 admin：客户端拿不到这两个字段也不需要，
 * 但它们出现在内部接口是合理的，所以不能靠商品接口自己删字段，
 * 必须在聚合层按端取舍。
 */
private async fetchCatalog(client: BffClient): Promise<CatalogSummary> {
  const products = await this.orders.listProducts();
  return {
    total: products.length,
    items: products.slice(0, PRODUCT_LIMITS[client]).map(toProductSummary),
  };
}

下游客户端是 BFF 与外部服务之间唯一的接触面，超时、状态码解析、错误归类都在这里完成：

ts
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import type { AppConfig, BffConfig } from '../../config/configuration.js';
import type { NotificationItem, SimulateKind } from '../dashboard.types.js';

/** 下游返回非 2xx 时抛这个错误，便于聚合层区分「超时」与「下游明确报错」 */
export class UpstreamError extends Error {
  constructor(
    readonly upstream: string,
    readonly status: number,
    message: string,
  ) {
    super(message);
    this.name = 'UpstreamError';
  }
}

export interface FetchNotificationsOptions {
  userId: string;
  /** 下游地址未配置时，用它拼出「本进程的 mock 服务」地址 */
  origin: string;
  limit: number;
  simulate?: SimulateKind;
  signal: AbortSignal;
}

/**
 * 通知服务的客户端。
 *
 * 这是 BFF 与下游之间唯一的接触面：超时、解析、错误归类都在这里完成，
 * 聚合层只处理「成功数据」和「降级结果」两种状态。
 * 示例中的下游是同进程的 mock controller；真实项目里它换成内网地址即可，
 * 聚合逻辑不用改。
 */
@Injectable()
export class NotificationsClient {
  private readonly config: BffConfig;
  private readonly apiPrefix: string;

  constructor(configService: ConfigService<AppConfig, true>) {
    this.config = configService.get('bff', { infer: true });
    this.apiPrefix = configService.get('apiPrefix', { infer: true });
  }

  async fetch(options: FetchNotificationsOptions): Promise<NotificationItem[]> {
    const base = this.config.notificationsBaseUrl ?? options.origin;
    const url = new URL(`/${this.apiPrefix}/mock/notifications`, base);
    url.searchParams.set('userId', options.userId);
    url.searchParams.set('limit', String(options.limit));

    // 演示开关最终变成下游的延迟/故障参数，而不是在 BFF 里假装降级
    if (options.simulate === 'notifications-timeout') {
      url.searchParams.set('delayMs', '2000');
    }
    if (options.simulate === 'notifications-error') {
      url.searchParams.set('fail', '1');
    }

    const response = await fetch(url, {
      signal: options.signal,
      headers: { accept: 'application/json' },
    });

    if (!response.ok) {
      throw new UpstreamError('notifications', response.status, `下游返回 HTTP ${response.status}`);
    }

    // 下游自己也用 { data, meta } 外壳：解析点只有这一处
    const body = (await response.json()) as { data?: { items?: NotificationItem[] } };
    return body.data?.items ?? [];
  }
}

示例里的下游是同进程的 mock controller：它有独立的响应外壳，可以注入延迟与 5xx，所以聚合走的是真实 HTTP 链路。真实部署时把 BFF_NOTIFICATIONS_BASE_URL 指向内部服务地址即可，聚合代码不用改。

边界与失败处理 ​

1. 两层超时：单块超时 + 总预算 ​

  • 单块超时（BFF_NOTIFICATIONS_TIMEOUT_MS=400）：一个慢下游不能拖死整个请求；
  • 总预算（BFF_TOTAL_BUDGET_MS=900）：即使前面已经花掉时间，剩余预算不足时直接跳过该块，保证请求先于网关超时返回。
ts
/**
 * 给一个聚合块加上「超时 + 降级」。
 *
 * 两层约束：
 * - 单块超时（例如下游 400ms）防止一个慢依赖拖死整个请求；
 * - 总预算（例如 900ms）保证请求一定在网关超时之前返回，哪怕前面已经用掉一部分。
 */
private async runBlock<T>(options: BlockOptions<T>): Promise<Block<T>> {
  const remaining = options.budgetEnd - Date.now();
  if (remaining <= 0) {
    return {
      status: 'degraded',
      data: options.fallback,
      reason: 'budget_exhausted',
      message: `聚合总预算 ${this.config.totalBudgetMs}ms 已耗尽，跳过 ${options.name}`,
      latencyMs: 0,
    };
  }

  const timeoutMs = Math.min(options.timeoutMs, remaining);
  const startedAt = Date.now();
  // AbortSignal.timeout 只负责「通知」；真正让 Promise 提前返回的是 withAbort
  const signal = AbortSignal.timeout(timeoutMs);

  try {
    const data = await withAbort(options.run(signal), signal);
    return { status: 'ok', data, latencyMs: Date.now() - startedAt };
  } catch (error) {
    const latencyMs = Date.now() - startedAt;
    const reason = signal.aborted ? 'timeout' : 'upstream_error';
    const message = signal.aborted
      ? `${options.name} 在 ${timeoutMs}ms 内未返回`
      : describeError(error);

    // 降级必须留下痕迹：日志 + 响应里的 meta.errors，否则线上没人知道数据是旧的
    this.logger.warn(
      JSON.stringify({
        msg: 'bff.block.degraded',
        block: options.name,
        reason,
        timeoutMs,
        latencyMs,
        message,
      }),
    );

    return { status: 'degraded', data: options.fallback, reason, message, latencyMs };
  }
}

AbortSignal.timeout 只负责发信号，真正让 Promise 提前返回的是 withAbort：

ts
/**
 * 让任意 Promise 服从 AbortSignal。
 *
 * 注意：这只能让**调用方**提前返回，不能取消已经发出的数据库查询；
 * 对 HTTP 下游，fetch 会收到同一个 signal 并真正断开连接。
 */
function withAbort<T>(task: Promise<T>, signal: AbortSignal): Promise<T> {
  return new Promise<T>((resolve, reject) => {
    if (signal.aborted) {
      reject(signal.reason);
      return;
    }
    const onAbort = (): void => reject(signal.reason);
    signal.addEventListener('abort', onAbort, { once: true });
    task.then(
      (value) => {
        signal.removeEventListener('abort', onAbort);
        resolve(value);
      },
      (error: unknown) => {
        signal.removeEventListener('abort', onAbort);
        reject(error instanceof Error ? error : new Error(String(error)));
      },
    );
  });
}

它只能让调用方提前返回，不能取消已经发出的数据库查询；对 HTTP 下游，fetch 收到同一个 signal 会真正断开连接。这个差异要写清楚，不能假装「超时 = 任务停止」。

3. 端与角色是两层边界 ​

client=admin 会返回审计与邮箱。如果只靠前端隐藏菜单，任何人改个参数就能拿到：

member 请求 client=admin → 403 BFF_CLIENT_FORBIDDEN

4. 故障注入只在非生产可用 ​

simulate=notifications-timeout 是演示与测试开关。生产环境会返回 403 BFF_SIMULATE_FORBIDDEN，否则它就是一个「任何人都能制造降级」的接口。

5. 降级结果也进缓存 ​

聚合缓存 10 秒，降级结果同样缓存。这是有意的负缓存：下游故障期间，重复请求不应该反复打下游、把恢复窗口拉长。代价是故障恢复后最多多等一个 TTL。

6. BFF、网关与聚合服务不是一回事 ​

这三个词经常被混用，职责差别很大：

角色关心什么本工程对应物不该做的事
网关（Gateway）南北向流量：TLS、路由、限流、鉴权前置、灰度没有实现（可用 Nginx / APISIX 替代）不做字段裁剪，它对「端」无感知
聚合服务（Aggregation）一次请求扇出多个后端，拼成一个响应本节的 BffService 内部结构不区分调用方，不关心客户端形态
BFF（Backend for Frontend）面向某个端的聚合：字段、粒度、降级策略都按端定GET /api/bff/dashboard?client=web|mobile|admin不承载业务规则（扣库存、改订单状态仍归 OrdersService）

判断标准很直接：

  • 如果这段逻辑离开「哪个端在调用」就没有意义，它属于 BFF。例如 mobile 端不要 updatedAt，admin 端要 sku——换个端结论就不成立。
  • 如果逻辑与调用方无关（例如「订单金额 = 明细求和」），它属于领域服务，BFF 只做投影，不做计算。
  • 如果只是转发、鉴权、限流，它属于网关。把它写进 NestJS 只会让业务代码背上基础设施职责。

本项目把三者的边界落在代码上：BffService 只依赖 UsersService / AuditService / OrdersService / NotificationsClient 的读方法，不注入任何写方法；鉴权由全局 Guard 完成（网关前置也可以，二者不冲突）；限流、TLS 留给网关层，没有塞进控制器。

商品块是检验这条边界的好例子：商品数据是公开的，但 sku 是内部编码、updatedAt 是盘点时间。「公开」不等于「该返回」，取舍取决于端——所以这个裁剪在 BFF，而不是在 OrdersService.listProducts() 里删字段，否则 admin 端也拿不到。

curl -s 'http://localhost:3000/api/bff/dashboard?client=mobile' -H "authorization: Bearer $MEMBER_TOKEN" \
  | jq -c '.data.catalog | {shown: (.data.items | length), firstKeys: (.data.items[0] | keys)}'
text
{"status":"ok","total":4,"firstKeys":["available","id","name","priceCents","sku","updatedAt"]}
{"status":"ok","total":4,"shown":4,"firstKeys":["available","id","name","priceCents"]}
{"shown":3,"firstKeys":["id","name","priceCents"]}

同一个商品，三端返回三种形状：

端条数上限字段
admin5id / sku / name / priceCents / available / updatedAt
web4id / name / priceCents / available
mobile3id / name / priceCents

total 恒为目录总数 4，与 items.length 解耦；mobile 只取 3 条，靠 total 知道还有更多。这就是「公开数据 ≠ 该返回的数据」：sku 和盘点时间对首屏没有价值，留在响应里只会让弱网端多传无用字段。

7. 下游超时：只降级通知块 ​

bash
curl -s 'http://localhost:3000/api/bff/dashboard?client=web&simulate=notifications-timeout' \
  -H "authorization: Bearer $MEMBER_TOKEN" \
  -o /tmp/timeout.json -w 'status=%{http_code} time=%{time_total}s\n'
jq -c '.data | {catalog: {status: .catalog.status, latencyMs: .catalog.latencyMs}, orders: {status: .orders.status, latencyMs: .orders.latencyMs}, notifications: {status: .notifications.status, reason: .notifications.reason, message: .notifications.message, latencyMs: .notifications.latencyMs}, meta: {partial: .meta.partial, elapsedMs: .meta.elapsedMs}}' /tmp/timeout.json
text
status=200 time=0.407079s
{"catalog":{"status":"ok","latencyMs":1},"orders":{"status":"ok","latencyMs":1},"notifications":{"status":"degraded","reason":"timeout","message":"notifications 在 400ms 内未返回","latencyMs":403},"meta":{"partial":true,"elapsedMs":406}}

这段输出就是「失败依赖的耗时证据」：mock 下游被要求延迟 2000ms，BFF 在 400ms 主动断开，notifications.latencyMs=403 精确落在单块超时上，整个请求 406ms 结束，远小于总预算 900ms。同一响应里 catalog 与 orders 各 1ms 正常返回——慢的只有那个坏掉的依赖，没有拖累整包。

如果只做整包超时（例如整个请求 900ms 截止），这个场景会白等 900ms 再返回 504。

8. 下游 5xx：错误被归类而不是伪装成超时 ​

text
status=200
{"notifications":{"status":"degraded","reason":"upstream_error","message":"notifications 返回 503: 下游返回 HTTP 503","latencyMs":2},"partial":true}

latencyMs=2 与超时场景的 403 形成对照：5xx 是「立刻失败」，超时是「等满预算才失败」。两者都降级，但 reason 不同，排障时要看的是完全不同的东西。

注意 orders 仍然是 ok：一个下游 5xx 不应该连带把订单块标成降级。

bash
docker exec nestjs-tutorial-redis redis-cli --scan --pattern 'nestjs-tutorial:bff*' | sort
text
nestjs-tutorial:bff:dashboard:admin:e778f815-...:live

键里带用户与端：不同端裁剪后的字段不同、不同用户数据不同，漏掉任一维度都会互相读到对方的数据。演示开关单独一个键，避免降级结果污染正常请求。

易错点 ​

现象根因修复
页面在某个下游故障时整屏白掉用 Promise.all 且不捕获单块错误改用「每块自带降级」的 runBlock，或 Promise.allSettled 后统一归类
超时设置了但请求还是很久只给 fetch 传了 signal，本地 Promise 没被竞速用 withAbort 让调用方也提前返回；同时检查总预算
用户看到别人的数据缓存键漏了 userId / client键里同时带身份与端，并写测试
降级了但没人知道只返回空数组，没有元信息meta.partial + meta.blocks + meta.errors，同时打 warn 日志
下游恢复后仍然一直空白降级结果 TTL 过长降级缓存用更短 TTL（本项目统一 10s，可按块拆分）
把业务规则写进 BFF聚合层顺手做了「下单校验」BFF 只编排与裁剪，业务规则留在领域服务

延伸追问 ​
