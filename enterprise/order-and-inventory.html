apps/api/src/orders 里有可运行的下单、幂等重放、条件扣减、状态机、取消回补、超时自动关单与库存盘点，配套并发脚本与单测/e2e。支付网关、退款、对账未实现，在文末清单里单独标注。

业务背景 ​

下单看起来只是「写一条订单」，实际要同时解决四个问题：

  • 重复提交：用户连点两次、网关重试、客户端超时重发，都会让同一个意图到达服务端多次；
  • 超卖：库存 5 件、20 个请求同时进来，先查后改的实现会让 20 个请求都读到 5；
  • 状态混乱：订单从待支付直接跳到「已完成」，或者取消后又被发货；
  • 金额不可信：价格由客户端提交，改个请求体就能一分钱买显示器。

本页对应的问题是：在并发与重试都真实存在的前提下，怎么让「一次下单」只发生一次、库存只扣一次、状态只能按规则前进。

数据模型 ​

表关键字段作用代码位置
productssku（唯一）、name、price_cents、active商品与定价apps/api/src/orders/product.entity.ts
inventoryproduct_id（主键）、available、version可售库存，一个商品一行apps/api/src/orders/inventory.entity.ts
ordersuser_id、status、total_cents、paid_at、cancelled_at订单主表apps/api/src/orders/order.entity.ts
order_itemsorder_id、product_id、sku、name、unit_price_cents、quantity明细快照apps/api/src/orders/order-item.entity.ts
order_idempotency(user_id, idempotency_key) 唯一、request_hash、order_id幂等回执apps/api/src/orders/order-idempotency.entity.ts

三个刻意的建模决定：

  1. 金额用整数分。price_cents / total_cents 都是 integer，浮点数不进入金额链路。
  2. 明细是快照。sku、name、unit_price_cents 在下单时从商品表复制一份。商品第二天改名或涨价，历史订单必须保持原样。
  3. 库存独立成表。热点的 UPDATE inventory 不会和商品信息的读写抢同一行；product_id 直接做主键，扣减就是单行条件更新。

数据库约束不只写在服务层（迁移见 apps/api/src/database/migrations/1750000001000-OrdersAndInventory.ts）：

  • UNIQUE (user_id, idempotency_key)：并发重复提交的最后防线；
  • CHECK (available >= 0)：即使代码写错，也不允许出现负库存；
  • CHECK (quantity > 0)、CHECK (total_cents >= 0)：脏数据进不来。

关键流程与实现 ​

text
POST /api/orders   Idempotency-Key: <客户端生成>
  │
  ├─ 全局 JWT Guard → 拿到用户
  ├─ 校验幂等键（缺失/长度不对 → 400）
  ├─ 查 order_idempotency（user_id + key）
  │     ├─ 命中且 request_hash 相同 → 200，返回原订单（idempotent-replay: true）
  │     └─ 命中但 request_hash 不同 → 409 IDEMPOTENCY_KEY_REUSED
  │
  └─ 未命中：开启事务
       ├─ 逐商品查 products（不存在 → 404 PRODUCT_NOT_FOUND）
       ├─ UPDATE inventory SET available = available - n
       │    WHERE product_id = ? AND available >= n
       │    影响行数 0 → 409 OUT_OF_STOCK（整个事务回滚）
       ├─ 按服务端价格算总额 → 写 orders + order_items
       ├─ 写 order_idempotency（唯一索引兜底并发）
       └─ 写审计日志（同一个事务）

入口只负责取请求头、把「是否重放」写进状态码与响应头：

ts
/**
 * 下单接口。
 *
 * 幂等键放在请求头而不是 body：
 * - 它是传输层语义（「这次请求可以安全重试」），不属于业务字段；
 * - 用 header 后，同一个请求体配不同的键就能重新下单，不需要改 body。
 *
 * 首次创建返回 201；幂等重放返回 200，并用 `idempotent-replay` 头显式告知。
 */
@Post()
async create(
  @Body() dto: CreateOrderDto,
  @Headers('idempotency-key') idempotencyKey: string | undefined,
  @CurrentUser() actor: AuthenticatedUser,
  @Res({ passthrough: true }) response: Response,
): Promise<CreateOrderResult> {
  const result = await this.ordersService.create(actor, dto, idempotencyKey);
  response.status(result.replayed ? HttpStatus.OK : HttpStatus.CREATED);
  response.setHeader('idempotent-replay', String(result.replayed));
  return result;
}

幂等判断、事务、扣减、落库都在服务层，顺序不能调换：

ts
/**
 * 下单：幂等 + 条件扣减 + 订单落库在同一个事务里。
 *
 * 三道防线，缺一不可：
 * 1. 询幂等记录（快路径，命中直接返回原订单）；
 * 2. 唯一索引 (user_id, idempotency_key)（并发下的最终防线）；
 * 3. `UPDATE ... WHERE available >= n`（库存的原子扣减，不先查后改）。
 */
async create(
  actor: AuthenticatedUser,
  dto: CreateOrderDto,
  rawIdempotencyKey: string | undefined,
): Promise<CreateOrderResult> {
  const key = normalizeIdempotencyKey(rawIdempotencyKey);
  const requestHash = fingerprintOrderItems(dto.items);

  const existing = await this.idempotency.findOne({ where: { userId: actor.id, key } });
  if (existing) {
    return this.replay(existing, requestHash);
  }

  const items = normalizeOrderItems(dto.items);

  try {
    const created = await this.dataSource.transaction(async (manager) => {
      const lines: Array<{ product: ProductEntity; quantity: number }> = [];

      for (const item of items) {
        const product = await manager.findOne(ProductEntity, {
          where: { id: item.productId, active: true },
        });
        if (!product) {
          throw new NotFoundException({
            code: 'PRODUCT_NOT_FOUND',
            message: `商品 ${item.productId} 不存在或已下架`,
            details: { productId: item.productId },
          });
        }

        const deducted = await this.deductStock(manager, product.id, item.quantity);
        if (!deducted) {
          const inventory = await manager.findOne(InventoryEntity, {
            where: { productId: product.id },
          });
          throw new ConflictException({
            code: 'OUT_OF_STOCK',
            message: `商品 ${product.sku} 库存不足`,
            details: {
              productId: product.id,
              sku: product.sku,
              requested: item.quantity,
              available: inventory?.available ?? 0,
            },
          });
        }

        lines.push({ product, quantity: item.quantity });
      }

      // 价格以服务端为准：客户端只提交商品与数量，传什么价格都不影响金额
      const totalCents = lines.reduce(
        (sum, line) => sum + line.product.priceCents * line.quantity,
        0,
      );

      const order = await manager.save(
        manager.create(OrderEntity, {
          userId: actor.id,
          status: 'pending' as OrderStatus,
          totalCents,
          currency: 'CNY',
        }),
      );

      const savedItems = await manager.save(
        lines.map((line) =>
          manager.create(OrderItemEntity, {
            orderId: order.id,
            productId: line.product.id,
            sku: line.product.sku,
            name: line.product.name,
            unitPriceCents: line.product.priceCents,
            quantity: line.quantity,
          }),
        ),
      );

      await manager.save(
        manager.create(OrderIdempotencyEntity, {
          userId: actor.id,
          key,
          requestHash,
          orderId: order.id,
        }),
      );

      await this.auditService.record(
        {
          action: 'order.created',
          actorId: actor.id,
          targetId: order.id,
          summary: `订单 ${order.id} 创建成功，金额 ${totalCents} 分，商品 ${lines.length} 种`,
        },
        manager,
      );

      return { order: toOrderView(order, savedItems), replayed: false };
    });
    // 事务提交之后再推送：回滚的订单不允许被客户端看到
    this.publishOrderEvent(created.order, 'order.created');
    return created;
  } catch (error) {
    // 并发同键：唯一索引拒绝第二个事务，回查已存在的记录并返回那张订单
    if (isUniqueViolation(error)) {
      const record = await this.idempotency.findOne({ where: { userId: actor.id, key } });
      if (record) {
        this.logger.warn(`幂等键 ${key} 并发命中，返回已有订单 ${record.orderId}`);
        return this.replay(record, requestHash);
      }
    }
    throw error;
  }
}

1. 幂等键：三道防线 ​

幂等键由客户端生成，重试时原样带上。服务端不猜「这两个请求是不是同一个」，只认键：

ts
/**
 * 幂等键由客户端生成并在重试时原样带上。
 * 太短的键（比如 "1"）在用户维度上很容易撞车，所以设下限；
 * 上限只是防止把请求头当存储用。
 */
export function normalizeIdempotencyKey(raw: string | undefined): string {
  const key = raw?.trim() ?? '';
  if (!key) {
    throw new BadRequestException({
      code: 'IDEMPOTENCY_KEY_REQUIRED',
      message: '下单必须携带 Idempotency-Key 请求头（8~128 个字符），用于识别重复提交',
    });
  }
  if (key.length < IDEMPOTENCY_KEY_MIN_LENGTH || key.length > IDEMPOTENCY_KEY_MAX_LENGTH) {
    throw new BadRequestException({
      code: 'IDEMPOTENCY_KEY_INVALID',
      message: `Idempotency-Key 长度必须在 ${IDEMPOTENCY_KEY_MIN_LENGTH}~${IDEMPOTENCY_KEY_MAX_LENGTH} 个字符之间`,
    });
  }
  return key;
}
防线位置拦截什么
快路径查询应用层 findOne99% 的顺序重试，直接返回原订单
唯一索引数据库 (user_id, idempotency_key)并发同键：两个请求都查不到，只有一个能插入成功
请求指纹request_hash（商品 + 数量的 SHA-256）客户端复用同一个键提交了不同内容

指纹只包含影响下单结果的字段。价格以服务端为准，所以客户端传什么价格都不参与指纹——这一点与「不信任客户端金额」是同一个原则。

2. 零超卖：条件扣减，不是「先查后改」 ​

ts
/**
 * 条件扣减：把「判断库存够不够」和「扣库存」压成一条 SQL。
 *
 * UPDATE inventory SET available = available - n
 *  WHERE product_id = ? AND available >= n
 *
 * 数据库在行锁内完成比较与写入，所以并发请求只会有一个拿到这一行；
 * 影响行数为 0 就代表「不满足条件」，不需要（也不能）先 SELECT 再判断。
 */
private async deductStock(
  manager: EntityManager,
  productId: string,
  quantity: number,
): Promise<boolean> {
  const result = await manager
    .createQueryBuilder()
    .update(InventoryEntity)
    .set({
      available: () => 'available - :quantity',
      version: () => 'version + 1',
    })
    .where('product_id = :productId', { productId })
    .andWhere('available >= :quantity', { quantity })
    .execute();

  return result.affected === 1;
}

/** 取消订单时原路回补。只在状态迁移成功（影响行数 1）之后调用，避免重复回补 */
private async restock(
  manager: EntityManager,
  orderItems: OrderItemEntity[],
): Promise<void> {
  for (const item of orderItems) {
    await manager
      .createQueryBuilder()
      .update(InventoryEntity)
      .set({
        available: () => 'available + :quantity',
        version: () => 'version + 1',
      })
      .where('product_id = :productId', { productId: item.productId })
      .setParameter('quantity', item.quantity)
      .execute();
  }
}

UPDATE ... WHERE available >= n 把比较和写入压进同一条语句，数据库在行锁内完成，所以并发请求天然串行化在库存行上。影响行数为 0 就代表条件不满足，不需要再 SELECT 一次。

这里没有用乐观锁重试（version 只用于观察改动次数）：库存扣减失败的正确语义是「卖完了」，不是「重试一次也许能成」。

3. 状态机：查表，不做 if 链 ​

ts
export const ORDER_TRANSITIONS: Readonly<Record<OrderStatus, readonly OrderStatus[]>> = {
  pending: ['paid', 'cancelled'],
  paid: ['shipped'],
  shipped: ['completed'],
  completed: [],
  cancelled: [],
};
pending ──pay──→ paid ──ship──→ shipped ──complete──→ completed
   │
   └──cancel──→ cancelled

取消只允许发生在未支付阶段。已支付订单要取消必须走退款，那是支付域的事，不能用一个状态位悄悄跳过。

迁移入口先查表拒绝非法目标，再用「读到的状态」作为更新条件，防止两个并发请求都通过检查：

ts
async transition(
  orderId: string,
  to: OrderStatus,
  actor: AuthenticatedUser,
): Promise<OrderView> {
  const updated = await this.dataSource.transaction(async (manager) => {
    const order = await manager.findOne(OrderEntity, { where: { id: orderId } });
    if (!order) {
      throw new NotFoundException({
        code: 'ORDER_NOT_FOUND',
        message: `订单 ${orderId} 不存在`,
      });
    }
    if (actor.role !== 'admin' && order.userId !== actor.id) {
      throw new ForbiddenException({
        code: 'ORDER_FORBIDDEN',
        message: '只能操作自己的订单',
        details: { orderUserId: order.userId },
      });
    }

    // 先查状态机：非法迁移在写库之前就被拒绝
    assertTransition(order.status, to);

    const patch = {
      status: to,
      ...(to === 'paid' ? { paidAt: new Date() } : {}),
      ...(to === 'cancelled' ? { cancelledAt: new Date() } : {}),
    };

    // 把「读到的状态」作为更新条件：两个并发请求只有一个能改成功
    const result = await manager.update(
      OrderEntity,
      { id: orderId, status: order.status },
      patch,
    );
    if (result.affected !== 1) {
      const current = await manager.findOneByOrFail(OrderEntity, { id: orderId });
      throw new ConflictException({
        code: 'ORDER_STATUS_CONFLICT',
        message: '订单状态已被其他请求修改，请刷新后重试',
        details: { expected: order.status, actual: current.status },
      });
    }

    const items = await manager.find(OrderItemEntity, { where: { orderId } });
    if (to === 'cancelled') {
      await this.restock(manager, items);
    }

    await this.auditService.record(
      {
        action: `order.${to}`,
        actorId: actor.id,
        targetId: orderId,
        summary: `订单 ${orderId} 由 ${order.status} 变更为 ${to}`,
      },
      manager,
    );

    return toOrderView({ ...order, ...patch }, items);
  });

  this.publishOrderEvent(updated, 'order.updated');
  return updated;
}

UPDATE orders SET status = ? WHERE id = ? AND status = <读到的状态> 影响行数为 1 才算迁移成功。并发下输掉的那个请求会拿到 409 ORDER_STATUS_CONFLICT，而不是把状态覆盖回去。

4. 取消回补：只在迁移成功后执行 ​

回补在同一个事务里、在状态 CAS 成功之后执行：

text
取消请求 A：UPDATE ... WHERE status='pending' → 1 行 → 回补库存
取消请求 B：UPDATE ... WHERE status='pending' → 0 行 → 409，不回补

重复取消返回 409 ORDER_INVALID_TRANSITION（allowed: []），库存不会被加两次。

边界与失败处理 ​

1. 错误语义分开：400 / 403 / 404 / 409 ​

场景状态码error.code
没带幂等键400IDEMPOTENCY_KEY_REQUIRED
同一商品在一张订单里出现两次400ORDER_DUPLICATE_ITEM
操作别人的订单403ORDER_FORBIDDEN
member 调发货接口403FORBIDDEN_ROLE
商品不存在404PRODUCT_NOT_FOUND
库存不足409OUT_OF_STOCK
状态不允许该迁移409ORDER_INVALID_TRANSITION
同键不同内容409IDEMPOTENCY_KEY_REUSED
并发修改同一订单409ORDER_STATUS_CONFLICT

「当前状态不允许」是 409，不是 400：请求参数本身合法，只是与资源当前状态冲突。客户端据此决定「刷新重试」还是「改参数」。

2. 重复商品行直接拒绝 ​

同一个 productId 出现两次时选择报错而不是合并数量：

  • 合并会让「用户以为买了两件、实际只扣了一次」变成静默数据错误；
  • 拒绝之后客户端必须显式合并数量，语义清晰。

商品行在进入事务前按 productId 排序，固定加锁顺序，降低多商品订单之间的死锁概率。

3. 事务边界覆盖「扣库存 + 写订单 + 写幂等记录 + 审计」 ​

任何一步失败都整体回滚。不会出现「库存扣了、订单没写」，也不会出现「订单写了、幂等记录没写」——后者会让同一个键的重试再下一单。

4. 权限：本人或 admin ​

  • 创建、查看、支付、取消、确认收货：本人或 admin；
  • 发货：仅 admin（@Roles('admin')）；
  • 列表：非 admin 强制 user_id = 当前用户，传别人的 userId 直接 403；admin 不传 userId 时看全量。

5. 超时关单：队列任务 + CAS，不覆盖正在支付的订单 ​

用户下单后不支付是常态。如果 pending 订单永远不关，库存会被慢慢占满。本示例把「超时关单」放进第 08 章的 BullMQ 定时任务：每 5 分钟扫一次，超过 30 分钟未支付的订单走与手动取消同一套状态机与回补逻辑。

ts
/**
 * 超时关单：由队列的定时任务调用，不是用户请求路径。
 *
 * 与 transition 的差别：
 * - 没有操作人（actorId 为 null），审计里记为系统动作；
 * - 状态迁移仍然用 CAS（WHERE status = 'pending'），
 *   所以「用户刚好在这一刻支付」不会被自动取消覆盖，只会被跳过。
 */
async cancelExpired(options: {
  olderThanMinutes: number;
  limit: number;
}): Promise<TimeoutSweepResult> {
  const now = new Date();
  const deadline = new Date(now.getTime() - options.olderThanMinutes * 60_000);

  // 只扫「已超时」的 pending 订单，避免把刚创建几秒的订单也捞出来
  const candidates = await this.orders.find({
    where: { status: 'pending' as OrderStatus, createdAt: LessThan(deadline) },
    order: { createdAt: 'ASC' },
    take: options.limit,
  });

  const cancelled: string[] = [];
  let skipped = 0;

  for (const candidate of candidates) {
    const cancelledNow = await this.dataSource.transaction(async (manager) => {
      const order = await manager.findOne(OrderEntity, { where: { id: candidate.id } });
      if (!order || order.status !== 'pending') {
        return false;
      }

      const result = await manager.update(
        OrderEntity,
        { id: order.id, status: 'pending' },
        { status: 'cancelled', cancelledAt: new Date() },
      );
      if (result.affected !== 1) {
        return false;
      }

      const items = await manager.find(OrderItemEntity, { where: { orderId: order.id } });
      await this.restock(manager, items);

      await this.auditService.record(
        {
          action: 'order.cancelled_by_timeout',
          actorId: null,
          targetId: order.id,
          summary: `订单 ${order.id} 超过 ${options.olderThanMinutes} 分钟未支付，系统自动取消并回补库存`,
        },
        manager,
      );
      return true;
    });

    if (cancelledNow) {
      cancelled.push(candidate.id);
      this.publishOrderEvent(
        {
          id: candidate.id,
          userId: candidate.userId,
          status: 'cancelled',
          totalCents: candidate.totalCents,
        },
        'order.updated',
      );
    } else {
      skipped += 1;
    }
  }

  const summary: TimeoutSweepResult = {
    scanned: candidates.length,
    cancelled,
    skipped,
    timeoutMinutes: options.olderThanMinutes,
    executedAt: now.toISOString(),
  };

  this.logger.log(
    JSON.stringify({
      msg: 'orders.timeout-sweep',
      scanned: summary.scanned,
      cancelled: summary.cancelled.length,
      skipped: summary.skipped,
      timeoutMinutes: summary.timeoutMinutes,
    }),
  );
  return summary;
}

三个关键点：

  1. 只扫已超时的 pending：created_at < now() - timeout，不会误伤刚下的单；
  2. CAS 迁移：UPDATE ... WHERE id = ? AND status = 'pending'，用户恰好在同一刻支付时，任务的影响行数为 0，计入 skipped 而不是把已支付订单改成取消；
  3. 复用回补：取消成功后按明细回补库存，与手动取消完全一致，不存在两套实现。

任务本身只负责读配置与限制批次，驱动层不认识订单：

ts
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import type { AppConfig, QueueConfig } from '../config/configuration.js';
import { OrdersService } from '../orders/orders.service.js';
import type { TimeoutSweepResult } from '../orders/orders.service.js';

/** 单轮最多处理多少张超时订单：控制任务时长，剩下的留给下一轮 */
const SWEEP_BATCH_SIZE = 100;

/**
 * 超时关单任务。
 *
 * 业务规则在 OrdersService 里（状态机 + CAS + 回补库存），
 * 这一层只负责读配置、限制批次，让队列模块不需要了解订单细节。
 */
@Injectable()
export class OrderTimeoutService {
  private readonly config: QueueConfig;

  constructor(
    private readonly orders: OrdersService,
    configService: ConfigService<AppConfig, true>,
  ) {
    this.config = configService.get('queue', { infer: true });
  }

  run(): Promise<TimeoutSweepResult> {
    return this.orders.cancelExpired({
      olderThanMinutes: this.config.orderPaymentTimeoutMinutes,
      limit: SWEEP_BATCH_SIZE,
    });
  }
}

调度与手动触发：cron 为 ORDER_TIMEOUT_CRON（默认 */5 * * * *），运维接口 POST /api/jobs/order-timeout-sweep 可立刻跑一次。

6. 未实现的边界 ​

  • 支付回调：POST /orders/:id/pay 是同步模拟支付，没有第三方回调验签、金额核对与重复回调处理。
  • 退款：paid 之后没有取消路径。
  • 库存预留：当前是「下单即扣减」，没有「先预留 N 分钟、支付后确认」的 reservation 模型；超时关单是这个模型的简化版。

易错点 ​

现象根因修复
压测时库存变成负数SELECT 判断后再 UPDATE，读写之间有窗口改成 UPDATE ... WHERE available >= n，用影响行数判断
同一用户重复下单只在应用层查幂等键，没有唯一约束落库 UNIQUE (user_id, key)，冲突时回查原记录
幂等键复用后返回了错误订单没校验请求内容存 request_hash，内容不一致返回 409
取消订单后库存加两次回补不在状态迁移成功之后先做状态 CAS，影响行数为 1 才回补，且放在同一事务
金额和前端算的不一致信任客户端提交的价格只接收 productId + quantity，价格从商品表读
订单状态被并发覆盖两个请求都通过「当前状态」检查更新条件里带上读到的状态；失败返回 409
历史订单金额变了明细只存 product_id，展示时 join 商品现价明细存下单时的 sku / name / unit_price_cents
商品列表暴露内部字段直接把实体返回给客户端统一走 toProductView / toOrderView
