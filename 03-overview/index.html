  • 模块（Module）：组织单位。把相关的控制器与提供者聚合在一起，声明它们之间的依赖与共享关系（详见第 4 章）；
  • 控制器（Controller）：流量入口。定义路由、解析请求参数、调用服务、返回响应（详见第 5 章）；
  • 提供者（Provider）：业务载体。服务、仓库、工厂、工具类都可以是提供者，由 DI 容器统一管理（详见第 6 章）。

依赖注入（DI）容器 ​

Nest 内置一个 IoC（控制反转）容器。你不需要手动 new 任何服务——只要在构造函数里声明依赖，容器在实例化时自动解析并注入：

ts
// 文件: server/src/ch02-quick-start/app.controller.ts
// 控制器：负责接收请求、调用服务、返回响应
import { Controller, Get } from '@nestjs/common';
import { AppService } from './app.service';

@Controller() // 无前缀，路由从 / 开始
export class AppController {
    // 构造函数注入：Nest 容器会自动解析 AppService 实例
    constructor(private readonly appService: AppService) {}

    @Get() // GET /
    getHello(): string {
        return this.appService.getHello();
    }

    @Get('health') // GET /health
    getHealth() {
        return { status: 'ok' };
    }
}

容器的工作流程：

  1. 注册：@Module({ providers: [...] }) 把提供者登记进容器；
  2. 解析：实例化控制器/服务时，容器读取构造函数的参数类型元数据（emitDecoratorMetadata 生成）；
  3. 注入：按类型（或令牌）找到对应实例，传入构造函数。

这种写法带来两个直接收益：依赖关系显式化（看构造函数就知道依赖什么）与可测试性（测试时可以轻松替换 mock 实例）。深入细节见第 7 章。

请求处理管线 ​

一个 HTTP 请求进入 Nest 应用后，会按固定顺序穿过一系列处理层。理解这条管线是掌握 Nest 的关键：

  ▼

记忆口诀

「中守拦管，控服拦异」——中间件、守卫、拦截器（前）、管道，到控制器与服务，再经拦截器（后），异常过滤器全程兜底。

元数据与反射：框架的魔法之源 ​

Nest 的装饰器之所以能驱动路由注册、依赖注入，靠的是两个机制：

  1. 装饰器：@Get('users') 本质是一个函数，在类定义时执行，把元数据（路径、方法）写到类上；
  2. 反射：reflect-metadata 库提供 Reflect.getMetadata()，框架在运行时读取这些元数据完成装配。

这也是为什么 tsconfig.json 必须开启 experimentalDecorators 与 emitDecoratorMetadata——前者启用装饰器语法，后者让 TypeScript 在编译产物中保留类型元数据，DI 容器靠它推断构造函数每个参数的类型。
