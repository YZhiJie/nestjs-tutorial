06 查询优化与慢查询治理 ​

用 pg_stat_statements 定位慢 SQL，改写深分页、N+1 与函数条件并建立防回归。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 建立「发现 → 定位 → 改写/索引 → 验证 → 防回归」的慢查询治理闭环；
  2. 用 pg_stat_statements 按总耗时找出最值得优化的 SQL，而不是凭感觉；
  3. 读懂 EXPLAIN (ANALYZE, BUFFERS) 中的排序落盘、Rows Removed by Filter、Buffers；
  4. 改写深分页、N+1、函数条件、SELECT * 四类高频慢查询；
  5. 用 keyset 分页把 OFFSET 200000 的 9ms 降到 0.3ms；
  6. 区分「数据库能解决的慢」与「应该用缓存、归档、读写分离解决的慢」。

概念与原理 ​

1. 优化闭环：先量化，再动手 ​

text
监控/日志发现慢 SQL
      ↓
pg_stat_statements + EXPLAIN 定位
      ↓
改写 SQL / 加索引 / 改数据模型
      ↓
对比计划与指标（不只看单次毫秒）
      ↓
加回归测试或查询预算，防止再次退化

没有量化的优化容易变成「凭感觉调索引」。至少要记录四个数字：

指标含义用途
calls调用次数高频 SQL 即使单次不慢，总耗时也可能最大
total_exec_time总执行时间排序优化优先级的第一指标
mean_exec_time平均耗时判断单次是否异常
rows平均返回行数判断是否过量取数

接口层面还要看 p95 / p99，平均值会掩盖长尾。一个 p99 2 秒的接口，用户能明显感知。

2. pg_stat_statements：数据库自带的「慢 SQL 排行榜」 ​

启用方式（本章 compose 已配置）：

yaml
command:
  - postgres
  - -c
  - shared_preload_libraries=pg_stat_statements
  - -c
  - pg_stat_statements.track=all

查询：

sql
SELECT calls,
       round(total_exec_time::numeric, 2) AS total_ms,
       round(mean_exec_time::numeric, 3)  AS mean_ms,
       rows,
       left(query, 72) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

注意：

  • SQL 里的常量会被归一化成 $1，所以「同一形状、不同参数」会合并统计；
  • 重启或 pg_stat_statements_reset() 后统计清零；
  • track=all 会统计存储过程/函数内部的语句，开销略高；
  • 它不是采样，长期开启对性能影响通常可接受，但要监控扩展占用的共享内存。

3. 慢查询日志：兜底与取证 ​

log_min_duration_statement=200 会记录超过 200ms 的语句。日志适合：

  • 捕获偶发尖刺（pg_stat_statements 只给聚合值）；
  • 拿到完整 SQL 与参数，复现问题；
  • 审计未走应用的直连查询。

生产建议按环境设置：开发 0~100ms，预发 200ms，生产 500ms~1s，避免日志写满磁盘。

4. 深分页：OFFSET 是「先丢掉再取」 ​

sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 200000;

数据库必须生成前 200020 行，再丢掉前 200000 行。页码越深越慢，而且并发插入会导致重复/漏行。两种改写：

keyset（推荐）：

sql
SELECT * FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

Web 端把上一页最后一行的 (created_at, id) 编码进 next_cursor，下一页只读 20 行。要求排序键唯一且稳定，所以用 (created_at, id) 而不是只用一个可能重复的列。

延迟关联（不能改接口时）：

sql
SELECT o.*
FROM orders AS o
JOIN (
  SELECT id FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 200000
) AS page ON page.id = o.id;

子查询只取主键，减少回表；但 OFFSET 仍然存在，深页码依旧线性变慢。

5. N+1：一次请求打了 N 次数据库 ​

text
查 50 个用户 → 循环里每个用户查一次订单数 → 1 + 50 次查询

数据库侧的开销是「50 次解析 + 50 次执行 + 50 次网络往返」。即使每次有索引，累计也可能明显；如果没索引，每次都是全表扫描，直接灾难。

修复方式：

  • 一次聚合：SELECT user_id, count(*) FROM orders WHERE user_id IN (...) GROUP BY user_id；
  • JOIN + 去重：需要明细时用 JOIN，注意行数放大；
  • 批量加载：ORM 的 IN 查询 + 应用层分组（DataLoader 模式）；
  • 禁止在循环里查库：代码评审时重点看 for 循环内的 repository 调用。

6. 让索引失效的写法 ​

写法问题改写
date_trunc('day', created_at) = ...对列做函数运算，普通索引失效改成范围条件；或建表达式索引
created_at::date = ...列被强转改成 >= 当天 00:00 AND < 次日 00:00
name LIKE '%键盘'前置通配符无法按前缀查找pg_trgm + GIN，或全文检索
WHERE status != 'paid'取反通常命中大部分行白名单 IN (...)，或部分索引
WHERE phone = 13800138000（列是 text）隐式转换可能作用在列上参数类型与列类型一致
SELECT *读多余列、无法覆盖索引只取需要的列

7. 过量取数：SELECT * 与「先查全部再过滤」 ​

  • SELECT * 会让覆盖索引失效，增加网络传输与 ORM 映射成本；
  • 把过滤放在应用层（findAll().filter(...)）等于把数据库当文件系统；
  • 分页接口返回总数时，COUNT(*) 大表很贵，可以用估算值或「是否有下一页」替代。

8. 慢不一定是 SQL：锁、连接池、缓存 ​

现象可能原因排查
SQL 单独跑很快，线上很慢锁等待、连接池排队pg_locks、pg_blocking_pids()、池指标
间歇性尖刺批量任务、autovacuum、检查点慢日志时间分布、pg_stat_bgwriter
第一次慢，后面快冷缓存EXPLAIN (ANALYZE, BUFFERS) 看 read
数据量越大越慢缺索引、深分页、全表聚合本章的闭环
单条很快但 QPS 高高频简单查询打满 CPU缓存、连接池、读写分离

优化顺序：先改 SQL/索引，再考虑缓存，最后才分库分表。缓存会引入一致性成本，分库分表会引入分布式事务成本，不要跳过前两步。

最小可跑示例 ​

示例目录 examples/database/06-query-optimization/。先建表，初始只有主键：

sql
-- 06 查询优化：用户与订单
-- 初始只建主键，方便复现「缺索引」的慢查询。
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS users;

CREATE TABLE users (
  id    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email text   NOT NULL UNIQUE,
  name  text   NOT NULL,
  city  text   NOT NULL
);

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint      NOT NULL REFERENCES users (id),
  status      text        NOT NULL,
  created_at  timestamptz NOT NULL,
  total_cents integer     NOT NULL CHECK (total_cents >= 0)
);

ALTER DATABASE shop SET timezone TO 'Asia/Shanghai';

灌入 5000 用户、30 万订单：

sql
-- 5000 个用户、30 万订单
INSERT INTO users (id, email, name, city)
SELECT
  g,
  'user' || g || '@example.com',
  'User ' || g,
  (ARRAY['上海', '北京', '深圳', '杭州', '成都'])[(g % 5) + 1]
FROM generate_series(1, 5000) AS g;

INSERT INTO orders (user_id, status, created_at, total_cents)
SELECT
  (g % 5000) + 1,
  CASE
    WHEN g % 100 = 0 THEN 'refunded'
    WHEN g % 3 = 0   THEN 'pending'
    WHEN g % 2 = 0   THEN 'paid'
    ELSE 'shipped'
  END,
  timestamptz '2026-01-01 00:00:00+08'
    + (g % 365) * interval '1 day'
    + (g % 86400) * interval '1 second',
  (g % 200000) + 100
FROM generate_series(1, 300000) AS g;

ANALYZE users;
ANALYZE orders;

SELECT (SELECT count(*) FROM users) AS users,
       (SELECT count(*) FROM orders) AS orders;

真实输出：

text
 users | orders
-------+--------
  5000 | 300000
(1 row)

一、四类慢查询 ​

sql
-- 03 慢查询模式：在「没有业务索引」的表上执行
-- \timing 打开后，psql 会输出每条语句的耗时。
\timing on

\echo '== 1. 深分页：OFFSET 10 万 =='
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20 OFFSET 100000;

\echo '== 2. 对列做函数运算：索引无法直接使用 =='
SELECT count(*) FROM orders
WHERE date_trunc('day', created_at) = timestamptz '2026-06-01 00:00:00+08';

\echo '== 3. N+1 的数据库侧：50 个用户各查一次 =='
DO $$
DECLARE
  uid bigint;
  cnt bigint;
BEGIN
  FOR uid IN SELECT id FROM users ORDER BY id LIMIT 50 LOOP
    SELECT count(*) INTO cnt FROM orders WHERE user_id = uid;
  END LOOP;
END $$;

\echo '== 4. 同样需求，一次聚合完成 =='
SELECT count(*) FROM orders WHERE user_id <= 50;

真实输出（\timing on）：

text
== 1. 深分页：OFFSET 10 万 ==
Time: 28.462 ms

== 2. 对列做函数运算 ==
Time: 12.047 ms

== 3. N+1 的数据库侧：50 个用户各查一次 ==
DO
Time: 316.422 ms

== 4. 同样需求，一次聚合完成 ==
Time: 5.430 ms

N+1 的 316ms 与单次聚合的 5.4ms 差近 60 倍。这还只是 50 个用户；线上 500 个用户时，差距会继续放大。

二、慢查询日志 ​

compose 里设置了 log_min_duration_statement=200，所以 N+1 的 DO 块会被记录：

text
db06-postgres | LOG:  duration: 316.329 ms  statement: DO $$
db06-postgres | LOG:  duration: 345.678 ms  statement: DO $$

日志给的是「哪条语句慢」，pg_stat_statements 给的是「哪类语句累计最耗时」，两者配合使用。

逐步拆解 ​

第 1 步：先看深分页的执行计划 ​

sql
-- 04 慢查询的执行计划
\echo '== 深分页：Seq Scan + Sort =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20 OFFSET 100000;

\echo '== 函数条件：Filter 里逐行计算 date_trunc =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders
WHERE date_trunc('day', created_at) = timestamptz '2026-06-01 00:00:00+08';

\echo '== 按 user_id 统计：没有索引，只能全表扫描 =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE user_id = 42;

真实输出（深分页）：

text
Limit  (cost=36974.84..36977.14 rows=20) (actual time=39.653..41.768 rows=20 loops=1)
  ->  Gather Merge
        ->  Sort  (Sort Key: created_at DESC)
              Sort Method: external merge  Disk: 7272kB
              ->  Parallel Seq Scan on orders
                    Rows Removed by Filter: ...
Execution Time: 42.570 ms

三个信号：

  • Parallel Seq Scan：没有可用的排序索引；
  • external merge Disk: 7272kB：排序数据超过 work_mem，落盘了；
  • Buffers: temp read=926 written=1701：临时文件读写，磁盘 IO 放大。

第 2 步：加索引，但别指望 OFFSET 消失 ​

sql
-- 05 建索引：分别服务排序分页、用户查询、时间范围
-- 先删后建，保证脚本可以重复执行。
DROP INDEX IF EXISTS idx_orders_created_at_id;
DROP INDEX IF EXISTS idx_orders_user_created;
DROP INDEX IF EXISTS idx_orders_created_day;

-- (created_at DESC, id DESC) 同时支持「按时间倒序」和 keyset 分页的行比较。
CREATE INDEX idx_orders_created_at_id
  ON orders (created_at DESC, id DESC);

CREATE INDEX idx_orders_user_created
  ON orders (user_id, created_at DESC);

-- 函数条件也可以建表达式索引；但表达式必须是 IMMUTABLE。
-- date_trunc('day', timestamptz) 依赖会话时区，是 STABLE，不能直接建索引；
-- 先固定时区再取日期，表达式才可变。
CREATE INDEX idx_orders_created_day
  ON orders (((created_at AT TIME ZONE 'Asia/Shanghai')::date));

ANALYZE orders;
VACUUM orders;

SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders'
ORDER BY indexname;

(created_at DESC, id DESC) 同时支持「按时间倒序」与 keyset 的行比较；(user_id, created_at DESC) 服务用户维度的查询；表达式索引演示函数条件。

真实输出（建索引后）：

text
Limit  (cost=6383.08..6384.36 rows=20) (actual time=18.884..18.888 rows=20 loops=1)
  ->  Index Scan using idx_orders_created_at_id on orders
        Buffers: shared hit=100019 read=386
Execution Time: 18.905 ms

排序落盘消失了，时间从 42ms 降到 19ms。但 Buffers: shared hit=100019 说明仍然读了 10 万个索引条目——OFFSET 的成本还在。索引解决「排序」，不解决「跳过」。

第 3 步：keyset 分页只读 20 行 ​

sql
-- 07 深分页：OFFSET vs keyset
\timing on

\echo '== OFFSET：跳过 20 万行 =='
SELECT id, created_at FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 200000;

\echo '== keyset：从上一页最后一行之后继续 =='
SELECT id, created_at FROM orders
WHERE (created_at, id) < (timestamptz '2026-07-01 00:00:00+08', 0)
ORDER BY created_at DESC, id DESC
LIMIT 20;

\echo '== keyset 的执行计划：Index Scan，只读 20 行 =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at FROM orders
WHERE (created_at, id) < (timestamptz '2026-07-01 00:00:00+08', 0)
ORDER BY created_at DESC, id DESC
LIMIT 20;

真实输出：

text
== OFFSET：跳过 20 万行 ==
Time: 8.992 ms

== keyset：从上一页最后一行之后继续 ==
Time: 0.333 ms

== keyset 的执行计划 ==
Limit  (cost=0.42..1.08 rows=20) (actual time=0.004..0.007 rows=20 loops=1)
  ->  Index Only Scan using idx_orders_created_at_id on orders
        Index Cond: (ROW(created_at, id) < ROW('2026-07-01 00:00:00+08', 0))
        Heap Fetches: 0
        Buffers: shared hit=4
Execution Time: 0.011 ms

从 9ms 降到 0.33ms，Buffers 从上千降到 4。代价是接口不能直接跳页，只能「下一页 / 上一页」；这是深分页场景下值得的交换。

第 4 步：N+1 改成一次聚合 ​

sql
-- 反例：循环里查 50 次
FOR uid IN SELECT id FROM users LIMIT 50 LOOP
  SELECT count(*) FROM orders WHERE user_id = uid;
END LOOP;

-- 正例：一次分组
SELECT user_id, count(*)
FROM orders
WHERE user_id <= 50
GROUP BY user_id;

真实对比：316.422 ms vs 5.430 ms。如果业务需要用户详情，再按返回的 user_id 批量查用户表，总共 2 次查询。

第 5 步：函数条件改写 ​

sql
-- 慢：对每一行计算 date_trunc
SELECT count(*) FROM orders
WHERE date_trunc('day', created_at) = timestamptz '2026-06-01 00:00:00+08';

-- 快：范围条件，走 created_at 索引
SELECT count(*) FROM orders
WHERE created_at >= timestamptz '2026-06-01 00:00:00+08'
  AND created_at <  timestamptz '2026-06-02 00:00:00+08';

真实输出：

text
函数条件：Execution Time: 12.316 ms
范围条件：Execution Time: 0.625 ms

表达式索引也能救函数条件，但要注意：

  • 表达式必须 IMMUTABLE，date_trunc('day', timestamptz) 依赖会话时区，不能直接建；
  • 查询表达式必须与索引表达式完全一致；
  • 能改写成范围时，优先改写，索引更通用。

第 6 步：用 pg_stat_statements 排优先级 ​

sql
-- 08 pg_stat_statements：按总耗时找最值得优化的 SQL
SELECT pg_stat_statements_reset();

-- 模拟一段重复调用的业务流量
DO $$
BEGIN
  FOR i IN 1..30 LOOP
    PERFORM count(*) FROM orders WHERE status = 'paid';
    PERFORM count(*) FROM orders WHERE user_id = 42;
    PERFORM count(*) FROM orders WHERE created_at >= timestamptz '2026-06-01 00:00:00+08';
  END LOOP;
END $$;

SELECT
  calls,
  round(total_exec_time::numeric, 2) AS total_ms,
  round(mean_exec_time::numeric, 3)  AS mean_ms,
  rows,
  left(query, 72) AS query
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_stat_statements%'
ORDER BY total_exec_time DESC
LIMIT 8;

真实输出：

text
 calls | total_ms | mean_ms | rows |                             query
-------+----------+---------+------+----------------------------------------------------------------
     1 |   345.65 | 345.646 |    0 | DO $$
    30 |   178.61 |   5.954 |   30 | SELECT count(*) FROM orders WHERE status = $1
    30 |   165.01 |   5.500 |   30 | SELECT count(*) FROM orders WHERE created_at >= timestamptz $1
    30 |     0.30 |   0.010 |   30 | SELECT count(*) FROM orders WHERE user_id = $1
(4 rows)

读法：

  • DO 块总耗时最高，但只调用 1 次，属于一次性任务；
  • status 与 created_at 查询各 30 次、平均 5.5ms，是持续成本，优先优化；
  • user_id 查询 30 次、平均 0.01ms，有索引后已不是问题。

优化优先级 = 调用次数 × 单次耗时，不是单看某一次跑得多慢。

第 7 步：防回归 ​

优化完成后，至少做三件事：

  1. 把 SQL 加入慢查询回归测试：固定数据集 + EXPLAIN 断言计划形状；
  2. 设置查询预算：接口 p95 超过阈值告警；
  3. 记录索引变更：迁移文件中保留索引，避免下次部署被「清理无用索引」误删。

常见坑与排查 ​

现象根因处理
单次执行很快，线上 p99 很高锁等待、连接池排队、缓存击穿看 pg_locks、池指标、缓存命中率
加了索引仍然慢OFFSET 仍要跳过、返回行数多、统计过期keyset 分页；ANALYZE；检查选择性
EXPLAIN 估计行数与实际差几个数量级统计信息过期、列相关性强ANALYZE；CREATE STATISTICS
排序落盘work_mem 不足调大会话级 work_mem，或减少排序数据量
N+1 在开发环境不明显数据少、全在缓存用真实数据量压测；代码评审盯循环内查询
慢日志刷屏log_min_duration_statement 太小按环境调整；先修 Top SQL
COUNT(*) 分页总数很慢大表精确计数代价高用估算值、缓存总数、或「是否有下一页」
批量任务把库拖慢大事务、一次性更新太多行分批提交；低峰执行；限制并发
只看平均耗时长尾被平均掉看 p95/p99 与慢日志
盲目加缓存一致性问题被掩盖先修 SQL/索引；缓存要有失效策略

企业级做法 ​

  1. 每个服务都有慢查询看板：pg_stat_statements Top 20 + p95/p99 + 慢日志趋势。
  2. 优化有基线：改动前后记录 calls / total_ms / mean_ms / Buffers，用数据证明有效。
  3. 分页统一用游标：列表接口默认 keyset，后台管理确需跳页时用延迟关联并限制最大页码。
  4. ORM 禁止循环查库：Code Review 检查 for / map 内的 repository 调用；批量用 IN 或 JOIN。
  5. 查询预算进 CI：核心查询在固定数据集上跑 EXPLAIN，断言不出现 Seq Scan / external merge。
  6. 读写分离与分析隔离：报表走只读副本或数据仓库，避免大聚合压主库（第 09 章）。
  7. 归档与分区：历史订单归档/分区，减少热表体积；深分页与 COUNT 都会随之变便宜。
  8. 缓存是最后一层：先确认 SQL 与索引已优化；缓存要定义 key、TTL、失效与降级策略（第 11 章）。
  9. 慢查询复盘写进文档：SQL、计划、数据量、根因、修复、验证，形成团队知识库。
  10. 不要在生产随便 EXPLAIN ANALYZE 写语句：它会真的执行；写操作先用事务包住并回滚，或用 EXPLAIN（不带 ANALYZE）。

练习与验收标准 ​

练习

  1. 把 07-keyset-pagination.sql 改成「上一页」查询（> + ORDER BY ... ASC），验证仍走索引。
  2. 给 orders(status, created_at) 建联合索引，比较 WHERE status = 'paid' ORDER BY created_at DESC LIMIT 20 的计划。
  3. 用 pg_stat_statements 找出你本地调用次数最多的 3 条 SQL，说明它们是否值得优化。
  4. 把 N+1 的 DO 块改成一次 GROUP BY，记录两者耗时。
  5. 给 created_at 建表达式索引，验证 date_trunc 为什么不能直接建，以及改写后是否能命中。
  6. 把 work_mem 临时调大，重跑深分页 EXPLAIN，观察 external merge 是否消失。

验收标准

  • [ ] 30 万行数据灌入成功，users=5000、orders=300000；
  • [ ] 深分页建索引前出现 external merge Disk；
  • [ ] 建索引后排序落盘消失，但 Buffers 仍显示大量读取；
  • [ ] keyset 分页执行时间低于 1ms，计划为 Index Only Scan；
  • [ ] N+1 与单次聚合的耗时差距能被稳定复现；
  • [ ] pg_stat_statements 能按 total_exec_time 排序并识别 Top SQL；
  • [ ] 慢查询日志能捕获超过 200ms 的语句；
  • [ ] 能说出至少三种「SQL 单独快、线上慢」的原因。
