本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清 RDB 与 AOF 分别丢什么、丢多少，并能为业务选对组合；
  2. 用 INFO persistence、BGSAVE、BGREWRITEAOF 验证持久化是否真的生效；
  3. 从零搭一个三节点 Redis Cluster，理解槽位、MOVED/ASK 重定向与 -c 的作用；
  4. 写出「互斥 + 防死锁 + 防误删」的分布式锁，知道续期与 Redlock 的边界；
  5. 用 Lua 实现固定窗口、滑动窗口、令牌桶三种限流，并说清各自缺陷；
  6. 为 Redis 生产部署列出持久化、集群、内存、监控四类必查项。

第 11 章讲了数据结构与缓存模式，本章只讲「上线之后」的问题。

概念与原理 ​

1. 持久化：Redis 的持久性是「可配置的」 ​

Redis 是内存数据库，进程退出内存就没了。它提供两种落盘方式：

方式机制丢数据窗口恢复速度适用
RDB周期性 fork 子进程写全量快照最后一次快照之后快（直接加载二进制）备份、灾备、冷启动
AOF追加每条写命令，可配置刷盘频率appendfsync 决定慢（重放命令）不能丢太多数据的业务
混合AOF 重写时基准用 RDB 格式同 AOF较快Redis 7 默认思路

AOF 的 appendfsync 三档：

text
always    每条命令都 fsync     最安全，QPS 直接掉一个量级
everysec  每秒 fsync 一次      最多丢约 1 秒，默认推荐
no        交给操作系统          最多丢 30 秒，仅在可接受时使用

关键认知：持久化不等于不丢数据。即使 appendfsync always，异步复制的主从切换也可能丢；要强一致就得用数据库或接受额外协调成本。

RDB 的 fork 也有代价：数据集越大，fork 的页表复制越慢，写时复制（COW）期间内存可能翻倍。40GB 的实例做 RDB，要预留足够内存与磁盘 IO。

2. 集群：16384 个槽位决定数据在哪 ​

Redis Cluster 把键空间切成 16384 个槽（slot），每个主节点负责一段：

text
slot = CRC16(key) % 16384

客户端访问任意节点，节点发现 key 不在自己负责的槽，就返回：

  • MOVED 1330 192.168.80.3:6379：槽已经稳定迁移到别的节点，客户端应更新路由表；
  • ASK 1330 ...：槽正在迁移中，本次临时去目标节点问一次，不改路由表。

所以客户端必须支持集群协议（redis-cli -c、ioredis 的 cluster 模式、Jedis Cluster）。单机客户端连集群会频繁报 MOVED。

多 key 命令（MGET、SUNION、事务、Lua）要求所有 key 在同一个槽，否则报 CROSSSLOT。解决办法是 hash tag：

text
{user:1}:profile 和 {user:1}:orders  → 只对 {} 里的内容算槽，必然同槽

3. 分布式锁：三个条件，一个都不能少 ​

text
1) 互斥      SET key token NX PX 30000
2) 防死锁    PX 到期自动释放，持有者崩溃也不会永久占锁
3) 防误删    Lua 比较 token 再 DEL

为什么第 3 条必须用 Lua：GET 和 DEL 是两条命令，中间可能插入其他客户端的操作，必须原子化。

三个常见误区：

  • 锁过期但业务没做完：租期是「预估」，不是「保证」。要么业务幂等，要么续期（看门狗），要么用 fencing token 让下游拒绝旧持有者的写；
  • 无条件 DEL：会删掉别人的锁，本章示例会现场复现；
  • 把 Redlock 当银弹：多 Redis 实例的 Redlock 在时钟漂移、网络分区下仍有争议（Martin Kleppmann 与 antirez 的著名辩论）。强一致场景请用 ZooKeeper/etcd，或让数据库唯一约束兜底。

4. 限流：三种算法的取舍 ​

算法原理优点缺点
固定窗口每个窗口一个计数器实现最简单、内存 O(1)窗口边界突刺：两倍瞬时流量
滑动窗口ZSET 存每次请求时间戳任意窗口都精确内存与请求量成正比
令牌桶桶容量 + 固定补充速率允许突发、长期速率可控状态需原子读写

漏桶是令牌桶的镜像（恒定流出），适合「保护下游固定处理能力」；令牌桶适合「允许短时突发」的对外 API。生产还要决定：超限是拒绝（429）、排队还是降级。

单实例的配置单独放文件，便于对照每一项：

ini
# 第 12 章单实例 Redis 配置：持久化与内存
#
# Redis 的持久化是「可配置的持久性」，不是数据库的 WAL 那么强。
# 这里同时打开两种方式，便于观察它们的差异：
#   AOF：每次写命令追加到日志，appendfsync everysec 最多丢 1 秒；
#   RDB：周期性快照，适合备份与快速恢复，但会丢最近一段数据。
# 生产只选一种也可以，但必须知道「丢了会丢多少」。

# 监听所有网卡（容器内）
bind 0.0.0.0
protected-mode no
port 6379

# ---- RDB ----
# 900 秒内至少 1 次写、300 秒内至少 10 次写、60 秒内至少 10000 次写，分别触发快照
save 900 1
save 300 10
save 60 10000
dbfilename dump.rdb
dir /data

# ---- AOF ----
appendonly yes
appendfilename "appendonly.aof"
# everysec：每秒刷盘，性能与安全的折中；always 最安全但最慢
appendfsync everysec
# AOF 重写期间不 fsync，避免重写 IO 影响主线程
no-appendfsync-on-rewrite no
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# ---- 内存 ----
# 单机演示给 128MB，生产按「数据集 + 峰值 + 碎片」估算
maxmemory 128mb
# 纯缓存用 allkeys-lru；混合存储用 noeviction 或 volatile-*，禁止被当缓存淘汰
maxmemory-policy allkeys-lru

# ---- 慢日志 ----
# 超过 10ms 的命令记入慢日志，可用 SLOWLOG GET 查看
slowlog-log-slower-than 10000
slowlog-max-len 128

逐步拆解 ​

第 1 步：写入 → 重启 → 校验 ​

bash
$R FLUSHALL >/dev/null
$R SET order:9001 '{"status":"paid","amount":29900}'
$R HSET product:1001 name '机械键盘' stock 10
# 批量写 100 个计数键，模拟真实业务写入
docker compose exec -T persist sh -c \
  'for i in $(seq 1 100); do redis-cli SET counter:$i $i >/dev/null; done'
echo "写入完成，key 数量：$($R DBSIZE | tr -d '\r')"

脚本会写 102 个 key，然后 docker compose restart persist。重启后的校验：

bash
$R GET order:9001
$R HGET product:1001 name
echo "重启后 key 数量：$($R DBSIZE | tr -d '\r')"
$R GET counter:100
$R TTL order:9001

真实输出：

text
{"status":"paid","amount":29900}
机械键盘
重启后 key 数量：102
100
-1

TTL 返回 -1 表示这个 key 本来就没有过期时间。如果 key 设置了 TTL，重启后过期时间会被恢复；但重启期间已经到期的 key 会在加载时被丢弃。

观察落盘文件：

text
20.0K	/data/appendonlydir
4.0K	/data/dump.rdb
total 20
-rw-------    1 redis    root            89 Nov 10 13:12 appendonly.aof.1.base.rdb
-rw-------    1 redis    root         10849 Nov 10 13:21 appendonly.aof.1.incr.aof
-rw-------    1 redis    root            88 Nov 10 13:12 appendonly.aof.manifest

Redis 7 的 AOF 是多文件结构：base 是重写后的基准（这里用 RDB 格式存），incr 是增量命令，manifest 记录清单。看到 .base.rdb 不要误以为是 RDB 快照，它是 AOF 的一部分。

第 2 步：持久化状态与手动触发 ​

text
aof_enabled:1
aof_last_bgrewrite_status:ok
aof_last_write_status:ok
rdb_last_bgsave_status:ok
rdb_changes_since_last_save:103

四个状态字段就是巡检清单：

  • aof_last_write_status 不是 ok：磁盘满了或权限问题，此时 AOF 已经停止写入；
  • aof_last_bgrewrite_status 不是 ok：重写失败，AOF 会持续膨胀；
  • rdb_last_bgsave_status 不是 ok：快照失败，常见于 fork 失败或磁盘不足；
  • rdb_changes_since_last_save 持续增长但 rdb_last_save_time 不动：快照没成功。

第 4 步：验证路由与 MOVED ​

bash
# 同一个 key 永远落在同一个槽，槽决定节点
docker compose exec -T cluster-1 redis-cli CLUSTER KEYSLOT order:9001
docker compose exec -T cluster-1 redis-cli CLUSTER KEYSLOT user:1
# -c 表示跟随 MOVED 重定向；不带 -c 会直接返回 MOVED 错误
docker compose exec -T cluster-1 redis-cli -c SET order:9001 '{"status":"paid"}'
docker compose exec -T cluster-2 redis-cli -c GET order:9001
# 不带 -c：只做一次路由，遇到 MOVED 就报错
docker compose exec -T cluster-2 redis-cli GET order:9001 || true

真实输出：

text
1330
10778
OK
{"status":"paid"}
MOVED 1330 192.168.80.5:6379

CLUSTER KEYSLOT order:9001 算出槽 1330，属于 192.168.80.5（cluster-1）。客户端连在 192.168.80.3（cluster-2）上执行 GET，节点返回 MOVED 并附上正确地址；加上 -c 后客户端会跟随重定向。

第 5 步：锁的互斥与释放 ​

bash
$R FLUSHDB >/dev/null
$R SET lock:order:42 token-A NX PX 3000
$R SET lock:order:42 token-B NX PX 3000
$R GET lock:order:42
$R PTTL lock:order:42

真实输出：

text
OK

token-A
2682

第二次 SET NX 返回 nil（空行），GET 仍是 token-A，PTTL 显示 2682ms 后过期。

释放锁必须校验 token：

bash
# B 拿不到锁，却来释放：返回 0，锁还在
$R --eval /scripts/lua/unlock.lua lock:order:42 , token-B
$R GET lock:order:42
# A 释放自己的锁：返回 1
$R --eval /scripts/lua/unlock.lua lock:order:42 , token-A
$R GET lock:order:42

真实输出：

text
0
token-A
1

token-B 来释放返回 0，锁还在；token-A 释放返回 1。Lua 脚本本体：

lua
-- 分布式锁的安全释放脚本
--
-- 为什么不能直接 DEL？
--   客户端 A 拿到锁后业务超时，锁自动过期；客户端 B 拿到同一把锁；
--   此时 A 回来执行 DEL，会把 B 的锁删掉，互斥失效。
--
-- 正确做法：比较 token 再删除。GET + DEL 必须是原子的，
-- 所以用 Lua（Redis 执行脚本期间不会插入其他命令）。
--
-- KEYS[1] = 锁 key
-- ARGV[1] = 加锁时写入的唯一 token
-- 返回 1 表示确实删除，0 表示锁已不属于当前持有者

if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end

第 6 步：复现「删掉别人的锁」 ​

这是面试高频、线上真实发生的 bug：

text
A 持有锁 token-old，租期 1000ms；业务卡住……
锁已过期，GET：
B 重新拿到锁 token-new
A 回来后无条件 DEL，锁消失：GET：
→ 此时 B 还在临界区，互斥已被破坏

因为 A 的业务执行时间超过了租期，锁自动过期，B 拿到锁；A 醒来后执行 DEL lock:order:42，删的是 B 的锁。修法只有两种：

  • 释放时校验 token（本章做法）；
  • 让下游用 fencing token 校验「写请求的序号必须大于已见最大值」，从根上防住过期持有者的写入。

第 7 步：续期也要校验 token ​

bash
$R SET lock:order:42 token-A NX PX 2000 >/dev/null
echo "初始 PTTL：$($R PTTL lock:order:42 | tr -d '\r')"
# 错误持有者续期：返回 0，租期不变
echo "token-B 续期：$($R --eval /scripts/lua/renew.lua lock:order:42 , token-B 10000 | tr -d '\r')"
echo "续期后 PTTL：$($R PTTL lock:order:42 | tr -d '\r')"
# 正确持有者续期：返回 1，租期被拉长
echo "token-A 续期：$($R --eval /scripts/lua/renew.lua lock:order:42 , token-A 10000 | tr -d '\r')"
echo "续期后 PTTL：$($R PTTL lock:order:42 | tr -d '\r')"

真实输出：

text
初始 PTTL：1889
token-B 续期：0
续期后 PTTL：1674
token-A 续期：1
续期后 PTTL：9892

token-B 续期失败，PTTL 自然递减（1889 → 1674）；token-A 续期成功，PTTL 被拉回 9892ms。续期的脚本：

lua
-- 分布式锁续期脚本
--
-- 业务执行时间不确定时，固定租期迟早会不够用。续期同样必须先校验持有者：
-- 否则「已经丢锁的客户端」会把新持有者的锁续上，临界区出现两个执行者。
--
-- KEYS[1] = 锁 key
-- ARGV[1] = 持有者 token
-- ARGV[2] = 新的租期（毫秒）
-- 返回 1 表示续期成功，0 表示锁已不属于当前持有者（应立即停止业务）

if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])
else
  return 0
end

生产里自己写看门狗容易出错，通常直接用 Redisson 的 RLock，它内置了「每 1/3 租期续一次」的机制。

第 8 步：三种限流 ​

固定窗口：

bash
$R DEL rate:fixed:user:1 >/dev/null
for i in $(seq 1 7); do
  result=$($R --eval /scripts/lua/rate-fixed.lua rate:fixed:user:1 , 5 10000 | tr -d '\r')
  echo "第 $i 次请求：$result"
done
echo "窗口计数：$($R GET rate:fixed:user:1 | tr -d '\r')，剩余 TTL(ms)：$($R PTTL rate:fixed:user:1 | tr -d '\r')"

真实输出：

text
第 1 次请求：1
...
第 5 次请求：1
第 6 次请求：0
第 7 次请求：0
窗口计数：7，剩余 TTL(ms)：9132

注意计数是 7 而不是 5：被拒绝的请求也执行了 INCR。这在固定窗口里通常可接受，但如果你要求「拒绝的请求不占配额」，就要把判断放在 INCR 之前，或直接不计数。

滑动窗口：

bash
$R DEL rate:sliding:user:1 >/dev/null
NOW=$(now_ms)
echo "同一秒内连续请求："
for i in $(seq 1 5); do
  # 成员用「毫秒时间戳-序号」保证唯一，否则会覆盖而不是累加
  result=$($R --eval /scripts/lua/rate-sliding.lua rate:sliding:user:1 , 3 1000 "$NOW" "req-$NOW-$i" | tr -d '\r')
  echo "第 $i 次请求：$result"
done
echo "窗口内记录数：$($R ZCARD rate:sliding:user:1 | tr -d '\r')"
sleep 1.1
NOW=$(now_ms)
echo "1.1 秒后再请求：$($R --eval /scripts/lua/rate-sliding.lua rate:sliding:user:1 , 3 1000 "$NOW" "req-after-$NOW" | tr -d '\r')"

真实输出：

text
第 1 次请求：1
第 2 次请求：1
第 3 次请求：1
第 4 次请求：0
第 5 次请求：0
窗口内记录数：3
1.1 秒后再请求：1

ZSET 的成员必须唯一（示例用「时间戳-序号」），否则同一毫秒的两次请求会覆盖，计数永远上不去。

令牌桶：

bash
$R DEL rate:bucket:api >/dev/null
NOW=$(now_ms)
echo '立即连续请求 5 次（桶里有 3 个令牌）：'
for i in $(seq 1 5); do
  echo "第 $i 次：$($R --eval /scripts/lua/token-bucket.lua rate:bucket:api , 3 1 "$NOW" 1 | tr -d '\r' | paste -sd ' ' -)"
done
sleep 1.2
NOW=$(now_ms)
echo "等 1.2 秒后（补回约 1 个令牌）：$($R --eval /scripts/lua/token-bucket.lua rate:bucket:api , 3 1 "$NOW" 1 | tr -d '\r' | paste -sd ' ' -)"

真实输出：

text
第 1 次：1 2.000
第 2 次：1 1.000
第 3 次：1 0.000
第 4 次：0 0.000
第 5 次：0 0.000
等 1.2 秒后（补回约 1 个令牌）：1 0.887

第一个返回值是「是否放行」，第二个是剩余令牌。空桶后等待 1.2 秒，理论上补回 1.2 个令牌、用掉 1 个应剩 0.2；实际返回 0.887，多出来的部分是「脚本取时间戳 → 5 次 redis-cli 调用 → sleep」这段真实耗时也被计入了补充量，属于预期内的误差。生产里时间戳由应用传入，误差只取决于传入时刻的准确性。

完整的令牌桶逻辑：

lua
-- 令牌桶限流
--
-- 思路：桶有固定容量，按固定速率补充令牌；请求消耗令牌，不够就拒绝。
-- 优点：允许短时突发（桶里攒下的令牌），长期平均速率受控。
-- 缺点：状态是「令牌数 + 上次时间」，需要一次读数一次写回，必须原子执行。
--
-- KEYS[1] = hash key，字段 tokens / ts
-- ARGV[1] = 桶容量（最大突发量）
-- ARGV[2] = 每秒补充令牌数
-- ARGV[3] = 当前毫秒时间戳
-- ARGV[4] = 本次请求消耗的令牌数
-- 返回 {是否允许, 剩余令牌数}，是否允许 1/0

local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local cost = tonumber(ARGV[4])

local data = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts = tonumber(data[2])

-- 第一次访问：桶是满的
if tokens == nil then tokens = capacity end
if ts == nil then ts = now end

-- 按流逝时间补充，最多补到容量
local delta_ms = now - ts
if delta_ms < 0 then delta_ms = 0 end
tokens = math.min(capacity, tokens + (delta_ms / 1000.0) * rate)

local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- 桶空闲后自动回收，避免 key 越积越多
redis.call('PEXPIRE', KEYS[1], 60000)

return { allowed, string.format('%.3f', tokens) }

常见坑与排查 ​

现象根因处理
重启后数据全没了没开 AOF，RDB 也没触发过开 AOF everysec；关键数据不要只依赖 Redis
aof_last_write_status:err磁盘满、只读挂载、权限错误立刻恢复磁盘；Redis 会拒绝写入直到恢复
RDB 快照周期性失败fork 失败（内存不足/overcommit 限制）检查 vm.overcommit_memory=1、THP 关闭、留足内存
主从切换后丢了最后几秒数据异步复制接受窗口，或业务侧做补偿/对账
集群一直 cluster_state:fail槽位没分配完、总线端口不通CLUSTER INFO 看 cluster_slots_assigned；放行 16379
客户端疯狂 MOVED用了单机客户端连集群换 cluster 客户端；或 -c
多 key 命令报 CROSSSLOTkey 落在不同槽用 hash tag {user:1}:a、{user:1}:b
某节点宕机后部分 key 不可用3 主 0 从没有副本至少 3 主 3 从；评估 cluster-require-full-coverage
锁偶尔失效、两个消费者同时处理业务超过租期续期 + 业务幂等 + fencing token
锁被误删未校验 token用 Lua 比较后删除
限流边界被打穿固定窗口突刺换滑动窗口或令牌桶
限流 key 内存暴涨key 没设过期、维度太细每个 key 必须 PEXPIRE；限制维度基数
KEYS * 把实例打挂单线程阻塞用 SCAN；生产禁用 KEYS/FLUSHALL

企业级做法 ​

  1. 持久化按业务定档：纯缓存可以只开 RDB 甚至不开；会话、队列、计数器开 AOF everysec；不允许丢的不要放 Redis。
  2. 持久化要有演练：定期在预发用真实备份恢复一次，验证「备份可恢复」而不是「备份文件存在」。
  3. 集群至少 3 主 3 从，跨机架/可用区分布；cluster-node-timeout 按网络质量调，太小会误判故障。
  4. 客户端用集群感知驱动：ioredis cluster、Jedis Cluster、go-redis ClusterClient；配置重试与拓扑刷新。
  5. 热 key 与 big key 治理：--bigkeys、--hotkeys、SLOWLOG 定期扫描；big key 拆分，热 key 本地缓存或多副本。
  6. 锁只保护「短临界区」：临界区里不要放长事务、远程调用；优先用数据库唯一约束/状态机做最终防线。
  7. 限流维度提前设计：用户、IP、租户、接口四个维度选一个主维度，避免 key 爆炸；超限返回 429 并带 Retry-After。
  8. 容量规划：maxmemory 留 25%~30% 给碎片与 COW；used_memory_rss / used_memory 长期 > 1.5 要排查碎片。
  9. 监控四件套：内存与淘汰次数、命中率、持久化状态、主从延迟（INFO replication 的 master_repl_offset 差值）。
  10. 变更要可回滚：集群扩容用 CLUSTER SETSLOT 迁移并留回滚方案；配置改动走配置中心，不手改容器。

练习与验收标准 ​

练习

  1. 把 appendfsync 改成 always，用 redis-benchmark -n 10000 -c 50 set k __rand_int__ 对比 everysec 的 QPS。
  2. 关闭 AOF 只留 RDB，写入后立即 docker compose kill，观察丢失多少数据。
  3. 在集群里用 {user:1}:profile、{user:1}:orders 验证 MGET 不再报 CROSSSLOT。
  4. 给集群加一个从节点（CLUSTER MEET + CLUSTER REPLICATE），kill 主节点，观察自动切换。
  5. 把固定窗口改成「每个用户每分钟 5 次」，用 rate:fixed:{user_id}:{yyyyMMddHHmm} 拼接 key。
  6. 给锁加一个「获取失败重试 3 次、每次间隔 100ms」的封装，并处理超时。

验收标准

  • [ ] 重启后 DBSIZE 仍为 102，GET order:9001 返回原值；
