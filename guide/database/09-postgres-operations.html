09 PostgreSQL 运维：备份、复制、连接池与监控 ​

pg_dump/pg_restore、逻辑复制、连接数预算与生产关键监控 SQL。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 区分逻辑备份与物理备份，用 pg_dump -Fc / pg_restore 做一次可校验的恢复；
  2. 理解 WAL、RPO/RTO，知道「有备份」和「能恢复」是两件事；
  3. 用 CREATE PUBLICATION / CREATE SUBSCRIPTION 搭一套逻辑复制，并观察复制状态；
  4. 说清物理流复制与逻辑复制的适用边界；
  5. 做连接数预算，理解应用连接池与 PgBouncer 各自解决什么问题；
  6. 用一组 SQL 看住连接、容量、索引、慢查询、锁、复制延迟、缓存命中率和检查点。

概念与原理 ​

1. 备份：先定义 RPO / RTO ​

  • RPO（Recovery Point Objective）：最多能接受丢多少数据。每天全量备份 → RPO 最坏 24 小时；持续归档 WAL → RPO 可以到秒级。
  • RTO（Recovery Time Objective）：多久能恢复服务。恢复 1TB 数据的时间必须实测，不能拍脑袋。
方式工具粒度典型 RPO适合
逻辑备份pg_dump / pg_restore库/表备份时刻跨版本迁移、单表恢复、开发环境
物理备份pg_basebackup + WAL 归档整个实例秒级（配合归档）生产全量恢复、PITR
快照云盘/文件系统快照卷快照时刻大规模、快速回滚
复制流复制/逻辑复制实例/表毫秒~秒高可用、读写分离

逻辑备份不能替代物理备份：它慢、占 CPU、恢复要重放 SQL，且不包含角色、扩展等实例级对象。它的优势是灵活、可跨大版本。

2. WAL 与 PITR ​

PostgreSQL 所有修改先写 WAL（预写日志），再改数据页。只要保留「基础备份 + 从那一刻起的 WAL」，就能恢复到任意时间点（Point-In-Time Recovery）。

text
基础备份（周日）── WAL 1 ── WAL 2 ── ... ── 故障点（周三 10:00）
                                      └─ 恢复到 09:59:59

没有 WAL 归档，只有基础备份，就只能恢复到备份时刻。

3. 复制：物理 vs 逻辑 ​

物理流复制逻辑复制
复制单位整个实例（块级）表级（行变更）
备库可写否（只读）是（但业务上应只读）
跨大版本不支持支持
复制 DDL是否（要单独建表）
复制序列是否
典型用途高可用、只读副本按表同步、跨版本升级、多下游分发

物理复制像「磁盘镜像」，逻辑复制像「变更事件流」。生产高可用通常用物理流复制 + 自动故障转移（Patroni/repmgr）；跨团队数据分发用逻辑复制。

4. 连接池的两层 ​

text
应用实例 1 ── poolSize=10 ─┐
应用实例 2 ── poolSize=10 ─┼── PgBouncer（可选）── PostgreSQL max_connections=100
应用实例 3 ── poolSize=10 ─┘
  • 应用侧连接池（pg.Pool、TypeORM poolSize）：复用连接、避免每次请求 TCP + 认证；
  • PgBouncer：把成百上千个客户端连接复用到少量数据库连接，适合 Serverless、多实例、短连接场景。

预算公式：

text
实例数 × 每实例 poolSize + 运维/迁移连接 < max_connections - superuser_reserved_connections

超过之后客户端会收到 FATAL: sorry, too many clients already，而不是排队。

5. 监控看什么 ​

最小集合：

  1. 连接数与使用率；
  2. 数据库/表/索引容量增长；
  3. 慢查询与等待事件；
  4. 锁等待与阻塞链；
  5. 复制延迟与复制槽堆积；
  6. 缓存命中率、检查点频率；
  7. 备份是否成功、恢复演练是否通过。

逐步拆解 ​

第 1 步：逻辑备份与恢复 ​

bash
docker compose exec -T primary pg_dump -U demo -d pg_ops -Fc -f "${remote}"
docker compose cp "primary:${remote}" "${local_file}"
ls -lh "${local_file}"
bash
./scripts/backup-restore.sh

真实输出：

text
== 1. 备份主库到 backups/pg_ops-20261110-210439.dump ==
-rw-r--r--  7.7K  backups/pg_ops-20261110-210439.dump

-Fc 是 custom 格式：压缩、可选择性恢复、支持并行恢复（pg_restore -j 4）。对比其他格式：

格式参数特点
plain默认SQL 文本，可直接 psql，不能选择性恢复
custom-Fc压缩、灵活，最常用
directory-Fd每表一个文件，支持并行
tar-Ft归档，较少用

恢复到新库：

bash
docker compose exec -T primary dropdb -U demo --if-exists pg_ops_restore
docker compose exec -T primary createdb -U demo pg_ops_restore
docker compose exec -T primary pg_restore -U demo -d pg_ops_restore "${remote}"

真实输出：

text
== 3. 校验恢复结果（应与主库一致） ==
 table_name | rows
------------+------
 products   |    6
 orders     |    6

 table_name | rows
------------+------
 products   |    6
 orders     |    6

恢复演练才是备份的验收。只看到「备份文件存在」不算数，必须定期在独立环境恢复并校验行数/校验和。

第 2 步：逻辑复制 ​

发布端（主库）：

bash
docker compose exec -T primary psql -U demo -d pg_ops -v ON_ERROR_STOP=1 <<'SQL'
DROP PUBLICATION IF EXISTS pub_ops;
CREATE PUBLICATION pub_ops FOR TABLE products, orders;
SQL

订阅端（副本）：

bash
docker compose exec -T replica psql -U demo -d pg_ops -v ON_ERROR_STOP=1 <<'SQL'
DROP SUBSCRIPTION IF EXISTS sub_ops;
CREATE SUBSCRIPTION sub_ops
  CONNECTION 'host=primary port=5432 user=repl password=repl dbname=pg_ops'
  PUBLICATION pub_ops;
SQL

真实输出：

text
== 1. 主库创建发布（publication） ==
CREATE PUBLICATION
== 2. 副本删除旧订阅并重建（subscription） ==
NOTICE:  created replication slot "sub_ops" on publisher
CREATE SUBSCRIPTION
== 3. 等待初始同步（最多 20 秒） ==
第 1 次检查，副本 products = 5

CREATE SUBSCRIPTION 会：

  1. 连接主库，创建复制槽 sub_ops；
  2. 对 products、orders 做一次全量拷贝（initial sync）；
  3. 之后持续消费 WAL 中的行变更。

增量验证：在主库插入 LP-5001，1 秒后副本可读到：

text
   sku   |    name    | stock
---------+------------+-------
 ...
 LP-5001 | 台灯       |    30
(6 rows)

复制状态的真实输出：

text
 application_name |   state   | sync_state
------------------+-----------+------------
 sub_ops          | streaming | async

 slot_name |  plugin  | active | retained_wal
-----------+----------+--------+--------------
 sub_ops   | pgoutput | t      | 0 bytes

retained_wal = 0 bytes 说明订阅端跟上了，没有 WAL 堆积。如果这个值持续增长，磁盘会被复制槽吃满。

逻辑复制的边界：

  • 不复制 DDL：副本必须先有同名表（示例的 sql/replica/01-schema.sql）；
  • 不复制序列：副本的 products_id_seq 不会前进，不能直接在副本插入；
  • 需要主键或 REPLICA IDENTITY 才能更新/删除；
  • 大事务、长事务会放大延迟；
  • 订阅端默认可写，只读要靠权限或路由保证。

第 3 步：物理流复制（未在示例中启动） ​

物理复制用 pg_basebackup 初始化备库数据目录，再通过 primary_conninfo 持续接收 WAL：

bash
pg_basebackup -h primary -p 5432 -U repl -D /var/lib/postgresql/data \
  -Fp -Xs -P -R

-R 会自动写 standby.signal 和 primary_conninfo。备库启动后处于只读、持续恢复状态。

本章示例没有启动物理复制，原因是：它要求备库数据目录完全由主库初始化，容器编排要定制 entrypoint，且不能在同一个 compose 里「先建库再订阅」；逻辑复制更适合在教程里逐步观察。生产的高可用方案应另外验证故障转移。

第 4 步：连接数预算 ​

bash
for i in $(seq 1 "${N}"); do
  docker compose exec -T primary \
    psql -U demo -d pg_ops -c 'SELECT pg_sleep(8);' >/dev/null &
  pids+=("$!")
done
bash
./scripts/connection-demo.sh 10

真实输出：

text
== 打开 10 个会话，每个保持 8 秒 ==
== 观察连接数（应约为 N + 1，包含本次查询自身） ==
 state  | connections
--------+-------------
 active |          11
(1 row)

每个会话都直接连数据库。如果这是 3 个应用实例 × 每实例 10 个连接，就是 30 个；再加迁移、监控、运维，很快逼近 max_connections。

连接不是越多越好：PostgreSQL 每个连接是一个进程，上下文切换和内存开销随连接数上升。常见做法：

  • 应用侧 poolSize 控制在 5~20；
  • 多实例时用 PgBouncer（transaction pooling）；
  • 给运维保留 superuser_reserved_connections；
  • 设置 idle_in_transaction_session_timeout，回收悬挂事务。

第 5 步：连接与容量监控 ​

sql
\echo '=== 2. 连接使用情况（按状态/应用分组） ==='
SELECT state, count(*) AS connections
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state
ORDER BY connections DESC;

SELECT current_setting('max_connections')::int AS max_connections,
       count(*) FILTER (WHERE backend_type = 'client backend') AS client_connections,
       round(100.0 * count(*) FILTER (WHERE backend_type = 'client backend')
             / current_setting('max_connections')::int, 2) AS used_pct
FROM pg_stat_activity;
sql
\echo '=== 3. 数据库与表容量 ==='
SELECT datname,
       pg_size_pretty(pg_database_size(datname)) AS size
FROM pg_database
ORDER BY pg_database_size(datname) DESC;

SELECT relname,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
       pg_size_pretty(pg_relation_size(relid)) AS table_size,
       pg_size_pretty(pg_total_relation_size(relid) - pg_relation_size(relid)) AS index_toast
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;

真实输出：

text
 max_connections | client_connections | used_pct
-----------------+--------------------+----------
              50 |                  1 |     2.00

 relname  | total_size | table_size | index_toast
----------+------------+------------+-------------
 products | 48 kB      | 8192 bytes | 40 kB
 orders   | 40 kB      | 8192 bytes | 32 kB

pg_stat_activity 里 state 的分布比总数更有用：

  • 大量 idle：连接池开太大或泄漏；
  • 大量 active 且时间长：慢查询或锁等待；
  • idle in transaction：应用忘了提交/回滚，会阻塞 vacuum。

第 6 步：锁与慢查询 ​

sql
\echo '=== 6. 锁等待：谁在等谁 ==='
SELECT blocked.pid AS blocked_pid,
       blocked.query AS blocked_query,
       blocking.pid AS blocking_pid,
       blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN LATERAL unnest(pg_blocking_pids(blocked.pid)) AS b(pid) ON true
JOIN pg_stat_activity blocking ON blocking.pid = b.pid
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;

pg_blocking_pids(pid) 返回阻塞该进程的 PID 列表，unnest 展开后 join 回 pg_stat_activity 就能看到「谁挡住了谁」。

长查询查询（超过 1 秒）：

sql
SELECT pid, now() - query_start AS duration, state, left(query, 80) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
  AND now() - query_start > interval '1 second'
ORDER BY duration DESC;

示例运行时，逻辑复制 worker 的 START_REPLICATION 会出现在结果里，这是正常的——它本来就是长连接。

第 7 步：复制与缓存监控 ​

sql
\echo '=== 7. 复制槽与逻辑复制延迟 ==='
SELECT slot_name,
       plugin,
       active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS retained_wal
FROM pg_replication_slots;

SELECT application_name, state, sync_state
FROM pg_stat_replication;
sql
\echo '=== 8. 缓存命中率（低于 99% 要关注） ==='
SELECT datname,
       blks_hit,
       blks_read,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 3) AS cache_hit_pct
FROM pg_stat_database
WHERE datname = current_database();

真实输出：

text
 slot_name |  plugin  | active | retained_wal
-----------+----------+--------+--------------
 sub_ops   | pgoutput | t      | 0 bytes

 datname | blks_hit | blks_read | cache_hit_pct
---------+----------+-----------+---------------
 pg_ops  |    23345 |       599 |        97.498

OLTP 库的缓存命中率通常应在 99% 以上（除非刚重启、缓存还冷）。低于 99% 时先看：

  • shared_buffers 是否太小；
  • 是否有全表扫描把缓存冲掉；
  • 是否有超大表/索引导致 working set 超过内存。

第 8 步：副本侧监控 ​

bash
docker compose exec replica psql -U demo -d pg_ops -f /sql/04-monitoring-replica.sql
text
 subname | pid | running | received_lsn | latest_end_lsn
---------+-----+---------+--------------+----------------
 sub_ops | 123 | t       | 0/16B5C50    | 0/16B5C50
  • pid 为空：订阅 worker 没起来，看日志；
  • received_lsn 落后主库很多：网络或大事务；
  • pg_stat_subscription_stats.apply_error_count > 0：约束冲突/类型不匹配，复制已停。

第 9 步：PG17 的检查点统计 ​

PostgreSQL 17 把检查点统计从 pg_stat_bgwriter 拆到了 pg_stat_checkpointer：

sql
SELECT num_timed AS checkpoints_timed,
       num_requested AS checkpoints_req,
       write_time AS checkpoint_write_time,
       buffers_written AS buffers_checkpoint
FROM pg_stat_checkpointer;

checkpoints_req 远高于 checkpoints_timed，通常说明 max_wal_size 太小或写入突增。

常见坑与排查 ​

现象根因处理
备份文件有，恢复失败备份时未检查、权限/扩展缺失定期恢复演练；记录扩展与角色
恢复后序列重复逻辑备份按数据恢复，序列需重置setval 或 pg_dump --sequence
复制槽占满磁盘订阅端长期离线监控 retained_wal；删除废弃槽
副本插入报主键冲突逻辑复制不复制序列副本只读，写入统一走主库
副本没有新表DDL 不复制先在副本执行相同迁移
更新/删除不同步表没有主键/REPLICA IDENTITY补主键或设置 REPLICA IDENTITY FULL
too many clients连接数超 max_connections降 poolSize、上 PgBouncer、加告警
大量 idle in transaction应用忘记提交设 idle_in_transaction_session_timeout
缓存命中率骤降重启/大表扫描看 shared_buffers、慢查询
checkpoints_req 很高WAL 太小/写入突增调 max_wal_size，分散写入
备份期间业务变慢pg_dump 全表扫描占 IO低峰执行、从备库备份、限速
复制延迟持续增长大事务/网络/单线程 apply拆大事务、检查网络、PG16+ 并行 apply

企业级做法 ​

  1. 备份分级：每日全量 + 持续 WAL 归档 + 定期恢复演练；备份与数据库不同故障域（对象存储/另一可用区）。
  2. 明确 RPO/RTO 并演练：把恢复时间写进 SLA，每季度做一次真实恢复，记录耗时。
  3. 高可用用物理复制：Patroni/repmgr + 仲裁；逻辑复制用于数据分发，不承担自动故障转移。
  4. 复制槽告警：retained_wal > 阈值 立即告警，避免磁盘被 WAL 吃满。
  5. 连接池分层：应用 poolSize 小、PgBouncer 做多路复用；给迁移/监控预留连接。
  6. 超时兜底：statement_timeout、lock_timeout、idle_in_transaction_session_timeout 三件套，防止慢查询和悬挂事务拖垮实例。
  7. 监控四件套：连接、容量、慢查询、复制延迟；再加备份成功与恢复演练结果。
  8. 权限分离：业务账号无 DDL，复制账号只读 + REPLICATION，监控账号只读系统视图。
  9. 变更窗口：备份/恢复/大版本升级都要有回滚方案；升级前在副本上先跑一遍。
  10. 容量规划：按「表 + 索引 + WAL + 备份」估算磁盘，留 30% 余量；监控增长率而不是绝对值。

练习与验收标准 ​

练习

  1. 把备份改成 directory 格式（-Fd），用 pg_restore -j 4 并行恢复，比较耗时。
  2. 在主库删除一行，观察副本是否同步删除；再模拟「副本停机 1 分钟」，看复制槽的 retained_wal。
  3. 用 pgbench 或脚本把 max_connections 打满，记录报错信息。
  4. 给 products 加一列（DDL），验证逻辑复制不会同步，手动在副本补迁移后再写入数据。
  5. 用 pg_stat_statements（第 06 章）找出最耗时的 5 条 SQL，结合本章监控定位。
  6. 设计一个「3 实例 × poolSize 10 + PgBouncer」的连接预算表。

验收标准

  • [ ] 两个容器都 healthy；
  • [ ] setup-replication.sh 可重复执行，最终副本 products = 6；
  • [ ] pg_stat_replication 显示 sub_ops / streaming；
  • [ ] retained_wal 为 0 bytes；
  • [ ] 备份文件存在，恢复库行数与主库一致；
  • [ ] connection-demo.sh 10 显示 11 个 client backend；
  • [ ] 监控脚本能查出连接、容量、锁、复制、缓存命中率；
  • [ ] 能解释逻辑复制为什么不复制 DDL/序列；
  • [ ] 能写出自己项目的连接数预算公式。
