本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清 Redis 单线程模型、内存存储与「快」的边界；
  2. 按场景选对五种基础结构：String / Hash / List / Set / ZSet；
  3. 写出正确的 Cache-Aside 缓存读写与失效逻辑；
  4. 识别缓存穿透、击穿、雪崩，并知道各自的工程解法；
  5. 设计可读、可治理的 key 命名与 TTL 策略；
  6. 用 SCAN、OBJECT ENCODING、MEMORY USAGE、CONFIG GET 观察与治理内存。

持久化、集群、分布式锁与限流在第 12 章展开，本章只讲数据结构与缓存模式。

概念与原理 ​

1. Redis 为什么快，以及快在哪里 ​

  • 纯内存：读写不落盘（持久化是异步/后台的）；
  • 单线程执行命令：没有锁竞争，命令天然原子；
  • IO 多路复用：一个线程处理大量连接；
  • 高效数据结构：小集合用 listpack/intset 等紧凑编码。

单线程也意味着：一条慢命令会阻塞所有请求。KEYS *、大 Hash 的 HGETALL、ZRANGE 0 -1、复杂 Lua 脚本都是生产事故来源。

2. 五种基础结构 ​

结构典型用途关键命令注意
String缓存值、计数器、锁SET/GET/INCR/SET NX EX值不要过大（建议 < 10KB）
Hash对象字段读写HSET/HGET/HINCRBY/HGETALL大 Hash 不要整体读
List队列、栈、时间线RPUSH/LPOP/LRANGE只适合两端操作，中间随机访问慢
Set去重、标签、交并差SADD/SINTER/SUNION大集合的交集开销高
ZSet排行榜、延迟队列、范围查询ZADD/ZRANGE/ZINCRBY按分数排序，分数是 double

还有 Bitmap、HyperLogLog、GEO、Stream。它们不是「第五种结构」的替代，而是特定场景的压缩结构；本章不展开。

3. 编码与内存 ​

Redis 会根据元素数量和大小自动选择紧凑编码：

text
小 Hash  -> listpack（连续内存，省指针）
大 Hash  -> hashtable
小 ZSet  -> listpack
大 ZSet  -> skiplist + dict

OBJECT ENCODING 可以查看当前编码。编码转换是单向的（小 → 大），一旦变成 hashtable，即使删元素也不会自动变回 listpack。这也是「大 key 删不掉内存」的原因之一。

4. TTL 与淘汰 ​

  • EXPIRE key seconds / SET key value EX seconds：设置过期时间；
  • TTL：剩余秒数，-1 永不过期，-2 不存在；
  • maxmemory + maxmemory-policy：内存达到上限后的淘汰策略。

常见策略：

策略行为适用
noeviction写入报错不允许丢数据的队列/配置
allkeys-lru所有 key 里淘汰最近最少使用纯缓存
volatile-lru只淘汰设置了 TTL 的 key缓存与持久数据混布
allkeys-lfu按访问频率淘汰热点差异明显
volatile-ttl优先淘汰快过期的TTL 有业务含义

生产必须显式配置。默认 noeviction，内存打满后写入直接失败。

5. 缓存模式 ​

模式读写特点
Cache-Aside先读缓存，未命中回源并回填更新 DB，再删缓存最常用、实现简单
Read-Through缓存层负责回源—需要缓存组件支持
Write-Through—同时写缓存与 DB一致性好，写放大
Write-Behind—先写缓存，异步刷 DB吞吐高，可能丢数据

绝大多数业务用 Cache-Aside：

text
读：GET cache -> 命中返回
              -> 未命中 -> 查 DB -> SET cache EX ttl -> 返回
写：UPDATE DB -> DEL cache

为什么是「删缓存」而不是「更新缓存」？

  • 并发写时，更新缓存的顺序难以保证，容易写入旧值；
  • 删除后下一次读自然回填，逻辑简单；
  • 删除失败可以重试/补偿，更新失败则可能长期脏数据。

6. 三个经典问题 ​

问题现象解法
穿透查不存在的数据，每次都打到 DB空值缓存（短 TTL）、布隆过滤器、参数校验
击穿热点 key 过期瞬间大量请求打到 DB互斥锁重建、逻辑过期、热点永不过期
雪崩大量 key 同时过期/Redis 故障TTL 加随机抖动、多级缓存、熔断降级、集群

逐步拆解 ​

第 1 步：String——缓存值、计数器、锁的原语 ​

bash
$R FLUSHDB >/dev/null
$R SET product:1001:name '机械键盘'
$R GET product:1001:name
$R INCR page:home:views
$R INCR page:home:views
$R EXPIRE product:1001:name 60
$R TTL product:1001:name
$R SET lock:job worker-a NX EX 10
$R SET lock:job worker-b NX EX 10
$R GET lock:job
$R MSET user:1:name Alice user:2:name Bob
$R MGET user:1:name user:2:name

真实输出：

text

1

OK

几个关键点：

  • INCR 是原子操作，天然适合计数器；
  • SET key value NX EX 10：不存在才设置，并带过期时间。第二个 worker 返回 nil，说明没抢到；
  • SET NX EX 是分布式锁的基础，但释放锁必须校验持有者，第 12 章展开；
  • MSET/MGET 减少往返，但注意单次 value 总量。

$R HSET product:1001 name '机械键盘' price_cents 29900 stock 10

Hash 适合「一个对象的多个字段频繁单独更新」：HINCRBY stock -2 只改一个字段，不需要读整个对象。

小 Hash 的编码是 listpack，字段多了会变成 hashtable。不要对生产大 Hash 直接 HGETALL，会阻塞单线程。

第 3 步：List——队列与栈 ​

bash
$R RPUSH queue:orders order:1 order:2 order:3
$R LPOP queue:orders

$R LPOP stack:jobs

  • RPUSH + LPOP = 先进先出队列；
  • LPUSH + LPOP = 后进先出栈；
  • 生产队列更推荐 Stream 或专业消息队列（BullMQ/Kafka），List 没有 ACK、重试、消费组。

真实应用里的伪代码：

ts
async function getProduct(id: string) {
  const key = `product:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const product = await db.findProduct(id);
  if (!product) {
    // 空值缓存，防止穿透；TTL 要短
    await redis.set(key, '__NULL__', 'EX', 30);
    return null;
  }
  await redis.set(key, JSON.stringify(product), 'EX', 300 + Math.floor(Math.random() * 60));
  return product;
}

async function updateProduct(id: string, data: ProductInput) {
  await db.updateProduct(id, data);
  await redis.del(`product:${id}`); // 删除而不是更新
}

第 7 步：空值缓存与穿透 ​

text
OK
__NULL__
30

查询不存在的数据时，缓存一个特殊标记，短期挡住重复请求。注意：

  • TTL 要短（30~60 秒），否则数据创建后长时间读不到；
  • 标记值要与真实数据可区分（__NULL__、JSON null）；
  • 更彻底的做法是布隆过滤器，但删除/更新麻烦。

第 8 步：遍历键用 SCAN ​

bash
$R MSET user:1:email a@example.com user:2:email b@example.com user:3:email c@example.com >/dev/null
$R --scan --pattern 'user:*:email'
text
user:2:email
user:1:email
user:3:email

KEYS * 会阻塞整个实例，生产禁用。SCAN 用游标分批返回，允许重复，适合清理/巡检，不适合业务实时查询。

  • MEMORY USAGE key 估算单个 key 占用；
  • OBJECT ENCODING 看编码；
  • INFO memory 看总内存与上限；
  • CONFIG GET maxmemory-policy 确认淘汰策略。

示例把 maxmemory 设为 64MB、策略设为 allkeys-lru，是为了让配置可见。生产按「能容忍丢哪些 key」选择策略，并设置内存告警。

第 10 步：key 设计 ​

推荐格式：

text
业务:实体:ID:字段[:维度]
product:1001
product:1001:stock
user:42:session
rate:login:ip:1.2.3.4

原则：

  • 可读：看到 key 知道属于哪个业务；
  • 可治理：前缀统一，便于 SCAN 清理与容量统计；
  • 不过长：key 本身占内存；
  • 避免热 key：单一 key 的 QPS 过高时，考虑分片或本地缓存；
  • TTL 必填：除明确要持久化的数据外，缓存 key 一律带过期时间，并加随机抖动。

常见坑与排查 ​

现象根因处理
Redis 卡住/超时KEYS *、大 key 全量读、慢 Lua用 SCAN、拆分 key、SLOWLOG GET
内存持续上涨无 TTL、编码转换、大 key设 TTL、拆分、MEMORY USAGE 排查
写入报 OOMnoeviction 且内存满配淘汰策略或扩容
缓存与 DB 不一致先删缓存后写 DB、并发写先写 DB 再删缓存；延迟双删/消息补偿
热点 key 过期打爆 DB击穿互斥重建、逻辑过期、热点不过期
大量 key 同时失效TTL 相同TTL 加随机抖动
空值没挡住穿透没缓存 null / TTL 太长空值短 TTL + 布隆过滤器
INCR 结果不对对非数字值操作/被重置检查 key 类型与持久化
锁被误删释放时没校验 tokenLua 比较 token 后再 DEL（第 12 章）
主从读到旧值异步复制延迟关键读走主库或等待同步
集群下 key 找不到多 key 命令跨 slot用 hash tag {user:42}:a 固定 slot

企业级做法 ​

  1. 缓存只缓存「可重建」的数据：缓存挂了系统能降级回源，而不是把缓存当唯一存储。
  2. TTL 分层 + 抖动：热点短 TTL、冷数据长 TTL，统一加 ±10% 随机，避免雪崩。
  3. 空值缓存 + 布隆过滤器：穿透防护双保险。
  4. 互斥重建：击穿用 SET NX 锁或单飞（singleflight），只允许一个请求回源。
  5. 大 key 治理：单 key 控制在 10KB/1万元素以内；用 redis-cli --bigkeys 定期巡检。
  6. 热 key 治理：本地缓存 + 随机后缀分片 + 读写分离。
  7. 淘汰策略显式化：纯缓存 allkeys-lru；混合存储 volatile-lru + 全部 TTL。
  8. 监控：命中率、内存、连接数、慢日志、evicted_keys、keyspace hits/misses。
  9. 命名规范与容量规划：前缀、TTL、预估 QPS/内存写入开发规范。
  10. 缓存一致性方案：先写 DB 再删缓存；高要求场景用 binlog/canal 订阅补偿；读多写少的配置类可接受短时间不一致。
