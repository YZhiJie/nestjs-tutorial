本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清 InnoDB 的聚簇索引、二级索引与 PostgreSQL 堆表的本质差异；
  2. 解释 MySQL 默认 REPEATABLE-READ 与 PostgreSQL READ COMMITTED 带来的行为差异；
  3. 完成一份常见类型/语法对照表（jsonb ↔ json、text[] ↔ JSON、timestamptz ↔ datetime(6) 等）；
  4. 用 MySQL 的方式实现 upsert、返回自增 ID、JSON 过滤与展开；
  5. 识别迁移时最容易出事的点：字符集、大小写、DDL 非事务、时间精度、自增与序列；
  6. 在 TypeORM/应用层做出正确的驱动适配，而不是把 PostgreSQL 的写法硬套过来。

本章只讲 MySQL 的独有与差异部分；SQL 基础、建模、索引原理不重复展开，见第 02~06 章。

概念与原理 ​

1. InnoDB 的聚簇索引 ​

PostgreSQL 的表是「堆表」：数据行无序存放，主键索引是独立的 B-tree，索引叶子存行指针（ctid）。

InnoDB 的表是「聚簇索引」：数据按主键顺序存放在主键 B+ 树的叶子节点。二级索引的叶子存的是主键值，不是物理地址。

text
InnoDB:
  PRIMARY (id)  ──叶子──> 完整行数据
  INDEX (sku)   ──叶子──> 主键 id ──回表──> 完整行数据

PostgreSQL:
  heap          ──> 行数据（无序）
  PRIMARY (id)  ──叶子──> ctid ──> heap
  INDEX (sku)   ──叶子──> ctid ──> heap

直接影响：

  • InnoDB 的主键要短、单调、不变。用随机 UUID 当主键会导致页分裂、写入放大；PostgreSQL 的堆表对随机主键容忍度高得多。
  • InnoDB 二级索引天然「覆盖」主键列，SELECT id FROM t WHERE sku = ? 不需要回表。
  • 没有主键时 InnoDB 会建隐藏的 6 字节 row ID，二级索引指向它；生产表应显式定义主键。

2. MVCC 与隔离级别 ​

PostgreSQLMySQL / InnoDB
MVCC 实现行上保留多版本（tuple + xmin/xmax），旧版本由 vacuum 清理undo log 保存旧版本，由 purge 线程清理

快照时机每条语句开始事务第一条一致性读

锁行锁，无 gap lock行锁 + gap lock / next-key lock

这带来两个常见差异：

  • MySQL 的 REPEATABLE READ 事务里多次读同一张表，结果不变；PostgreSQL 默认 READ COMMITTED 会看到新提交的数据（第 04 章演示过）。
  • MySQL 在 REPEATABLE READ 下执行 SELECT ... FOR UPDATE 可能锁住间隙，两个事务插入相邻主键时更容易死锁。

3. 自增 vs 序列 ​

  • MySQL：AUTO_INCREMENT，值属于表，回滚不回收，重启后从持久化的计数器继续；
  • PostgreSQL：serial / GENERATED ... AS IDENTITY，本质是序列，nextval 不受事务回滚影响。

两者都不保证连续。MySQL 的 LAST_INSERT_ID() 是连接级的，返回该连接最后一次插入的自增值；PostgreSQL 用 INSERT ... RETURNING id。

5. 字符集与排序规则 ​

MySQL 8 默认 utf8mb4 / utf8mb4_0900_ai_ci：

  • utf8mb4 才能存 emoji（旧的 utf8 是 3 字节，存不下）；
  • _ci 表示大小写不敏感，'Alice' = 'alice' 为真；PostgreSQL 默认区分大小写；
  • 索引比较、唯一约束都受排序规则影响。迁移时唯一键冲突经常是大小写差异导致的。

建库/建表时显式写：

sql
DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci

不要依赖服务器默认值，不同环境可能不一致。

6. DDL 非事务 ​

PostgreSQL 的 DDL 在事务里，迁移失败可以整体回滚。MySQL 的 DDL 会隐式提交当前事务，且 8.0 之前多数 DDL 不能原子回滚（8.0 有 atomic DDL，但仍有边界）。

这意味：

  • 一个迁移文件里混多条 DDL，中途失败会留下「半套 schema」；
  • 迁移脚本必须可重入（IF NOT EXISTS）或能人工修复；
  • 大表 ALTER TABLE 要用 online DDL 工具（gh-ost / pt-online-schema-change），并评估锁与复制延迟。

二、表定义 ​

sql
-- 第 10 章 MySQL schema
--
-- 与 PostgreSQL 版本的关键差异：
--   1. 表必须显式 ENGINE=InnoDB（8.4 默认就是 InnoDB，但写出来便于对照）；
--   2. 主键是聚簇索引：数据按主键物理组织，二级索引叶子存主键值；
--   3. 自增用 AUTO_INCREMENT，不是序列；
--   4. 金额用 INT UNSIGNED，MySQL 没有 PostgreSQL 的 numeric 任意精度（DECIMAL 有）；

--   7. 枚举用 ENUM，PostgreSQL 通常用 varchar + CHECK。

DROP TABLE IF EXISTS order_items;

CREATE TABLE customers (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  email      VARCHAR(254) NOT NULL,
  name       VARCHAR(80) NOT NULL,
  created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  UNIQUE KEY uq_customers_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE products (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  sku         VARCHAR(32) NOT NULL,
  name        VARCHAR(80) NOT NULL,

  stock       INT UNSIGNED NOT NULL DEFAULT 0,
  attributes  JSON NOT NULL,
  tags        JSON NOT NULL,

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE orders (

  PRIMARY KEY (id),
  KEY idx_orders_user_created (user_id, created_at),
  CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES customers (id)

CREATE TABLE order_items (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_id       BIGINT UNSIGNED NOT NULL,
  product_id     BIGINT UNSIGNED NOT NULL,

  unit_price_cents INT UNSIGNED NOT NULL,
  PRIMARY KEY (id),
  KEY idx_order_items_order (order_id),
  CONSTRAINT fk_items_order FOREIGN KEY (order_id) REFERENCES orders (id) ON DELETE CASCADE,
  CONSTRAINT fk_items_product FOREIGN KEY (product_id) REFERENCES products (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

逐步拆解 ​

第 1 步：看表定义，理解聚簇索引 ​

SHOW CREATE TABLE products\G 的输出里，几个关键点：

  • ENGINE=InnoDB：事务、行锁、聚簇索引、外键都由它提供；
  • PRIMARY KEY (id)：数据按 id 组织；
  • UNIQUE KEY uq_products_sku (sku)：二级索引，叶子存 id；
  • DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci：能存 emoji，比较不区分大小写。

SHOW INDEX FROM orders 会显示 PRIMARY、idx_orders_user_created 两个索引，Index_type 都是 BTREE。InnoDB 没有 PostgreSQL 的 GIN/Hash 索引类型（Hash 仅内存表）。

第 2 步：默认隔离级别与 sql_mode ​

sql
SELECT @@transaction_isolation, @@sql_mode;

真实输出：

text
REPEATABLE-READ
ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION

与 PostgreSQL 的差异：

  • REPEATABLE-READ 是默认值，不是 READ COMMITTED；
  • ONLY_FULL_GROUP_BY 默认开启：SELECT 里的非聚合列必须在 GROUP BY 中，否则报 1055；
  • STRICT_TRANS_TABLES：超长/非法值报错而不是截断（老版本会静默截断）。

迁移时不要想当然地认为「SQL 一样」。先在目标库跑一遍 sql_mode 与隔离级别检查。

第 3 步：大小写与排序规则 ​

sql
SELECT 'Alice' = 'alice' AS equal_in_mysql;
text
equal_in_mysql
1

同一个查询在 PostgreSQL 里是 false。如果业务依赖「邮箱不区分大小写」：

  • PostgreSQL：CITEXT 扩展或 lower(email) 唯一索引；
  • MySQL：默认 collation 已经满足，但要注意换成 _bin / _cs 后会变成区分大小写。

第 4 步：JSON 的读写与索引 ​

sql
SELECT '=== 4. JSON：->> 提取、JSON_CONTAINS 过滤 ===' AS section;
SELECT sku,
       name,
       attributes ->> '$.color' AS color,
       attributes ->> '$.wireless' AS wireless
FROM products
ORDER BY sku;

SELECT sku, name
FROM products
WHERE JSON_CONTAINS(attributes, '{"wireless": true}', '$')
ORDER BY sku;

注意：

  • MySQL 的 ->> 语法是 attributes ->> '$.color'，路径必须带 $；
  • JSON_CONTAINS(attributes, '{"wireless": true}') 做包含判断；
  • MySQL 没有 JSONB GIN 索引。要加速 JSON 过滤，常用两种方式：
sql
-- 方式一：生成列 + 普通索引
ALTER TABLE products
  ADD COLUMN color VARCHAR(16)
  GENERATED ALWAYS AS (attributes ->> '$.color') STORED,
  ADD KEY idx_products_color (color);

-- 方式二：函数索引（8.0.13+）
CREATE INDEX idx_products_color ON products ((CAST(attributes ->> '$.color' AS CHAR(16))));

PostgreSQL 的 CREATE INDEX ... USING gin (attributes) 在 MySQL 没有直接对应物。

第 5 步：把 JSON 数组展开成行 ​

SELECT p.sku, jt.tag

HP-3001 | travel

对应 PostgreSQL 的 jsonb_array_elements_text / unnest。MySQL 的 JSON_TABLE 更通用，可以把数组、嵌套对象映射成关系行。

第 6 步：Upsert 与 INSERT IGNORE ​

sql
SELECT '=== 6. Upsert：ON DUPLICATE KEY UPDATE ===' AS section;
INSERT INTO products (sku, name, price_cents, stock, attributes, tags)
VALUES ('KB-1001', '机械键盘', 29900, 12,
        JSON_OBJECT('color', 'black', 'wireless', false, 'switch', 'brown'),
        JSON_ARRAY('keyboard', 'wired', 'office')) AS new
ON DUPLICATE KEY UPDATE
  stock = new.stock,
  price_cents = new.price_cents;

SELECT ROW_COUNT() AS affected_rows;
SELECT stock FROM products WHERE sku = 'KB-1001';

真实输出：

text
affected_rows
2
stock
12

ROW_COUNT() 的语义：插入新行 = 1，更新已有行 = 2，值没变化 = 0。PostgreSQL 的 ON CONFLICT DO UPDATE 没有这个「2 倍计数」的约定。

INSERT IGNORE 会把重复键错误降级为警告并跳过：

sql
INSERT IGNORE INTO products (...) VALUES (...);
SELECT ROW_COUNT();  -- 0，库存仍是 12

慎用：它也会忽略其他错误（如数据截断、非空约束），容易掩盖问题。明确知道只可能重复键时再用。

第 7 步：没有 RETURNING 怎么办 ​

sql
SELECT '=== 8. LAST_INSERT_ID：MySQL 没有 RETURNING ===' AS section;
START TRANSACTION;
INSERT INTO customers (email, name) VALUES ('dave@example.com', 'Dave');
SELECT LAST_INSERT_ID() AS new_customer_id;
ROLLBACK;
-- 注意：AUTO_INCREMENT 不会因为回滚而回收，ID 会出现空洞
text
new_customer_id
6

LAST_INSERT_ID() 是连接级的，连接池里必须确保「插入」和「取 ID」用的是同一个连接，否则会拿到别人的 ID。TypeORM 的 save() 会处理这件事；手写 SQL 时要小心。

另外，自增值回滚不回收：上面的 ROLLBACK 之后，customers 表没有 Dave，但下一个 ID 已经是 7。业务不能依赖 ID 连续。

第 8 步：窗口函数与 CTE 基本通用 ​

MySQL 8 支持窗口函数和 CTE，第 08 章的写法大部分可以平移：

text
sku     | name     | revenue_cents | rnk
HP-3001 | 降噪耳机 | 89900         | 1
KB-1001 | 机械键盘 | 59800         | 2
MS-2001 | 无线鼠标 | 19900         | 3

差异主要在函数名和语法细节：

  • 字符串聚合：MySQL GROUP_CONCAT，PostgreSQL string_agg；
  • 日期截断：MySQL DATE_FORMAT / DATE_TRUNC（8.0 无 date_trunc，用 DATE_FORMAT 或 CAST(... AS DATE)）；
  • 正则：MySQL REGEXP_LIKE，PostgreSQL ~；
  • FILTER (WHERE ...)：MySQL 不支持，用 CASE WHEN 或 SUM(IF(...))。

第 9 步：执行计划 ​

sql
SELECT '=== 10. EXPLAIN ANALYZE：8.0.18+ 才有真正的执行统计 ===' AS section;
EXPLAIN ANALYZE
SELECT sku, name, price_cents
FROM products
WHERE price_cents > 20000
ORDER BY price_cents DESC;
text
-> Index range scan on products using idx_products_price over (20000 < price_cents) (reverse), with index condition: (products.price_cents > 20000)  (cost=1.61 rows=3) (actual time=0.00492..0.00575 rows=3 loops=1)

MySQL 8.0.18+ 的 EXPLAIN ANALYZE 输出树形计划，和 PostgreSQL 的 EXPLAIN (ANALYZE, BUFFERS) 思路一致：

  • Index range scan 对应 PostgreSQL 的 Index Scan；
  • actual time=... rows=... loops=... 是真实执行统计；
  • MySQL 没有 Buffers 细节，缓存看 performance_schema / InnoDB buffer pool。

第 10 步：迁移清单 ​

从 PostgreSQL 迁到 MySQL（或反向）时，按这个顺序检查：

  1. 字符集：建库建表显式 utf8mb4，检查唯一键大小写语义；
  2. 类型：uuid、jsonb、数组、timestamptz、boolean、numeric；
  3. 自增/序列：数据迁移后重置 AUTO_INCREMENT，避免主键冲突；
  4. DDL：MySQL DDL 隐式提交，迁移脚本拆小、可重入；
  5. SQL 方言：ON CONFLICT、RETURNING、ILIKE、::、FILTER、string_agg；
  6. 时间精度：datetime(6) 才有微秒，timestamp 有 2038 年限制；
  7. 索引：MySQL 无 GIN/部分索引/表达式索引（8.0.13+ 有函数索引），需要生成列；
  8. 隔离级别与锁：默认 RR + gap lock，死锁模式不同；
  9. 运维：备份工具、复制方式、监控指标全部要换；
  10. 回归测试：用真实数据量跑一遍，不只看单元测试。

企业级做法 ​

  1. 新项目优先 PostgreSQL：JSONB、数组、部分索引、表达式索引、DDL 事务、RETURNING 都更省事；已有 MySQL 团队则不必强行迁移。
  2. MySQL 主键用有序 ID：BIGINT UNSIGNED AUTO_INCREMENT 或 Snowflake；避免随机 UUID 造成页分裂。
  3. 金额整数分、时间 UTC：与数据库无关的硬规则，迁移时不动业务语义。
  4. 字符集全链路统一：数据库、表、连接（characterEncoding=utf8mb4）、应用都显式设置。
  5. 迁移用双写/影子库验证：不要一次性切库；先双写、对比、再读切换、最后停旧库。
  6. DDL 变更走工具：Flyway/Liquibase + gh-ost；每个变更可回滚、可重入、有备份。
  7. 隔离级别显式声明：不要依赖默认值；在连接初始化时设置并写进文档。
  8. 索引策略按引擎调整：InnoDB 善用覆盖索引（二级索引自带主键），避免过多索引拖慢写入。
  9. 监控换一套：performance_schema、slow_query_log、SHOW ENGINE INNODB STATUS、information_schema.INNODB_TRX。
  10. 回归测试覆盖方言：把「upsert、分页、时间、JSON、聚合」写成跨库测试，CI 两个引擎都跑。

练习与验收标准 ​

练习

  1. 在 MySQL 里给 attributes ->> '$.color' 建生成列 + 索引，用 EXPLAIN ANALYZE 验证命中。
  2. 用 JSON_TABLE 统计每个标签下的商品数，对照 PostgreSQL 的 unnest 写法。
  3. 开两个会话，在 REPEATABLE-READ 下复现「同一事务两次读结果一致」，再切到 READ COMMITTED 对比。
  4. 把第 07 章的 TypeORM 示例改成 MySQL 驱动（mysql2），记录需要改的实体字段。
  5. 用 mysqldump --single-transaction 备份并恢复，校验行数与自增值。
  6. 写一个脚本，把 PostgreSQL 的 ON CONFLICT 批量改写成 ON DUPLICATE KEY UPDATE。
