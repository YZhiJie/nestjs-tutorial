本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清数据库替你做的五件事：持久化、索引、并发控制、事务、故障恢复；
  2. 用一张表区分关系型、文档型、键值型数据库的数据形状与一致性能力，而不是背「SQL / NoSQL」口号；
  3. 说清 PostgreSQL、MySQL、Redis、MongoDB 各自擅长什么、不擅长什么；
  4. 用四个真实容器跑通版本探测与最小查询，拿到第一手输出；
  5. 面对一个业务需求，按「数据形状 → 一致性 → 访问模式 → 团队运维」四步给出有理由的选型，并能说出代价。

概念与原理 ​

1. 数据库不是「存数据的地方」，是五件事的打包 ​

把一个 INSERT 写进文件只需要几行代码，难的是后面这些：

能力没有它会怎样数据库怎么解决
持久化进程崩了数据没了WAL / redo log，先写日志再改数据页
索引查一行要扫全表B+ 树、LSM、倒排索引、地理索引
并发控制两个人同时改同一行，后写的覆盖先写的MVCC、行锁、乐观锁
事务扣了库存没生成订单BEGIN / COMMIT / ROLLBACK + 隔离级别
故障恢复断电后文件写了一半崩溃恢复、备份、时间点恢复（PITR）

零基础读者常把数据库当成「高级 Excel」。区别在于：Excel 只保证文件被保存，数据库保证在并发、崩溃、磁盘满、主从切换这些坏情况下，数据仍然符合你声明的约束。后面 13 章讲的都是这五件事在不同产品里的实现差异。

2. 关系型与文档型，差在「一行数据怎么组织」 ​

维度关系型（PostgreSQL / MySQL）文档型（MongoDB）键值型（Redis）
基本单位行 + 列，列由表结构定义文档（近似 JSON），字段可不同key → value
结构变更迁移（ALTER TABLE），需评审应用层兼容，旧文档可缺字段无 schema
关联查询JOIN，数据库负责$lookup，但更鼓励内嵌不支持，应用自己拼
事务成熟，跨多表4.0+ 支持多文档，需副本集单命令原子，多 key 用 Lua
典型场景订单、账务、权限内容、日志、商品详情缓存、计数、会话、限流

「MongoDB 没有 schema」是误解：它只是把 schema 从数据库搬到了应用代码里。字段该有哪些、哪个必填，仍然要有人负责，否则半年后同一集合里会出现三种 price 写法。

3. OLTP 与 OLAP：不要在主库上跑报表 ​

  • OLTP（在线事务处理）：短事务、按主键/索引点查、高并发。订单、支付、用户中心属于这类。
  • OLAP（在线分析处理）：大范围扫描、聚合、列式存储。报表、风控离线特征属于这类。

把 GROUP BY 全表报表直接压在主库上，会拖慢所有下单请求。企业里的常规做法是：主库只做 OLTP，通过 CDC（变更数据捕获）或定时同步把数据送到分析库/数据仓库。第 06 章会讲怎么用执行计划判断一条 SQL 属于哪类负载。

4. 四种数据库的定位 ​

PostgreSQL：默认答案

  • 标准 SQL 支持最完整，JOIN、窗口函数、CTE、JSONB、数组、全文检索都在一个引擎里；
  • 事务与 MVCC 成熟，支持 SERIALIZABLE、部分唯一索引、行级安全（RLS）；
  • 扩展生态强：pg_trgm、PostGIS、pg_stat_statements、pgvector；
  • 代价：单机写入扩展性不如 MySQL 的部分场景；连接是进程模型，必须配连接池（第 09 章）。

MySQL：生态与运维惯性

  • InnoDB 是默认引擎，事务、行锁、崩溃恢复都够用；
  • 互联网公司使用极广，DBA 与云厂商托管成熟；
  • 与 PostgreSQL 的关键差异：默认隔离级别是 REPEATABLE-READ、自增主键、ON DUPLICATE KEY UPDATE、utf8mb4 排序规则、在线 DDL 行为。第 10 章专门对照。

Redis：内存数据结构服务器

  • 不是「缓存」的同义词，而是 String / Hash / List / Set / ZSet / Stream / Bitmap / HyperLogLog 等结构的原子操作；
  • 适合缓存、计数器、排行榜、会话、分布式锁、限流；
  • 不适合当唯一数据源：持久化有窗口，内存成本高，复杂查询能力弱。第 11、12 章展开。

MongoDB：文档模型

  • 一条业务对象可以整体读写，避免大量 JOIN；适合商品详情、内容、事件日志这类「聚合根清晰」的数据；
  • 聚合管道（$match / $group / $lookup / $unwind）能表达不少分析逻辑；
  • 事务需要副本集，且跨文档事务的代价高于单文档原子更新；第 13、14 章展开。

5. 选型的四个问题 ​

按顺序问，前面的问题能否定后面的选项：

  1. 数据形状：强关联、需要多表一致性 → 关系型；整体读写、字段差异大 → 文档型；纯 key 访问、极低延迟 → 键值型。
  2. 一致性要求：钱、库存、权限 → 强一致关系库；点赞数、推荐列表 → 最终一致可接受。
  3. 访问模式：点查为主还是范围聚合为主？写入 QPS 与单行大小是多少？读写比例如何？
  4. 团队与运维：有没有人能处理备份恢复、主从切换、慢查询？引入一种新数据库，等于引入一套新的监控、备份、升级和故障处理流程。

一个常见的误区是「多语言持久化 = 先进」。每多一种数据库，就多一份备份脚本、一套监控指标、一种故障演练。能用一个 PostgreSQL 解决的问题，不要拆成三个组件；只有当某类访问模式真的成为瓶颈时，再引入专用存储。

6. 一个订单系统的最小组合 ​

数据放哪理由
用户、商品、订单、支付流水PostgreSQL强关联、需要事务与唯一约束
会话、热点商品缓存、接口限流Redis低延迟、可丢失、原子计数
商品详情富文本 / 行为事件MongoDB（可选）文档整体读写、字段不固定
报表与对账分析库 / 数据仓库避免大扫描压垮主库

这张表不是标准答案，而是一个能解释每个选择的起点。选型文档里应该写下：为什么选它、什么情况下会换、换的成本是什么。

最小可跑示例 ​

本章的示例目录在 examples/database/01-landscape/，一次起齐四种数据库。compose 文件把密码、端口、数据卷都写清楚了：

yaml
# 数据库全景实验：一次起齐四种主流数据库，用同一条业务问题对比它们的形状。
# 仅用于本地学习：密码是明文默认值，不要用于任何共享环境。
name: db-tutorial-01

services:
  postgres:
    image: postgres:17
    container_name: db01-postgres
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: landscape
      TZ: Asia/Shanghai
    ports:
      # 宿主机 55431 → 容器 5432，避开本机可能已有的 5432
      - '55431:5432'
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U postgres -d landscape']
      interval: 5s
      timeout: 3s
      retries: 20

  mysql:
    image: mysql:8.4
    container_name: db01-mysql
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: landscape
      TZ: Asia/Shanghai
    ports:
      - '33305:3306'
    volumes:
      - mysqldata:/var/lib/mysql
    healthcheck:
      # 注意：mysqladmin 通过 TCP 探测，避免 socket 已就绪但 TCP 还没监听的误判
      test: ['CMD-SHELL', 'mysqladmin ping -h 127.0.0.1 -uroot -proot --silent']
      interval: 5s
      timeout: 3s
      retries: 20

  redis:
    image: redis:7-alpine
    container_name: db01-redis
    # appendonly yes：让 Redis 也具备可验证的持久化，而不是纯内存玩具
    command: ['redis-server', '--appendonly', 'yes']
    ports:
      - '56378:6379'
    volumes:
      - redisdata:/data
    healthcheck:
      test: ['CMD', 'redis-cli', 'ping']
      interval: 5s
      timeout: 3s
      retries: 20

  mongo:
    image: mongo:7.0
    container_name: db01-mongo
    environment:
      MONGO_INITDB_DATABASE: landscape
      TZ: Asia/Shanghai
    ports:
      - '57016:27017'
    volumes:
      - mongodata:/data/db
    healthcheck:
      test: ['CMD-SHELL', 'mongosh --quiet --eval "db.adminCommand({ ping: 1 }).ok" | grep 1']
      interval: 5s
      timeout: 5s
      retries: 20

volumes:
  pgdata:
  mysqldata:
  redisdata:
  mongodata:

bash
#!/usr/bin/env bash
# 依次询问四种数据库：你是谁、你支持什么。
# 所有命令都通过 docker compose exec 在容器内执行，避免依赖宿主机客户端。
set -euo pipefail

cd "$(dirname "$0")"

echo '== PostgreSQL =='
# version() 返回完整编译信息，SHOW server_version 只返回版本号
docker compose exec -T postgres psql -U postgres -d landscape \
  -c 'SELECT version();' \
  -c 'SHOW server_version;' \
  -c "SELECT '{\"sku\":\"A-1\",\"tags\":[\"new\"]}'::jsonb ->> 'sku' AS jsonb_probe;"

echo '== MySQL =='
# -N 去掉列名，-B 用制表符分隔，便于阅读
docker compose exec -T mysql mysql -uroot -proot -N -B -e \
  'SELECT VERSION(); SELECT @@innodb_version, @@transaction_isolation;'

echo '== Redis =='
docker compose exec -T redis redis-cli INFO server | grep -E 'redis_version|os:'
docker compose exec -T redis redis-cli SET demo:counter 1
docker compose exec -T redis redis-cli INCR demo:counter

echo '== MongoDB =='
docker compose exec -T mongo mongosh --quiet --eval \
  'print("version: " + db.version());
   printjson(db.adminCommand({ hello: 1 }).topologyVersion);'

这段输出已经暴露了四个关键差异：

  • PostgreSQL 的 jsonb_probe 返回 A-1：关系库能直接查询 JSON 字段；
  • MySQL 默认隔离级别是 REPEATABLE-READ，PostgreSQL 默认是 READ COMMITTED；

逐步拆解 ​

第 1 步：端口映射的方向 ​

每行 PORTS 都是 宿主机端口->容器端口：

text
0.0.0.0:55431->5432/tcp

前面的 55431 是你在 Mac 上用客户端连的端口，后面的 5432 是容器内 PostgreSQL 的默认端口。这样设计是为了不和本机已有的 5432 冲突，也方便同时跑多个数据库示例。

容器里的 localhost 指容器自己。如果应用也跑在 compose 网络里，连接地址要写服务名 postgres，不是 127.0.0.1。

第 2 步：连接串的语义 ​

text
postgres://postgres:postgres@127.0.0.1:55431/landscape
mysql://root:root@127.0.0.1:33305/landscape
redis://127.0.0.1:56378/0
mongodb://127.0.0.1:57016/landscape

格式都是 协议://用户:密码@主机:端口/库名。生产环境不要把密码写进连接串明文，应该由环境变量或密钥管理注入（参见第 05 章配置管理）。

第 3 步：用一条最小查询确认「能用」 ​

bash
docker compose exec -T postgres psql -U postgres -d landscape -c 'SELECT 1;'
docker compose exec -T mysql mysql -uroot -proot -N -B -e 'SELECT 1;'
docker compose exec -T redis redis-cli PING
docker compose exec -T mongo mongosh --quiet --eval 'db.runCommand({ ping: 1 })'

返回值分别是 1、1、PONG、{ ok: 1 }。注意 docker compose exec 是在已运行的容器里执行命令，不是宿主机客户端；因此你不需要安装 psql 或 mongosh。

第 4 步：观察「同类数据」的不同形状 ​

同一条商品数据，在四种库里可以这样表达：

text
PostgreSQL: INSERT INTO products (sku, name, tags) VALUES ('A-1', '键盘', '["new","hot"]');
MySQL:      INSERT INTO products (sku, name, tags) VALUES ('A-1', '键盘', JSON_ARRAY('new','hot'));
Redis:      HSET product:A-1 sku A-1 name 键盘 tags '["new","hot"]'
MongoDB:    db.products.insertOne({ sku: 'A-1', name: '键盘', tags: ['new','hot'] })

形状不同，查询能力就不同：PostgreSQL 能用 GIN 索引查 tags @> '["new"]'，MongoDB 能用 { tags: 'new' } 查数组包含，Redis 只能把整个 Hash 取回应用再判断。第 08、13 章会分别展开。

第 5 步：为什么示例用固定端口 ​

四个容器如果都用默认端口，会和你本机可能已安装的数据库冲突。示例统一采用 5xxxx 段：

示例PostgreSQLMySQLRedisMongoDB
01 全景55431333055637857016
02~0955432~55440———
10 MySQL—33306——
11~12 Redis——56379~56382—
13~14 MongoDB———57017~57018

遇到端口占用时，改 compose 的左边端口，并同步改连接命令，不要改容器内端口。

现象根因处理

企业级做法 ​

  1. 默认选 PostgreSQL，除非有明确理由：一个团队维护一种关系库的成本，远低于同时维护两种。选 MySQL 也可以，但要能说清是生态、托管服务还是历史包袱。
  2. 把选型写成 ADR：记录背景、候选方案、决策、代价、复审条件。半年后新人问「为什么用 MongoDB」，文档能回答。
  3. OLTP 与 OLAP 分离：主库不跑大报表；分析需求走只读副本或数据仓库，避免一条 SQL 拖垮全站。
  4. 金额用整数分，时间用 UTC：price_cents integer、timestamptz；不要用浮点存钱，不要用本地时间存库。
  5. 每种存储都要有备份与恢复演练：没有恢复演练的备份等于没有备份。Redis 也要明确「丢了怎么重建」。
  6. 连接数按池算，不按请求算：PostgreSQL 默认 max_connections=100，应用侧连接池上限要小于它，并留出运维连接（第 09 章）。
  7. 给每种数据库定一个「退出条件」：例如「当单表超过 X 亿行且写入成为瓶颈时，评估分库分表」，避免无限期拖延架构决策。
  8. 不要为了简历引入技术：多一种数据库就多一套值班手册；能复用的能力优先复用。

练习与验收标准 ​

练习

  1. 用 docker compose up -d 起四个容器，记录每个容器 docker compose ps 的 STATUS 与 PORTS。
  2. 分别用四种客户端执行 SELECT 1 / PING / ping，把返回值记下来。
  3. 给 docker-compose.yml 增加一个 PostgreSQL 只读账号，并用它连接后尝试 CREATE TABLE，记录报错原文。
  4. 把 MySQL 的 MYSQL_ROOT_PASSWORD 改成环境变量 ${MYSQL_ROOT_PASSWORD:-root}，验证不设置时仍能启动。
  5. 画一张你所在业务的数据流图：哪些数据必须强一致，哪些可以最终一致，分别应该放哪种存储。

验收标准

  • [ ] docker compose ps 四行 STATUS 均包含 (healthy)；
  • [ ] check-versions.sh 能输出 PostgreSQL 17.x、MySQL 8.4.x、Redis 7.x、MongoDB 7.0.x；
  • [ ] 能解释 0.0.0.0:55431->5432/tcp 中两个端口各指什么；
  • [ ] 能说出 PostgreSQL 与 MySQL 默认隔离级别的差异；
