本章目标 ​

读完并动手做完本章，你应该能：

  1. 用 Docker 起一个 PostgreSQL 17，理解 database / schema / table 三层结构与 psql 的基本用法；
  2. 写出一份类型安全、显式声明列类型的 TypeORM 实体，并解释为什么金额用「分」；
  3. 用显式 SQL 迁移管理 schema，理解 synchronize: false 与 migrationsRun 的分工；
  4. 在 Repository、QueryBuilder、原生 SQL 三种写法之间做出有依据的选择；
  5. 用 dataSource.transaction + SELECT ... FOR UPDATE 实现不超卖的下单；
  6. 看懂仓库 apps/api 里现成的 database-options.ts、data-source.ts 与迁移文件，并知道每一行配置为什么在那里。

概念与原理 ​

1. PostgreSQL 的层级：实例 → 数据库 → schema → 表 ​

一个 PostgreSQL 进程（实例）可以管理多个 database；database 之间默认不能直接 join。每个 database 里又有多个 schema，默认是 public。

text
PostgreSQL 实例（容器 / 5432）
├── database: pg_demo
│   ├── schema: public
│   │   ├── table: products
│   │   └── table: orders
│   └── schema: information_schema（系统视图）
└── database: postgres（维护库）

连接串里的路径部分指的是 database，不是 schema：

text
postgresql://demo:demo@127.0.0.1:55437/pg_demo
                             │           │
                          端口          database

跨 schema 访问要写 schema.table；search_path 决定不写 schema 时去哪里找。应用一般固定用 public，多租户/模块化时才引入自定义 schema。

2. TypeORM 的三层对象 ​

对象职责生命周期
DataSource连接池 + 实体/迁移注册表应用级单例
EntityManager一组操作入口，可绑定事务请求/事务级
Repository<T>针对单个实体的查询封装可随时从 manager 取

关键点：Repository 会记住自己来自哪个 manager。在事务里必须用事务传入的 manager.getRepository(...)，不能用全局 dataSource.getRepository(...)，否则那条 SQL 会跑在事务之外，回滚也带不走它。

3. 迁移是 schema 的唯一真相 ​

synchronize: true 会让 TypeORM 在启动时对比实体与数据库，自动 ALTER TABLE。它在 demo 里很方便，在生产里是事故源：

  • 自动生成的 DDL 可能锁表很久，且没有评审；
  • 删列/改类型可能静默丢数据；
  • 多实例同时启动会并发改 schema；
  • 代码回滚时 schema 不会跟着回滚。

所以仓库 apps/api 的选择是：synchronize: false + 显式 SQL 迁移 + 启动时 migrationsRun: true。迁移文件本身就是可评审的 DDL。

4. 实体是映射，不是 schema ​

实体告诉 TypeORM「这个类对应哪张表、哪个字段对应哪一列」。它不负责建表。实体与迁移不一致时，运行期报错通常是 column ... does not exist，而不是自动修复。

因此本章示例的所有列都显式写 type：

ts
@Column({ name: 'price_cents', type: 'int' })
priceCents!: number;

这带来两个好处：

  1. 不依赖 emitDecoratorMetadata（esbuild/tsx、SWC 默认不生成反射元数据）；
  2. 类型是团队约定，而不是编译器猜出来的 number → integer。

5. Repository、QueryBuilder、原生 SQL 的边界 ​

写法适合不适合
repository.find/findOne/save单表 CRUD、按主键/唯一键查询多表联查、复杂聚合
createQueryBuilder联表、聚合、动态条件、行锁极端复杂的报表 SQL
dataSource.query数据库特有语法、批量运维、EXPLAIN日常业务查询（难维护、无类型）

判断标准不是「哪种更高级」，而是这段 SQL 是否需要被类型系统和查询构造器保护。报表类 SQL 用原生 SQL 反而更清晰。

二、唯一的 DataSource 工厂 ​

ts
export function createDataSource(): DataSource {
  return new DataSource({
    type: 'postgres',
    host: process.env.PGHOST ?? '127.0.0.1',
    port: Number.parseInt(process.env.PGPORT ?? '55437', 10),
    username: process.env.PGUSER ?? 'demo',
    password: process.env.PGPASSWORD ?? 'demo',
    database: process.env.PGDATABASE ?? 'pg_demo',
    entities: [ProductEntity, OrderEntity],
    migrations: [DemoSchema1750000003000],
    synchronize: false,
    // 启动时自动执行未跑的迁移；生产也可以改由独立 migrate 任务执行
    migrationsRun: true,
    // 默认打印 SQL，正文里的输出就来自这里；噪音太大时设 SQL_LOG=off
    logging: process.env.SQL_LOG === 'off' ? ['error'] : ['query', 'error'],
  });
}

三、实体 ​

ts
@Entity('products')
export class ProductEntity {
  @PrimaryGeneratedColumn('uuid')
  id!: string;

  /** 业务唯一编号。不要用自增 ID 当对外标识，避免被枚举、迁移时冲突 */
  @Index('uq_products_sku', { unique: true })
  @Column({ type: 'varchar', length: 32 })
  sku!: string;

  @Column({ type: 'varchar', length: 80 })
  name!: string;

  /** 单价，单位：分。99900 表示 999.00 元 */
  @Column({ name: 'price_cents', type: 'int' })
  priceCents!: number;

  /** 可售库存。扣减必须放在事务里，并用行锁避免超卖 */
  @Column({ type: 'int', default: 0 })
  stock!: number;

  @CreateDateColumn({ name: 'created_at', type: 'timestamptz' })
  createdAt!: Date;

  @UpdateDateColumn({ name: 'updated_at', type: 'timestamptz' })
  updatedAt!: Date;
}
ts
@Entity('orders')
export class OrderEntity {
  @PrimaryGeneratedColumn('uuid')
  id!: string;

  @Index('idx_orders_product_id_created_at')
  @Column({ name: 'product_id', type: 'uuid' })
  productId!: string;

  @Column({ type: 'int' })
  quantity!: number;

  /** 下单时的单价快照（分） */
  @Column({ name: 'unit_price_cents', type: 'int' })
  unitPriceCents!: number;

  @Column({ type: 'varchar', length: 16, default: 'pending' })
  status!: OrderStatus;

  @CreateDateColumn({ name: 'created_at', type: 'timestamptz' })
  createdAt!: Date;
}

四、显式 SQL 迁移 ​

ts
export class DemoSchema1750000003000 implements MigrationInterface {
  name = 'DemoSchema1750000003000';

  async up(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`
      CREATE TABLE "products" (
        "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
        "sku" varchar(32) NOT NULL,
        "name" varchar(80) NOT NULL,
        "price_cents" integer NOT NULL CHECK ("price_cents" >= 0),
        "stock" integer NOT NULL DEFAULT 0 CHECK ("stock" >= 0),
        "created_at" timestamptz NOT NULL DEFAULT now(),
        "updated_at" timestamptz NOT NULL DEFAULT now()
      )
    `);
    await queryRunner.query(`CREATE UNIQUE INDEX "uq_products_sku" ON "products" ("sku")`);

    await queryRunner.query(`
      CREATE TABLE "orders" (
        "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
        "product_id" uuid NOT NULL REFERENCES "products" ("id"),
        "quantity" integer NOT NULL CHECK ("quantity" > 0),
        "unit_price_cents" integer NOT NULL CHECK ("unit_price_cents" >= 0),
        "status" varchar(16) NOT NULL DEFAULT 'pending'
          CHECK ("status" IN ('pending', 'paid', 'cancelled')),
        "created_at" timestamptz NOT NULL DEFAULT now()
      )
    `);
    await queryRunner.query(
      `CREATE INDEX "idx_orders_product_id_created_at" ON "orders" ("product_id", "created_at")`,
    );
  }

  async down(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`DROP TABLE "orders"`);
    await queryRunner.query(`DROP TABLE "products"`);
  }
}

逐步拆解 ​

第 1 步：连接串与健康检查 ​

docker compose up -d 只是「容器进程起来了」，PostgreSQL 还要初始化数据目录、创建用户和库。健康检查用 pg_isready，它比 docker ps 的 Up 更可靠：

yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U demo -d pg_demo"]
  interval: 3s
  timeout: 3s
  retries: 20

应用侧不要用「启动时睡 5 秒」等数据库，而应：

  • 依赖编排层的 depends_on: condition: service_healthy；
  • 或让驱动带有限重试（TypeORM 的 retryAttempts），并在失败时快速退出。

仓库 apps/api 把 retryAttempts 设为 1，就是因为默认的 10 次约 30 秒会让人误以为「服务卡住了」。

第 2 步：DataSource 的每个字段 ​

ts
new DataSource({
  type: 'postgres',
  host: process.env.PGHOST ?? '127.0.0.1',
  port: Number.parseInt(process.env.PGPORT ?? '55437', 10),
  username: process.env.PGUSER ?? 'demo',
  password: process.env.PGPASSWORD ?? 'demo',
  database: process.env.PGDATABASE ?? 'pg_demo',
  entities: [ProductEntity, OrderEntity],
  migrations: [DemoSchema1750000003000],
  synchronize: false,
  migrationsRun: true,
  logging: process.env.SQL_LOG === 'off' ? ['error'] : ['query', 'error'],
});
  • entities：显式注册，避免用 glob 扫描在不同运行目录下失效；
  • migrations：显式列出顺序，避免文件系统顺序不可控；
  • migrationsRun: true：启动时自动跑未执行迁移。它适合单实例/开发环境，多实例生产更推荐独立的迁移 Job，原因见「常见坑」；
  • logging: ['query']：打印 SQL 与参数，是学习 ORM 最好的工具，也是生产日志噪音的来源，要按环境开关。

第 3 步：实体映射的关键细节 ​

  1. 表名显式写：@Entity('products')。类名重构不应改变表名。
  2. 列名显式写：@Column({ name: 'price_cents' })。数据库用 snake_case，TypeScript 用 camelCase，映射层负责转换。
  3. 金额用整数分：int 存 29900 表示 299.00 元。浮点数在 0.1 + 0.2 上就会失真，金额绝对不能碰。
  4. 索引用装饰器声明：@Index('uq_products_sku', { unique: true }) 让实体自解释；真正的索引仍以迁移里的 CREATE UNIQUE INDEX 为准。
  5. 时间用 timestamptz：存 UTC 瞬时时刻，显示时按会话时区转换。timestamp（不带时区）在跨时区/夏令时下容易出错。
  6. ! 断言：严格模式下类属性未初始化会报错；实体字段由 ORM 填充，用 ! 表示「运行期一定有值」。

第 4 步：迁移是怎么被执行的 ​

TypeORM 首次连接会创建 migrations 表，记录已执行的迁移名与时间戳。每次启动：

  1. 读取 migrations 表；
  2. 对比代码里注册的迁移列表；
  3. 在事务中执行缺失的迁移，并写入记录；
  4. 全部成功后应用才开始处理请求。

所以迁移必须可重复执行：CREATE TABLE 不要裸写，回滚脚本要能跑通。本章的 down() 按依赖顺序先删 orders 再删 products，否则外键会阻止删除。

第 5 步：Repository 的适用边界 ​

ts
const keyboard = await productRepo.findOneByOrFail({ sku: 'KB-1001' });

生成：

sql
SELECT ... FROM "products" "ProductEntity" WHERE (("ProductEntity"."sku" = $1)) LIMIT 1

这是最安全的写法：参数化查询、单表、按唯一索引。适合「按 ID / 唯一键取一条」的场景。

但下面这种就要警惕：

ts
for (const id of ids) {
  await productRepo.findOneBy({ id }); // N+1
}

循环里的每次查询都是一次网络往返。改成 In(ids) 一次取回，或用 QueryBuilder join。

第 6 步：QueryBuilder 做联表聚合 ​

ts
const summary = await orderRepo
  .createQueryBuilder('o')
  .innerJoin(ProductEntity, 'p', 'p.id = o.product_id')
  .select('p.sku', 'sku')
  .addSelect('p.name', 'name')
  .addSelect('SUM(o.quantity)', 'sold')
  .addSelect('SUM(o.quantity * o.unit_price_cents)', 'revenue_cents')
  .groupBy('p.sku')
  .addGroupBy('p.name')
  .orderBy('SUM(o.quantity * o.unit_price_cents)', 'DESC')
  .getRawMany<{ sku: string; name: string; sold: string; revenue_cents: string }>();

真实生成的 SQL：

sql
SELECT "p"."sku" AS "sku", "p"."name" AS "name",
       SUM("o"."quantity") AS "sold",
       SUM("o"."quantity" * "o"."unit_price_cents") AS "revenue_cents"
FROM "orders" "o"
INNER JOIN "products" "p" ON "p"."id" = "o"."product_id"
GROUP BY "p"."sku", "p"."name"
ORDER BY SUM("o"."quantity" * "o"."unit_price_cents") DESC

注意：

  • 聚合查询返回的是「扁平行」，用 getRawMany() 并显式声明结果类型，而不是 getMany()；
  • GROUP BY 必须包含所有非聚合的 SELECT 列（sku、name）；
  • 金额乘法 quantity * unit_price_cents 在整数范围内计算，不会丢精度。

第 7 步：事务与悲观锁 ​

ts
async function placeOrder(ds: DataSource, sku: string, quantity: number): Promise<OrderEntity> {
  return ds.transaction(async (manager) => {
    const product = await manager
      .getRepository(ProductEntity)
      .createQueryBuilder('p')
      .setLock('pessimistic_write')
      .where('p.sku = :sku', { sku })
      .getOne();

    if (!product) {
      throw new Error(`商品不存在：${sku}`);
    }
    if (product.stock < quantity) {
      throw new Error(`库存不足：${product.name} 剩余 ${product.stock}，需要 ${quantity}`);
    }

    product.stock -= quantity;
    await manager.save(product);

    const order = manager.create(OrderEntity, {
      productId: product.id,
      quantity,
      unitPriceCents: product.priceCents,
      status: 'paid',
    });
    return manager.save(order);
  });
}

执行顺序：

  1. START TRANSACTION；
  2. SELECT ... WHERE sku = $1 FOR UPDATE：锁住这一行，其他事务的 FOR UPDATE 会等待；
  3. 检查库存、扣减、写订单；
  4. COMMIT；
  5. 任一步抛错 → TypeORM 捕获 → ROLLBACK。

第 3 段输出里，HP-3001 库存为 0，抛错后 ROLLBACK，所以 orders 仍然是 0。这就是「要么全成功，要么全不做」。

为什么不用「先查再更新」？

sql
SELECT stock FROM products WHERE sku = 'KB-1001'; -- 读到 10
-- 另一个事务也读到 10
UPDATE products SET stock = 9 WHERE sku = 'KB-1001'; -- 覆盖对方的扣减

两个请求都以为自己是第一个，最终只扣了 1。行锁把「读-判断-写」变成串行，才能避免超卖。第 04 章已经用两个会话复现过丢失更新。

第 8 步：分页 ​

ts
const [page, total] = await orderRepo.findAndCount({
  order: { createdAt: 'DESC' },
  take: 2,
  skip: 0,
});

findAndCount 会执行两条 SQL：一条 LIMIT/OFFSET 取数据，一条 COUNT(1) 取总数。数据量大时 COUNT 会成为瓶颈，深分页的 OFFSET 也会退化（第 06 章用 keyset 分页解决）。

第 9 步：对照仓库 apps/api 的真实接法 ​

仓库里的 TypeORM 配置同样关闭了 synchronize，并在启动时跑迁移：

ts
import type { TypeOrmModuleOptions } from '@nestjs/typeorm';
import type { ConfigService } from '@nestjs/config';
import type { AppConfig } from '../config/configuration.js';
import { InitialSchema1750000000000 } from './migrations/1750000000000-InitialSchema.js';
import { OrdersAndInventory1750000001000 } from './migrations/1750000001000-OrdersAndInventory.js';
import { WebhookEvents1750000002000 } from './migrations/1750000002000-WebhookEvents.js';

/**
 * 应用与 CLI 之外的唯一 ORM 配置入口。
 *
 * 两种驱动，职责严格分开：
 * - postgres：开发与生产。schema 由迁移文件管理（synchronize 永久关闭）。
 * - sqljs：仅测试。内存库 + synchronize，让 `pnpm verify` 不需要 Docker 也能跑。
 *
 * 注意这里没有「postgres 连不上就退回 sqljs」的分支：
 * 静默降级会让人以为数据落库了，实际上重启就没了。
 */
export function buildTypeOrmOptions(config: ConfigService<AppConfig, true>): TypeOrmModuleOptions {
  const database = config.get('database', { infer: true });

  if (database.driver === 'sqljs') {
    return {
      type: 'sqljs',
      autoSave: false,
      synchronize: true,
      migrationsRun: false,
      logging: ['error'],
      autoLoadEntities: true,
    };
  }

  return {
    type: 'postgres',
    host: database.host,
    port: database.port,
    username: database.username,
    password: database.password,
    database: database.name,
    ssl: database.ssl ? { rejectUnauthorized: false } : false,
    // 让 @PrimaryGeneratedColumn('uuid') 使用 gen_random_uuid()（PG13+ 内置）
    uuidExtension: 'pgcrypto',
    synchronize: false,
    migrationsRun: true,
    migrations: [
      InitialSchema1750000000000,
      OrdersAndInventory1750000001000,
      WebhookEvents1750000002000,
    ],
    logging: database.logging ? ['query', 'error'] : ['error'],
    autoLoadEntities: true,
    // 默认会重试 10 次（约 30 秒）才报错；开发期希望快速失败并给出可执行提示
    retryAttempts: 1,
  };
}

实体同样用显式列名与索引：

ts
import {
  Column,
  CreateDateColumn,
  Entity,
  Index,
  PrimaryGeneratedColumn,
  UpdateDateColumn,
} from 'typeorm';

export const ORDER_STATUSES = ['pending', 'paid', 'shipped', 'completed', 'cancelled'] as const;
export type OrderStatus = (typeof ORDER_STATUSES)[number];

/**
 * 订单主表。
 *
 * 这里刻意不写 `@OneToMany` 关系：
 * - 订单与明细的读取路径只有「详情」一处，显式查两次比隐式 join 更容易看清 SQL；
 * - 两个实体互相 import 在 ESM + 装饰器下容易踩到初始化顺序问题（详见第 02 章）。
 */
@Entity('orders')
export class OrderEntity {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Index('idx_orders_user_id_created_at')
  @Column({ name: 'user_id', type: 'uuid' })
  userId: string;

  @Index('idx_orders_status')
  @Column({ type: 'varchar', length: 16, default: 'pending' })
  status: OrderStatus;

  /** 金额一律用「分」存整数：浮点数做金额迟早会出现 0.1 + 0.2 的问题 */
  @Column({ name: 'total_cents', type: 'int' })
  totalCents: number;

  @Column({ type: 'varchar', length: 3, default: 'CNY' })
  currency: string;

  /**
   * 与 RefreshTokenEntity.revokedAt 同样的写法：数据库可空，TS 不写 `Date | null`，
   * 否则反射元数据变成 Object，TypeORM 推断不出列类型。
   */
  @Column({ name: 'paid_at', nullable: true })
  paidAt: Date;

  @Column({ name: 'cancelled_at', nullable: true })
  cancelledAt: Date;

  @CreateDateColumn({ name: 'created_at' })
  createdAt: Date;

  @UpdateDateColumn({ name: 'updated_at' })
  updatedAt: Date;
}

迁移也全部是显式 SQL，时间字段统一 timestamptz：

ts
import type { MigrationInterface, QueryRunner } from 'typeorm';

/**
 * 初始 schema。迁移全部用显式 SQL，而不是让 TypeORM 根据实体「猜」：
 * - 团队评审迁移时看到的是可执行的 DDL，不是一段框架内部逻辑；
 * - 索引名、默认值、外键行为都由我们决定，回滚也有明确语义。
 *
 * 时间字段统一用 timestamptz（Postgres 推荐做法），
 * 实体侧不写死 type，是为了让同一套实体也能跑在测试用的 sqljs 上。
 */
export class InitialSchema1750000000000 implements MigrationInterface {
  name = 'InitialSchema1750000000000';

常见坑与排查 ​

现象根因处理
启动后表被自动改掉/删列误开 synchronize: true生产永久关闭；用迁移
column "xxx" does not exist实体改了但没写迁移先写迁移，再改实体；CI 校验迁移与实体一致
relation "migrations" does not exist首次运行且无建表权限给应用账号建表权限，或由 DBA 预建
多实例部署时迁移冲突每个实例都 migrationsRun: true迁移交给独立 Job / initContainer，或加 advisory lock
uuid_generate_v4() does not exist用了 uuid 默认值但没装扩展PG13+ 用 gen_random_uuid()；TypeORM 设置 uuidExtension: 'pgcrypto'
时间差 8 小时混用 timestamp 与 timestamptz统一 timestamptz，连接时设置时区
事务里更新「没生效」用了事务外的 Repository全程使用 manager.getRepository()
库存偶尔超卖先查后写、无行锁SELECT ... FOR UPDATE 或原子 UPDATE ... SET stock = stock - ? WHERE stock >= ?
too many clients already连接池开太大或多实例叠加计算 实例数 × poolSize < max_connections；必要时上 PgBouncer
启动卡 30 秒才报连不上默认 retryAttempts: 10显式设小，快速失败并给出可执行提示
装饰器元数据丢失用了 esbuild/tsx，未生成 design:type所有列显式写 type，或改用 tsc 编译
迁移顺序错乱依赖文件名排序迁移类显式注册数组，时间戳单调递增
@Index 与迁移索引重复两边都建了同名索引约定「迁移是唯一真相」，装饰器只做文档
日志打印明文密码/手机号logging: ['query'] 带参数生产关参数日志或做脱敏，慢日志单独采集

企业级做法 ​

  1. 迁移与发布解耦：CI 产出镜像后，由独立的 migrate Job 执行迁移；应用只负责启动。多实例并发时用 pg_advisory_lock 或迁移工具自带的锁。
  2. expand / contract 三步走：加列（可空）→ 双写/回填 → 删旧列。任何一步都可独立回滚，避免「一次性大改表」。
  3. 应用账号最小权限：业务账号只有 DML 权限；DDL 由迁移账号执行；报表用只读账号（本章 report_ro 就是最小示例）。
  4. 连接池预算：poolSize × 实例数 + 迁移/运维连接 < max_connections，并设置 statement_timeout、idle_in_transaction_session_timeout，防止慢查询和悬挂事务拖垮数据库。
  5. 实体与迁移双人评审：实体变更必须伴随迁移；CI 里跑一次「空库全量迁移 + 回滚」验证可逆性。
  6. 迁移前必须可恢复：执行破坏性迁移前先做备份/快照；生产变更窗口内禁止同时做 schema 变更与数据回填。
  7. 统一时间与金额约定：时间 timestamptz + UTC 存储；金额整数分；枚举用 varchar + CHECK 或数据库 enum，但都要与代码常量对齐。
  8. 索引随迁移走：索引变更写进迁移，禁止在生产手工 CREATE INDEX；大表用 CREATE INDEX CONCURRENTLY（不能放在事务里）。
  9. 可观测性：暴露连接池使用率、查询耗时、慢查询数量；TypeORM 的 query 日志只用于排障，不长期全量开启。
  10. 版本锁定：typeorm、pg 精确版本进 lockfile；升级前在预发跑全量迁移与回滚。

练习与验收标准 ​

练习

  1. 给 orders 增加 currency 列：写一个 up/down 可逆迁移，并用 migration:show 验证。
  2. 把 placeOrder 改成失败时返回 { ok: false, reason } 而不是抛错，观察事务是否仍会提交。
  3. 用 dataSource.query('EXPLAIN ANALYZE ...') 查看第 2 步 FOR UPDATE 查询的计划。
  4. 把 findAndCount 改成 keyset 分页（WHERE created_at < ?），比较两条 SQL。
  5. 故意把实体字段名改成 price（迁移不改），观察报错信息，并总结排查顺序。
  6. 在事务里故意使用 dataSource.getRepository() 而非 manager.getRepository()，制造「回滚后数据仍在」，解释原因。
