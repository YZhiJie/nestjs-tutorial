05 索引与执行计划 ​

B+ 树、联合/覆盖/部分索引与 EXPLAIN 读法，20 万行数据实测索引收益。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 用 B+ 树解释索引为什么能把「扫 20 万行」变成「读几页」；
  2. 看懂 EXPLAIN (ANALYZE, BUFFERS) 的关键字段：扫描类型、估计/实际行数、Buffers、Heap Fetches；
  3. 设计联合索引，理解最左前缀、等值在前、排序/范围在后；
  4. 判断什么时候该用覆盖索引、部分索引、表达式索引，以及什么时候索引根本不会被用；
  5. 用 pg_stat_user_indexes 找出未使用与冗余索引，理解索引的写入成本；
  6. 在 20 万行真实数据上对比建索引前后的执行计划，拿到第一手数字。

概念与原理 ​

1. 索引是什么：一张排好序的「目录」 ​

没有索引时，查 WHERE customer_id = 42 只能逐行读表，这叫顺序扫描（Seq Scan）。索引把某一列（或几列）的值排好序，存成 B+ 树：

text
              [ 1000 | 2000 | 3000 ]        ← 内部节点：只存分隔键
             /        |        |       \
      [1..999]   [1000..1999] ...   [3000..]  ← 叶子节点：键 + 行位置

PostgreSQL 的 B+ 树叶子节点存 (键, heap TID)，通过 TID 回到表里取整行。由此带来三种扫描方式：

扫描方式过程适合
Index Scan沿索引找到 TID，再逐行回表返回行数少、需要整行
Bitmap Index Scan + Bitmap Heap Scan先把 TID 收进位图，再按物理顺序批量回表返回行数中等、减少随机 IO
Index Only Scan只读索引，不回表查询列都被索引覆盖

2. 选择性与成本：索引不是「用了就快」 ​

优化器按成本选计划，成本由「读多少页、是否随机 IO、是否需要排序」估算。核心变量是选择性：

text
选择性 = 满足条件的行数 / 总行数
  • status = 'refunded' 只占 1%：索引能跳过 99% 的数据，收益大；
  • status = 'paid' 占 50%：索引要读大量索引页 + 回表，可能还不如顺序扫描；
  • 本章实测里 paid 仍走了 Index Only Scan，但耗时 6ms，远高于 1% 查询的 0.16ms。这说明优化器会算账，不是看到索引就用。

3. 联合索引：顺序决定用途 ​

sql
CREATE INDEX idx_orders_customer_created
  ON orders (customer_id, created_at DESC);

这个索引可以支持：

  • WHERE customer_id = 42（用到第一列）；
  • WHERE customer_id = 42 ORDER BY created_at DESC（第一列等值 + 第二列排序）；
  • WHERE customer_id = 42 AND created_at >= '2026-10-01'（第一列等值 + 第二列范围）。

不能高效支持：

  • WHERE created_at >= '2026-10-01'（跳过第一列，违反最左前缀）；
  • WHERE created_at = ... AND customer_id = ... 中只按 created_at 过滤的部分。

设计口诀：等值条件放前面，范围/排序放后面；区分度高的列优先，但要服从查询模式。如果两个列都只做等值查询，顺序影响较小；如果有一个范围或排序，它通常放最后。

4. 覆盖索引与仅索引扫描 ​

如果查询只需要索引里已有的列，数据库可以只读索引：

sql
CREATE INDEX idx_orders_refunded_total
  ON orders (status) INCLUDE (total_cents);

SELECT sum(total_cents) FROM orders WHERE status = 'refunded';

INCLUDE 的列只存在叶子节点，不参与排序与唯一性判断。执行计划出现 Index Only Scan 且 Heap Fetches: 0，说明没有回表。

Heap Fetches 不为 0 通常是因为visibility map 没更新：刚写入/更新的行还没被 VACUUM 标记为「所有事务可见」，索引扫描仍要回表确认。所以演示里先 VACUUM 再观察。

5. 部分索引：只为关心的行建索引 ​

sql
CREATE INDEX idx_orders_pending_created
  ON orders (created_at)
  WHERE status = 'pending';
  • 索引更小（本章实测 376KB，普通 status 索引是 MB 级）；
  • 写入成本更低，因为不索引无关行；
  • 查询条件必须包含 WHERE status = 'pending'，否则优化器不能用它。

典型场景：软删除表只索引 deleted_at IS NULL 的行；订单表只索引未完成订单；消息表只索引未读消息。

6. 其他索引类型 ​

类型适用例子
B-tree（默认）等值、范围、排序、前缀WHERE email = ?、ORDER BY created_at
Hash只支持等值极少用，B-tree 通常足够
GIN多值类型：数组、JSONB、全文检索tags @> ARRAY['new']（第 08 章）
GiST几何、范围、模糊匹配PostGIS、tsrange 重叠
BRIN超大且物理有序的表按时间追加的日志表，索引只有几 MB

BRIN 的原理是记录每个数据块的 min/max，适合「数据按时间顺序写入、查询按时间范围」的场景；它不是精确索引，扫描后会再过滤。

7. 索引的代价 ​

每个索引都要：

  • 占磁盘与内存（本章 20 万行表的索引合计约 14MB，表本身 13MB）；
  • 每次 INSERT / UPDATE / DELETE 都维护索引，写入越多的表越明显；
  • 参与 VACUUM，索引膨胀同样需要重建；
  • 可能被优化器误选，导致比全表扫描更慢。

所以索引不是越多越好，按查询模式建，按使用统计删。

最小可跑示例 ​

示例目录 examples/database/05-indexes/。表结构只有主键，先制造「没有业务索引」的基线：

sql
-- 05 索引示例：订单表
-- 初始只建主键，方便观察「没有业务索引」时的执行计划。
DROP TABLE IF EXISTS orders;

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint      NOT NULL,
  status      text        NOT NULL,
  created_at  timestamptz NOT NULL,
  total_cents integer     NOT NULL CHECK (total_cents >= 0)
);

生成 20 万行，refunded 只占 1%，用于观察选择性：

sql
-- 生成 20 万行订单：
-- customer_id 在 1~5000 之间循环，每个客户约 40 单；
-- status 故意做成倾斜分布：paid 约 50%，refunded 只有 1%。
INSERT INTO orders (customer_id, status, created_at, total_cents)
SELECT
  (g % 5000) + 1,
  CASE
    WHEN g % 100 = 0 THEN 'refunded'
    WHEN g % 4 = 0   THEN 'cancelled'
    WHEN g % 3 = 0   THEN 'pending'
    ELSE 'paid'
  END,
  timestamptz '2026-01-01 00:00:00+08' + (g % 300) * interval '1 day',
  (g % 100000) + 100
FROM generate_series(1, 200000) AS g;

-- 统计信息不更新，优化器会按默认估算行数，执行计划不可信
ANALYZE orders;

SELECT count(*) AS total_rows,
       count(*) FILTER (WHERE status = 'paid')     AS paid_rows,
       count(*) FILTER (WHERE status = 'refunded') AS refunded_rows
FROM orders;

真实输出：

text
 total_rows | paid_rows | refunded_rows
------------+-----------+---------------
     200000 |    100000 |          2000
(1 row)

一、建索引前的执行计划 ​

sql
\echo '== 1. 按客户查最近 10 单（没有索引） =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 10;

\echo '== 2. 统计退款订单数（选择性高：约 1%） =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE status = 'refunded';

\echo '== 3. 统计已支付订单数（选择性低：约 75%） =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE status = 'paid';

\echo '== 4. 时间范围查询 =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE created_at >= '2026-10-01 00:00:00+08'
  AND created_at <  '2026-10-08 00:00:00+08'
ORDER BY created_at;

\echo '== 5. 主键点查：走索引，作为对照 =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE id = 12345;

真实输出（按客户查最近 10 单）：

text
Limit  (cost=4196.12..4197.27 rows=10 width=34) (actual time=3.996..4.926 rows=10 loops=1)
  ->  Gather Merge  ...
        Workers Planned: 1
        ->  Sort  (Sort Key: created_at DESC)
              Sort Method: top-N heapsort  Memory: 26kB
              ->  Parallel Seq Scan on orders
                    Filter: (customer_id = 42)
                    Rows Removed by Filter: 99980
Execution Time: 4.953 ms

读法：

  • Parallel Seq Scan：并行全表扫描，两个 worker 各扫一半；
  • Rows Removed by Filter: 99980：过滤掉近 10 万行，只为留下 40 行；
  • Sort：因为要 ORDER BY created_at DESC LIMIT 10，还得排序；
  • Buffers: shared hit=1762：读了 1762 个缓存页。

二、建索引 ​

sql
-- 04 建业务索引
-- 联合索引的顺序：等值条件在前，排序/范围条件在后。
CREATE INDEX idx_orders_customer_created
  ON orders (customer_id, created_at DESC);

CREATE INDEX idx_orders_status
  ON orders (status);

CREATE INDEX idx_orders_created_at
  ON orders (created_at);

-- 新建索引后必须更新统计信息，否则优化器仍按旧估算选择计划
ANALYZE orders;

-- 让 visibility map 生效，后续才能观察到 Index Only Scan
VACUUM orders;

SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders'
ORDER BY indexname;

真实输出（索引列表）：

text
          indexname          |                                               indexdef
-----------------------------+------------------------------------------------------------------------------------------------------
 idx_orders_created_at       | CREATE INDEX idx_orders_created_at ON public.orders USING btree (created_at)
 idx_orders_customer_created | CREATE INDEX idx_orders_customer_created ON public.orders USING btree (customer_id, created_at DESC)
 idx_orders_status           | CREATE INDEX idx_orders_status ON public.orders USING btree (status)
 orders_pkey                 | CREATE UNIQUE INDEX orders_pkey ON public.orders USING btree (id)
(4 rows)

三、建索引后的执行计划 ​

sql
\echo '== 1. 按客户查最近 10 单（联合索引直接有序） =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 10;

\echo '== 2. 退款订单数（选择性高，走索引） =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE status = 'refunded';

\echo '== 3. 已支付订单数（选择性低，可能仍走全表扫描） =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE status = 'paid';

\echo '== 4. 时间范围查询（走 created_at 索引） =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE created_at >= '2026-10-01 00:00:00+08'
  AND created_at <  '2026-10-08 00:00:00+08'
ORDER BY created_at;

真实输出（同一个查询）：

text
Limit  (cost=0.29..41.46 rows=10 width=35) (actual time=0.023..0.060 rows=10 loops=1)
  ->  Index Scan using idx_orders_customer_created on orders
        Index Cond: (customer_id = 42)
Execution Time: 0.068 ms

Sort 节点消失，Seq Scan 变成 Index Scan，执行时间从约 5ms 降到约 0.07ms。这就是「索引同时服务过滤与排序」的价值。

逐步拆解 ​

第 1 步：读懂 EXPLAIN 的四个数字 ​

text
Limit  (cost=0.29..41.46 rows=10 width=35) (actual time=0.023..0.060 rows=10 loops=1)
字段含义怎么用
cost=0.29..41.46启动成本..总成本（抽象单位）比较不同计划，不是毫秒
rows=10优化器估计返回行数与实际差很多 → 统计信息过期或列相关
actual time=0.023..0.060实际启动..总耗时（毫秒）需要 ANALYZE 才有
loops=1该节点执行次数嵌套循环里很大 → 可能 N+1

再加 BUFFERS：

  • shared hit：命中共享缓存，不读磁盘；
  • shared read：从磁盘读；
  • Heap Fetches：Index Only Scan 回表次数，理想为 0。

第 2 步：为什么 1% 和 50% 差 40 倍 ​

text
退款（1%）  Index Only Scan ... Execution Time: 0.163 ms
已支付（50%）Index Only Scan ... Execution Time: 6.044 ms

两者的计划形状一样，但返回行数差 50 倍，读取的索引页也差几十倍。索引减少的是「要读的数据量」，不是「常数时间」。当返回行数占表很大比例时，顺序扫描反而更便宜，优化器可能切换计划。

第 3 步：覆盖索引消除回表 ​

sql
-- 06 覆盖索引：把查询需要的列放进 INCLUDE，避免回表
-- 先删掉普通的 status 索引，避免优化器在两者之间摇摆。
DROP INDEX IF EXISTS idx_orders_status;

CREATE INDEX idx_orders_refunded_total
  ON orders (status) INCLUDE (total_cents);

VACUUM ANALYZE orders;

\echo '== 覆盖索引：只读索引就能完成 sum =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT sum(total_cents) FROM orders WHERE status = 'refunded';

SELECT indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY indexrelname;

真实输出：

text
Aggregate
  ->  Index Only Scan using idx_orders_refunded_total on orders
        Index Cond: (status = 'refunded')
        Heap Fetches: 0
Execution Time: 0.175 ms

Heap Fetches: 0 是关键：查询所需列都在索引里，不需要回表。覆盖索引适合「高频、列少、聚合」的查询；如果 SELECT *，覆盖索引就失效了。

第 4 步：部分索引把体积降下来 ​

sql
-- 07 部分索引：只为「待处理订单」建索引
-- 待处理订单通常只占少数，部分索引更小、写入成本更低。
CREATE INDEX idx_orders_pending_created
  ON orders (created_at)
  WHERE status = 'pending';

ANALYZE orders;

\echo '== 部分索引：查询条件必须包含 WHERE status = pending =='
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE status = 'pending'
  AND created_at >= '2026-10-01 00:00:00+08'
ORDER BY created_at
LIMIT 20;

\echo '== 索引占用空间 =='
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;

真实输出：

text
Limit  (cost=0.29..31.98 rows=20 width=34) (actual time=0.009..0.022 rows=20 loops=1)
  ->  Index Scan using idx_orders_pending_created on orders
        Index Cond: (created_at >= '2026-10-01 00:00:00+08'::timestamp with time zone)
Execution Time: 0.028 ms

索引空间对比：

text
 idx_orders_refunded_total   | 6192 kB
 orders_pkey                 | 4408 kB
 idx_orders_customer_created | 1840 kB
 idx_orders_created_at       | 1456 kB
 idx_orders_pending_created  |  376 kB

部分索引 376KB，因为只收录 status = 'pending' 的行。代价是查询必须带上同样的 WHERE 条件，否则用不上。

第 5 步：哪些写法会让索引失效 ​

写法为什么失效改法
WHERE lower(email) = 'a@b.com'对列做了函数运算建表达式索引 ON users (lower(email))
WHERE created_at::date = '2026-10-01'列被强转，索引键类型不匹配改成范围 >= '2026-10-01' AND < '2026-10-02'
WHERE name LIKE '%键盘'前置通配符无法按前缀查找用 pg_trgm GIN 索引，或改成后缀/全文检索
WHERE status != 'paid'取反通常命中大部分行改成白名单 IN (...)，或部分索引
WHERE phone = 13800138000（列是 text）隐式类型转换可能作用在列上参数类型与列类型一致
刚大批量写入后查询统计信息过期ANALYZE；必要时调 autovacuum
小表只有几百行全表扫描更便宜不要强行建索引

第 6 步：找出没用的索引 ​

sql
SELECT indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY idx_scan, pg_relation_size(indexrelid) DESC;

idx_scan = 0 且持续很久，说明索引没人用，可以考虑删除。删除前确认：

  • 统计从上次重置后开始，是否覆盖了完整业务周期（例如月末报表）；
  • 是否是唯一索引/主键（不能只看 idx_scan）；
  • 是否被外键、约束依赖。

第 7 步：生产建索引要用 CONCURRENTLY ​

普通 CREATE INDEX 会阻塞写入。生产大表用：

sql
CREATE INDEX CONCURRENTLY idx_orders_status
  ON orders (status);

注意：

  • 不能放在事务块里；
  • 失败会留下 INVALID 索引，需要 DROP INDEX CONCURRENTLY 后重试；
  • 执行时间更长，但期间不阻塞读写；
  • 建完仍需 ANALYZE 更新统计。

常见坑与排查 ​

现象根因处理
建了索引但计划仍是 Seq Scan选择性低、统计过期、或写法导致索引失效ANALYZE；检查条件是否对列做运算；看 EXPLAIN 的 Filter
索引扫描比全表扫描还慢返回行数占比高、随机 IO 多接受顺序扫描；考虑覆盖索引或调整查询
Index Only Scan 但 Heap Fetches 很大visibility map 未更新VACUUM；检查 autovacuum 是否落后
联合索引只用到了第二列违反最左前缀调整索引列顺序，或为第二列单独建索引
写入变慢索引太多，每次写入维护所有索引用 idx_scan 找无用索引并删除
索引体积远大于表索引膨胀、重复索引、宽键REINDEX CONCURRENTLY；改用部分/覆盖索引
生产建索引导致业务卡顿普通 CREATE INDEX 持锁用 CREATE INDEX CONCURRENTLY，低峰执行
两个索引定义几乎一样历史遗留、重复建设删除被包含的索引（如 (a) 被 (a,b) 覆盖前导列）
LIKE '%x%' 很慢B-tree 不支持中缀匹配用 pg_trgm + GIN，或全文检索
时间范围查询仍全表扫描数据物理无序、BRIN 不适用，或统计过期建 B-tree；超大有序表评估 BRIN

企业级做法 ​

  1. 索引跟着查询走：先收集真实慢查询（pg_stat_statements），再设计索引，不要给每一列都建。
  2. 联合索引覆盖高频组合：等值列在前，排序列在后；用 EXPLAIN 验证是否消除 Sort。
  3. 外键列建索引：JOIN 与 ON DELETE CASCADE 都依赖它；PostgreSQL 不会自动为外键建索引。
  4. 唯一索引用作幂等防线：订单号、支付流水号、(user_id, idempotency_key)，比「先查再插」可靠。
  5. 部分索引服务热数据：未完成订单、未读消息、软删除表的活跃行。
  6. 覆盖索引服务高频聚合：INCLUDE 需要的列，观察 Heap Fetches: 0。
  7. 生产变更用 CONCURRENTLY：并监控 pg_stat_progress_create_index；失败留下的 invalid 索引要清理。
  8. 定期审计索引：idx_scan = 0、重复前缀、超大索引，每季度清理一次。
  9. 统计信息也是 schema 的一部分：大批量写入后 ANALYZE；多列相关性强时用 CREATE STATISTICS。
  10. 用真实数据量测试：1 万行和 1000 万行的计划可能完全不同；本章的 20 万行只是最小可信规模。

练习与验收标准 ​

练习

  1. 把 idx_orders_customer_created 改成 (created_at DESC, customer_id)，重跑查询 1，观察计划是否还能消除 Sort。
  2. 为 WHERE status = 'refunded' ORDER BY created_at DESC LIMIT 10 设计一个联合索引，并用 EXPLAIN 验证。
  3. 建一个 lower(status) 的表达式索引，比较 WHERE lower(status) = 'paid' 前后的计划。
  4. 用 pg_stat_user_indexes 找出一个 idx_scan = 0 的索引，说明它为什么没被使用。
  5. 在 20 万行基础上再插入 20 万行，观察 ANALYZE 前后同一查询的估计行数变化。
  6. 用 CREATE INDEX CONCURRENTLY 建一个索引，故意在另一个会话里查询 pg_stat_progress_create_index。

验收标准

  • [ ] 建索引前查询 1 出现 Seq Scan 与 Sort；
  • [ ] 建索引后查询 1 出现 Index Scan，Sort 消失；
  • [ ] 退款查询从 Seq Scan 变为 Index Only Scan；
  • [ ] 覆盖索引查询出现 Heap Fetches: 0；
  • [ ] 部分索引体积明显小于普通索引；
  • [ ] 能解释 cost、rows、actual time、loops、Buffers、Heap Fetches 的含义；
  • [ ] 能说出至少三种索引失效的写法及改法；
  • [ ] 能用 pg_stat_user_indexes 判断索引是否被使用。
