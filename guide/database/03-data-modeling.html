03 数据建模：范式、主键、约束与迁移 ​

范式与反范式、主键选型、约束设计与版本化迁移的落地方法。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 用函数依赖解释 1NF / 2NF / 3NF，并说出范式解决的是哪三类异常；
  2. 在代理键与自然键、bigint identity 与 UUID 之间做出有理由的选择；
  3. 用 NOT NULL / UNIQUE / CHECK / FOREIGN KEY 把业务规则写进数据库，而不是只写在代码里；
  4. 识别「有意的反范式」与「无意的数据冗余」，例如订单行保存价格快照；
  5. 用版本化迁移管理 schema 变更，做到 up → down → up 可逆；
  6. 用数据质量 SQL 验证模型真的在约束数据，而不是只存在于文档里。

概念与原理 ​

1. 建模的目标：让错误的数据写不进来 ​

一个表结构好不好，不看画得漂不漂亮，而看它能不能在下面这些情况下仍然正确：

  • 两个人同时改同一条数据；
  • 商品改价后，历史订单金额不能变；
  • 删除一个客户时，不能留下无主订单；
  • 订单状态只能从 pending 走到 paid，不能从 cancelled 回到 paid；
  • 半年后新人加字段时，不需要猜「这个字段到底能不能为空」。

这些要求，有的靠约束（数据库强制），有的靠事务（第 04 章），有的靠应用逻辑。能交给数据库的，优先交给数据库，因为应用可能有多个入口、多个版本、甚至有人直接连库改数据。

2. 三范式：消除三类异常 ​

先看一张「什么都塞在一起」的宽表：

text
bad_orders(order_id, customer_id, customer_name, customer_city,
           product_name, quantity, unit_price)
范式要求这张表违反了什么
1NF每列不可再分如果 product_name 存成 "键盘,鼠标" 就违反了
2NF非主键列完全依赖整个主键主键是 (order_id, product_name) 时，customer_name 只依赖 order_id，是部分依赖
3NF非主键列不依赖其他非主键列customer_city 依赖 customer_id，而 customer_id 又依赖 order_id，是传递依赖

违反范式会带来三类异常：

  • 插入异常：新客户还没下单，就没地方存客户信息；
  • 更新异常：客户搬家，要改所有历史订单行，漏改一行就出现两个地址；
  • 删除异常：删掉最后一个订单，客户信息也跟着消失。

把宽表拆成 customers / orders / order_items / products 后，每个事实只存一处，异常自然消失。示例里的反例脚本会真实复现「改了一行、同一个客户出现两个城市」的更新异常：

sql
BEGIN;

CREATE TEMP TABLE bad_orders (
  order_id      bigint,
  customer_id   bigint,
  customer_name text,
  customer_city text,
  product_name  text,
  quantity      integer,
  unit_price    integer
);

INSERT INTO bad_orders VALUES
  (1001, 1, 'Ada Lovelace', '上海', '机械键盘',     1, 49900),
  (1001, 1, 'Ada Lovelace', '上海', '人体工学鼠标', 1, 25900),
  (1002, 2, 'Grace Hopper', '北京', '27 寸显示器',  1, 189900);

-- 只改了一行：同一个客户的地址在两条订单行里变得不一致
UPDATE bad_orders SET customer_city = '北京' WHERE order_id = 1001 AND product_name = '机械键盘';

SELECT order_id, customer_name, customer_city, product_name
FROM bad_orders
ORDER BY order_id, product_name;

ROLLBACK;

真实输出：

text
 order_id | customer_name | customer_city |  product_name
----------+---------------+---------------+---------------
     1001 | Ada Lovelace  | 上海          | 人体工学鼠标
     1001 | Ada Lovelace  | 北京          | 机械键盘
     1002 | Grace Hopper  | 北京          | 27 寸显示器
(3 rows)

3. 主键：代理键与自然键 ​

类型例子优点代价
自然键身份证号、SKU、邮箱业务含义清晰，天然唯一业务可能变；长字符串索引大；隐私字段泄露
代理键bigint identity、UUID稳定、短、与业务解耦需要额外唯一约束表达业务唯一性

本教程的选择：

  • 主键用 bigint GENERATED ... AS IDENTITY：短、有序、索引友好；
  • 业务唯一性用 UNIQUE 单独表达：email、sku、(order_id, product_id)；
  • 对外暴露用 UUID 或单独的业务号：避免用户从 /orders/1001 推断出订单量（企业级常见做法）。

UUID 不是不能用，而是要知道代价：随机 UUID 作为主键会让 B+ 树插入分散、索引更大；需要时可以用 UUIDv7 这类时间有序的变体，或把 UUID 只作为对外标识，内部仍用 bigint。

4. 约束清单：把规则写进 schema ​

约束作用示例
NOT NULL禁止缺失email text NOT NULL
UNIQUE唯一性，最终防线email text NOT NULL UNIQUE
CHECK值域 / 状态机status IN ('pending','paid','shipped','cancelled')
FOREIGN KEY引用完整性customer_id REFERENCES customers(id)
ON DELETE RESTRICT有引用时禁止删除删除客户前必须先处理订单
ON DELETE CASCADE子记录随父记录删除删除订单时删除订单行
部分唯一索引带条件的唯一性软删除后允许同邮箱重新注册（见第 04 章）

约束要命名。默认名如 orders_status_check 在不同环境可能不同，迁移回滚时对不上。企业项目统一用 chk_、uq_、fk_、idx_ 前缀。

5. 反范式：有意冗余 vs 无意冗余 ​

订单行里的 unit_price_cents 是有意的反范式：

  • 商品价格会变，历史订单必须保留下单时的价格；
  • 如果每次展示订单都去 products 查当前价，历史金额会被改写；
  • 冗余的代价是「商品调价后要同步哪些表」需要明确，但收益是账务可追溯。

判断标准：冗余字段是否有独立的业务含义与生命周期。有，就是快照；没有，就是重复，迟早不一致。

6. 迁移：schema 变更也要有版本 ​

迁移的本质是「把数据库从一个版本推到下一个版本」，要求：

  1. 有序：文件名带序号或时间戳，按序执行；
  2. 可记录：schema_migrations 表记录已执行版本，重复执行不报错；
  3. 可回滚（开发环境）：每个 up 有对应 down，down 按 up 的逆序写；
  4. 生产只前进：线上出问题用「新迁移修复」，而不是回滚，避免数据丢失；
  5. 大表变更拆步：加可空列 → 回填 → 收紧约束（本章示例 002）。

ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT 在 PostgreSQL 11+ 对常量默认值已经很快，但在大表上仍要评估锁；更稳妥的做法始终是「先加可空列，再回填，再收紧」。

7. 类型选择：钱、时间、文本、枚举 ​

数据推荐不要用原因
金额integer 分 / numeric(12,2)float / double浮点有精度误差
时间timestamptz（UTC 存储）timestamp 无时区跨时区/夏令时会错
短文本textvarchar(n)PostgreSQL 的 text 无性能劣势，长度约束用 CHECK
状态text + CHECK 或 PostgreSQL 枚举魔法数字可读性与约束兼得
半结构化jsonbjson（文本）jsonb 可索引、可查询

最小可跑示例 ​

示例目录 examples/database/03-data-modeling/，包含三份迁移、一个最小迁移工具、种子数据与数据质量检查。

一、初始 schema ​

sql
CREATE TABLE customers (
  id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email      text        NOT NULL UNIQUE,
  name       text        NOT NULL,
  city       text        NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
  id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku         text    NOT NULL UNIQUE,
  name        text    NOT NULL,
  category    text    NOT NULL,
  price_cents integer NOT NULL CHECK (price_cents >= 0),
  stock       integer NOT NULL DEFAULT 0 CHECK (stock >= 0)
);

CREATE TABLE orders (
  id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  customer_id bigint      NOT NULL REFERENCES customers (id) ON DELETE RESTRICT,
  status      text        NOT NULL CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
  ordered_at  timestamptz NOT NULL DEFAULT now(),
  total_cents integer     NOT NULL DEFAULT 0 CHECK (total_cents >= 0)
);

-- 订单行保存「下单时的单价」快照，而不是每次去 products 表现查价格。
-- 这是有意的反范式：商品改价不能改变历史订单金额。
CREATE TABLE order_items (
  id               bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  order_id         bigint  NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
  product_id       bigint  NOT NULL REFERENCES products (id) ON DELETE RESTRICT,
  quantity         integer NOT NULL CHECK (quantity > 0),
  unit_price_cents integer NOT NULL CHECK (unit_price_cents >= 0),
  UNIQUE (order_id, product_id)
);

三个设计点：

  • id 是代理键，email / sku 用 UNIQUE 表达业务唯一性；
  • orders.customer_id 用 ON DELETE RESTRICT：有订单的客户不能被无声删除；
  • order_items 用 UNIQUE (order_id, product_id)：同一订单同一商品只允许一行，数量放 quantity。

二、给已有表加非空列 ​

sql
ALTER TABLE customers ADD COLUMN tier text;

UPDATE customers SET tier = 'basic' WHERE tier IS NULL;

ALTER TABLE customers ALTER COLUMN tier SET NOT NULL;
ALTER TABLE customers ALTER COLUMN tier SET DEFAULT 'basic';
ALTER TABLE customers
  ADD CONSTRAINT chk_customers_tier CHECK (tier IN ('basic', 'silver', 'gold'));

这条迁移演示了「三步法」：先加可空列，回填，再 SET NOT NULL 与 CHECK。如果表很大，回填要分批（例如每批 1 万行），避免长事务与锁表。

三、只追加的审计表 ​

sql
CREATE TABLE order_status_history (
  id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  order_id   bigint      NOT NULL REFERENCES orders (id),
  old_status text,
  new_status text        NOT NULL CHECK (new_status IN ('pending', 'paid', 'shipped', 'cancelled')),
  changed_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_order_status_history_order_id
  ON order_status_history (order_id, changed_at);

-- 任何 UPDATE / DELETE 都直接报错，应用账号即使有权限也改不了历史
CREATE FUNCTION reject_history_mutation() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'order_status_history 只允许追加，禁止 UPDATE/DELETE';
END;
$$;

CREATE TRIGGER trg_order_status_history_immutable
BEFORE UPDATE OR DELETE ON order_status_history
FOR EACH ROW EXECUTE FUNCTION reject_history_mutation();

BEFORE UPDATE OR DELETE 触发器让历史表真正只可追加。应用账号即使误写 UPDATE，也会被数据库拒绝。这比「在代码里约定不要改」可靠得多。

四、执行迁移 ​

bash
#!/usr/bin/env bash
# 最小迁移工具：按文件名顺序执行 migrations/*.up.sql，并记录到 schema_migrations。
# 用法：
#   ./scripts/migrate.sh up      应用所有未执行的迁移
#   ./scripts/migrate.sh down    回滚最近一个迁移
#   ./scripts/migrate.sh status  查看已应用版本
set -euo pipefail

cd "$(dirname "$0")/.."

PSQL=(docker compose exec -T postgres psql -U postgres -d shop -v ON_ERROR_STOP=1)

# 迁移记录表本身也由脚本创建，避免第一次执行前还要手动建表
"${PSQL[@]}" -q -c "
  CREATE TABLE IF NOT EXISTS schema_migrations (
    version    text PRIMARY KEY,
    applied_at timestamptz NOT NULL DEFAULT now()
  );" >/dev/null

apply_up() {
  for file in migrations/*.up.sql; do
    version="$(basename "$file" .up.sql)"
    applied="$("${PSQL[@]}" -tAc "SELECT 1 FROM schema_migrations WHERE version = '${version}'")"
    if [ "$applied" = "1" ]; then
      echo "跳过 ${version}（已应用）"
      continue
    fi
    echo "应用 ${version}"
    "${PSQL[@]}" -q -f - < "$file"
    "${PSQL[@]}" -q -c "INSERT INTO schema_migrations (version) VALUES ('${version}');"
  done
}

apply_down() {
  version="$("${PSQL[@]}" -tAc "SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 1")"
  if [ -z "$version" ]; then
    echo "没有可回滚的迁移"
    return
  fi
  echo "回滚 ${version}"
  "${PSQL[@]}" -q -f - < "migrations/${version}.down.sql"
  "${PSQL[@]}" -q -c "DELETE FROM schema_migrations WHERE version = '${version}';"
}

show_status() {
  "${PSQL[@]}" -c "SELECT version, applied_at FROM schema_migrations ORDER BY version;"
}

case "${1:-up}" in
  up) apply_up ;;
  down) apply_down ;;
  status) show_status ;;
  *)
    echo "用法：$0 {up|down|status}" >&2
    exit 1
    ;;
esac

真实输出（首次执行）：

text
应用 001_init
应用 002_add_customer_tier
应用 003_create_order_status_history

status 子命令：

             version             |          applied_at
---------------------------------+-------------------------------
 001_init                        | 2026-11-10 20:48:14.687598+08
 002_add_customer_tier           | 2026-11-10 20:48:15.089528+08
 003_create_order_status_history | 2026-11-10 20:48:17.447467+08
(3 rows)

逐步拆解 ​

第 1 步：为什么订单行要存单价快照 ​

order_items.unit_price_cents 不是多余字段，它记录的是下单那一刻的价格。假设商品从 499 元涨到 599 元：

  • 如果订单展示时去 products 查当前价，历史订单会「涨价」；
  • 如果存了快照，历史金额不变，商品调价只影响新订单。

同理，订单的 total_cents 也应该是下单时计算并保存的，而不是每次查询时现算。现算适合对账校验，不适合作为账务依据。

第 2 步：迁移工具必须记录版本 ​

migrate.sh 的核心不是「执行 SQL」，而是「只执行一次」：

bash
applied="$("${PSQL[@]}" -tAc "SELECT 1 FROM schema_migrations WHERE version = '${version}'")"
if [ "$applied" = "1" ]; then
  echo "跳过 ${version}（已应用）"
  continue
fi

没有这张表，重复部署会重复执行 DDL，轻则报错，重则重复回填数据。生产环境还要加锁（如 PostgreSQL advisory lock），避免两个实例同时跑迁移。

第 3 步：down 要按 up 的逆序写 ​

001_init.up.sql 的建表顺序是 customers → products → orders → order_items，down 必须反过来：

text
DROP order_items → orders → products → customers

否则外键依赖会导致 DROP TABLE 失败。002 的 down 先删 CHECK 再删列；003 的 down 先删触发器、再删函数、最后删表。

第 4 步：验证可逆 ​

bash
./scripts/migrate.sh down
./scripts/migrate.sh status
./scripts/migrate.sh up
./scripts/migrate.sh status

真实输出（回滚后只剩两条，重新 up 后恢复三条）：

text
回滚 003_create_order_status_history
        version        |          applied_at
-----------------------+-------------------------------
 001_init              | 2026-11-10 20:48:14.687598+08
 002_add_customer_tier | 2026-11-10 20:48:15.089528+08
(2 rows)

注意：down 会删表，只适合本地与预发。生产的回滚策略是「用新迁移修复」，不是执行 down。

第 5 步：约束真的会拦住错误吗 ​

bash
docker compose exec -T postgres psql -U postgres -d shop \
  -c "UPDATE order_status_history SET new_status = 'cancelled' WHERE id = 1;"

真实输出：

text
ERROR:  order_status_history 只允许追加，禁止 UPDATE/DELETE
CONTEXT:  PL/pgSQL function reject_history_mutation() line 3 at RAISE

再试重复邮箱：

text
ERROR:  duplicate key value violates unique constraint "customers_email_key"
DETAIL:  Key (email)=(ada@example.com) already exists.

报错是预期行为。如果这些语句成功了，才说明约束没生效。

第 6 步：把检查固化进流程 ​

数据质量 SQL 的价值在于「可重复执行、结果可断言」：

  • 本地开发：灌完种子数据跑一遍；
  • CI：每次迁移后在临时库跑一遍，任何一项大于 0 就失败；
  • 生产巡检：每天低峰期跑一遍，结果进监控。

第 06 章会把这类检查与慢查询治理放在一起讲。

常见坑与排查 ​

现象根因处理
insert or update on table violates foreign key constraint子表写入的父记录不存在，或删除顺序错先写父表；删除时先删子表或用 ON DELETE CASCADE
null value in column violates not-null constraint迁移加了 NOT NULL 但没回填用三步法：加可空列 → 回填 → SET NOT NULL
down 执行失败删表顺序与外键依赖相反按 up 的逆序删；先删触发器/函数再删表
重复执行迁移报「已存在」没有 schema_migrations 记录用迁移工具统一执行，不要手工跑 SQL
订单金额与明细对不上只算了明细，没保存快照；或改了历史价格下单时同时写 total_cents 与 unit_price_cents；对账 SQL 常态巡检
软删除后同邮箱无法注册唯一索引覆盖了已删除行用部分唯一索引 WHERE deleted_at IS NULL（第 04 章）
加字段后旧代码报错新列 NOT NULL 且无默认值先加可空列/默认值，再发布代码，最后收紧
大表 ALTER TABLE 卡住业务长时间持有 ACCESS EXCLUSIVE 锁拆成 expand/contract；设置 lock_timeout；在低峰执行
状态出现 PAID / paid 两种值没有 CHECK 或枚举约束加 CHECK (status IN (...))，并在应用层统一常量
时间差 8 小时用了 timestamp 无时区，或连接时区不对统一 timestamptz，应用与数据库都用 UTC，展示层再转本地

企业级做法 ​

  1. 约束优先于代码校验：应用层校验为了体验，数据库约束为了正确性，两者都要有。
  2. 代理键 + 业务唯一键：内部关联用 bigint，对外暴露用 UUID/业务号，避免 ID 枚举与信息泄露。
  3. 迁移只前进：生产不做 down；出问题写修复迁移，保留数据。
  4. 大表变更 expand/contract：加列 → 双写 → 回填 → 切读 → 删旧列，每一步都可单独发布与回滚。
  5. 审计表只追加：用触发器或权限限制 UPDATE/DELETE；归档走独立任务，不直接删历史。
  6. 状态机用约束 + 应用双重表达：CHECK 收敛值域，应用层控制合法迁移；不要只靠前端按钮。
  7. 金额、时间、文本类型统一：整数分、timestamptz、text；团队写进规范，评审时检查。
  8. 迁移与代码同仓库、同评审：schema 变更是代码变更的一部分，不能由某个人在数据库客户端里手工改。
  9. 每个环境都能从零重建：docker compose down -v 后，迁移 + 种子能还原一套可用数据；这是可复现性的底线。

练习与验收标准 ​

练习

  1. 给 products 加一个 status 字段（on_sale / off_shelf），要求非空、默认 on_sale、带 CHECK；写出 up 与 down。
  2. 给 orders 增加 paid_at timestamptz，只允许 paid / shipped 订单有值，用 CHECK 表达这个约束。
  3. 设计一张 coupons 表与 coupon_redemptions 表，要求同一用户同一优惠券只能核销一次；写出主键、外键与唯一约束。
  4. 把 02-data-quality.sql 增加一项「已支付订单必须有支付时间」，并在种子里故意制造一条违规，确认检查能查出来。
  5. 把 003 的状态历史改成「由触发器自动记录」：orders.status 更新时自动插入历史。思考：这比应用层写入好在哪里、差在哪里。
