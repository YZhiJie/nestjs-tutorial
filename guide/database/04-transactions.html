04 事务与隔离级别 ​

ACID、四种隔离级别、MVCC 与并发异常，用真实并发会话观察脏读与幻读。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 用 ACID 解释「转账要么全成功、要么全失败」靠的是什么；
  2. 说清 BEGIN / COMMIT / ROLLBACK / SAVEPOINT 的边界，知道哪些操作不能放进事务；
  3. 区分脏读、不可重复读、幻读、丢失更新与写偏斜，并知道 PostgreSQL 各隔离级别分别能挡住哪些；
  4. 用原子增量、SELECT ... FOR UPDATE、乐观锁三种方式修复丢失更新；
  5. 看懂并处理死锁，知道应用层必须重试；
  6. 用两个真实会话复现不可重复读、丢失更新与死锁，拿到第一手输出。

概念与原理 ​

1. ACID：四个字母分别保证什么 ​

字母含义转账场景里的体现
Atomicity 原子性事务里的操作要么全做，要么全不做扣款成功但加款失败时，扣款也要撤销
Consistency 一致性事务前后满足约束余额不能为负、借贷总额相等
Isolation 隔离性并发事务互不看到中间状态转账提交前，别人看不到「只扣了款」
Durability 持久性提交后即使断电也不丢COMMIT 返回后，数据已在 WAL 里

数据库保证 A、I、D，C 需要你自己写对约束与业务规则。CHECK (balance_cents >= 0) 是数据库帮你守一致性；「转账前后总额不变」则要靠事务把两条 UPDATE 放在一起。

2. 事务边界：越短越好 ​

sql
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 20000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 20000 WHERE id = 2;
INSERT INTO ledger (from_account_id, to_account_id, amount_cents) VALUES (1, 2, 20000);
COMMIT;

三条语句必须在一起，因为中间任何一步失败都会让账不平。但下面这些不要放进事务：

  • HTTP / RPC 调用：外部服务慢，事务会一直占着连接与锁；
  • 发消息、写文件：失败后无法随事务回滚；
  • 密码哈希、图片压缩等 CPU 密集计算：占着事务做无用功。

正确做法是「事务内只做数据库写入，事务外做副作用」，跨系统一致性用 Outbox（第 08 章）。

3. 隔离级别与并发异常 ​

隔离级别脏读不可重复读幻读序列化异常（写偏斜）
READ UNCOMMITTED允许（PG 视为 RC）允许允许允许
READ COMMITTED（PG 默认）不允许允许允许允许
REPEATABLE READ不允许不允许PG 不允许允许
SERIALIZABLE不允许不允许不允许不允许

几个容易混的点：

  • PostgreSQL 的 READ UNCOMMITTED 实际按 READ COMMITTED 执行，因为 MVCC 根本不暴露未提交数据；
  • PostgreSQL 的 REPEATABLE READ 比 SQL 标准更强：同一事务看到同一个快照，幻读也不会出现；
  • SERIALIZABLE 用 SSI（Serializable Snapshot Isolation）检测冲突，冲突时主动报 could not serialize access due to read/write dependencies，应用必须重试；
  • MySQL InnoDB 默认 REPEATABLE READ，实现方式与 PostgreSQL 不同（next-key lock），第 10 章对照。

4. MVCC：读不阻塞写，写不阻塞读 ​

PostgreSQL 更新一行时不会原地覆盖，而是写一个新版本，旧版本保留给仍在读的事务。由此：

  • 普通 SELECT 不加锁，读的是事务/语句开始时的快照；
  • UPDATE / DELETE 会给目标行加行锁，后到的事务等待；
  • 旧版本由 VACUUM 回收，长事务会让旧版本堆积，导致表膨胀。

READ COMMITTED 下每条语句取一次新快照，所以同一事务两次 SELECT 可能看到不同结果；REPEATABLE READ 下整个事务共用一个快照，所以两次读一致。

5. 丢失更新：先读后写的经典陷阱 ​

text
A: 读 balance = 100000
B: 读 balance = 100000
A: 写 balance = 110000（+10000）
B: 写 balance = 120000（+20000）
最终 120000，A 的 +10000 丢了

三种修复方式：

方式写法适用
原子增量SET balance = balance + 10000加减、计数、库存扣减
行锁SELECT ... FOR UPDATE 后再算需要基于当前值做复杂判断
乐观锁UPDATE ... WHERE version = :v，检查影响行数冲突少、读多写少

本教程的订单库存扣减用「条件更新」：UPDATE products SET stock = stock - :n WHERE id = :id AND stock >= :n，影响行数为 0 就说明库存不足。这是原子增量 + 条件判断的组合，比「先查再扣」可靠。

6. 死锁：顺序不一致就会互相等 ​

text
事务 A：锁行 1 → 等行 2
事务 B：锁行 2 → 等行 1

PostgreSQL 有死锁检测器，默认约 1 秒后发现环并中止其中一个事务，报 deadlock detected。处理原则：

  1. 统一加锁顺序：所有事务按 id 升序锁行；
  2. 缩小锁范围：只锁需要的行，尽快提交；
  3. 应用必须重试：捕获 40P01（deadlock）与 40001（serialization failure），退避后重试整个事务。

7. 长事务与连接池 ​

一个「开了事务但忘了提交」的连接，会：

  • 占住连接池名额，最终把池耗尽；
  • 持有旧快照，阻止 VACUUM 回收，表越来越膨胀；
  • 可能持有行锁，阻塞其他写入。

监控 SQL：

sql
SELECT pid, state, now() - xact_start AS xact_age, query
FROM pg_stat_activity
WHERE state = 'idle in transaction';

生产要设置 idle_in_transaction_session_timeout 与 statement_timeout，让失控事务自动被杀掉（第 09 章展开）。

最小可跑示例 ​

示例目录 examples/database/04-transactions/。先看表结构：

sql
-- 04 事务示例：账户余额 + 流水
-- balance_cents 用 bigint，CHECK 保证不会转出负数。
DROP TABLE IF EXISTS ledger;
DROP TABLE IF EXISTS accounts;

CREATE TABLE accounts (
  id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  owner         text   NOT NULL UNIQUE,
  balance_cents bigint NOT NULL CHECK (balance_cents >= 0)
);

-- 流水只追加：金额、方向、时间都能追溯
CREATE TABLE ledger (
  id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  from_account_id bigint      REFERENCES accounts (id),
  to_account_id   bigint      REFERENCES accounts (id),
  amount_cents    bigint      NOT NULL CHECK (amount_cents > 0),
  created_at      timestamptz NOT NULL DEFAULT now()
);

ALTER DATABASE shop SET timezone TO 'Asia/Shanghai';

ledger 只追加，记录每次转账；accounts.balance_cents 用 CHECK 保证不会出现负数。

一、单会话：提交、回滚、保存点 ​

sql
-- 03 单会话事务演示：提交、回滚、保存点
-- 先重置数据，保证每次执行结果一致
UPDATE accounts SET balance_cents = 100000 WHERE id = 1;
UPDATE accounts SET balance_cents = 50000  WHERE id = 2;
DELETE FROM ledger;

\echo '== 1. 转账：两条 UPDATE + 一条 INSERT 同一事务 =='
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 20000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 20000 WHERE id = 2;
INSERT INTO ledger (from_account_id, to_account_id, amount_cents)
VALUES (1, 2, 20000);
COMMIT;

SELECT id, owner, balance_cents FROM accounts ORDER BY id;
SELECT from_account_id, to_account_id, amount_cents FROM ledger ORDER BY id;

\echo '== 2. 回滚：中途失败，前面的写入也不保留 =='
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 10000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE id = 2;
ROLLBACK;

-- 余额应回到 80000 / 70000，与提交后的状态一致
SELECT id, owner, balance_cents FROM accounts ORDER BY id;

\echo '== 3. 保存点：只回滚一部分 =='
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 5000 WHERE id = 1;
SAVEPOINT before_bonus;
UPDATE accounts SET balance_cents = balance_cents + 5000 WHERE id = 2;
ROLLBACK TO SAVEPOINT before_bonus;
COMMIT;

-- A 扣了 5000，B 的加分被回滚：75000 / 70000
SELECT id, owner, balance_cents FROM accounts ORDER BY id;

真实输出（节选）：

text
== 1. 转账：两条 UPDATE + 一条 INSERT 同一事务 ==
BEGIN
UPDATE 1
UPDATE 1
INSERT 0 1
COMMIT
 id | owner | balance_cents
----+-------+---------------
  1 | alice |         80000
  2 | bob   |         70000
(2 rows)

== 2. 回滚：中途失败，前面的写入也不保留 ==
BEGIN
UPDATE 1
UPDATE 1
ROLLBACK
 id | owner | balance_cents
----+-------+---------------
  1 | alice |         80000
  2 | bob   |         70000
(2 rows)

第 2 段的关键：ROLLBACK 之后余额与提交后完全一致，说明中间两条 UPDATE 都没有留下痕迹。

二、双会话：不可重复读 ​

bash
"${PSQL[@]}" <<'SQL' &
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT 'A 第一次读' AS step, balance_cents FROM accounts WHERE id = 1;
SELECT pg_sleep(1.5);
SELECT 'A 第二次读' AS step, balance_cents FROM accounts WHERE id = 1;
COMMIT;
SQL
A_PID=$!

sleep 0.4
"${PSQL[@]}" <<'SQL'
BEGIN;
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE id = 1;
SELECT 'B 已提交' AS step, balance_cents FROM accounts WHERE id = 1;
COMMIT;
SQL
wait "$A_PID"

真实输出：

text
== 1. READ COMMITTED：同一事务内两次读到不同值（不可重复读） ==
 A 第一次读 |        100000
 B 已提交   |        110000
 A 第二次读 |        110000

A 的两次读之间，B 提交了 +10000。READ COMMITTED 下每条语句取新快照，所以 A 看到了变化。

三、双会话：REPEATABLE READ 的快照 ​

bash
"${PSQL[@]}" <<'SQL' &
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT 'A 第一次读' AS step, balance_cents FROM accounts WHERE id = 1;
SELECT pg_sleep(1.5);
SELECT 'A 第二次读' AS step, balance_cents FROM accounts WHERE id = 1;
COMMIT;
SQL
A_PID=$!

sleep 0.4
"${PSQL[@]}" <<'SQL'
BEGIN;
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE id = 1;
SELECT 'B 已提交' AS step, balance_cents FROM accounts WHERE id = 1;
COMMIT;
SQL
wait "$A_PID"

真实输出：

text
== 2. REPEATABLE READ：同一事务内看到同一个快照 ==
 A 第一次读 |        100000
 B 已提交   |        110000
 A 第二次读 |        100000

同一个事务里，A 始终看到 100000。这不是「缓存」，而是 MVCC 给事务固定了一个快照。

逐步拆解 ​

第 1 步：丢失更新是怎么发生的 ​

bash
"${PSQL[@]}" <<'SQL' &
BEGIN;
SELECT 'A 读到' AS step, balance_cents FROM accounts WHERE id = 1;
SELECT pg_sleep(1.5);
UPDATE accounts SET balance_cents = 110000 WHERE id = 1;
SELECT 'A 写入 110000' AS step, balance_cents FROM accounts WHERE id = 1;
COMMIT;
SQL
A_PID=$!

sleep 0.4
"${PSQL[@]}" <<'SQL'
BEGIN;
SELECT 'B 读到' AS step, balance_cents FROM accounts WHERE id = 1;
UPDATE accounts SET balance_cents = 120000 WHERE id = 1;
SELECT 'B 写入 120000' AS step, balance_cents FROM accounts WHERE id = 1;
COMMIT;
SQL
wait "$A_PID"

真实输出（调度顺序可能导致最终值在 110000 / 120000 之间变化，但都会丢一次更新）：

text
== 3. 丢失更新：两个事务都读 100000，再写绝对值 ==
 A 读到     |        100000
 B 读到     |        100000
 B 写入 120000 |      120000
 A 写入 110000 |      110000
 最终余额（丢失了 B 的 +20000） | 110000

两个事务都基于「旧值 100000」计算新值，后提交的绝对写覆盖了先提交的增量。注意：这不是数据库的 bug，而是应用把「读—算—写」拆成了非原子操作。

第 2 步：用原子增量修复 ​

bash
"${PSQL[@]}" <<'SQL' &
BEGIN;
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE id = 1;
SELECT 'A +10000' AS step, balance_cents FROM accounts WHERE id = 1;
COMMIT;
SQL
A_PID=$!

sleep 0.2
"${PSQL[@]}" <<'SQL'
BEGIN;
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE id = 1;
SELECT 'B +10000' AS step, balance_cents FROM accounts WHERE id = 1;
COMMIT;
SQL
wait "$A_PID"

真实输出：

text
== 4. 修复丢失更新：把读改写改成原子增量 ==
 A +10000 | 110000
 B +10000 | 120000
 最终余额（两次增量都保留） | 120000

SET balance = balance + 10000 在数据库内部完成「读当前值 + 加 + 写回」，两条 UPDATE 会串行执行，不会丢更新。

如果业务需要「先判断再扣」，用条件更新：

sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock >= 1;
-- 影响行数为 0：库存不足，回滚或返回业务错误

第 3 步：SELECT FOR UPDATE 的适用场景 ​

当新值依赖多行数据时，单条原子 UPDATE 不够：

sql
BEGIN;
-- 锁住账户行，其他事务的 FOR UPDATE 会等待
SELECT balance_cents FROM accounts WHERE id = 1 FOR UPDATE;
-- 在应用里做复杂计算，例如手续费、限额、风控
UPDATE accounts SET balance_cents = :new_balance WHERE id = 1;
COMMIT;

FOR UPDATE 会阻塞其他写和 FOR UPDATE 读，所以事务要短；不要在锁住之后调外部接口。

真实输出：

text
== 5. 死锁：两个事务以相反顺序锁两行 ==
ERROR:  deadlock detected
DETAIL:  Process 216 waits for ShareLock on transaction 763; blocked by process 223.
Process 223 waits for ShareLock on transaction 762; blocked by process 216.
HINT:  See server log for query details.

一个事务被中止，另一个继续。应用层要这样处理：

ts
// 伪代码：只重试可恢复的并发错误
for (let attempt = 0; attempt < 3; attempt++) {
  try {
    return await manager.transaction(work);
  } catch (error) {
    if (!isRetryableTransactionError(error)) throw error; // 40P01 / 40001
    await sleep(20 * 2 ** attempt);
  }
}

不要重试所有错误：唯一约束冲突、参数错误重试多少次都一样。

第 5 步：在 NestJS / TypeORM 里传事务管理器 ​

ts
async create(dto: CreateUserDto, actorId: string | null = null): Promise<PublicUser> {
  const email = dto.email.trim().toLowerCase();
  // 哈希是 CPU 密集操作，放在事务外，避免占着连接等计算
  const passwordHash = await hashPassword(dto.password);

  try {
    return await this.users.manager.transaction(async (manager) => {
      const saved = await manager.save(
        manager.create(UserEntity, {
          email,
          name: dto.name,
          role: dto.role ?? 'member',
          passwordHash,
        }),
      );

      await this.auditService.record(
        {
          action: 'user.created',
          actorId: actorId ?? saved.id,
          targetId: saved.id,
          summary: `用户 ${saved.email} 注册成功`,
        },
        manager,
      );

      return toPublicUser(saved);
    });
  } catch (error) {
    if (isUniqueViolation(error)) {
      throw new ConflictException({
        code: 'EMAIL_TAKEN',
        message: '该邮箱已被注册',
        details: { email },
      });
    }
    throw error;
  }
}

manager.transaction(cb) 里的 manager 是事务内的管理器。常见错误是回调里继续用 this.users.save()，那会走仓储自己的连接，可能不在同一事务里。把 manager 作为参数传给其他 Service，才能保证它们共享同一个事务（详见 04 数据层）。

bash

常见坑与排查 ​

现象根因处理
扣款成功、加款失败，账不平两条 UPDATE 不在同一事务用 BEGIN ... COMMIT 包住；或 ORM 的 manager.transaction
并发下余额少加了一次读—算—写丢失更新改成原子增量、FOR UPDATE 或乐观锁
deadlock detected两个事务加锁顺序相反统一按主键升序加锁；应用重试
could not serialize access due to concurrent updateRR / Serializable 下并发改了同一行重试整个事务；不要只重试单条 SQL
连接池被耗尽事务里有慢 HTTP 调用，或忘了 COMMIT事务内只做 DB 操作；设置 idle_in_transaction_session_timeout
表越来越大、VACUUM 不回收长事务持有旧快照查 pg_stat_activity，杀掉长事务，缩短事务
FOR UPDATE 之后所有请求都卡住锁范围太大或事务太长只锁必要行；尽快提交；考虑乐观锁
事务里发消息，回滚后消息已发出消息不在事务内用 Outbox 表 + 异步投递（第 08 章）
隔离级别调到 SERIALIZABLE 后频繁报错冲突检测更严格保留重试逻辑；或降低级别 + 行锁/原子写
以为 MySQL RR 与 PG RR 一样InnoDB 用 next-key lock，PG 用快照第 10 章专门对照，不要直接套用结论

企业级做法 ​

  1. 事务只包数据库写入：外部调用、发消息、文件 IO 全部移到事务外，跨系统一致性用 Outbox / Saga。
  2. 默认 READ COMMITTED，按需升级：大多数业务用原子写与行锁就够；只有真正的跨行不变量才用 SERIALIZABLE，并配套重试。
  3. 所有可重试错误统一封装：40P01（死锁）、40001（序列化失败）、连接中断，走指数退避；业务错误不重试。
  4. 加锁顺序写进规范：批量更新按主键排序；多表操作按固定表顺序。
  5. 库存、余额用条件更新：WHERE stock >= n / WHERE balance >= n，以影响行数判断成败，避免「先查再扣」。
  6. 给事务设置超时：statement_timeout、lock_timeout、idle_in_transaction_session_timeout 三件套，防止一个坏事务拖垮全库。
  7. 监控长事务与锁等待：pg_stat_activity、pg_locks、pg_blocking_pids() 做成看板（第 09 章）。
  8. 测试并发而不是只测单线程：用两个连接复现丢失更新与死锁，验证重试逻辑真的生效。

练习与验收标准 ​

练习

  1. 在 03-basic-transaction.sql 中制造一次「第二条 UPDATE 失败」，确认第一条也被回滚。
  2. 用 SELECT ... FOR UPDATE 改写转账，两个会话并发执行，确认不会丢失更新。
  3. 给 accounts 加 version 字段，用乐观锁实现转账；冲突时返回可重试错误。
  4. 把 run-isolation-demo.sh 的死锁段改成「统一按 id 升序加锁」，确认不再出现死锁。
  5. 开一个事务后不提交，另开会话查 pg_stat_activity，观察 idle in transaction 与 xact_age。

验收标准

  • [ ] 单会话脚本输出中，回滚后的余额与提交后一致；
  • [ ] READ COMMITTED 演示中 A 两次读到不同值；REPEATABLE READ 中两次读到相同值；
  • [ ] 丢失更新演示能观察到一次更新被覆盖；
  • [ ] 原子增量演示的最终余额等于两次增量之和；
  • [ ] 死锁演示能稳定复现 deadlock detected；
  • [ ] 能在 pg_stat_activity 中识别 idle in transaction；
  • [ ] 能说出至少两种修复丢失更新的方式及各自适用场景。
