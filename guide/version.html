二、NestJS 12 三个会影响写法的事实 ​

这三点都不是「新特性」，而是会直接让你复制旧教程代码报错的变化：

1. 纯 ESM ​

@nestjs/common 的 package.json 里是 "type": "module"，没有 CommonJS 入口。后果：

  • 工程要写 "type": "module"；
  • 相对导入必须带 .js 后缀（哪怕源文件是 .ts）；
  • 只支持 CommonJS 的测试器（如传统 Jest 配置）会报 ERR_REQUIRE_ESM，示例改用 Vitest；
  • __dirname 不可用，需要时用 import.meta.url 换算。

2. 官方模板的 tsconfig 是 nodenext ​

关键项：module: "nodenext"、moduleResolution: "nodenext"、isolatedModules: true、target: "ES2023"。 在 isolatedModules + emitDecoratorMetadata 同时开启时，装饰器签名里引用的类型必须用 import type 导入，否则编译器报 TS1272。示例代码里 DTO、Controller 的返回类型都按这个规则写。

3. 脚手架默认工具链换成了 Vitest + oxlint ​

用 @nestjs/cli 12 生成的新项目，package.json 里测试是 vitest run、Lint 是 oxlint。本仓库测试用 Vitest（与官方一致），Lint 用 ESLint（生态更成熟、规则可读性更好），属于有意识的取舍，不是照抄模板。

三、官方更新后怎么自查 ​

按下面的顺序做，10 分钟内能得到「我的教程/项目哪里会坏」。

步骤 1：看本仓库实际装了什么 ​

bash
pnpm --filter @nestjs-tutorial/api list --depth 0

步骤 2：看远端最新版本 ​

bash
npm view @nestjs/core version
npm view @nestjs/core engines

官方发布记录里重点看两件事：主版本号是否变化、是否出现 breaking change 标注。

步骤 3：用官方模板做对照实验 ​

这是最可靠的一步——直接看官方此刻怎么配置一个新项目：

bash
cd /tmp && npx @nestjs/cli@latest new ref-app --package-manager pnpm --skip-git --skip-install
cat /tmp/ref-app/package.json
cat /tmp/ref-app/tsconfig.json
ls /tmp/ref-app   # 看测试配置文件叫什么

对照下面四项，任何一项不同，本教程相关章节就要复核：

对照项本教程的取值不同意味着什么
package.json 是否有 "type": "module"有若取消，.js 后缀与 Vitest 选择都要重估
tsconfig.json 的 module / moduleResolutionnodenext / nodenext若改回 commonjs，第 01 章的导入规则整节失效
测试运行器Vitest若换回 Jest，第 12 章要重写
装饰器相关编译选项emitDecoratorMetadata + experimentalDecorators若改用标准装饰器，全书的 DI 写法都要复核

步骤 4：跑一遍本仓库门禁 ​

bash
pnpm install
pnpm verify

verify 覆盖 lint、类型检查、单测、e2e、构建与文档构建。升级依赖后如果它仍然全绿，说明写作层面的结论大概率还成立；红了就先修代码，再回来改文档。

步骤 5：确认 ESM 这一条是否仍成立 ​

bash
node -e "const p=require('@nestjs/common/package.json');console.log(p.type, p.exports)"

输出 module 说明仍是纯 ESM，第 01 章关于 .js 后缀、import type、Vitest 的结论继续有效。

四、本教程刻意不写的东西 ​

不写原因
具体性能数字（QPS、耗时对比）没有在同一台机器、同一负载下实测过；只在第 07 章讲机制与测量方法
「某版本之后才支持」的模糊说法除非能在官方发布记录里指到具体条目，否则不写
平台限制（连接数、文件大小上限）与部署环境强相关，放到第 13 章讲如何实测
未实现的业务代码企业级业务页会明确标注「设计讲解，示例未实现」

五、更新本页的流程 ​

  1. 升级依赖，pnpm verify 全绿；
  2. 按上面的「步骤 3」重做一次模板对照；
  3. 更新本页版本表、最后核对时间、以及受影响章节的 ChapterMeta；
  4. 如果变化影响写法（如 ESM、装饰器），同步修改相关章节正文，而不是只改版本号。
