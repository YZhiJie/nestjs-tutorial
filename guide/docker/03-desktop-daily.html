03 Docker Desktop 日常使用：面板、日志、终端与 CLI 对照 ​

面板与 CLI 的逐项对照、日志来源、exec 与 attach 的差别，以及 stats/inspect/history 的排障用法。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 把 Docker Desktop 面板上的每个常用按钮，对应到一条可复制的 CLI 命令；
  2. 区分 docker logs 与「进容器看日志文件」，知道为什么后者经常什么都看不到；
  3. 说清 docker exec 与 docker attach 的差别，避免一次 Ctrl+C 把服务停掉；
  4. 用 docker stats、docker inspect、docker image history 快速定位「谁在吃 CPU」「端口为什么没通」「镜像为什么这么大」；
  5. 用 docker desktop 系列命令管理桌面端本身，而不只是管理容器。

概念与原理 ​

面板是 CLI 的一层封装，不是另一套系统 ​

Docker Desktop 面板的每个视图，背后都是同一套 Engine API：

面板位置等价 CLI说明
Containers 列表docker ps -a状态、端口、镜像、启动时间
容器详情 → Logsdocker logs -f <容器>只包含 stdout / stderr
容器详情 → Inspectdocker inspect <容器>JSON，可用 --format 取字段
容器详情 → Statsdocker stats <容器>CPU、内存、网络、磁盘 IO
容器详情 → Terminaldocker exec -it <容器> sh新开一个进程，不是「接管」主进程
容器详情 → Filesdocker cp <容器>:<路径> .浏览与导出容器内文件
Images 列表docker image ls大小、标签、创建时间
Images → 分层docker image history <镜像>每条 Dockerfile 指令的大小
Volumesdocker volume ls / inspect命名卷与挂载点
Buildsdocker buildx du / docker build 输出构建记录与缓存

先学 CLI 再看面板：面板不会告诉你它执行了哪条命令，而 CLI 可以贴进 issue、写进脚本、放进 CI。反过来，面板适合快速浏览和点按钮，不适合精确复现。

日志从哪里来 ​

Docker 收集的是容器 PID 1 及其子进程写到 stdout / stderr 的内容，由日志驱动（默认 json-file）落到宿主机磁盘。两个直接推论：

  • 应用把日志写进 /var/log/app.log，docker logs 看不到，除非你另外挂载或改用日志驱动；
  • 容器删除后，日志默认一起删除。要长期保留就得接 ELK / Loki / 云日志，或者至少配置轮转。

json-file 默认不限制大小。一个每请求打一行日志的服务跑几周，就能把 Docker 的虚拟磁盘写满。所以本仓库的 compose 和示例都显式配置了 max-size / max-file：

yml
# 03 章：把演示服务按「面板里能看到的每一项」配好，方便 CLI 对照。
services:
  demo:
    build:
      context: .
    image: docker-guide/03-desktop-cli:local
    container_name: docker-guide-03
    # 宿主机 18080 → 容器 8080，避免和仓库 API 的 3000 端口打架
    ports:
      - '127.0.0.1:18080:8080'
    environment:
      PORT: 8080
    # 日志轮转：默认 json-file 驱动不限制大小，长期运行会把磁盘吃满
    logging:
      driver: json-file
      options:
        max-size: '10m'
        max-file: '3'
    healthcheck:
      test:
        - CMD
        - node
        - -e
        - "fetch('http://127.0.0.1:8080/healthz').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 3s
    restart: unless-stopped

exec 与 attach 不是一回事 ​

text
docker exec -it 容器 sh   →  在容器里新起一个 shell 进程（PID 不是 1）
docker attach 容器        →  把终端接到 PID 1 的标准输入输出上

attach 时按 Ctrl+C，信号发给 PID 1，服务就停了；exec 里按 Ctrl+C 只影响你开的那个 shell。日常排查一律用 exec，attach 只在需要直接给主进程喂输入时使用（例如某些交互式 CLI）。

CPU 百分比可以超过 100% ​

docker stats 的 CPU % 是按「单核 = 100%」累计的。一个进程吃满 2 个核就显示 200%。别看到 180% 就以为出 bug，先看容器限制了几核。

最小可跑示例 ​

一、构建并启动演示服务 ​

示例是一个零依赖 Node 服务，会输出结构化 JSON 日志：

dockerfile
# 03 章演示镜像：一个零依赖的 Node HTTP 服务。
# 构建：docker build -t docker-guide/03-desktop-cli:local examples/docker/03-desktop-cli
FROM node:24-alpine

# WORKDIR 会创建目录并作为后续指令的工作目录，避免到处写绝对路径
WORKDIR /app

ENV NODE_ENV=production \
    PORT=8080

# 先复制源码再切用户：本例没有依赖安装，顺序影响不大；
# 但养成「不把 root 写权限留给运行进程」的习惯
COPY app/server.mjs ./server.mjs

# 创建无特权用户：容器内 uid 1000 左右，即使逃逸也不是宿主机的 root
RUN addgroup -S app && adduser -S app -G app
USER app

EXPOSE 8080

# 健康检查用 Node 自带的 fetch，不额外安装 curl
HEALTHCHECK --interval=10s --timeout=3s --start-period=3s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:8080/healthz').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

# 直接以 node 为 PID 1，SIGTERM 才能直达进程
CMD ["node", "server.mjs"]
bash
docker compose -f examples/docker/03-desktop-cli/compose.yaml up -d --build
docker compose -f examples/docker/03-desktop-cli/compose.yaml ps

本机真实输出：

text
NAME              IMAGE                               STATUS                    PORTS
docker-guide-03   docker-guide/03-desktop-cli:local   Up 15 seconds (healthy)   127.0.0.1:18080->8080/tcp

(healthy) 来自 compose 里的 healthcheck，不是「进程还在」的同义词。

二、制造一点可观察的流量 ​

bash
curl -s http://127.0.0.1:18080/
curl -s 'http://127.0.0.1:18080/work?ms=300'
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/boom
text
{"service":"docker-guide-03","hostname":"e840a40ba0ea","requestId":1,"path":"/"}
{"sleptMs":300,"requestId":2}
500

第三个请求故意返回 500，用来观察日志级别和 docker stats 的变化。

四、优雅停止，观察 SIGTERM ​

bash
docker stop docker-guide-03
docker logs --tail 3 docker-guide-03
json
{"time":"...","level":"info","message":"request handled","method":"GET","path":"/healthz","status":200,"durationMs":0,"requestId":5}
{"time":"...","level":"info","message":"shutting down","signal":"SIGTERM"}

docker stop 先发 SIGTERM，默认等 10 秒；应用没退出才 SIGKILL。日志里出现 shutting down，说明 PID 1 正确接收了信号。如果每次都等满 10 秒，通常是应用没有处理 SIGTERM，或者 PID 1 是 shell 而不是 node。

逐步拆解 ​

第 1 步：docker ps 的每一列怎么看 ​

bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
  • STATUS 里的 Up 15 seconds (healthy) 由 healthcheck 决定；没有 healthcheck 就只有 Up；
  • PORTS 的 127.0.0.1:18080->8080/tcp 是「宿主机 → 容器」，左边是宿主机；
  • 容器内 PID 1 是 node server.mjs，宿主机看到的 PID 是另一个数字（本例 43243），这是两个不同的 PID 命名空间。

第 2 步：日志的三个常用参数 ​

bash
docker logs --tail 100 -f docker-guide-03        # 最近 100 行并持续跟踪
docker logs --since 10m docker-guide-03          # 最近 10 分钟
docker logs --timestamps docker-guide-03          # 每行前加时间戳

docker compose logs -f demo 等价于按服务名过滤，还会带上 compose 的启动日志。日志很多时先 --tail，不要一上来就全量输出。

第 3 步：inspect 只取你要的字段 ​

docker inspect 的完整 JSON 有几百行。用 --format 取字段：

bash
docker inspect docker-guide-03 --format '{{.State.Status}} {{.State.Pid}} {{.RestartCount}}'
docker inspect docker-guide-03 --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
docker inspect docker-guide-03 --format '{{json .Config.Env}}' | jq

排查「端口为什么不通」时，先看 .NetworkSettings.Ports 和进程是否监听 0.0.0.0：

bash
docker exec docker-guide-03 node -e "console.log(process.env.PORT)"
docker port docker-guide-03

第 4 步：stats 的正确用法 ​

bash
docker stats --no-stream docker-guide-03

--no-stream 打印一次就退出，适合写进脚本；不加会持续刷新，按 q 退出。要看历史曲线，用面板或接 Prometheus，docker stats 不保存历史。

第 5 步：进容器排查，而不是靠猜 ​

bash
docker exec -it docker-guide-03 sh
# 容器内：
pwd; id; ps -o pid,ppid,user,args; ls -la /app

ps 里能看到 PID 1 是 node server.mjs，你开的 sh 是另一个 PID。容器里通常没有 ps 以外的工具，Alpine 镜像只有 busybox，别指望 top、netstat 全都可用。

第 6 步：管理 Docker Desktop 本身 ​

bash
docker desktop status
docker desktop version
docker desktop logs --help

本机真实输出：

text
Name                Value
Status              running
SessionID           65cf1dbe-ab9e-407e-97a1-36364194d364

docker desktop stop / start / restart 可以在不点托盘图标的情况下操作桌面端；docker desktop diagnose 会打包诊断信息，提 issue 时比截图有用。

常见坑与排查 ​

现象根因排查与修复
面板里有日志，docker logs 没有看的是不同容器，或命令打到了别的 contextdocker context show；docker ps 核对容器名
docker logs 只有启动那几行应用把日志写进文件而不是 stdout改成 stdout，或挂载日志目录后用 tail 看
日志把磁盘写满json-file 默认不轮转compose 加 logging.options.max-size / max-file
docker exec 报 container is not running容器已退出先 docker ps -a 看退出码，再 docker logs 看原因
docker exec -it 报 the input device is not a TTY在 CI / 管道里执行去掉 -t，只保留 -i，或改用 docker exec 非交互命令
attach 后 Ctrl+C 服务停了信号直接发给 PID 1日常用 exec；attach 退出用 Ctrl+P Ctrl+Q
docker stats CPU 超过 100%多核累计正常；结合 --cpus 限制与宿主机核数理解
面板 Terminal 里 apk add 很慢或失败容器内没有包管理源 / 网络受限不要在运行中的容器装工具；改镜像或单独起调试容器
宿主机改了代码，容器里没变没有挂载，或挂载路径写错docker inspect --format '{{json .Mounts}}' 核对
docker cp 报路径不存在容器内路径写错，或容器已删除docker exec <容器> ls 先确认；删除后无法再拷

三个命令覆盖八成日常排查

docker ps -a 看状态 → docker logs --tail=100 <容器> 看输出 → docker exec -it <容器> sh 看现场。面板只是这三步的可视化，顺序不要反。

企业级做法 ​

  1. 日志统一走 stdout，收集交给平台：应用只负责打印，轮转和归档交给 Docker 日志驱动或 Loki / ELK，别在容器里自己切文件。
  2. 给所有服务配日志上限：max-size: 10m、max-file: 3 是开发环境的合理默认值；生产按采集方案调整。
  3. 排查步骤写成 runbook：把 ps / logs / inspect / exec 四条命令和常见退出码写进值班文档，减少「凭感觉重启」。
  4. 镜像里装好排查工具：需要 curl、ps、dig 时在构建阶段装，而不是运行中 apk add；后者不可复现，还会污染容器。
  5. 区分交互与自动化：CI 里禁止 -it 和 attach；脚本里用 --no-stream、--format、--quiet 这类确定性输出。
  6. 用 docker desktop diagnose 而不是截图：桌面端问题让用户提供诊断包，包含版本、日志、设置，比聊天记录可靠。
  7. 定期清理构建记录与旧容器：面板的 Builds 列表不是无限免费，第 04 章给出安全清理顺序。

练习与验收标准 ​

练习

  1. 用 docker logs --since 1m --timestamps 观察 /healthz 的探测频率，解释 healthcheck 的 interval 如何体现。
  2. 进入容器执行 ps -o pid,ppid,user,args，指出 PID 1、你开的 shell、healthcheck 进程三者的关系。
  3. 把 compose 里的 logging 段删掉，重建容器，用 docker inspect --format '{{json .HostConfig.LogConfig}}' 观察差异。
  4. 故意让服务监听 127.0.0.1:8080（改 server.mjs 的 listen 地址），重建后从宿主机 curl，记录现象并解释。

验收标准（可逐条执行）

  • [ ] docker compose -f examples/docker/03-desktop-cli/compose.yaml ps 显示 (healthy)；
  • [ ] curl http://127.0.0.1:18080/healthz 返回 {"status":"ok",...}；
  • [ ] docker exec docker-guide-03 node -e "console.log(process.getuid?.())" 输出 100；
  • [ ] docker stop docker-guide-03 后，docker logs --tail 1 能看到 shutting down 与 SIGTERM；
  • [ ] 能说出面板 Logs / Terminal / Stats 分别对应哪条 CLI；
  • [ ] 能解释为什么 attach 里按 Ctrl+C 会停服务，而 exec 不会。
