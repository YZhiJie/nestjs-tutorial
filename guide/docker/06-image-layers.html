06 镜像分层、构建缓存与多阶段构建瘦身 ​

用 --progress=plain 看懂缓存命中，三阶段构建配合 pnpm deploy --prod，把镜像从 655MB 压到 407MB。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 用 docker build --progress=plain 看懂哪些层命中缓存、哪些层重跑；
  2. 通过一个可复现的实验，证明 COPY 顺序会直接改变依赖安装层是否缓存；
  3. 写出三阶段 Dockerfile：依赖层、构建层、运行层各司其职；
  4. 用 pnpm deploy --prod 把 devDependencies 挡在运行镜像之外；
  5. 把第 05 章的 655 MB 单阶段镜像压到 407 MB，并说清每一部分是怎么省下来的。

概念与原理 ​

缓存键由「指令 + 输入」决定 ​

Docker 判断一层能否复用，看的是：

text
父层 ID + 指令内容 + 该指令涉及的文件内容

对 COPY 来说，涉及的是被复制文件的内容和元数据；对 RUN 来说，涉及的是命令字符串和父层。因此：

  • 改 src/index.js 不会让 COPY package.json 失效，也不会让 RUN pnpm install 失效；
  • 改 pnpm-lock.yaml 会让 COPY 层失效，进而让 RUN pnpm install 重跑；
  • 在 COPY . . 之后执行安装，任何源码改动都会让安装层重跑。

这不是 Docker 的「优化技巧」，而是层模型的直接结果。理解模型，就不需要背「先 COPY 什么后 COPY 什么」。

多阶段构建不是在同一个镜像里删文件 ​

dockerfile
FROM node:24-alpine AS deps      # 阶段 1：装依赖
FROM deps AS build               # 阶段 2：编译 + 裁剪依赖
FROM node:24-alpine AS runtime   # 阶段 3：只复制产物

最终镜像只包含最后一个阶段。前两个阶段留在构建缓存里，不会进入运行镜像。不要用「装完再 rm -rf」的方式瘦身：被删除的文件仍然存在于之前的层里，镜像体积不会变小，只是看不到了。

pnpm deploy --prod 做了什么 ​

bash
pnpm --filter @nestjs-tutorial/api deploy --prod --legacy /prod/api

它把指定 workspace 包的生产依赖解析成一个自包含目录 /prod/api：

  • node_modules 只含 dependencies，不含 devDependencies；
  • 不会再依赖仓库根目录的 node_modules 软链接结构；
  • --legacy 是当前 pnpm 版本对非 injected workspace 的兼容开关。

对比第 05 章：单阶段镜像的 node_modules 是 279.2 MB，多阶段的运行层只有 134.4 MB。差的 145 MB 主要是 TypeScript、Vitest、ESLint、VitePress 等开发工具。

镜像大小不是「所有层的简单相加」 ​

docker image ls 显示的是镜像在当前机器上的实际占用，共享的基础层只算一次。所以：

  • 两个镜像都基于 node:24-alpine，这部分的实际磁盘只存一份；
  • 单阶段 655 MB、多阶段 407 MB，差的是这个镜像额外带的层；
  • 推送时 registry 也按层去重，但拉取方如果没有基础层，仍要下载。

COPY --chown 为什么放在 COPY 里 ​

dockerfile
RUN addgroup -S app && adduser -S app -G app
COPY --chown=app:app --from=build /prod/api/node_modules ./node_modules

如果先 COPY 再 RUN chown -R app:app /app，chown 会把整个 node_modules 复制成一个新层，镜像可能直接翻倍。--chown 在复制时就设置属主，不产生额外层。

最小可跑示例 ​

一、多阶段 Dockerfile ​

dockerfile
# 06 章：多阶段构建版 —— 只把「运行需要的东西」带进最终镜像。
# 构建命令（context 仍是仓库根目录）：
#   docker build -f examples/docker/06-multistage/Dockerfile -t docker-guide/06-multistage:multi .
# 与 05 章单阶段版的区别：编译工具、源码、devDependencies 都留在构建层，不进运行层。

# ---------- 依赖层 ----------
# 只复制清单文件：源码变化不会让 pnpm install 缓存失效
FROM node:24-alpine AS deps
ENV PNPM_HOME=/pnpm
ENV PATH=/pnpm:$PATH
RUN corepack enable
WORKDIR /repo
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/api/package.json apps/api/package.json
RUN pnpm install --frozen-lockfile

# ---------- 构建层 ----------
FROM deps AS build
WORKDIR /repo
# 这里才复制源码；上一层的依赖安装结果被复用
COPY . .
RUN pnpm --filter @nestjs-tutorial/api build
# deploy 会按 dependencies 重新解析出一个扁平目录，
# TypeScript、Vitest、VitePress 这些 devDependencies 不会进来
RUN pnpm --filter @nestjs-tutorial/api deploy --prod --legacy /prod/api

# ---------- 运行层 ----------
# 基于干净的 node 镜像，不带源码、不带编译工具链
FROM node:24-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app

# 先建非 root 用户，再 COPY --chown 落文件。
# 如果先 COPY 再 chown -R，会把几百 MB 依赖整层复制一遍，镜像直接胖一倍。
RUN addgroup -S app && adduser -S app -G app

COPY --chown=app:app --from=build /prod/api/node_modules ./node_modules
COPY --chown=app:app --from=build /prod/api/package.json ./package.json
COPY --chown=app:app --from=build /repo/apps/api/dist ./dist

USER app

EXPOSE 3000

# 就绪探针而不是存活探针：依赖没起来时容器不应接流量
HEALTHCHECK --interval=10s --timeout=3s --start-period=20s --retries=5 \
  CMD node -e "fetch('http://127.0.0.1:3000/api/health/ready').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

# 用 node 直接启动，让 SIGTERM 直达进程，而不是经过 pnpm 多一层转发
CMD ["node", "dist/main.js"]

三、缓存实验：同一份源码，两种 COPY 顺序 ​

dockerfile
# 正确顺序：先复制清单并「安装依赖」，再复制源码。
# 依赖层只依赖 package.json，改 src/ 不会让它失效。
FROM node:24-alpine
WORKDIR /app

COPY package.json ./
# 用 sleep 模拟一次耗时的依赖安装；真实项目这里是 RUN pnpm install --frozen-lockfile
RUN echo "simulate dependency install" && sleep 1

COPY src ./src
CMD ["node", "src/index.js"]
dockerfile
# 错误顺序：先 COPY 全部源码，再安装依赖。
# 任何源码改动都会让 COPY 层失效，导致后面的安装层每次都重跑。
FROM node:24-alpine
WORKDIR /app

COPY . .
RUN echo "simulate dependency install" && sleep 1

CMD ["node", "src/index.js"]
bash
bash examples/docker/06-multistage/scripts/cache-experiment.sh

本机真实输出（节选）：

text
===== good：第一次构建（无缓存）=====
#8 [4/5] RUN echo "simulate dependency install" && sleep 1
#8 0.069 simulate dependency install

===== good：只改源码后重建（依赖层应命中缓存）=====
#8 CACHED

===== bad：第一次构建（无缓存）=====
#8 [4/4] RUN echo "simulate dependency install" && sleep 1
#8 0.067 simulate dependency install

===== bad：只改源码后重建（依赖层重新执行）=====
#8 0.069 simulate dependency install

同一份源码改动量，good 的安装层命中缓存，bad 的安装层重新执行。真实项目里这一步是 pnpm install，差的是几十秒到几分钟。

四、确认多阶段镜像能运行 ​

bash
docker run --rm --entrypoint sh docker-guide/06-multistage:multi -c 'id; node -e "console.log(process.version)"'
text
uid=100(app) gid=101(app) groups=101(app),101(app)
v24.22.2

多阶段镜像没有 sqljs（被 --prod 裁掉了），所以不能像第 05 章那样脱离数据库启动。完整启动在第 08 章用 Postgres + Redis 验证。

逐步拆解 ​

第 1 步：读构建输出，找 CACHED ​

bash
docker build --progress=plain -f examples/docker/06-multistage/Dockerfile \
  -t docker-guide/06-multistage:multi . 2>&1 | tee /tmp/build.log

关注三类行：

  • CACHED：这一层复用了缓存；
  • DONE 0.8s：这一层实际执行了；
  • exporting attestation manifest：BuildKit 默认生成来源证明（provenance），不是镜像内容。

第二次构建时，deps 阶段的 pnpm install 应该是 CACHED，build 阶段的编译可能因源码变化而重跑。

第 2 步：为什么把 COPY . . 放在依赖安装之后 ​

deps 阶段只复制三个清单文件，因此依赖层只受锁文件影响。build 阶段才复制全部源码：

dockerfile
FROM deps AS build
COPY . .
RUN pnpm --filter @nestjs-tutorial/api build

这不是「少复制几次」的微优化，而是把「变化频率不同的输入」分到不同层：

输入变化频率放在哪一层
基础镜像最低FROM
依赖清单 / 锁文件低deps 的 COPY
业务源码高build 的 COPY

第 3 步：deploy --prod 生成的目录长什么样 ​

bash
docker run --rm --entrypoint sh docker-guide/06-multistage:multi -c 'ls /app; du -sh /app/node_modules; ls /app/node_modules | head'

运行层只有 dist、node_modules、package.json 三项。没有 src、没有 tsconfig.json、没有 vitest.config.ts，也没有 pnpm 的 workspace 链接。

第 4 步：COPY --chown 与用户 ​

dockerfile
RUN addgroup -S app && adduser -S app -G app
COPY --chown=app:app --from=build /prod/api/node_modules ./node_modules
...
USER app

顺序很重要：先建用户，再带 --chown 复制，最后 USER app。如果先复制再 chown -R，会多出一层与依赖同样大的文件；如果忘了 USER app，即使文件属主是 app，进程仍然以 root 运行。

验证：

bash
docker run --rm --entrypoint id docker-guide/06-multistage:multi

第 5 步：HEALTHCHECK 用 ready 还是 live ​

多阶段 Dockerfile 用的是 /api/health/ready：

  • live 只证明进程活着，依赖全挂也可能返回 200；
  • ready 会检查数据库 / 缓存，依赖没起来时返回非 200，编排系统不会把流量导进来。

本地单容器没有依赖时，ready 会失败；这正是第 08 章要用 compose 把 Postgres / Redis 一起起起来的原因。

第 6 步：体积还可以怎么继续降 ​

本章已经完成的：

  • 多阶段：编译工具链不进运行层；
  • --prod：devDependencies 不进运行层；
  • 非 root 用户：不是体积优化，但同属运行层设计。

还可以做但本章不展开的：

  • 更小的基础镜像（distroless / alpine + 只装运行时）；
  • 把 node_modules 进一步裁剪（只保留实际 import 的包）；
  • 用 BuildKit cache mount 加速安装，但不减小最终镜像；
  • 用 docker buildx build --sbom --provenance 生成 SBOM 与来源证明（第 10、12 章）。

常见坑与排查 ​

现象根因排查与修复
改一行源码，pnpm install 又跑了几分钟COPY . . 在安装之前调整顺序：清单 → 安装 → 源码
只改了锁文件，所有层都重跑这是预期行为，锁文件是依赖层的输入不需要修；把锁文件变更单独提交，便于定位
pnpm deploy 报 workspace 相关错误pnpm 版本与 workspace 配置不兼容使用 --legacy；确认根 package.json 的 packageManager 版本
运行镜像缺包，启动报 Cannot find module包在 devDependencies，但运行时需要把它移到 dependencies；不要靠关闭 --prod 掩盖
COPY --chown 后仍然 permission denied目录属主对，但文件是只读或进程用户不对ls -ln 核对；确认 USER 与 --chown 一致
多阶段镜像启动失败，日志提示缺 sql.js--prod 裁掉了仅用于本地演示的依赖本地冒烟用第 05 章单阶段；完整依赖用第 08 章 compose
docker image ls 大小和 docker history 之和对不上基础层共享、层压缩、元数据看「镜像额外层」而不是简单相加
CI 里缓存完全不生效CI 每次都是新 runner，本地缓存不存在配置 registry / GitHub Actions 缓存后端，见第 10 章
镜像还是很大，但 history 每层都不大基础镜像本身大，或有未清理的层换更小的基础镜像；检查是否在早期层装了大量工具
用 rm -rf 删了文件，体积没变删除发生在新的层里，旧层仍保留文件把「安装 + 使用 + 删除」放在同一条 RUN，或用多阶段

不要用「删文件」来瘦身

RUN apt-get install ... && rm -rf /var/lib/apt/lists/* 之所以有效，是因为安装和删除在同一条 RUN；分成两条指令时，安装层仍然保留全部文件。

企业级做法 ​

  1. 所有生产镜像必须多阶段：构建工具、源码、测试依赖都不应进入运行层。
  2. 基础镜像固定 digest：node:24-alpine 仍会随上游更新；关键服务固定到 digest，升级走显式变更。
  3. 依赖与源码分层：把锁文件变更与业务变更分开，构建缓存才有意义；CI 缓存后端要配。
  4. 运行层最小权限：非 root、只读根文件系统、no-new-privileges（第 12 章）。
  5. 镜像大小纳入门禁：给关键服务设体积阈值，超过就阻断合并；体积突然翻倍通常意味着误把工具装进运行层。
  6. 保留 provenance / SBOM：构建产物要能回答「这个镜像从哪来、包含哪些包」，第 10、12 章展开。
  7. 不要在 Dockerfile 里 git clone 私有仓库：构建上下文应自包含，私有依赖走 registry + 构建密钥。

练习与验收标准 ​

练习

  1. 把 examples/docker/06-multistage/Dockerfile 的 deps 阶段改成 COPY . .，连续构建两次，记录 pnpm install 是否重跑。
  2. 在 cache-demo 里改 package.json 的 version，观察 good 的安装层是否失效，并解释原因。
  3. 给多阶段 Dockerfile 增加一个 FROM runtime AS debug 阶段，装上 curl 与 ps，比较它与生产阶段的大小。
  4. 用 docker image history 找出多阶段镜像里最大的三层，分别说明它们来自哪个阶段。

验收标准（可逐条执行）

  • [ ] docker image ls docker-guide/06-multistage:multi 显示镜像存在，且体积明显小于单阶段（本机 407 MB vs 655 MB）；
  • [ ] docker run --rm --entrypoint sh docker-guide/06-multistage:multi -c 'id' 输出 uid 100；
  • [ ] docker run --rm --entrypoint sh docker-guide/06-multistage:multi -c 'ls /app' 只有 dist、node_modules、package.json；
  • [ ] bash examples/docker/06-multistage/scripts/cache-experiment.sh 中，good 第二次构建的安装层显示 CACHED，bad 第二次构建重新执行；
  • [ ] 能解释「多阶段构建」与「在单阶段里 rm 文件」为什么结果不同；
  • [ ] 能说出 pnpm deploy --prod 裁掉了什么，以及运行时缺包时应该改什么而不是关掉 --prod。
