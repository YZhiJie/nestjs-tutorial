04 Docker Desktop 资源、磁盘、文件共享与代理排障 ​

虚拟机资源上限、磁盘占用盘点与清理、bind mount 与命名卷的实测对比，以及文件共享与三层代理排查。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清 Docker Desktop 的 CPU / 内存 / 磁盘上限限制的是哪台机器，以及为什么调大不一定更好；
  2. 用脚本只读盘点镜像、容器、卷、构建缓存的占用，并按安全顺序清理；
  3. 用真实基准测试判断 bind mount 与命名卷在本机谁更快，而不是照搬「bind mount 一定慢」的旧结论；
  4. 定位文件共享相关的三类问题：改动不同步、权限不对、文件监听不触发；
  5. 把代理配置分清三层：Docker Desktop 自身、构建阶段、容器运行时。

概念与原理 ​

资源限制限制的是那台 Linux 虚拟机 ​

第 02 章说过：macOS / Windows 上的容器跑在 Docker Desktop 启动的 Linux 虚拟机里。Settings → Resources 里的 CPU、Memory、Swap、Disk image size 全部作用于这台虚拟机：

text
宿主机（你的 Mac / PC）
└── Docker Desktop 虚拟机（CPU / 内存 / 磁盘上限在这里）
    ├── 容器 A
    ├── 容器 B
    └── Docker Engine、镜像、卷、构建缓存

三个直接推论：

  • 给虚拟机 8 核，不代表容器能用满 8 核；还要看宿主机当时是否空闲；
  • 容器内存超限会被 OOM Killer 杀掉，退出码常见 137；
  • 磁盘镜像只增不减，删除镜像后虚拟机文件不会自动缩小，需要显式压缩或重建。

磁盘都被谁吃了 ​

docker system df 是第一步：

text
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          20        7         4.874GB   1.735GB (35%)
Containers      11        2         462.8kB   438.3kB (94%)
Local Volumes   7         6         214.8MB   0B (0%)
Build Cache     137       0         6.361GB   988.2MB

四类的含义：

类型内容删除后果
Images镜像层，多个镜像共享基础层删了要重新拉 / 重新构建
Containers已停止容器的可写层容器内未挂载的数据丢失
Local Volumes命名卷，数据库数据通常在这数据不可恢复，最危险
Build Cache构建中间层，用于加速重建下次构建变慢，不影响运行

RECLAIMABLE 是「删掉也不影响正在运行容器」的部分，但不等于「删了没有代价」。清理顺序应该是：构建缓存 → 悬空镜像 → 停止的容器 → 最后才考虑卷。卷永远手动处理，绝不放进自动脚本。

文件共享：VirtioFS、gRPC-FUSE 与 WSL2 ​

容器要看到宿主机代码，靠的是文件共享层：

平台实现特点
macOS（较新）VirtioFS性能接近原生，uid 映射仍由 Docker 决定
macOS（旧）gRPC-FUSE小文件与大量 stat 明显慢
Windows + WSL2（项目在 WSL2 内）原生 ext4最快
Windows + WSL2（项目在 C:\）9P 跨文件系统明显慢，node_modules 安装尤其明显

两个常见误区：

  1. 「bind mount 一定比命名卷慢」：在旧版 gRPC-FUSE 上成立，在 VirtioFS 上不一定。本章示例会实测，本机结果甚至相反；
  2. 「挂载进容器后 uid 还是我」：Docker Desktop 的虚拟化文件共享不保留宿主机 uid，容器内看到的通常是 root（uid 0）。Linux 原生 Docker 才保留 uid，这也是「Mac 上能跑、Linux CI 上权限报错」的常见来源。

文件监听为什么失效 ​

Node / Vite / Nest 的热重载依赖 inotify。文件共享层不一定把宿主机的变更事件转发进容器，于是出现「代码改了，容器里没反应」。三种处理方式：

  • 开发时应用跑在宿主机（本仓库的选择），容器只跑依赖；
  • 容器内用轮询模式（如 CHOKIDAR_USEPOLLING=true），代价是 CPU；
  • 用 compose watch / 同步工具，但会增加一层复杂度。

本仓库选择第一种，原因在第 01 章已经说明：热重载、断点、node --inspect 都不受虚拟化层影响。

代理要分三层 ​

层配置位置影响什么
Docker Desktop 自身Settings → Resources → Proxies，或 admin-settings.json拉镜像、登录 registry
构建阶段docker build --build-arg HTTP_PROXY=... 或 Dockerfile ARGRUN apt-get、pnpm install
容器运行时compose environment 或 .env应用访问外部 API

只配第一层，docker pull 能通，但 RUN pnpm install 可能仍然超时；只配第三层，镜像根本拉不下来。排查时先确认「哪一层在发请求」。

NO_PROXY 同样重要：容器访问同 compose 网络内的服务（postgres、redis）不应该走代理，否则会出现「数据库连不上但 ping 得通」的怪现象。

最小可跑示例 ​

一、只读盘点磁盘 ​

bash
bash examples/docker/04-resources/scripts/disk-report.sh

脚本不会删除任何东西，只打印四类占用、悬空镜像、悬空卷、构建缓存明细和容器可写层大小。

bash
#!/usr/bin/env bash
# 04 章：只读盘点 Docker 占用的磁盘，不做任何删除。
# 用法：bash examples/docker/04-resources/scripts/disk-report.sh
set -euo pipefail

echo '== docker system df =='
docker system df

echo
echo '== 悬空镜像（没有 tag、没有容器引用）=='
docker image ls --filter dangling=true --format '{{.ID}}  {{.Size}}  {{.Repository}}:{{.Tag}}'

echo
echo '== 未被容器使用的卷（dangling）=='
docker volume ls --filter dangling=true --format '{{.Name}}  {{.Driver}}'

echo
echo '== 构建缓存明细（前 10 条记录）=='
docker buildx du --verbose 2>/dev/null | awk 'BEGIN{RS=""} NR<=10 {print $0"\n"}' || echo 'buildx du 不可用，跳过'

echo
echo '== 容器可写层占用（前 10）=='
docker ps -a --size --format '{{.Names}}\t{{.Size}}' | sort -k2 -h | tail -10

二、对比 bind mount 与命名卷 ​

yml
# 04 章：在同一个容器镜像里对比 bind mount 与命名卷的写入吞吐。
# 运行：docker compose -f examples/docker/04-resources/compose.io.yml run --rm bind
services:
  bind:
    image: node:24-alpine
    # 宿主机目录直接挂进容器：改动立刻双向可见，但 macOS/Windows 上要过虚拟化层
    volumes:
      - ./data:/data
      - ./scripts/io-bench.mjs:/opt/io-bench.mjs:ro
    command: ['node', '/opt/io-bench.mjs', '/data', '64']

  named:
    image: node:24-alpine
    # 命名卷由 Docker 管理，落在虚拟磁盘里，不经过宿主机文件系统转发
    volumes:
      - io-data:/data
      - ./scripts/io-bench.mjs:/opt/io-bench.mjs:ro
    command: ['node', '/opt/io-bench.mjs', '/data', '64']

  bind-small:
    image: node:24-alpine
    volumes:
      - ./data:/data
      - ./scripts/io-bench.mjs:/opt/io-bench.mjs:ro
    # 1000 个 4KB 小文件，逐个 fsync
    command: ['node', '/opt/io-bench.mjs', '/data', '1000', 'small']

  named-small:
    image: node:24-alpine
    volumes:
      - io-data:/data
      - ./scripts/io-bench.mjs:/opt/io-bench.mjs:ro
    command: ['node', '/opt/io-bench.mjs', '/data', '1000', 'small']

volumes:
  io-data:

顺序写 64MB：

bash
docker compose -f examples/docker/04-resources/compose.io.yml run --rm bind
docker compose -f examples/docker/04-resources/compose.io.yml run --rm named

小文件写 1000 个 4KB 文件并逐个 fsync：

bash
docker compose -f examples/docker/04-resources/compose.io.yml run --rm bind-small
docker compose -f examples/docker/04-resources/compose.io.yml run --rm named-small

本机真实输出（macOS + Docker Desktop 4.97 + VirtioFS + Apple Silicon）：

json
{"dir":"/data","mode":"seq","writtenMb":64,"elapsedMs":44,"mbPerSecond":1469.7,"blockSize":1048576,"uid":0,"gid":0}
{"dir":"/data","mode":"seq","writtenMb":64,"elapsedMs":28,"mbPerSecond":2300,"blockSize":4096,"uid":0,"gid":0}
{"dir":"/data","mode":"small","files":1000,"elapsedMs":404,"filesPerSecond":2475.3,"uid":0,"gid":0}
{"dir":"/data","mode":"small","files":1000,"elapsedMs":510,"filesPerSecond":1962,"uid":0,"gid":0}

这组数字和常见说法相反：bind mount 的顺序写是 1469.7 MB/s，命名卷是 2300 MB/s；小文件反而是 bind mount 略快（2475 vs 1962 files/s）。结论不是「bind mount 更快」，而是：

  • 本机 VirtioFS 已经把跨层开销压得很低，旧结论不适用；
  • 小文件基准受页缓存、文件系统块大小、fsync 策略影响很大，单次结果不足以下结论；
  • 选型时要在目标机器上用自己的负载测，而不是抄博客。

真正稳定的差异在语义上：命名卷由 Docker 管理、可移植、适合数据库；bind mount 直接映射宿主机目录、适合开发时改代码。性能只是其中一项。

三、安全清理 ​

bash
bash examples/docker/04-resources/scripts/safe-prune.sh        # 预览
# 确认后：
bash examples/docker/04-resources/scripts/safe-prune.sh --yes
bash
#!/usr/bin/env bash
# 04 章：安全清理脚本。默认只打印将要删除什么，加 --yes 才真正执行。
# 用法：
#   bash scripts/safe-prune.sh              # 预览
#   bash scripts/safe-prune.sh --yes        # 真正清理
# 注意：永远不清理命名卷；卷里可能是数据库数据，删了不可恢复。
set -euo pipefail

apply=0
[ "${1:-}" = "--yes" ] && apply=1

echo '将清理以下对象（超过 7 天未使用）：'
echo '- 悬空镜像（dangling，无 tag）'
echo '- 构建缓存（builder cache，超过 168 小时）'
echo

if [ "$apply" -eq 0 ]; then
  echo '当前候选：'
  docker image ls --filter dangling=true --format '  image {{.ID}} {{.Size}}'
  docker buildx du --filter until=168h 2>/dev/null | tail -1 || true
  echo
  echo '这是预览模式。确认无误后执行：bash scripts/safe-prune.sh --yes'
  exit 0
fi

# 只删 dangling，不删有 tag 的镜像；只删 7 天前的缓存，保留最近构建加速
docker image prune --force --filter 'until=168h' --filter dangling=true
docker builder prune --force --filter 'until=168h'

echo
echo '清理后：'
docker system df

脚本只删「悬空镜像」和「7 天前的构建缓存」，不碰命名卷。这是有意的：卷里可能是数据库数据，删了没有回收站。

逐步拆解 ​

第 1 步：先看虚拟机拿到了多少资源 ​

bash
docker info --format 'CPU={{.NCPU}} Mem={{.MemTotal}} Driver={{.Driver}}'

本机输出：

text
CPU=18 Mem=8317267968 Driver=overlayfs

MemTotal 是字节，8 317 267 968 ≈ 7.75 GiB。和宿主机总内存对比，能看出 Docker Desktop 分走了多少。

第 2 步：容器被 OOM 杀掉怎么确认 ​

bash
docker inspect <容器> --format '{{.State.OOMKilled}} {{.State.ExitCode}}'

true 137 基本就是内存超限。处理顺序：

  1. 看容器限制：docker inspect --format '{{json .HostConfig.Memory}}'；
  2. 看应用实际用量：docker stats --no-stream；
  3. 调应用（缓存、并发、批大小）或调限制，不要直接无上限放开。

第 3 步：磁盘镜像只增不减 ​

Docker Desktop 的虚拟磁盘是一个大文件（macOS 在 ~/Library/Containers/com.docker.docker/Data/ 下，Windows 是 WSL2 的 ext4.vhdx）。删除镜像只会释放文件系统内部的块，文件本身不会自动缩小。

处理方式：

  • 先按第 4 步清理无用对象；
  • 再在 Docker Desktop 的 Troubleshoot / Resources 面板查看实际占用；
  • 需要彻底缩小时，才考虑清理全部数据或重建虚拟磁盘——这会删除所有镜像、容器、卷，必须提前备份。

第 4 步：按安全顺序清理 ​

bash
# 1. 构建缓存：最安全，代价只是下次构建变慢
docker builder prune --filter 'until=168h'

# 2. 悬空镜像：没有 tag、没有容器引用
docker image prune --filter dangling=true

# 3. 停止的容器：确认里面没有未挂载的数据
docker container prune

# 4. 悬空卷：最后做，逐个确认
docker volume ls --filter dangling=true

不要习惯性执行 docker system prune -a --volumes。它会删掉所有未使用镜像、网络、构建缓存和卷，包括你上周为排查问题保留的现场。

第 5 步：文件改了容器里没变 ​

按顺序排查：

bash
# a. 挂载是否存在
docker inspect <容器> --format '{{json .Mounts}}' | jq

# b. 宿主机路径是否解析成你以為的路径（相对路径以 compose 文件所在目录为基准）
docker compose -f examples/docker/04-resources/compose.io.yml config | sed -n '/volumes:/,/^[a-z]/p'

# c. 容器内看到的内容
docker exec <容器> ls -la /data

最常见的原因是相对路径理解错：compose 里的 ./data 相对 compose 文件所在目录，不是执行命令时的当前目录。

第 6 步：权限不对 ​

bash
docker exec <容器> id
docker exec <容器> ls -ln /data

如果容器内是 uid 1000，而宿主机目录属主是 501（macOS 第一个用户），在 Linux 原生 Docker 上会写失败；Docker Desktop 的虚拟化共享通常把权限「抹平」成 root，问题被掩盖，到了 CI 才爆。

可复现的做法：

  • 镜像里创建固定 uid/gid 的用户，compose 里用 user: "1000:1000"；
  • 或者在 Linux 上用 --user $(id -u):$(id -g)；
  • 数据库这类有状态服务用命名卷，绕开宿主机权限。

第 7 步：代理三层分别验证 ​

bash
# 第一层：拉镜像
docker pull node:24-alpine

# 第二层：构建阶段联网
docker build --build-arg HTTP_PROXY=http://proxy.example.com:8080 -t proxy-test examples/docker/03-desktop-cli

# 第三层：容器运行时联网
docker run --rm -e HTTPS_PROXY=http://proxy.example.com:8080 node:24-alpine \
  node -e "fetch('https://example.com').then(r=>console.log(r.status)).catch(e=>console.error(e.message))"

三层都通，才叫「代理配好了」。任何一层失败，先看该层的环境变量是否真的传进去了：

bash
docker build --build-arg HTTP_PROXY=... --progress=plain ...
docker exec <容器> env | grep -i proxy

常见坑与排查 ​

现象根因排查与修复
容器退出码 137内存超限被 OOM Killer 杀docker inspect --format '{{.State.OOMKilled}}'；调限制或降内存占用
构建到 pnpm install 就卡住 / 超时代理只配了 Docker Desktop，没传给构建阶段--build-arg HTTP_PROXY / HTTPS_PROXY，并在 Dockerfile 里 ARG
容器访问内网服务走了代理NO_PROXY 没包含服务名或网段把 postgres、redis、*.internal 加进 NO_PROXY
宿主机改代码，容器里不变挂载路径错、相对路径基准错、或挂的是镜像内副本docker inspect --format '{{json .Mounts}}' 核对 Source
容器内 npm install 极慢Windows 项目在 C:\，走 9P把仓库移到 WSL2 文件系统，用 Remote-WSL 打开
文件监听不触发共享层不转发 inotify 事件宿主机跑 dev server；或用轮询模式
容器写挂载目录报 Permission denieduid/gid 不匹配（Linux 原生 Docker 常见）固定 user:，或调整宿主机目录属主
删除镜像后磁盘没变小虚拟磁盘文件不会自动收缩先 prune，再在 Desktop 面板查看/压缩，最后才考虑重置
docker system df 的 RECLAIMABLE 很大但不敢删分不清卷和缓存先删构建缓存与悬空镜像；卷逐个 inspect 后再决定
磁盘镜像达到上限，构建报 no space left on device虚拟机磁盘满docker system df 定位；清理后在 Settings 里扩容

不要用 docker system prune -a --volumes 当日常命令

它不会问你「这个卷是不是数据库」，也不会区分「上周为排查保留的现场」。清理要按类型分步做，卷必须单独确认。

企业级做法 ​

  1. 资源上限写进团队基线：开发机建议 4 核 / 8 GiB 起步，CI 构建机按镜像复杂度单独评估，不要照抄开发机配置。
  2. 日志与构建缓存都要有上限：日志配 max-size，CI 定期 builder prune --filter until=...，避免构建机磁盘被缓存吃满。
  3. 数据库用命名卷，代码用 bind mount：语义清晰；数据库备份用 pg_dump，不要直接拷贝虚拟磁盘。
  4. Windows 团队统一 WSL2 工作目录：仓库放 WSL2 内部，文档写清路径，减少「我这儿很慢」的无效排查。
  5. 代理配置集中下发：admin-settings.json 统一 Desktop 层，CI 用环境变量注入构建层，应用层走配置中心；三层分别有验收命令。
  6. 磁盘告警而不是等报错：监控 Docker 虚拟磁盘占用，达到阈值先清理构建缓存，不要等 no space left on device。
  7. 清理脚本必须可预览：像本章的 safe-prune.sh 一样默认 dry-run，--yes 才执行，并且永不自动删卷。

练习与验收标准 ​

练习

  1. 在 compose.io.yml 里把 ./data 改成绝对路径，运行 docker compose config 对比解析结果。
  2. 给 bind 服务加 user: "1000:1000"，再跑一次 IO 基准，观察 uid 字段与写入是否成功。
  3. 用 docker stats --no-stream 记录空闲与 /work?ms=2000 请求期间的 CPU 差异。
  4. 执行 docker system df -v，找出占用最大的三个卷，逐个 docker volume inspect 看挂载点与创建时间。

验收标准（可逐条执行）

  • [ ] bash examples/docker/04-resources/scripts/disk-report.sh 能打印四类占用，且不删除任何对象；
  • [ ] 四次 IO 基准都能输出一行合法 JSON，mode 分别为 seq / seq / small / small；
  • [ ] 能说出本机 bind mount 与命名卷的实测数字，并解释为什么不能直接套用「bind mount 更慢」的结论；
  • [ ] safe-prune.sh 不加 --yes 时只预览，docker system df 不发生变化；
  • [ ] 能用一条命令判断容器是否被 OOM 杀掉；
  • [ ] 能说出代理三层分别在哪配置，以及漏配某一层时的典型症状。
