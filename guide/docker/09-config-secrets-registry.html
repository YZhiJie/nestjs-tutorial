09 配置、密钥与镜像仓库登录 ​

配置四种来源的优先级、compose secrets 的能力边界、tag→push→pull 流程，以及免费与付费能力的分界。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清 env_file、compose environment、镜像 ENV、命令行 -e 的优先级；
  2. 用 compose secrets 把密钥从环境变量挪到只读文件，并验证 docker inspect 看不到内容；
  3. 知道 compose secrets 的边界：它解决「不泄露到 inspect / 镜像」，不等于「落盘加密」；
  4. 完成一次镜像的 tag → push → pull 流程设计，理解 registry 域名、端口与认证的关系；
  5. 区分免费能力与 Docker 的付费能力（Scout 策略、Build Cloud、IAM / SSO）。

概念与原理 ​

配置的四种来源与优先级 ​

从低到高：

text
镜像 ENV  <  env_file  <  compose environment  <  命令行 -e / --env
  • 镜像 ENV：Dockerfile 里写死的默认值，适合 NODE_ENV、PORT 这类非敏感配置；
  • env_file：一个 KEY=VALUE 文件，适合本地开发的一批配置；
  • compose environment：直接写在 compose 里，覆盖 env_file 同名项；
  • 命令行 -e：临时覆盖，适合排查，不适合长期配置。

还有一个容易混淆的机制：compose 文件里的 ${VAR} 插值，读取的是执行 compose 命令时的 shell 环境或项目根目录的 .env，和服务的 env_file 不是一回事。env_file 只影响容器内的环境变量，不参与 compose 文件自身的插值。

本章示例同时放了 env_file 与 environment，脚本输出的 appMode 是 from-compose，这就是优先级生效的证据。

环境变量为什么不适合放密钥 ​

Docker 的环境变量会出现在多个地方：

bash
docker inspect <容器> --format '{{json .Config.Env}}'
docker compose config          # 展开后的完整配置
/var/run/docker.sock 的任何客户端

任何能访问 Docker daemon 的人都能看到。把密钥放进 ENV 还会写进镜像层，docker history 和镜像仓库都能翻出来。

compose secrets 做了什么 ​

yaml
secrets:
  db_password:
    file: ./secrets/db_password.txt

services:
  app:
    secrets:
      - db_password

compose 会把文件以 bind mount 的形式挂到容器内的 /run/secrets/db_password，只读。它不是环境变量，所以：

  • docker inspect 只看到挂载来源，看不到文件内容；
  • 应用要主动读文件，不能靠 process.env.DB_PASSWORD；
  • 容器内任何进程都能读这个文件（同一容器内不是隔离的）；
  • 文件在宿主机上是明文，compose secrets 不提供静态加密。

这一点必须说清楚：compose secrets 解决的是「不要把密钥塞进环境变量和镜像」，不是「密钥管理系统」。真正的密钥管理要用 Vault、云厂商 Secrets Manager、Kubernetes 加密存储 + RBAC，或至少把文件权限与宿主目录保护好。

BuildKit 的构建期 secret ​

如果构建阶段需要私有 registry 的 token（例如 pnpm install 拉私有包），不要用 ARG：

dockerfile
# 语法示例，不在本章运行
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    pnpm install --frozen-lockfile
bash
docker build --secret id=npmrc,src=$HOME/.npmrc ...

secret 只在那一层可见，不会留在最终镜像里。第 10 章会用到 BuildKit 的更多能力。

镜像名的结构 ​

text
[registry主机[:端口]/][命名空间/]仓库名[:标签][@digest]

例子：

text
docker-guide/06-multistage:multi              → Docker Hub 的 docker-guide 命名空间
127.0.0.1:5000/nestjs-api:dev                 → 本地 registry
ghcr.io/acme/nestjs-api:1.4.0                 → GitHub Container Registry
123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/api:sha-abc123

推送前必须把镜像 tag 成带 registry 主机的名字。只 docker tag 成 nestjs-api:dev 再 docker push，会默认推到 Docker Hub 的 library 或你的账号下，通常以 401 / denied 结束。

登录、凭据存储与 token ​

bash
docker login registry.example.com
docker info --format '{{.RegistryConfig.CredentialStore}}'
  • macOS 通常是 osxkeychain，Windows 是 wincred，Linux 可能是 secretservice 或明文 auths；
  • 开启 2FA 的 Docker Hub 必须用 Personal Access Token，不是账号密码；
  • CI 里用 echo "$TOKEN" | docker login ... --password-stdin，不要把密码写在命令参数里（会进 shell history 和进程列表）；
  • 用完 docker logout，尤其是共享机器。

localhost 的 registry 通常允许 HTTP（Docker 默认把 localhost / 127.0.0.1 当作 insecure registry 的特例），公司内网的其他 HTTP registry 需要在 Docker Desktop 设置里显式加入 insecure registries，生产不应使用 HTTP。

付费能力边界 ​

能力免费 / 开源付费或更高档订阅
Docker Engine / CLI / ComposeApache-2.0，免费—
Docker Hub 私有仓库有限额度更多仓库与拉取额度
Docker Scout基础漏洞查看策略、持续监控、组织级报告
Docker Build Cloud无远程构建加速、共享缓存
Docker Desktop IAM / SSO / RAM无组织级身份与权限管理
Docker Debug基础 CLI 可用增强调试能力视订阅而定

这些能力的可用性随订阅档位与版本变化，落地前以官方价格页和合同为准。不要假设「本机 Docker Desktop 能用」就等于「公司有授权」。

最小可跑示例 ​

一、用 secrets 读取密钥，并对比环境变量 ​

yml
# 09 章：env_file 与 secrets 的对比。
# 运行：docker compose -f examples/docker/09-secrets-registry/compose.secrets.yml run --rm app
services:
  app:
    image: node:24-alpine
    # 只读挂载脚本，避免每次改脚本都要重建镜像
    volumes:
      - ./app:/app:ro
    command: ['node', '/app/read-secrets.mjs']
    env_file:
      - ./env/app.env
    environment:
      # environment 的优先级高于 env_file，最终应看到 compose
      APP_MODE: from-compose
      # 故意放一个环境变量密钥，用来对比 docker inspect 是否泄露
      DB_PASSWORD: env-password-is-visible-0123456789
    secrets:
      - db_password
      - jwt_secret

secrets:
  db_password:
    file: ./secrets/db_password.txt
  jwt_secret:
    file: ./secrets/jwt_secret.txt
js
// 09 章：读取 Docker secrets（挂载在 /run/secrets）并对比环境变量。
// 只做演示，不会把真实密钥打印出来。
import { readFileSync } from 'node:fs';

const read = (path) => readFileSync(path, 'utf8').trim();
const mask = (value) => `${value.slice(0, 2)}***${value.slice(-2)}（长度 ${value.length}）`;

const dbPassword = read('/run/secrets/db_password');
const jwtSecret = read('/run/secrets/jwt_secret');

console.log(
  JSON.stringify(
    {
      // secret 来自文件，docker inspect 看不到内容
      dbPasswordFromFile: mask(dbPassword),
      jwtSecretFromFile: mask(jwtSecret),
      // 环境变量会出现在 docker inspect 里，不适合放密钥
      dbPasswordFromEnv: process.env.DB_PASSWORD ? mask(process.env.DB_PASSWORD) : null,
      // env_file 与 compose environment 的优先级演示
      appMode: process.env.APP_MODE ?? '(unset)',
      uid: process.getuid?.(),
    },
    null,
    2,
  ),
);
bash
docker compose -f examples/docker/09-secrets-registry/compose.secrets.yml run --rm app

本机真实输出：

json
{
  "dbPasswordFromFile": "lo***89（长度 33）",
  "jwtSecretFromFile": "lo***ef（长度 38）",
  "dbPasswordFromEnv": "en***89（长度 34）",
  "appMode": "from-compose",
  "uid": 0
}

三个结论：

  • dbPasswordFromFile 来自 /run/secrets/db_password，长度对得上文件内容；
  • dbPasswordFromEnv 也读到了，但它是明文环境变量，不该用于真实密钥；
  • appMode 是 from-compose，证明 environment 覆盖了 env_file 里的 from-env-file。

二、验证 inspect 到底能看到什么 ​

bash
docker compose -f examples/docker/09-secrets-registry/compose.secrets.yml run --name secrets-demo app
docker inspect secrets-demo --format '{{range .Mounts}}{{.Type}} {{.Source}} -> {{.Destination}} rw={{.RW}}{{"\n"}}{{end}}'
docker inspect secrets-demo --format '{{json .Config.Env}}'
docker rm -f secrets-demo

本机真实输出（节选）：

text
bind /Users/.../examples/docker/09-secrets-registry/secrets/db_password.txt -> /run/secrets/db_password rw=false
bind /Users/.../examples/docker/09-secrets-registry/secrets/jwt_secret.txt -> /run/secrets/jwt_secret rw=false
text
"DB_PASSWORD=env-password-is-visible-0123456789"
"APP_MODE=from-compose"

inspect 能看到 secret 的来源路径，看不到文件内容；环境变量密钥则原样出现。生产环境里，能 docker inspect 的人本来就有很大权限，但「少一个泄露面」仍然值得。

三、不用 registry 也能搬镜像：docker save / docker load ​

bash
#!/usr/bin/env bash
# 09 章：不依赖 registry，用 docker save / load 把镜像搬到另一台机器。
# 用法：bash examples/docker/09-secrets-registry/scripts/image-transfer.sh
set -euo pipefail

image=${1:-docker-guide/06-multistage:multi}
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT

echo "== 导出 $image =="
docker save "$image" -o "$tmp/api.tar"
ls -lh "$tmp/api.tar"

echo
echo '== 归档内的清单（OCI / Docker 层格式）=='
tar -tf "$tmp/api.tar" | head -10

echo
echo '== 删除本地镜像再导入 =='
docker image rm "$image" >/dev/null
docker load -i "$tmp/api.tar"

echo
echo '== 导入后确认 =='
docker image ls "$image" --format 'table {{.Repository}}:{{.Tag}}\t{{.ID}}\t{{.Size}}'

本机真实输出：

text
== 导出 docker-guide/06-multistage:multi ==
-rw-------  1 yangzhijie  staff   84M  .../api.tar

== 归档内的清单（OCI / Docker 层格式）==
blobs/
blobs/sha256/
blobs/sha256/0064b04e...

== 删除本地镜像再导入 ==
Loaded image: docker-guide/06-multistage:multi

== 导入后确认 ==
REPOSITORY:TAG                     IMAGE ID       SIZE
docker-guide/06-multistage:multi   716bd5cafcea   407MB

这适合离线环境、内网隔离环境、或临时把镜像拷到另一台机器。缺点是没有版本管理、没有访问控制、没有层去重，不适合作为团队的发布方式。

四、registry 登录 / 推送流程（当前环境未实测） ​

bash
#!/usr/bin/env bash
# 09 章：本地 registry 的登录 / 打标签 / 推送 / 拉取流程。
#
# 前置条件（未满足时脚本会直接退出，不会伪造输出）：
#   1. 本地已有 registry:2 镜像，或能联网拉取：
#        docker pull registry:2
#   2. 5000 端口未被占用。
#
# 说明：不带头认证的本地 registry 允许匿名推送，docker login 只是为了演示
#       「凭据写进哪个 credential store」；真实仓库（Harbor / GHCR / ECR）必须登录。
set -euo pipefail

if ! docker image inspect registry:2 >/dev/null 2>&1; then
  echo '缺少 registry:2 镜像，当前环境无法演示推送流程。'
  echo '先执行：docker pull registry:2'
  exit 1
fi

container=docker-guide-registry
source_image=${1:-docker-guide/06-multistage:multi}
target=127.0.0.1:5000/nestjs-api:dev

cleanup() {
  docker rm -f "$container" >/dev/null 2>&1 || true
}
trap cleanup EXIT

echo '== 1. 启动本地 registry =='
docker run -d --name "$container" -p 127.0.0.1:5000:5000 registry:2

echo '== 2. 登录（本地无认证 registry 仅演示命令与 credential store）=='
docker login 127.0.0.1:5000 -u demo --password-stdin <<<'demo-password'

echo '== 3. 打标签：镜像名必须带 registry 主机与端口 =='
docker tag "$source_image" "$target"

echo '== 4. 推送 =='
docker push "$target"

echo '== 5. 删除本地镜像后从 registry 拉回 =='
docker image rm "$target"
docker pull "$target"

echo '== 6. 查看仓库目录 =='
curl -s http://127.0.0.1:5000/v2/_catalog
echo
curl -s "http://127.0.0.1:5000/v2/nestjs-api/tags/list"

echo
echo '== 7. 退出登录并清理 =='
docker logout 127.0.0.1:5000

本节的 registry 流程未在本机实测

当前网络无法拉取 registry:2，docker pull registry:2 报 connection refused，所以脚本会主动检测并退出，不输出伪造结果。完整输出需要：

bash
docker pull registry:2
bash examples/docker/09-secrets-registry/scripts/registry-flow.sh

真实仓库（Harbor / GHCR / ECR）的登录参数与权限模型不同，脚本里的本地 registry 只用于演示命令顺序。

逐步拆解 ​

第 1 步：先确认配置最终展开成什么 ​

bash
docker compose -f examples/docker/09-secrets-registry/compose.secrets.yml config

config 会展开 env_file、environment、secrets 的最终形态。排查「为什么容器里的值不对」时，先看展开结果，再看容器内 env。

注意：docker compose config 会显示环境变量的值，在共享终端里执行前先确认屏幕安全；需要脱敏时用 --no-interpolate 或只看特定字段。

第 2 步：把密钥从 env 迁到文件 ​

迁移步骤：

  1. 应用代码改成「优先读 *_FILE 环境变量指向的文件」；
  2. compose 里加 secrets，把原来的 DB_PASSWORD 删除；
  3. 保留一个兼容期：DB_PASSWORD 与 DB_PASSWORD_FILE 同时支持，但日志里只打印「来自文件 / 来自环境」；
  4. 观察一段时间后删除环境变量分支。

本章的 read-secrets.mjs 就是这种「文件优先」的写法。

第 3 步：secret 文件本身的权限 ​

bash
ls -l examples/docker/09-secrets-registry/secrets/
chmod 600 examples/docker/09-secrets-registry/secrets/*.txt

compose 只负责把文件挂进去，不负责保护宿主机上的源文件。仓库里不要提交真实 secret；示例值是假的，但仍然建议在 .gitignore 里排除真实文件名。

第 4 步：CI 里登录 registry ​

bash
# 推荐：从 stdin 读 token，不落 shell history
printf '%s' "$REGISTRY_TOKEN" | docker login registry.example.com \
  -u "$REGISTRY_USER" --password-stdin

docker build -t registry.example.com/acme/api:"$GIT_SHA" .
docker push registry.example.com/acme/api:"$GIT_SHA"

docker logout registry.example.com

三个要点：

  • tag 用不可变的 git sha 或版本号，不要只用 latest；
  • 登录 token 用 CI 的 secret 注入，不要写进仓库；
  • 构建、推送、部署用同一个 digest，避免「推上去的」和「部署的」不是同一个镜像。

第 5 步：私有 registry 的证书问题 ​

公司 Harbor 常用自签 CA，报错通常是：

text
x509: certificate signed by unknown authority

处理方式：

  • 把 CA 放到 Docker Desktop 的信任列表（Settings → Docker Engine 的 insecure-registries 只解决 HTTP，不解决 TLS 校验）；
  • 或在 CI runner 的系统信任库里安装 CA；
  • 不要用 --insecure-registry 绕过 TLS 校验，那等于放弃中间人防护。

第 6 步：推送失败怎么排查 ​

报错含义处理
unauthorized: authentication required没登录 / token 过期 / 无仓库权限docker login，检查 token scope
denied: requested access to the resource is denied登录了，但没有该命名空间的写权限让管理员加权限，或改 tag 到自己的命名空间
name unknown / repository does not exist推送前仓库不存在且账号无创建权限先在 registry 创建项目 / 仓库
connection refusedregistry 地址或端口错，或 HTTP/HTTPS 不匹配curl https://registry/v2/ 验证
x509: certificate signed by unknown authority自签 CA 未信任安装 CA，不要关校验
no space left on deviceregistry 存储满联系管理员清理，或配置 retention policy
推送很慢 / 断流层太大、网络差、没有复用层多阶段瘦身；用 registry 缓存；分块重试

常见坑与排查 ​

现象根因排查与修复
docker inspect 里看到数据库密码用了 environment / ENV迁到 secrets 文件；轮换已泄露密码
镜像历史里能搜到 token构建时用 ARG 传了密钥改用 RUN --mount=type=secret
env_file 写了但不生效同名变量被 environment 覆盖docker compose config 看最终值
compose 里 ${DB_HOST} 是空插值读的是 shell / 项目 .env，不是服务 env_file在 shell 或项目 .env 里设置，或改用 environment
docker push 推到意外仓库镜像名没有 registry 前缀docker tag 成完整名字再推
登录成功但推送 denied命名空间权限不足检查 registry 项目成员与 token scope
本地 registry 推送报 HTTPS 错误用了非 localhost 的 HTTP 地址本地用 127.0.0.1:5000；其他地址配置 TLS
换了机器拉不到镜像私有仓库未登录，或镜像没推先 docker login，再确认 tag 与 digest
secret 文件改了容器没变secret 在容器创建时挂载重新创建容器；restart 不会重新挂载
以为 compose secrets 是加密的它只是文件挂载需要加密就用 Vault / 云 Secrets Manager / K8s 加密存储

判断一个「密钥方案」是否合格

问三个问题：会不会出现在 docker inspect？会不会留在镜像层？宿主机磁盘上是不是明文？三个都过关，才谈得上「密钥管理」。

企业级做法 ​

  1. 密钥不落镜像、不进 Git、不进环境变量：优先文件挂载或密钥管理服务；环境变量只放非敏感配置。
  2. 区分开发与生产密钥来源：开发用本地假值，生产用 Vault / Secrets Manager / K8s Secret（开启加密存储）。
  3. 镜像 tag 不可变：git sha 或语义化版本；部署按 digest 固定，latest 只用于本地实验。
  4. CI 登录用短期凭据：OIDC 联合云厂商，token 生命周期按流水线时长设置；用完 logout。
  5. Registry 开漏洞扫描与保留策略：推上去的镜像要能追溯、能清理；Scout 的策略与持续监控属于付费能力，按订阅评估。
  6. CA 与 TLS 统一管理：自签 CA 通过镜像 / 系统信任库下发，禁止 --insecure-registry 上生产。
  7. 最小权限：CI 只拥有推送目标仓库的写权限，不给组织管理员；人肉发布用单独账号并审计。

练习与验收标准 ​

练习

  1. 在 compose.secrets.yml 里删除 environment.APP_MODE，重新运行，观察 appMode 是否变成 from-env-file。
  2. 把 DB_PASSWORD 从 environment 删掉，改成 /run/secrets/db_password，用 docker inspect 对比差异。
  3. 给 read-secrets.mjs 增加一个 DB_PASSWORD_FILE 环境变量支持，让它可以在「文件路径可配置」的模式下工作。
  4. 用 docker save 导出第 08 章的多阶段镜像，docker load 到另一台机器（或删除后重导），验证 digest 是否一致。

验收标准（可逐条执行）
