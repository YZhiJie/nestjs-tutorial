05 第一个 Dockerfile：把 NestJS 应用装进镜像 ​

写出可构建、可启动的 NestJS 镜像：构建上下文、依赖层缓存顺序，以及构建期与运行期变量的边界。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 写出一份能构建、能启动、能通过健康检查的 NestJS 镜像；
  2. 说清构建上下文（build context）是什么，为什么 COPY 找不到文件通常不是 Dockerfile 写错；
  3. 用「先复制依赖清单、再复制源码」的顺序让依赖安装层可缓存；
  4. 区分构建期变量与运行期变量，知道为什么密钥不能写进 ENV；
  5. 用 docker image history 看懂镜像为什么大，为第 06 章的瘦身建立基线。

概念与原理 ​

镜像是一层层叠出来的 ​

Dockerfile 的每条指令都会生成一个只读层，最终镜像就是这些层的叠加：

text
FROM node:24-alpine        ← 基础层（本地已有则复用）
COPY package.json ...      ← 依赖清单层
RUN pnpm install           ← 依赖安装层（最重，最希望被缓存）
COPY . .                   ← 源码层（经常变）
RUN pnpm build             ← 编译产物层
ENV / EXPOSE / CMD         ← 元数据层（几乎不占空间）

构建时 Docker 会逐层判断「输入有没有变」：没变就显示 CACHED，变了就从这一层开始重跑。所以指令顺序直接决定构建速度。

构建上下文不是 Dockerfile 所在目录 ​

docker build -f <Dockerfile> <context> 里的 <context> 才是关键：

bash
docker build -f examples/docker/05-first-dockerfile/Dockerfile .

末尾的 . 表示把**当前目录（仓库根目录）**打包发给构建器。COPY package.json ... 里的路径都相对于这个上下文，而不是 Dockerfile 所在目录。这也解释了两种常见错误：

  • 在 examples/docker/05-first-dockerfile/ 里执行 docker build .，会报 COPY pnpm-lock.yaml: not found，因为上下文里只有这个示例目录；
  • 上下文太大（包含 .git、node_modules、docs/dist），构建开始前就要传很久，所以需要 .dockerignore。

本仓库根目录已有 .dockerignore，排除了 node_modules、dist、.git 等：

CMD 与 ENTRYPOINT 的区别 ​

  • ENTRYPOINT 是「这个镜像就是某个程序」，docker run 镜像 参数 里的参数会追加给它；
  • CMD 是「默认命令」，docker run 镜像 别的命令 会整体覆盖它。

应用镜像通常用 CMD ["node", "dist/main.js"]，需要临时排查时可以直接覆盖：

bash
docker run --rm -it docker-guide/05-first-dockerfile:single sh

构建期与运行期要分开 ​

类型写法会留在镜像里吗适合放什么
构建参数ARG + --build-arg可能出现在 docker history代理地址、构建编号
构建期环境变量ENV（构建阶段）是PNPM_HOME、NODE_ENV
运行期环境变量compose environment / docker run -e不进镜像数据库地址、密钥

密钥永远走运行期注入。把 JWT_ACCESS_SECRET 写进 ENV 会被 docker history 看到，也会被任何能拉镜像的人拿到。本章示例在第一次启动时就因为生产校验要求显式设置 WEBHOOK_SECRET 而失败，后来改成 compose 注入才通过——这不是示例的瑕疵，而是这类校验应该起的作用。

最小可跑示例 ​

一、单阶段 Dockerfile ​

dockerfile
# 05 章：第一个 Dockerfile —— 单阶段，把「能跑」放第一位。
# 构建命令（context 必须是仓库根目录，因为要复制 pnpm workspace 清单）：
#   docker build -f examples/docker/05-first-dockerfile/Dockerfile -t docker-guide/05-first-dockerfile:single .
# 这一版故意不做多阶段、不裁依赖：先跑通，再在第 06 章瘦身。

FROM node:24-alpine

# pnpm 通过 corepack 启用，版本由 package.json 的 packageManager 字段锁定
ENV PNPM_HOME=/pnpm
ENV PATH=/pnpm:$PATH
RUN corepack enable

WORKDIR /repo

# 只复制依赖清单，先让依赖层可缓存；源码变化不会触发重新安装
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/api/package.json apps/api/package.json

# --frozen-lockfile：锁文件与 package.json 不一致时直接失败，避免镜像里悄悄升级依赖
RUN pnpm install --frozen-lockfile

# 再复制全部源码并编译
COPY . .
RUN pnpm --filter @nestjs-tutorial/api build

# 运行期变量：用进程内 sql.js + 内存缓存，让这个镜像不依赖 Postgres / Redis 也能起
# 真实环境请换成 postgres / redis，见第 08 章
# 密钥不写进镜像：JWT_ACCESS_SECRET 由 compose / 部署平台在运行时注入
ENV NODE_ENV=production \
    PORT=3000 \
    API_PREFIX=api \
    DB_DRIVER=sqljs \
    CACHE_DRIVER=memory \
    QUEUE_DRIVER=memory

EXPOSE 3000

# 单阶段镜像里 node 就是 PID 1；生产版会用 dist/main.js 直接启动
CMD ["node", "apps/api/dist/main.js"]

二、用 compose 固定构建与运行参数 ​

yml
# 05 章：用一个 compose 文件固定「怎么构建、怎么起、怎么验证」。
# 运行：docker compose -f examples/docker/05-first-dockerfile/compose.single.yml up -d --build
services:
  api:
    build:
      # context 是仓库根目录：镜像需要 pnpm workspace 的清单与 apps/api 源码
      context: ../../..
      dockerfile: examples/docker/05-first-dockerfile/Dockerfile
    image: docker-guide/05-first-dockerfile:single
    container_name: docker-guide-05
    environment:
      NODE_ENV: production
      PORT: 3000
      API_PREFIX: api
      # 本章只验证「应用能装进镜像并启动」，用进程内实现规避外部依赖
      DB_DRIVER: sqljs
      CACHE_DRIVER: memory
      QUEUE_DRIVER: memory
      JWT_ACCESS_SECRET: local-image-smoke-secret-0123456789
      # 生产模式的校验要求显式覆盖 webhook 开发默认值，长度至少 16
      WEBHOOK_SECRET: local-image-webhook-secret-0123456789
    ports:
      # 宿主机 13000 → 容器 3000，避免和本地 pnpm dev 抢占
      - '127.0.0.1:13000:3000'
    healthcheck:
      test:
        - CMD
        - node
        - -e
        - "fetch('http://127.0.0.1:3000/api/health/live').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 15s

四、看体积与分层 ​

bash
docker image ls docker-guide/05-first-dockerfile:single --format '{{.Size}}'
docker image history docker-guide/05-first-dockerfile:single --format 'table {{.Size}}\t{{.CreatedBy}}' | head -10

本机真实输出（节选）：

text
655MB

SIZE      CREATED BY
0B        CMD ["node" "apps/api/dist/main.js"]
1.95MB    RUN /bin/sh -c pnpm --filter @nestjs-tutorial/api build
3.11MB    COPY . . # buildkit
329MB     RUN /bin/sh -c pnpm install --frozen-lockfile
209kB     COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./

pnpm install 一层就 329 MB，加上基础镜像和全量源码，最终 655 MB。这不是「错误」，而是单阶段构建的正常结果：编译工具链、devDependencies、源码全都留在了运行镜像里。第 06 章会把它们裁掉。

逐步拆解 ​

第 1 步：先确认上下文里有什么 ​

bash
ls pnpm-lock.yaml pnpm-workspace.yaml apps/api/package.json

这三个文件是构建的前置条件。pnpm-workspace.yaml 决定 workspace 边界，apps/api/package.json 提供 workspace 内依赖，缺一个都会在 COPY 或 pnpm install 阶段失败。

第 2 步：为什么先 COPY 清单再 COPY 源码 ​

dockerfile
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/api/package.json apps/api/package.json
RUN pnpm install --frozen-lockfile
COPY . .

依赖只由清单决定，不由源码决定。这样改一行 src/ 只会让后面的层失效，pnpm install 仍然 CACHED。反过来写成 COPY . . 再 RUN pnpm install，任何源码改动都会重装依赖——第 06 章的缓存实验会用真实构建日志证明这一点。

第 3 步：--frozen-lockfile 是干什么的 ​

bash
RUN pnpm install --frozen-lockfile

它要求 pnpm-lock.yaml 与 package.json 完全一致，否则直接失败。CI / 镜像构建里应该始终开启：镜像里的依赖必须可复现，不能因为构建当天 registry 上某个包发了新版本就悄悄变化。

第 4 步：编译产物在哪 ​

bash
docker exec docker-guide-05 ls -la /repo/apps/api/dist | head

nest build 默认输出到 apps/api/dist，入口是 dist/main.js。单阶段镜像直接从 /repo 启动，所以 CMD 写的是 apps/api/dist/main.js；多阶段镜像会把 dist 复制到 /app/dist，CMD 相应变成 dist/main.js。

第 5 步：运行期变量与密钥 ​

第一次启动时容器退出了，日志是：

text
Error: 环境变量校验失败: 生产环境必须显式设置 WEBHOOK_SECRET（当前值仍是开发默认值）

这是应用在保护你：NODE_ENV=production 下，JWT_ACCESS_SECRET 和 WEBHOOK_SECRET 都不允许停留在开发默认值。修复方式不是把密钥写进 Dockerfile，而是在 compose 里注入：

yaml
environment:
  JWT_ACCESS_SECRET: local-image-smoke-secret-0123456789
  WEBHOOK_SECRET: local-image-webhook-secret-0123456789

这两个值只用于本地冒烟，长度足够通过校验，但不是生产密钥。真实环境应由密钥管理服务注入，见第 09 章。

第 6 步：健康检查放在镜像还是 compose ​

两处都写了 healthcheck：

  • 镜像里的 HEALTHCHECK 让镜像自带「我是否健康」的定义；
  • compose 里的 healthcheck 覆盖镜像设置，方便按环境调整参数。

镜像里的检查用 node -e "fetch(...)"，不依赖 curl，这样 Alpine 基础镜像不需要额外装工具。健康检查发现的是「进程活着但接口不通」，比只看容器状态更可靠。

第 7 步：进容器确认它到底装了什么 ​

bash
docker run --rm -it docker-guide/05-first-dockerfile:single sh
# 容器内：
ls /repo
du -sh /repo/node_modules

本机 du -sh /repo/node_modules 是 279.2 MB，里面有 TypeScript、Vitest、VitePress 等开发依赖。运行 NestJS 并不需要这些，第 06 章会用 pnpm deploy --prod 把它们裁掉。

常见坑与排查 ​

现象根因排查与修复
COPY pnpm-lock.yaml: not found构建上下文选错确认 docker build ... . 在仓库根目录；-f 只指定 Dockerfile，不改变上下文
pnpm: not found基础镜像没启用 corepackRUN corepack enable；或改用 npm ci
ERR_PNPM_OUTDATED_LOCKFILE锁文件与 package.json 不一致本地执行 pnpm install 更新锁文件并提交
构建很慢，每次都在 pnpm install先 COPY . . 再安装，源码变化让依赖层失效按「清单 → 安装 → 源码」的顺序重排
镜像里有密钥把密钥写进 ARG / ENV删除，改由 compose / 密钥管理注入；轮换已经泄露的密钥
容器启动即退出，日志只有环境变量校验生产模式要求显式密钥注入 JWT_ACCESS_SECRET、WEBHOOK_SECRET，长度至少 16
容器里 127.0.0.1 访问不到应用只监听回环地址改成 0.0.0.0；容器内的 localhost 不是宿主机
宿主机端口被占用3000 常被本地 dev server 占用compose 映射到 13000，或先停掉本地进程
构建上下文有几 GB没有 .dockerignore排除 node_modules、.git、dist、日志
Apple Silicon 上构建 amd64 镜像很慢走了 QEMU 模拟用多架构构建或明确 --platform，见第 10 章
docker run 后 Ctrl+C 停不掉PID 1 是 shell，信号没转发用 CMD ["node", ...] 直接启动；必要时加 init
镜像 655 MB，推送很慢单阶段带上了编译工具与 devDependencies第 06 章多阶段构建

构建失败先看「上下文」和「层」

COPY 找不到文件，九成是上下文不对；RUN 失败，九成是基础镜像里缺工具或网络不通。把 --progress=plain 打开，能看到每一层的完整输出。

企业级做法 ​

  1. 基础镜像固定到具体版本或 digest：node:24-alpine 比 node:latest 好，node:24.22.2-alpine3.22@sha256:... 更好；至少不要用 latest。
  2. 构建与运行分离：本章是学习用的单阶段；生产必须多阶段，运行层只保留 dist + 生产依赖（第 06 章）。
  3. 容器内非 root 运行：USER app，并确保文件属主正确；第 12 章会展开。
  4. 密钥零入库：镜像、Dockerfile、compose 默认值里都不放真实密钥；CI 用 OIDC 或短期 token。
  5. 健康检查用就绪探针：/api/health/ready 检查依赖，/api/health/live 只检查进程；编排系统据此决定是否接流量。
  6. 构建可复现：锁文件 + --frozen-lockfile + 固定基础镜像；CI 缓存只加速，不改变结果。
  7. 镜像构建纳入流水线门禁：构建成功不等于可发布，还要跑测试、扫描漏洞、检查镜像大小与用户身份。

练习与验收标准 ​

练习

  1. 在 examples/docker/05-first-dockerfile/ 目录里执行 docker build .，记录报错，并解释为什么。
  2. 把 COPY . . 移到 RUN pnpm install 之前，连续构建两次并修改一个源文件，观察第二次构建哪些层重跑。
  3. 去掉 compose 里的 WEBHOOK_SECRET，重启容器，记录报错原文；再加回来。
  4. 用 docker run --rm -it --entrypoint sh docker-guide/05-first-dockerfile:single 进入镜像，找出 node_modules 里三个只用于开发的包。

验收标准（可逐条执行）

  • [ ] docker image ls docker-guide/05-first-dockerfile:single 显示镜像存在（本机 655 MB）；
  • [ ] docker compose -f examples/docker/05-first-dockerfile/compose.single.yml ps 显示 (healthy)；
  • [ ] curl http://127.0.0.1:13000/api/health/live 返回 data.status = ok；
  • [ ] curl http://127.0.0.1:13000/api/health/dependencies 返回 database 与 cache 均为 up；
  • [ ] 能说出构建上下文与 Dockerfile 目录的区别，并能解释 COPY ... not found 的排查顺序；
  • [ ] 能说出至少三条「密钥不能写进镜像」的理由；
  • [ ] 能从 docker image history 指出最重的一层，并说明第 06 章准备怎么裁。
