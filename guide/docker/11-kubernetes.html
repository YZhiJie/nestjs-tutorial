11 Docker Desktop 内置 Kubernetes 与本地编排入门 ​

把 compose 四件套翻译成 Deployment/Service/Job/ConfigMap，用 initContainer 与 Job 补启动顺序，分清两类探针。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清 Docker Desktop 内置 Kubernetes 跑在哪、和 Docker Engine 共用什么；
  2. 把第 08 章的 compose 四件套翻译成 Deployment / Service / Job / ConfigMap / Secret / PVC；
  3. 用 initContainer 与 Job 替代 compose 的 depends_on，补上 Kubernetes 没有的启动顺序语义；
  4. 分清 readiness 与 liveness 探针，知道为什么存活探针不能检查数据库；
  5. 在没有集群的情况下，用 kubectl kustomize 完成可复现的离线校验。

概念与原理 ​

内置 Kubernetes 是什么 ​

在 macOS / Windows 上，Docker Desktop 的容器跑在一台 Linux 虚拟机里（第 02 章）。启用 Kubernetes 后，同一台虚拟机里会再启动一个单节点集群：

text
宿主机
└── Docker Desktop 虚拟机
    ├── Docker Engine（镜像、容器、卷）
    └── Kubernetes 单节点控制面 + kubelet
        ├── 系统 Pod（kube-system）
        └── 你的命名空间

关键差异：

  • 镜像共享：本地 docker build 出来的镜像，Kubernetes 通常能直接用，不需要先推 registry；
  • 单节点：没有多节点调度、没有真正的故障转移，适合本地验证清单，不适合压测高可用；
  • 资源占用：控制面本身要占 CPU 和内存，Settings → Resources 里的上限对它同样生效；
  • 启停：Settings → Kubernetes → Enable Kubernetes，首次启动需要等控制面就绪。

compose 与 Kubernetes 的对应关系 ​

composeKubernetes说明
services.<name>Deployment + Service一个跑副本，一个提供稳定 DNS
portsService（ClusterIP / NodePort / Ingress）默认不发布到宿主机
volumes（命名卷）PersistentVolumeClaim由 StorageClass 动态供给
environmentConfigMap非敏感配置
secretsSecret只是 base64，不是加密
depends_oninitContainer / Job / 探针K8s 不保证启动顺序
一次性任务Job成功退出即完成
healthcheckreadinessProbe / livenessProbe两个探针语义不同

Kubernetes 没有 depends_on ​

这是从 compose 迁移过来最容易踩的坑。Kubernetes 里所有对象是声明式并发协调的，不保证「A 好了再起 B」。常见替代：

  • initContainer：主容器启动前运行，失败会重试；适合「等端口可连」「等表存在」；
  • Job：一次性任务，成功退出即完成；适合迁移；
  • readinessProbe：依赖没就绪就不接流量，但容器已经在跑；
  • 应用内重试：连接失败指数退避，最终一致。

本章的组合：Job 跑迁移，api 的 initContainer 等 Postgres、等 Redis、等 migrations 表，三个条件都满足才开始接流量。

readiness 与 liveness 的区别 ​

探针失败后果该检查什么
readinessProbe从 Service 后端摘除，不重启依赖是否可用（数据库、缓存）
livenessProbe重启容器进程是否卡死，不要检查外部依赖

如果 liveness 也去查数据库，数据库抖动一次就会把所有 api 容器重启，反而放大故障。这是生产事故的常见来源。

kustomize：不引入模板也能分层 ​

kubectl kustomize 会读取 kustomization.yaml，把多个 YAML 渲染成一份清单。它不需要集群，因此可以在 CI 里做「清单是否合法」的第一道检查。

注意：kubectl apply --dry-run=client 在新版 kubectl 里仍需要 API discovery，没有集群时会去连 localhost:8080 并失败。所以本章的离线校验只用 kubectl kustomize，不假装 client dry-run 能离线工作。

付费与授权边界 ​

  • Kubernetes 本身是开源项目，免费；
  • Docker Desktop 内置 Kubernetes 属于 Desktop 订阅条款覆盖的功能，商用授权要求与 Desktop 整体一致；
  • 内置集群没有高可用、没有多节点，不能替代生产集群；
  • 需要更接近生产的环境，可用 kind / minikube / k3d，或直接接云厂商托管集群。

最小可跑示例 ​

一、迁移 Job：用 initContainer 等数据库 ​

yml
# 11 章：迁移任务。Kubernetes 没有 compose 的 depends_on，
# 用 initContainer 轮询等待 Postgres，再用 Job 保证「只成功执行一次」。
# Job 完成后 api 的 initContainer 会检测到 migrations 表，才真正启动。
apiVersion: batch/v1
kind: Job
metadata:
  name: migrate
  namespace: docker-guide
spec:
  # 失败最多重试 3 次；成功一次即完成
  backoffLimit: 3
  # 完成 1 小时后自动清理 Job 对象，便于重复演示
  ttlSecondsAfterFinished: 3600
  template:
    spec:
      restartPolicy: Never
      initContainers:
        - name: wait-postgres
          image: docker-guide/08-compose:api
          imagePullPolicy: IfNotPresent
          command:
            - node
            - -e
            - |
              // 轮询 60 次，每次 1 秒：直到 postgres:5432 可连接
              const net = require('net');
              let tries = 0;
              const probe = () => {
                const s = net.connect(5432, 'postgres');
                s.on('connect', () => { s.end(); console.log('postgres ready'); process.exit(0); });
                s.on('error', () => {
                  s.destroy();
                  if (++tries > 60) { console.error('postgres not ready'); process.exit(1); }
                  setTimeout(probe, 1000);
                });
              };
              probe();
      containers:
        - name: migrate
          image: docker-guide/08-compose:api
          imagePullPolicy: IfNotPresent
          command: ['node', 'dist/database/cli/migrate.js']
          envFrom:
            - configMapRef:
                name: api-config
            - secretRef:
                name: api-secrets

二、API：两个副本 + 三个 initContainer + 两个探针 ​

yml
# 11 章：API。两个副本 + 就绪/存活探针；Service 只在集群内暴露，
# 从宿主机访问用 kubectl port-forward。
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: docker-guide
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      initContainers:
        # 等待 Redis 可连接
        - name: wait-redis
          image: docker-guide/08-compose:api
          imagePullPolicy: IfNotPresent
          command:
            - node
            - -e
            - |
              const net = require('net');
              let tries = 0;
              const probe = () => {
                const s = net.connect(6379, 'redis');
                s.on('connect', () => { s.end(); console.log('redis ready'); process.exit(0); });
                s.on('error', () => {
                  s.destroy();
                  if (++tries > 60) { console.error('redis not ready'); process.exit(1); }
                  setTimeout(probe, 1000);
                });
              };
              probe();
        # 等待迁移完成：migrations 表存在才继续。
        # 这是 Kubernetes 里替代 compose depends_on: service_completed_successfully 的常见写法。
        - name: wait-migrations
          image: docker-guide/08-compose:api
          imagePullPolicy: IfNotPresent
          workingDir: /app
          command:
            - node
            - -e
            - |
              const { Client } = require('pg');
              const client = new Client({
                host: 'postgres', port: 5432, user: 'postgres',
                password: process.env.DB_PASSWORD, database: 'nestjs_tutorial',
              });
              let tries = 0;
              const probe = async () => {
                try {
                  await client.connect();
                  const r = await client.query("select to_regclass('public.migrations') as t");
                  await client.end();
                  if (r.rows[0].t) { console.log('migrations ready'); process.exit(0); }
                } catch (e) {
                  try { await client.end(); } catch {}
                }
                if (++tries > 90) { console.error('migrations not found'); process.exit(1); }
                setTimeout(probe, 1000);
              };
              probe();
          envFrom:
            - configMapRef:
                name: api-config
            - secretRef:
                name: api-secrets
      containers:
        - name: api
          image: docker-guide/08-compose:api
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 3000
          envFrom:
            - configMapRef:
                name: api-config
            - secretRef:
                name: api-secrets
          readinessProbe:
            # 就绪：依赖（数据库、缓存）都可用才接流量
            httpGet:
              path: /api/health/ready
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
          livenessProbe:
            # 存活：只看进程自身，不检查依赖，避免数据库抖动导致容器被反复重启
            httpGet:
              path: /api/health/live
              port: 3000
            initialDelaySeconds: 15
            periodSeconds: 20
            timeoutSeconds: 3
            failureThreshold: 3
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
---
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: docker-guide
spec:
  selector:
    app: api
  ports:
    - port: 3000
      targetPort: 3000

三、离线校验（本机真实执行） ​

bash
bash examples/docker/11-kubernetes/scripts/validate.sh
bash
#!/usr/bin/env bash
# 11 章：校验 Kubernetes 清单。
#
# 两种模式：
#   1. 已启用 Kubernetes（kubectl cluster-info 成功）：做服务端 dry-run，检查 API 是否接受；
#   2. 未启用：只做客户端渲染与校验，并把「为什么不能继续」打印清楚。
#
# 用法：bash examples/docker/11-kubernetes/scripts/validate.sh
set -euo pipefail

here=$(cd "$(dirname "$0")/.." && pwd)
cd "$here"

if ! command -v kubectl >/dev/null 2>&1; then
  echo '未找到 kubectl。Docker Desktop 用户可在 Settings → Kubernetes 启用后使用内置 kubectl。'
  exit 1
fi

echo '== 1. 渲染 kustomize（这一步不需要集群）=='
kubectl kustomize "$here" | sed -n '1,25p'
echo '...（只显示前 25 行）'
echo

if kubectl cluster-info >/dev/null 2>&1; then
  echo '== 2. 集群可达，执行服务端 dry-run =='
  kubectl apply -k "$here" --dry-run=server
  echo
  echo '校验通过。真正部署：kubectl apply -k examples/docker/11-kubernetes'
else
  echo '== 2. 集群不可达 =='
  echo '原因：当前 Docker Desktop 未启用 Kubernetes（kubectl config get-contexts 没有可用上下文）。'
  echo '因此不做 apply，也不输出任何「已部署」之类的伪结果。'
  echo
  echo '== 2.1 离线可做的校验：kustomize 渲染 + 对象计数 =='
  # kubectl kustomize 会真正解析 YAML 并展开 kustomization，语法/字段错误会非零退出。
  # 注意：`kubectl apply --dry-run=client` 在新版 kubectl 仍需要 API discovery，
  # 无集群时会去连 localhost:8080 并失败，所以这里不假装它能离线工作。
  count=$(kubectl kustomize "$here" | grep -c '^kind:')
  echo "渲染成功，共 $count 个对象："
  kubectl kustomize "$here" | grep '^kind:' | sort | uniq -c
  echo
  echo '启用 Kubernetes 后重跑本脚本，才会走服务端 dry-run 与真实部署。'
fi

逐步拆解 ​

第 1 步：启用内置 Kubernetes ​

Docker Desktop → Settings → Kubernetes：

  1. 勾选 Enable Kubernetes；
  2. 选择 kubeconfig 写入位置（默认覆盖 ~/.kube/config 的 docker-desktop 上下文）；
  3. Apply & Restart，等待左下角 Kubernetes 变成绿色。

验证：

bash
kubectl config get-contexts
kubectl cluster-info
kubectl get nodes

本机当前的真实结果是 get-contexts 只有表头、没有上下文——这正是「未启用」的证据。

第 2 步：确认镜像在集群里可见 ​

bash
docker image ls docker-guide/08-compose:api
kubectl -n docker-guide get pods

Docker Desktop 的 Kubernetes 与 Docker Engine 共用镜像存储，所以第 08 章构建的 docker-guide/08-compose:api 不需要推送。清单里写了 imagePullPolicy: IfNotPresent，避免它去远端拉取。

如果换到 kind / minikube，必须 kind load docker-image 或 minikube image load，否则会 ErrImagePull。

第 3 步：先起有状态服务 ​

bash
kubectl apply -f examples/docker/11-kubernetes/00-namespace.yaml
kubectl apply -f examples/docker/11-kubernetes/01-config.yaml
kubectl apply -f examples/docker/11-kubernetes/02-postgres.yaml
kubectl apply -f examples/docker/11-kubernetes/03-redis.yaml

kubectl -n docker-guide get pods -w
kubectl -n docker-guide get pvc

PVC 需要 StorageClass。Docker Desktop 自带默认 StorageClass，会动态创建本地卷；如果 PVC 一直 Pending，先 kubectl get storageclass 确认有默认项。

第 4 步：跑迁移并等它完成 ​

bash
kubectl apply -f examples/docker/11-kubernetes/04-migrate-job.yaml
kubectl -n docker-guide wait --for=condition=complete job/migrate --timeout=180s
kubectl -n docker-guide logs job/migrate

Job 的 backoffLimit: 3 表示失败最多重试 3 次；ttlSecondsAfterFinished: 3600 让完成的 Job 一小时后自动清理，方便重复演示。

第 5 步：起 API 并观察 initContainer ​

bash
kubectl apply -f examples/docker/11-kubernetes/05-api.yaml
kubectl -n docker-guide get pods -l app=api -w
kubectl -n docker-guide logs -l app=api -c wait-migrations

wait-migrations 用 pg 查询 to_regclass('public.migrations')，表存在才退出 0。它把「迁移必须完成」这件事从编排顺序变成了显式契约。

第 6 步：从宿主机访问 ​

bash
kubectl -n docker-guide port-forward svc/api 13003:3000
curl -s http://127.0.0.1:13003/api/health/ready
curl -s http://127.0.0.1:13003/api/health/live

Service 是 ClusterIP，不暴露到宿主机；port-forward 是本地调试最安全的方式。需要长期暴露再用 NodePort / Ingress。

第 7 步：排障常用命令 ​

bash
kubectl -n docker-guide get all
kubectl -n docker-guide describe pod <pod>
kubectl -n docker-guide logs <pod> --previous
kubectl -n docker-guide get events --sort-by=.lastTimestamp
kubectl -n docker-guide exec -it <pod> -- sh

describe 看事件，logs --previous 看崩溃前的日志，get events 看调度与拉镜像失败的原因。

常见坑与排查 ​

现象根因排查与修复
kubectl 没有上下文未启用 KubernetesSettings → Kubernetes 勾选并等待就绪
Pod ImagePullBackOff镜像不在集群可见的存储里Docker Desktop 直接可用；kind/minikube 需 load
PVC 一直 Pending没有默认 StorageClasskubectl get storageclass，必要时手动指定
api 一直 Init:0/3依赖没就绪或迁移没跑logs -c wait-postgres、logs -c wait-migrations
迁移 Job 反复失败数据库未就绪或迁移脚本报错logs job/migrate、describe job，先修脚本
readiness 一直失败依赖不可用或路径写错exec 进容器手动 curl 探针地址
数据库抖动导致 api 全部重启liveness 检查了数据库liveness 只查 /health/live，依赖放 readiness
改了镜像但 Pod 没更新同 tag 且 imagePullPolicy: IfNotPresent换 tag，或 rollout restart，或临时 Always
kubectl apply --dry-run=client 离线报连接拒绝新版 kubectl 需要 API discovery离线只用 kubectl kustomize 校验
kubectl delete namespace 后数据没了PVC 随命名空间删除生产先备份，清理用精确资源名

本地 Kubernetes 的定位

它适合验证清单、练习 kubectl、跑通「镜像 → Deployment → Service」的闭环。不要用它评估调度性能、高可用或网络插件行为，单节点给不出这些答案。

企业级做法 ​

  1. 环境分层用 kustomize / Helm：base 放通用清单，overlay 放环境差异，避免复制 YAML。
  2. 镜像用不可变 tag 或 digest：latest + IfNotPresent 在本地很方便，在生产是事故来源。
  3. 迁移用 Job 并由流水线等待完成：不要放进应用启动钩子，也不要用 initContainer 跑迁移（重试会重复执行）。
  4. readiness 查依赖、liveness 只查自身：这是探针最基本的纪律。
  5. 资源 requests / limits 必填：没有 requests 的 Pod 会被调度器当成「不占资源」，容易把节点压垮。
  6. Secret 要真正加密：K8s Secret 默认只是 base64；开启 etcd 加密，或用 External Secrets / Sealed Secrets / 云 KMS。
  7. 本地集群不承担生产职责：需要多节点、滚动发布、网络策略，用托管集群或 kind + CI。

练习与验收标准 ​

练习

  1. 把 replicas 改成 3，观察 kubectl get endpoints api 的后端数量变化。
  2. 把 livenessProbe 的路径改成 /api/health/ready，然后停掉 Redis，观察 api 是否被反复重启（做完改回）。
  3. 给 api 加一个 HorizontalPodAutoscaler（需要 metrics-server，Docker Desktop 默认可能没有，先确认前提）。
  4. 用 kubectl kustomize 输出完整清单，统计每个 kind 的数量，与本章的 12 个对象核对。

验收标准（可逐条执行）

  • [ ] bash examples/docker/11-kubernetes/scripts/validate.sh 能渲染成功并打印 12 个对象；
  • [ ] 能解释为什么离线时 kubectl apply --dry-run=client 仍会失败；
  • [ ] 启用集群后，kubectl -n docker-guide get pods 中 migrate 为 Completed；
  • [ ] api 的 initContainer 依次等到 Postgres、Redis、migrations 表；
  • [ ] kubectl get endpoints api 的后端数量与 replicas 一致；
  • [ ] port-forward 后 /api/health/ready 返回 "status":"ok"；
  • [ ] 能说出 readiness 与 liveness 的失败后果差异。
