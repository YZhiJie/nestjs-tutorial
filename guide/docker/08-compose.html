08 docker compose 多服务编排与依赖顺序 ​

用 compose 编排 Postgres、Redis、迁移任务与 API：depends_on 三种条件、healthcheck 与数据卷生命周期。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 用一个 compose 文件描述 Postgres、Redis、一次性迁移任务和常驻 API 四类服务；
  2. 分清 depends_on 的三种条件：service_started、service_healthy、service_completed_successfully；
  3. 写出真正有意义的 healthcheck，而不是「容器在跑就算健康」；
  4. 用服务名做容器间访问，并解释为什么内部服务不需要 ports；
  5. 用命名卷保存数据库数据，并说清 down 与 down -v 的区别。

概念与原理 ​

compose 解决的是「一组容器」的问题 ​

docker run 一次只能表述一个容器。真实应用至少有三类角色：

  • 有状态依赖（Postgres、Redis）；
  • 一次性任务（建表迁移、初始化数据）；
  • 常驻服务（API）。

docker compose 把这些写进一个 YAML，用项目（project）为单位管理生命周期。默认项目名是 compose 文件所在目录名，所以本章的容器名形如 08-compose-api-1。

四个服务与启动顺序 ​

text
postgres ──healthy──┐
                    ├──> migrate ──completed(0)──> api
redis ────healthy───┘

depends_on 只控制启动顺序，不保证依赖「可用」。因此：

条件含义适用
service_started依赖容器已启动（进程跑起来了）无健康检查的简单服务
service_healthy依赖的 healthcheck 返回 healthy数据库、缓存
service_completed_successfully依赖容器以退出码 0 结束迁移、初始化任务

本仓库最容易踩的坑：Postgres 容器「Up」时数据库还在初始化，此时 api 连接会 ECONNREFUSED。所以本章的 postgres 必须配 pg_isready 健康检查，api 用 service_healthy。

healthcheck 检查什么 ​

yaml
healthcheck:
  test: ['CMD-SHELL', 'pg_isready -U postgres -d nestjs_tutorial']
  interval: 5s
  timeout: 3s
  retries: 10
  start_period: 5s
  • test 必须是「真的能回答服务是否可用」的命令，不是 ps aux | grep；
  • start_period 给冷启动留时间，期间失败不计入 retries；
  • api 自己也要有 healthcheck，否则 depends_on api: service_healthy 无从谈起。

服务发现：用服务名，不用 localhost ​

compose 默认创建一个 bridge 网络，并把服务名注册为 DNS：

text
DB_HOST=postgres
REDIS_HOST=redis

容器里的 localhost 指的是它自己，不是宿主机，也不是别的容器。这是「本机跑得通、进容器就连不上」的第一大原因，第 07 章已经用 ENOTFOUND 演示过。

ports 与 expose 的区别 ​

  • ports: '127.0.0.1:13001:3000'：发布到宿主机，只有需要从宿主机/外部访问的服务才写；
  • expose / Dockerfile EXPOSE：只是元数据，供同网络的服务发现端口，不发布到宿主机。

本章只有 api 发布端口，Postgres 和 Redis 都不发布。这样即使宿主机已经有一个 5432 在跑，也不会冲突——docker compose port postgres 5432 会返回 :0。

命名卷与数据生命周期 ​

yaml
volumes:
  - pgdata:/var/lib/postgresql/data
  • docker compose down：删容器和网络，保留卷；
  • docker compose down -v：连卷一起删，数据库数据不可恢复；
  • 卷名默认加项目前缀：08-compose_pgdata。

一份镜像，两种角色 ​

migrate 和 api 用同一个镜像、同一份构建上下文，只是 command 不同：

yaml
migrate:
  build: ...
  command: ['node', 'dist/database/cli/migrate.js']
api:
  build: ...

这避免了「迁移脚本和运行时代码版本不一致」的经典事故。镜像构建复用第 06 章的多阶段 Dockerfile。

最小可跑示例 ​

yml
# 08 章：多服务编排。Postgres / Redis 先健康，migrate 成功，api 才启动。
# 启动：docker compose -f examples/docker/08-compose/compose.full.yml up -d --build
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: nestjs_tutorial
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      # pg_isready 返回 0 才说明数据库接受连接，仅「容器在跑」不够
      test: ['CMD-SHELL', 'pg_isready -U postgres -d nestjs_tutorial']
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 5s
    networks:
      - backend

  redis:
    image: redis:7-alpine
    command: ['redis-server', '--appendonly', 'yes']
    volumes:
      - redisdata:/data
    healthcheck:
      test: ['CMD', 'redis-cli', 'ping']
      interval: 5s
      timeout: 3s
      retries: 10
    networks:
      - backend

  migrate:
    # 与 api 共用同一个镜像，只是换了一条启动命令
    build:
      context: ../../..
      dockerfile: examples/docker/06-multistage/Dockerfile
    image: docker-guide/08-compose:api
    command: ['node', 'dist/database/cli/migrate.js']
    environment: &api-env
      NODE_ENV: production
      PORT: 3000
      API_PREFIX: api
      DB_DRIVER: postgres
      DB_HOST: postgres
      DB_PORT: '5432'
      DB_USERNAME: postgres
      DB_PASSWORD: postgres
      DB_NAME: nestjs_tutorial
      DB_SSL: 'false'
      CACHE_DRIVER: redis
      QUEUE_DRIVER: redis
      REDIS_HOST: redis
      REDIS_PORT: '6379'
      JWT_ACCESS_SECRET: compose-full-stack-access-secret-0123456789
      WEBHOOK_SECRET: compose-full-stack-webhook-secret-0123456789
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - backend
    restart: 'no'

  api:
    build:
      context: ../../..
      dockerfile: examples/docker/06-multistage/Dockerfile
    image: docker-guide/08-compose:api
    environment: *api-env
    ports:
      - '127.0.0.1:13001:3000'
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
      migrate:
        # 迁移是一次性任务，必须成功退出后 api 才启动
        condition: service_completed_successfully
    healthcheck:
      test:
        - CMD
        - node
        - -e
        - "fetch('http://127.0.0.1:3000/api/health/ready').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 20s
    networks:
      - backend

volumes:
  pgdata:
  redisdata:

networks:
  backend:
bash
# 构建并启动整栈
docker compose -f examples/docker/08-compose/compose.full.yml up -d --build

# 观察状态（migrate 应该是 Exited (0)）
docker compose -f examples/docker/08-compose/compose.full.yml ps -a

# 验证 api 就绪
curl -s http://127.0.0.1:13001/api/health/ready

逐步拆解 ​

第 1 步：先让有状态服务健康 ​

bash
docker compose -f examples/docker/08-compose/compose.full.yml up -d postgres redis
docker compose -f examples/docker/08-compose/compose.full.yml ps

在 postgres 变成 (healthy) 之前，任何连接尝试都可能失败。可以用日志确认初始化完成：

bash
docker compose -f examples/docker/08-compose/compose.full.yml logs postgres | tail -5

第 2 步：迁移只跑一次 ​

bash
docker compose -f examples/docker/08-compose/compose.full.yml run --rm migrate

migrate 服务不是常驻进程，它执行完就退出。restart: 'no' 是刻意的：迁移失败应该让编排停下来，而不是无限重启。

用 run --rm 手动执行一次，能单独验证迁移逻辑，不影响 api。

第 3 步：启动 api，并确认它等到迁移完成 ​

bash
docker compose -f examples/docker/08-compose/compose.full.yml up -d api
docker compose -f examples/docker/08-compose/compose.full.yml logs --tail=20 api

如果 depends_on.migrate.condition 写成 service_started，api 可能在表还没建好时启动，然后在启动期查询里报 relation "users" does not exist。这正是 service_completed_successfully 的意义。

第 4 步：确认表结构 ​

bash
docker compose -f examples/docker/08-compose/compose.full.yml exec postgres \
  psql -U postgres -d nestjs_tutorial -c '\dt'

本机真实输出：

text
               List of relations
 Schema |       Name        | Type  |  Owner
--------+-------------------+-------+----------
 public | audit_logs        | table | postgres
 public | inventory         | table | postgres
 public | migrations        | table | postgres
 public | order_idempotency | table | postgres
 public | order_items       | table | postgres
 public | orders            | table | postgres
 public | products          | table | postgres
 public | refresh_tokens    | table | postgres
 public | users             | table | postgres
 public | webhook_events    | table | postgres
(10 rows)

第 5 步：区分「发布了端口」和「没发布端口」 ​

bash
docker compose -f examples/docker/08-compose/compose.full.yml port api 3000
docker compose -f examples/docker/08-compose/compose.full.yml port postgres 5432

本机真实输出：

text
127.0.0.1:13001
:0

:0 表示没有发布到宿主机。数据库不需要对宿主机开放，同网络的 api 用 postgres:5432 就能访问。

第 6 步：验证数据持久化 ​

bash
# 停掉栈但保留卷
docker compose -f examples/docker/08-compose/compose.full.yml down

# 再启动，数据应该还在
docker compose -f examples/docker/08-compose/compose.full.yml up -d
docker compose -f examples/docker/08-compose/compose.full.yml exec postgres \
  psql -U postgres -d nestjs_tutorial -c 'select count(*) from migrations;'

卷还在，迁移记录就还在，迁移任务会识别为「已执行」。这一步能直观看到 down 与 down -v 的差别。

第 7 步：常用排障命令 ​

bash
# 展开后的最终配置（检查变量、端口、依赖）
docker compose -f examples/docker/08-compose/compose.full.yml config

# 只看服务名
docker compose -f examples/docker/08-compose/compose.full.yml config --services

# 跟踪某个服务日志
docker compose -f examples/docker/08-compose/compose.full.yml logs -f api

# 进入容器
docker compose -f examples/docker/08-compose/compose.full.yml exec api sh

常见坑与排查 ​

现象根因排查与修复
api 启动报 ECONNREFUSED postgres:5432postgres 只是 Up，尚未接受连接用 service_healthy + pg_isready 健康检查
api 报 relation "users" does not exist迁移没跑完就启动，或用了 service_started改为 service_completed_successfully；先看 migrate 日志
depends_on 写了但顺序还是乱只写了列表形式，没写条件使用长语法 condition:
宿主机 5432 被占用给数据库也发布了端口内部服务不写 ports；需要调试时临时映射到非常用端口
容器里连 localhost 失败localhost 指容器自己用服务名：postgres、redis
改了 compose 但行为没变容器没重建up -d --build 或 up -d --force-recreate
down -v 之后数据没了卷被删除生产禁用 down -v；用 pg_dump 备份
迁移容器反复重启restart 策略设成了 always一次性任务用 restart: 'no'
服务启动很慢但 healthcheck 一直 unhealthystart_period 太短或 test 命令错先手动执行 test 命令确认返回码
docker compose 报 YAML 解析错误缩进或 & / * 锚点使用不当docker compose config 会指出行号

健康检查不是万能的

pg_isready 只说明 Postgres 接受连接，不说明你的业务表已建好；redis-cli ping 只说明 Redis 响应，不说明数据已恢复。健康检查要检查「这个服务对这个应用可用」，而不是「进程活着」。

企业级做法 ​

  1. 一份 compose 拆成 base + override：compose.yml 放通用配置，compose.dev.yml / compose.prod.yml 覆盖差异，避免复制粘贴。
  2. 迁移与启动分离：迁移作为独立的一次性任务，在发布流水线里先执行，成功后再滚动更新应用；不要塞进应用启动钩子。
  3. 所有依赖都有健康检查：没有健康检查的 depends_on 只是「启动顺序」，不是「可用顺序」。
  4. 内部服务不发布端口：只暴露入口（网关 / BFF），数据库与缓存留在内部网络。
  5. 资源与日志有上限：deploy.resources.limits 或 mem_limit，日志配 max-size / max-file。
  6. 生产不用 compose 直接跑：compose 适合本地与单机；多机、滚动发布、自动扩缩交给 Kubernetes 或云平台（第 11 章）。
  7. 配置外置：镜像不变，环境变量与 secrets 按环境注入（第 09 章）。

练习与验收标准 ​

练习

  1. 把 depends_on.migrate.condition 改成 service_started，清空卷后重启，观察 api 是否报错，再改回。
  2. 给 redis 增加 --maxmemory 128mb --maxmemory-policy allkeys-lru，用 docker compose exec redis redis-cli info memory 验证。
  3. 把 api 的端口改成 127.0.0.1:13002:3000，确认 port api 3000 的输出变化。
  4. 只启动 postgres，用 docker compose run --rm migrate 手动迁移，理解「服务」和「一次性任务」的区别。

验收标准（可逐条执行）

  • [ ] ps -a 中 migrate 是 Exited (0)，不是 Restarting；
  • [ ] postgres、redis、api 三个常驻服务都是 (healthy)；
  • [ ] curl 127.0.0.1:13001/api/health/ready 返回 "status":"ok"，且 database 与 cache 都是 up；
  • [ ] psql \dt 能看到 10 张业务表；
  • [ ] docker compose port postgres 5432 返回 :0；
  • [ ] down 后重新 up，迁移记录仍然存在；
  • [ ] 能解释三种 depends_on 条件的差别，并各举一个适用场景。
