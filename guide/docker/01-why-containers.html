01 为什么需要容器：从进程隔离到镜像 ​

容器与虚拟机的差别、镜像分层与容器生命周期，用仓库自带依赖完成第一次实战。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 用一句话说清容器与虚拟机的差别，以及这个差别带来的真实代价；
  2. 在仓库根目录起 Postgres 与 Redis，并确认它们是「可用」而不只是「在跑」；
  3. 读懂 docker compose ps 的每一列，知道 0.0.0.0:5432->5432/tcp 的方向；
  4. 说清镜像分层与容器生命周期，理解「主进程退出 = 容器退出」意味着什么；
  5. 判断什么该进容器、什么不该，理解本仓库「依赖容器化、应用留在宿主机」的选择。

概念与原理 ​

三个词：镜像、容器、仓库 ​

概念是什么类比
镜像（image）只读的文件系统快照 + 启动命令，不可修改类（class）
容器（container）镜像的一次运行实例，自带一个可写层对象（instance）
仓库（registry）存放镜像的服务，如 Docker Hub、私有 Harbornpm registry

docker run postgres:17 的真实含义是：拉取镜像 → 加一层可写层 → 创建进程 → 启动。postgres:17 里的 17 是标签（tag），不带标签默认 latest，生产环境不要这么写。

容器不是轻量级虚拟机 ​

维度虚拟机容器
内核每台虚拟机一套完整内核共享宿主机内核
启动数十秒（要引导系统）毫秒到秒级（只是起进程）
隔离硬件级（Hypervisor）进程级（namespace + cgroup）
体积GB 级磁盘镜像MB 级，依赖基础镜像
能跑别的内核能不能（Linux 容器跑不了 Windows 内核）

「共享内核」是理解后面所有问题的钥匙：macOS / Windows 上没有 Linux 内核，所以 Docker Desktop 必须先跑一台 Linux 虚拟机，你的容器实际跑在里面。这也是文件挂载慢、内存有上限、CPU 要分配的根源——第 04 章会专门处理这些设置。

隔离靠的是 Linux 的三样东西：namespace（看不见别人的进程、网络、挂载点）、cgroup（限制能用多少 CPU 与内存）、capabilities / seccomp（限制能调用哪些内核能力）。容器里的 root 不等于宿主机的 root，但默认也没那么安全，第 12 章会讲运行时加固。

镜像分层：为什么第二次拉取和构建都更快 ​

镜像由一层层只读文件系统叠加而成，每条构建指令通常产生一层：

text
postgres:17
├── 基础系统层（debian-slim）
├── apt 安装的依赖层
├── postgres 二进制层
└── ENTRYPOINT / CMD 元数据层

层是共享的：同一台机器上两个镜像用了同一个基础层，磁盘只存一份。容器启动时在最上面加一个可写层，写文件触发 copy-on-write——修改一个 1MB 的文件，不会把整层复制一遍。

这也是 Dockerfile 里「先复制 package.json 再装依赖、最后复制源码」的原因：依赖层能被缓存复用。第 06 章会用本仓库的 apps/api/Dockerfile 完整拆解。

容器生命周期与 PID 1 ​

text
created ──start──▶ running ──stop──▶ exited ──start──▶ running
                     │  ▲
                  pause └─unpause

关键事实：容器的生命周期绑定的是 PID 1 进程。PID 1 退出，容器立刻结束，不管里面还有没有别的进程。所以镜像的 CMD 必须是前台进程（postgres、redis-server、node dist/main.js），不能是 systemctl start 那种把服务丢到后台就返回的写法。

代价是：PID 1 默认不处理 SIGTERM 的「转发」和「回收僵尸进程」。本仓库的生产镜像用 CMD ["node", "dist/main.js"] 让 Node 直接成为 PID 1，SIGTERM 才能直达进程并触发 enableShutdownHooks（见 apps/api/src/main.ts 的 enableShutdownHooks 调用）。第 12 章会讲 --init 与 tini 的适用场景。

本仓库的分工：依赖进容器，应用留宿主机 ​

打开 compose 文件顶部就能看到这个决定：

yml
services:
  postgres:
    image: postgres:17
    container_name: nestjs-tutorial-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${DB_USERNAME:-postgres}
      POSTGRES_PASSWORD: ${DB_PASSWORD:-postgres}
      POSTGRES_DB: ${DB_NAME:-nestjs_tutorial}
    ports:
      - '${DB_PORT:-5432}:5432'
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U ${DB_USERNAME:-postgres} -d ${DB_NAME:-nestjs_tutorial}']
      interval: 5s
      timeout: 3s
      retries: 10

  # 第 07 章缓存与第 08 章队列共用同一个 Redis。
  # 缓存可以丢，但队列里的任务不能凭空消失，因此开启 AOF 持久化。
  redis:
    image: redis:7-alpine
    container_name: nestjs-tutorial-redis
    restart: unless-stopped
    command: ['redis-server', '--appendonly', 'yes']
    ports:
      - '${REDIS_PORT:-6379}:6379'
    volumes:
      - redisdata:/data
    healthcheck:
      test: ['CMD', 'redis-cli', 'ping']
      interval: 5s
      timeout: 3s
      retries: 10
  • Postgres / Redis 进容器：版本固定、随起随停、不污染本机、团队环境一致；
  • 应用留在宿主机：pnpm dev 的热重载、IDE 断点、node --inspect 都不受文件系统与网络隔离影响；
  • 生产镜像单独用 profile 隔离：api 服务带 profiles: ['container']，默认 up 不会启动它，避免和你本地的 3000 端口打架。

这不是「不容器化」，而是把容器用在收益最高的地方：环境依赖。第 05 章起再把自己的应用真正装进镜像。

最小可跑示例 ​

一、确认 Docker 可用 ​

bash
docker version --format '{{.Server.Version}}'
docker compose version

本机实测输出（版本随你的安装变化）：

text
29.9.2
Docker Compose version v5.6.1

注意 docker version 有 Client 与 Server 两段。如果只打印 Client、Server 段报 Cannot connect to the Docker daemon，说明守护进程没起来——macOS / Windows 上通常是 Docker Desktop 没启动。第 02 章专门讲安装与首次配置。

二、只起两个依赖 ​

bash
docker compose up -d postgres redis
docker compose ps --format 'table {{.Name}}\t{{.Image}}\t{{.Service}}\t{{.Status}}\t{{.Ports}}'

真实输出（省略 CREATED 列以便阅读）：

text
NAME                       IMAGE            SERVICE    STATUS                 PORTS
nestjs-tutorial-postgres   postgres:17      postgres   Up 4 hours (healthy)   0.0.0.0:5432->5432/tcp, [::]:5432->5432/tcp
nestjs-tutorial-redis      redis:7-alpine   redis      Up 4 hours (healthy)   0.0.0.0:6379->6379/tcp, [::]:6379->6379/tcp

两条都是 (healthy) 才叫「可用」。第一次跑会先拉镜像，Postgres 还要执行 initdb，Up 之后会有一段 (health: starting)。

为什么没起 api？因为它在 profiles: ['container'] 里。查看「实际会被启动的服务」用 docker compose config --services，输出只有 postgres 和 redis。

三、验证「能用」，而不是「在跑」 ​

bash
docker compose exec postgres pg_isready -U postgres -d nestjs_tutorial
docker compose exec redis redis-cli ping
text
/var/run/postgresql:5432 - accepting connections
PONG

docker compose exec 是「在已运行的容器里执行一条命令」，和 docker exec -it <容器名> sh 等价，只是用服务名代替容器名。想进交互式 shell：

bash
docker compose exec postgres psql -U postgres -d nestjs_tutorial

进库后 \dt 能看到本仓库迁移创建的表（users、orders、migrations 等），\q 退出。

四、停与删：三个命令的区别 ​

bash
docker compose stop postgres redis    # 停进程，容器与数据都还在
docker compose start postgres redis   # 再起来
docker compose down                    # 删容器 + 网络，保留数据卷
docker compose down -v                 # 连数据卷一起删，数据不可恢复

日常切换分支、改配置用 down 就够了；只有「初始化参数变了、库结构要重来」时才用 -v。

逐步拆解 ​

第 1 步：up -d 到底按什么顺序做事 ​

  1. 解析 docker-compose.yml，校验语法与变量插值（${DB_PORT:-5432}）；
  2. 检查镜像是否存在，不存在则从仓库拉取；
  3. 创建项目专属网络（nestjs-tutorial_default）；
  4. 按 depends_on 顺序创建并启动容器，挂载卷与端口；
  5. -d 只是「不等日志输出、直接返回」，不代表服务已就绪。

第 5 点最容易踩：up -d 返回成功时，Postgres 可能还在初始化。判断就绪只能看 healthcheck 或自己探测。

第 2 步：端口映射的方向与绑定地址 ​

yaml
ports:
  - '${DB_PORT:-5432}:5432'

格式是 宿主机端口:容器端口，方向别记反。展开成 0.0.0.0:5432->5432/tcp 表示：宿主机所有网卡（含局域网）的 5432 转发到容器 5432。

两个推论：

  • 容器里的 localhost 指容器自己，不是宿主机。所以应用在容器内连接数据库时必须写服务名 postgres（compose 内置 DNS 会解析），而不是 127.0.0.1。本仓库 api 服务的 DB_HOST: postgres 就是这个原因。
  • 只在宿主机本机访问时，写成 127.0.0.1:5432:5432 更安全，避免同网段的人连上你的开发库。

第 3 步：healthcheck 决定「什么时候算起来」 ​

yaml
healthcheck:
  test: ['CMD-SHELL', 'pg_isready -U ${DB_USERNAME:-postgres} -d ${DB_NAME:-nestjs_tutorial}']
  interval: 5s
  timeout: 3s
  retries: 10

pg_isready 会真正连一次数据库，返回 0 才算健康；Redis 用 redis-cli ping 期待 PONG。健康状态有三档：starting → healthy / unhealthy。

配合 depends_on 的条件写法，应用才会「等依赖真的能连」再启动：

yaml
depends_on:
  postgres:
    condition: service_healthy
  redis:
    condition: service_healthy

短语法 depends_on: [postgres] 只保证「容器已创建」，不保证「数据库能接受连接」，这是新手最常见的启动时序事故。

第 4 步：卷——容器可删，数据不可删 ​

yaml
volumes:
  - pgdata:/var/lib/postgresql/data

命名卷（named volume）由 Docker 管理，存在 Docker Desktop 的虚拟磁盘里；容器删了卷还在，新容器挂同一个卷就能看到旧数据。所以：

  • docker compose down 之后数据仍在，这是设计如此，不是 bug；
  • 环境变量（POSTGRES_PASSWORD）只在数据目录为空时生效。卷里已有旧库时改密码不生效，还会报认证失败，只能 down -v 重来。

数据库为什么不用 bind mount（./data:/var/lib/postgresql/data）？macOS / Windows 上宿主机文件系统经虚拟化层转发，随机 IO 明显更慢，uid/gid 映射也容易出权限问题。开发期用命名卷，需要备份时用 pg_dump 导出，而不是直接拷贝目录。

第 5 步：这些名字是从哪来的 ​

text
容器：nestjs-tutorial-postgres      ← compose 里的 container_name
网络：nestjs-tutorial_default        ← 项目名_default
卷：  nestjs-tutorial_pgdata         ← 项目名_卷名

项目名默认取 compose 文件所在目录名。多份 checkout、或者本机同时跑两个项目时，容器名可能冲突；用 docker compose -p myproj up -d 或环境变量 COMPOSE_PROJECT_NAME 显式指定。

第 6 步：容器里跑的是什么 ​

bash
docker compose exec postgres ps -ef
text
UID          PID    PPID  C STIME TTY          TIME CMD
postgres       1       0  0 07:57 ?        00:00:02 postgres
postgres      27       1  0 07:57 ?        00:00:00 postgres: checkpointer
postgres      28       1  0 07:57 ?        00:00:00 postgres: background writer

postgres 就是 PID 1。它前面没有 init、没有 systemd，容器里看到的就是这一组进程。这解释了为什么「进容器 service postgresql restart」通常没用：没有服务管理器，重启要在宿主机执行 docker compose restart postgres。

常见坑与排查 ​

现象根因排查与修复
Cannot connect to the Docker daemon守护进程没运行启动 Docker Desktop，等托盘图标变为运行中；docker info 能通再继续
Bind for 0.0.0.0:5432 failed: port is already allocated本机已有 Postgres 或另一个容器占了 5432lsof -i :5432 找占用者；或 DB_PORT=5433 docker compose up -d postgres，同时把 apps/api/.env 的 DB_PORT 改成 5433
docker compose ps 显示 Up，但应用连不上数据库还在初始化，端口通了不代表能登录看 STATUS 是否 healthy；docker compose logs -f postgres 尾部是否有 database system is ready to accept connections
password authentication failed for user "postgres"卷里是旧数据，新的 POSTGRES_PASSWORD 不生效确认可以丢数据后 docker compose down -v 再 up；不要反复改密码试
no such service: postgres不在仓库根目录执行，或文件名不叫 docker-compose.ymlpwd 确认在仓库根；compose 文件必须在当前目录或 -f 指定
容器 Exited (0) 立刻退出主进程执行完就结束了（如用 CMD 跑了 --version）docker compose logs <service> 看最后几行输出
端口映射写了 5432:5432 但外部访问不到服务只监听了容器内的 127.0.0.1容器内服务要监听 0.0.0.0；docker compose port postgres 5432 确认映射
Apple Silicon 上大量 WARNING: The requested image's platform (linux/amd64)拉了 amd64 镜像，走 QEMU 模拟，慢且可能崩优先选支持 arm64 的标签；第 10 章讲多架构构建
docker compose down 后数据还在命名卷不随容器删除预期行为；要清空用 down -v
磁盘空间莫名减少旧镜像、构建缓存、卷堆积docker system df 看占用，第 04 章讲安全清理顺序

先看状态，再看日志

容器类问题按这个顺序查，能省一半时间：docker compose ps（状态与端口）→ docker compose logs --tail=50 <service>（进程输出）→ docker compose exec <service> sh（进容器看现场）。跳过前两步直接翻代码，通常是在猜。

企业级做法 ​

  1. 依赖容器化、应用按需容器化：本地开发用 compose 起中间件，应用跑在宿主机；只有验收生产镜像时才用 --profile container。减少一层网络与文件系统转发，调试体验完全不一样。
  2. 镜像标签写死到次版本：postgres:17 可接受，postgres:latest 不可接受。更严格的做法是写 digest（postgres:17@sha256:...），保证任何机器拉到的字节一致。
  3. 用 healthcheck + 条件依赖，不用 sleep 10：sleep 在快机器上浪费时间，在慢机器上照样失败。
  4. 开发端口只绑回环：127.0.0.1:5432:5432，尤其在公司网络或咖啡厅 Wi-Fi 下。
  5. 密码与连接串走环境变量：compose 里的 ${DB_PASSWORD:-postgres} 只是本地默认值，共享环境必须外部注入；.env 已在 .gitignore 里，只提交 .env.example。
  6. 明确项目名：CI 或一台机器多项目时用 -p / COMPOSE_PROJECT_NAME，避免容器名、网络、卷互相污染。
  7. 数据卷要能重建：任何「只能靠卷里的手改数据才能跑」的环境都是定时炸弹。备份用 pg_dump，恢复脚本进仓库。

练习与验收标准 ​

练习

  1. 用 DB_PORT=5433 docker compose up -d postgres 起第二份 Postgres，观察容器名冲突并解决（提示：-p）。
  2. 删掉 compose 里 postgres 的 healthcheck，把 api 的 depends_on 改成短语法，用 --profile container 启动，记录 api 的报错原文。
  3. 在容器里执行 docker compose exec postgres psql -U postgres -d nestjs_tutorial -c '\dt'，对照 apps/api/src/database/migrations 说出每张表由哪个迁移创建。
  4. 执行 docker system df，记录 images / containers / local volumes / build cache 四项占用，先不清理。

验收标准（可逐条执行）

  • [ ] docker compose up -d postgres redis 后，docker compose ps 两行 STATUS 均为 Up ... (healthy)；
  • [ ] docker compose exec postgres pg_isready -U postgres -d nestjs_tutorial 输出 accepting connections；
  • [ ] docker compose exec redis redis-cli ping 输出 PONG；
  • [ ] docker compose down 再 up -d，之前写入的数据仍在；down -v 后数据清空；
  • [ ] 能解释 0.0.0.0:5432->5432/tcp 中两个 5432 各指什么、0.0.0.0 意味着什么；
  • [ ] 能说出为什么 compose 里 api 的 DB_HOST 是 postgres，而宿主机 .env 里是 localhost；
  • [ ] 能解释「容器里 PID 1 是谁」以及为什么它退出容器就结束。
