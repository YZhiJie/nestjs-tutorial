02 Docker Desktop 安装与首次配置 ​

Docker Desktop 的组成、macOS/Windows 安装差异、首次自检、context 切换、授权边界与升级策略。

本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清 Docker Desktop 在 macOS 与 Windows 上分别多做了哪几件事，为什么不能只装一个 docker 客户端；
  2. 用一条自检脚本判断「装好了」和「真的能用了」的区别；
  3. 在 default 与 desktop-linux 两个 context 之间切换，知道命令为什么有时连不上；
  4. 区分 Docker Engine（开源）与 Docker Desktop（订阅）的授权边界，避免在公司环境里用错；
  5. 制定一条可执行的升级策略，而不是每次弹窗都点「稍后提醒」。

概念与原理 ​

Docker Desktop 不是「Docker 的图形界面」 ​

它是一套打包好的开发环境：

组件作用没有它会怎样
Docker CLI你敲的 docker 命令命令不存在
Docker Engine真正创建容器、管理镜像的守护进程Cannot connect to the Docker daemon
Linux 虚拟机macOS / Windows 没有 Linux 内核，容器跑在里面容器无法启动
Compose / buildx 插件docker compose、多架构构建子命令缺失
文件共享层把宿主机目录挂进容器源码改动容器看不见
Docker Desktop GUI面板、日志、设置、Kubernetes 开关只能改配置文件

第 01 章说过「容器共享宿主机内核」。macOS 和 Windows 的内核不是 Linux，所以 Docker Desktop 必须先启动一台轻量 Linux 虚拟机，再在里面跑 engine。你所有的容器都跑在这台虚拟机里，这也是第 04 章资源限制、文件共享性能问题的根源。

macOS 与 Windows 的差异 ​

维度macOSWindows
虚拟化Apple Virtualization.framework（Intel 用 HyperKit 的历史包袱已基本退场）默认 WSL2 后端；旧版可选 Hyper-V
文件共享VirtioFS（较新版本）或 gRPC-FUSEWSL2 跨文件系统访问，/mnt/c 与 /home 性能差异大
设置文件~/Library/Group Containers/group.com.docker/settings-store.json%APPDATA%\Docker\settings-store.json
企业统一配置/Library/Application Support/Docker Desktop/admin-settings.jsonC:\ProgramData\DockerDesktop\admin-settings.json
架构Apple Silicon 为 arm64，Intel 为 x86_64以 x86_64 为主，ARM 设备走模拟

Windows 上还有一个容易忽略的差异：WSL2 里的 Linux 文件系统比 /mnt/c 快得多。项目放在 C:\Users\... 下再挂进容器，等价于每次都跨一层 9P 文件共享；放在 WSL2 发行版内部（\\wsl$\Ubuntu\home\...）会明显更快。

两个 context：default 与 desktop-linux ​

bash
docker context ls

本机真实输出：

text
NAME              DESCRIPTION                               DOCKER ENDPOINT                                    ERROR
default           Current DOCKER_HOST based configuration   unix:///var/run/docker.sock
desktop-linux *   Docker Desktop                            unix:///Users/yangzhijie/.docker/run/docker.sock

带 * 的是当前 context。default 指向 /var/run/docker.sock，这是 Linux 上原生 Docker Engine 的路径；macOS 上通常没有这个 socket，所以切到 default 就会报连不上。Docker Desktop 把 socket 放在用户目录下，通过 desktop-linux 这个 context 暴露出来。

切换 context 不会重启容器，但会让后续命令打到另一台「引擎」上。排查「为什么我的容器不见了」时，先看这里。

授权边界：Engine 免费，Desktop 不一定 ​

对象许可证什么时候需要付费
Docker Engine（dockerd、CLI、Compose 插件）Apache-2.0不需要
Docker Desktop商业订阅（含个人免费条款）大型企业、政府机构等超出免费范围的使用
Docker Hub免费额度 + 付费档需要更多私有仓库、更高拉取限额时
Docker Build Cloud / Scout / IAM / SSO付费或更高档订阅团队级构建加速、策略扫描、组织级权限

Docker Desktop 的免费范围以官方订阅协议为准，通常表述为：个人使用、教育、非商业开源项目，以及同时满足员工数少于 250 人、年收入低于 1000 万美元的小型企业。超过这个范围（或属于政府机构）需要付费订阅。这条边界会随官方条款调整，落地前请以 Docker 官网当前条款为准，不要拿本文当法务依据。

判断方法：如果公司在用 Docker Desktop 做商业开发，先问 IT / 法务有没有订阅，而不是看「能不能装上」。装得上不等于授权合规。

登录与更新策略 ​

docker login 不是使用容器的前提，公开镜像不登录也能拉。登录主要带来三件事：推送私有镜像、提高 Docker Hub 拉取限额、让 Scout / Build Cloud 等云能力关联到账号。

更新策略有两种典型做法：

  • 个人机器跟随自动更新：省事，但某天面板升级后构建行为可能变化；
  • 团队 / CI 固定版本：记录当前版本号，升级前在分支上跑一遍镜像构建与 compose 验收，再统一升级。

查看版本：

bash
docker version --format 'Client {{.Client.Version}} / Server {{.Server.Version}}'
docker desktop version

本机真实输出：

text
Client 29.9.2 / Server 29.9.2
Docker Desktop CLI plugin version: 4.97.0

注意 Client 与 Server 版本可以不同（尤其是连远程引擎时）。两者差距过大时，新客户端的一些参数可能不被旧引擎识别，报错往往很隐晦。

最小可跑示例 ​

一、跑自检脚本 ​

bash
bash examples/docker/02-install-check/check-environment.sh

脚本按「客户端与插件 → 守护进程 → 架构一致性 → 资源与磁盘」四段检查。核心的 Server 检查：

bash
section "守护进程与服务端"
if docker info >/dev/null 2>&1; then
  ok "守护进程可达（context: $(docker context show)）"
  printf '       Server: %s (%s/%s, %s 核, %s)\n' \
    "$(docker version --format '{{.Server.Version}}')" \
    "$(docker info --format '{{.OperatingSystem}}')" \
    "$(docker info --format '{{.Architecture}}')" \
    "$(docker info --format '{{.NCPU}}')" \
    "$(docker info --format '{{.MemTotal}}' | awk '{ printf "%.1f GiB", $1/1024/1024/1024 }')"
else
  bad "Cannot connect to the Docker daemon：先启动 Docker Desktop，等托盘图标变为运行中"
  printf '\n结果：%d 通过 / %d 警告 / %d 失败\n' "$pass" "$warn" "$fail"
  exit 1
fi

# Docker Desktop 专属的桌面 CLI（4.37+），Linux 上的 Docker Engine 没有这个命令
if docker desktop version >/dev/null 2>&1; then
  ok "Docker Desktop CLI: $(docker desktop version 2>/dev/null | head -1)"
  status=$(docker desktop status 2>/dev/null | awk '$1=="Status"{print $2; exit}')
  if [ "$status" = "running" ]; then
    ok "Docker Desktop 状态: running"
  else
    warning "Docker Desktop 状态: ${status:-unknown}，引擎可用但桌面端可能未完全就绪"
  fi
else
  warning "未检测到 docker desktop 子命令：可能是较旧版本或使用纯 Docker Engine"
fi

本机真实输出：

text
== 客户端与插件 ==
[PASS] docker CLI: Docker version 29.9.2, build a82e528
[PASS] compose 插件: Docker Compose version v5.6.1
[PASS] buildx 插件: github.com/docker/buildx v0.38.1

== 守护进程与服务端 ==
[PASS] 守护进程可达（context: desktop-linux）
       Server: 29.9.2 (Docker Desktop/aarch64, 18 核, 7.7 GiB)
[PASS] Docker Desktop CLI: Docker Desktop CLI plugin version: 4.97.0
[PASS] Docker Desktop 状态: running

== 架构一致性 ==
[PASS] 宿主机 arm64 与引擎 aarch64 一致，不会触发 QEMU 模拟

== 资源与磁盘 ==
[PASS] CPU 分配: 18 核
[PASS] 内存分配: 8 GiB
Images: 3.762GB（可回收 622.6MB (16%)）
Containers: 462.8kB（可回收 438.3kB (94%)）
Local Volumes: 214.8MB（可回收 0B (0%)）
Build Cache: 6.361GB（可回收 988.1MB）

结果：9 通过 / 0 警告 / 0 失败

docker desktop 是 4.37 之后才有的桌面 CLI，纯 Docker Engine（Linux 服务器）没有这个子命令。脚本把它标成 WARN 而不是 FAIL，因为「没有桌面端」对服务器来说是正常的。

二、跑一个一次性容器 ​

yml
# 02 章最小示例：验证「拉镜像 → 建容器 → 打印 → 退出码」整条链路。
# 运行：docker compose -f examples/docker/02-install-check/compose.hello.yml run --rm hello
services:
  hello:
    # 固定到次版本，不用 latest：不同机器拉到的字节一致，排查问题时不会互相甩锅
    image: node:24-alpine
    # 一次性任务，不需要重启策略（默认就是 no，这里写出来是为了让读者看见）
    restart: 'no'
    command:
      - node
      - -e
      - |
        // compose 会把美元符号加花括号解析成变量插值，所以这里用字符串拼接
        console.log('arch: ' + process.arch);
        console.log('node: ' + process.version);
        console.log('hostname: ' + require('node:os').hostname());
        console.log('image is working');
bash
docker compose -f examples/docker/02-install-check/compose.hello.yml run --rm hello

本机真实输出：

text
arch: arm64
node: v24.22.2
hostname: 746d1ec63c65
image is working

arch: arm64 说明容器跑在 arm64 上，没有走模拟。如果是 Apple Silicon 却打印 x64，说明镜像只有 amd64 版本，Docker 正在用 QEMU 翻译指令——能跑，但构建和运行都会慢，第 10 章会处理多架构镜像。

逐步拆解 ​

第 1 步：安装后先确认「引擎活了」 ​

Docker Desktop 启动分两个阶段：GUI 起来，引擎就绪。托盘图标变成「运行中」不代表 engine 已经接受连接，docker info 成功才作数。

bash
docker info --format '{{.ServerVersion}} {{.OperatingSystem}} {{.Architecture}}'

本机输出 29.9.2 Docker Desktop aarch64。失败时优先看 Docker Desktop 的 Troubleshoot 面板，而不是重装。

第 2 步：Windows 的 WSL2 后端要单独确认 ​

WSL2 后端不是「装完 Docker Desktop 就自动好」。依次确认：

powershell
wsl --status
wsl --update
wsl -l -v

wsl -l -v 里应能看到 docker-desktop 发行版，且 VERSION 为 2。如果 Docker Desktop 设置里勾选了「Use the WSL 2 based engine」，但 wsl --status 报内核需要更新，按提示执行 wsl --update 后重启。

还要注意：项目放在 Windows 文件系统还是 WSL2 文件系统，性能差一个数量级。做 Node 项目时，把仓库放在 WSL2 的 ~/projects 下，用 VS Code 的 Remote-WSL 打开，比在 C:\ 下挂载快得多。

第 3 步：看 context，而不是猜 ​

bash
docker context show
docker context inspect desktop-linux --format '{{.Endpoints.docker.Host}}'

如果 docker context show 输出 default，但你的容器都在 Desktop 里，执行：

bash
docker context use desktop-linux

反过来，如果连的是公司远程构建机，docker context use <name> 切过去即可，不需要改 DOCKER_HOST。context 是比环境变量更不容易出错的机制。

第 4 步：登录与凭据存储 ​

bash
docker login
docker info --format '{{.RegistryConfig.CredentialStore}}'

macOS 上通常是 osxkeychain，Windows 上是 wincred。登录成功后凭据进系统钥匙串，不会以明文写进 ~/.docker/config.json。

常见失败是 401：Docker Hub 开启了两步验证时，密码位置要填 Personal Access Token，不是账号密码。公司私有仓库则要先 docker login harbor.example.com，域名写全。

不想在共享机器上留凭据时，用完执行 docker logout。

第 5 步：资源设置在哪里改 ​

GUI 路径：Settings → Resources。对应到文件是 settings-store.json，但不建议手改：Docker Desktop 运行时可能覆盖，而且不同版本字段会变。企业批量下发用的是另一份 admin-settings.json，优先级更高。

资源设置影响的是那台 Linux 虚拟机，不是你的 Mac：

  • CPU / Memory 给太少，pnpm install 和 TypeScript 编译会 OOM；
  • 给太多，宿主机其他程序会卡；
  • Disk image size 是虚拟磁盘上限，只增不减，扩容容易缩容难。

本机分配 18 核 / 8 GiB，是 Docker Desktop 根据宿主机配置给的默认值。日常 NestJS 开发 4 核 / 4 GiB 就够，跑镜像构建时再临时调高。

第 6 步：更新策略落地 ​

个人机器可以跟随自动更新。团队环境建议做三件事：

  1. 记录当前版本：docker desktop version；
  2. 升级前在分支跑 docker compose --profile container up -d --build 与健康检查；
  3. 把版本写进团队文档，而不是「大家自己看着办」。

Docker Desktop 的更新很频繁，且会同时升级 CLI、Compose、buildx、containerd。一次升级同时变四个组件，出问题时很难定位，所以升级要有可回退的验收步骤。

常见坑与排查 ​

现象根因排查与修复
zsh: command not found: dockerCLI 没进 PATH，或装的是旧版 Docker Toolboxwhich -a docker；macOS 检查 /usr/local/bin/docker 或 ~/.docker/bin；重开终端
Cannot connect to the Docker daemon引擎没启动，或 context 指错先 docker desktop status，再 docker context show；必要时 docker context use desktop-linux
docker: 'compose' is not a docker command只装了 CLI，没有 Compose 插件docker compose version；检查 ~/.docker/cli-plugins/docker-compose
Windows 上提示 WSL2 内核版本过低WSL2 没更新wsl --update 后重启；仍失败则 wsl --shutdown 再启动 Docker Desktop
拉镜像报 no matching manifest for linux/arm64镜像只有 amd64找支持 arm64 的 tag，或用 --platform linux/amd64 明确接受模拟
docker login 报 401用了账号密码而不是 PAT，或开了 2FA在 Docker Hub 创建 Personal Access Token 当密码用
面板显示 Docker Desktop is starting 很久虚拟磁盘损坏、代理阻断、资源不足看 Troubleshoot → Logs；先重启 Docker Desktop，再考虑 Reset
磁盘镜像只增不减已删除的镜像层仍留在 Docker.raw / ext4.vhdx第 04 章清理；必要时用 Docker Desktop 的 disk usage 面板压缩
公司网络下拉取超时代理未配置到 Docker DesktopSettings → Resources → Proxies 配置；容器内代理需要另外注入环境变量
提示订阅到期 / 无法启动商业使用超出免费范围联系管理员购买订阅；不要用破解补丁，审计与支持都会失效

先分清「没装好」和「没连上」

docker --version 成功只证明客户端在；docker info 成功才证明引擎在。绝大部分「Docker 坏了」其实是引擎没启动或 context 指错，重装是最后手段。

企业级做法 ​

  1. 用 MDM 统一下发安装包与 admin-settings.json：把代理、镜像仓库、资源上限、是否允许自动更新固定下来，避免每台机器各配一套。
  2. 固定版本并记录升级窗口：Docker Desktop 升级会同时改变 CLI / Compose / buildx / containerd 行为，团队要有一个「升级后跑哪几条验收命令」的清单。
  3. 明确授权责任人：Docker Desktop 是商业产品，Engine 是开源项目。公司规模超过免费范围时，采购与合规要提前介入，别等审计。
  4. 配置镜像加速或私有仓库：公司网络直连 Docker Hub 往往不稳定，用内部 Harbor 或受控的 registry mirror，并在 admin-settings.json 里统一下发。
  5. Windows 团队统一 WSL2 工作目录：仓库放 WSL2 文件系统，文档里写清楚路径，避免「在我机器上很快」的争议。
  6. 不要把 Docker Desktop 当生产运行时：生产用 Docker Engine / containerd / Kubernetes，Desktop 只负责本地开发与镜像构建。
  7. 凭据不进仓库：docker login 用系统钥匙串；CI 用短期 token 或 OIDC，不要往 .env 里写长期密码。

练习与验收标准 ​

练习

  1. 执行 docker context use default，再跑 docker info，记录报错原文，然后切回 desktop-linux。
  2. 把 compose.hello.yml 的镜像改成 --platform linux/amd64 的写法，观察宿主机是 arm64 时的行为差异。
  3. 在 Docker Desktop 的 Settings → Resources 里把内存调到 2 GiB，跑一次 docker compose --profile container build，记录失败点，再调回去。
  4. 执行 docker info --format '{{json .DriverStatus}}'，找到虚拟磁盘的实际路径与文件系统类型。

验收标准（可逐条执行）

  • [ ] bash examples/docker/02-install-check/check-environment.sh 退出码为 0，且输出里没有 FAIL；
  • [ ] docker context show 输出 desktop-linux；
  • [ ] docker compose -f examples/docker/02-install-check/compose.hello.yml run --rm hello 打印 arch: 与 image is working；
  • [ ] 能说出 Client 与 Server 的差别，以及 docker --version 成功但 docker info 失败意味着什么；
  • [ ] 能说出 macOS 与 Windows 各自用什么虚拟化后端，以及设置文件大概在哪；
  • [ ] 能解释 Docker Engine 与 Docker Desktop 的授权边界，并说出判断公司是否要付费的两个维度。
