12 运行时安全与生产落地 ​

非 root、只读根文件系统、cap_drop 与 no-new-privileges 的运行时加固，以及镜像与运行时两层安全清单。

成稿正文、示例代码与验收标准均已完整，可直接跟练
难度
★★★★☆
预计课时
2 小时
最后核对
2026-11-10

本章目标 ​

读完并动手做完本章，你应该能：

  1. 用非 root、只读根文件系统、cap_drop: ALL、no-new-privileges 收敛一个容器的攻击面；
  2. 用 docker inspect 与容器内 /proc/self/status 验证配置真的生效；
  3. 说清「镜像安全」与「运行时安全」是两件事，各自该做什么；
  4. 知道漏洞扫描、策略管控、调试工具里哪些属于 Docker 付费能力；
  5. 列出一份可以直接落到生产的最小加固清单。

概念与原理 ​

两层安全：镜像与运行时 ​

text
镜像层：基础镜像、依赖、是否 root、有没有多余工具、漏洞
运行时层：以什么用户跑、有哪些 capabilities、能不能写、能不能提权、资源上限

只做其中一层都不够：

  • 镜像里删了 curl，但容器以 root + 默认 capabilities 跑，被利用后仍可能影响宿主机；
  • 运行时加固得很好，但基础镜像里有已知高危漏洞，攻击面依然存在。

本章示例两层都演示：Dockerfile 固定非 root uid，compose 再加运行时限制。

默认容器并不「安全隔离」 ​

Docker 默认给容器一组 Linux capabilities（常见 CAP_CHOWN、CAP_NET_RAW、CAP_SETUID 等），并且以 root 运行是常态。默认的 CapEff 在本机实测是：

text
00000000a80425fb

这意味着容器内的 root 拥有相当一部分特权。cap_drop: ALL 后：

text
0000000000000000

权限被清空，应用只能做它真正需要的事。如果确实需要绑定 80 端口这类能力，再单独 cap_add 回 NET_BIND_SERVICE。

每个开关挡住什么 ​

配置挡住什么代价
user: 10001:10001容器内 root 被利用后的影响面需要处理文件属主与写目录
read_only: true篡改二进制、写 webshell应用不能写根文件系统，要挂 tmpfs
cap_drop: ALL原始套接字、改属主、挂载等特权操作需要时逐项 cap_add
no-new-privileges:truesetuid / setcap 提权极少影响普通应用
pids_limitfork 炸弹并发高的应用要调大
mem_limit / cpus单容器吃满宿主机资源需要按负载评估
tmpfs: /tmp临时文件落盘、残留容器重启后丢失

只读根文件系统与可写目录 ​

read_only: true 后，整个根文件系统只读，典型报错：

text
EROFS: read-only file system

应用通常需要写这些位置，必须显式挂载：

  • /tmp：用 tmpfs；
  • 缓存目录、上传目录：用命名卷或 bind mount；
  • 日志：输出到 stdout / stderr，交给 Docker 日志驱动。

本章的演示服务把「写 /app 失败、写 /tmp 成功」直接做成了接口返回值，方便验证。

镜像扫描与策略 ​

漏洞扫描回答「这个镜像里有哪些已知 CVE」，常见工具是 Trivy、Grype、Docker Scout。

  • Docker Scout：基础查看免费，策略、持续监控、组织级报告属于付费能力，具体以订阅档位为准；
  • Trivy / Grype：开源，可离线或自建漏洞库镜像；
  • 扫描结果要接入 CI 门禁，否则只是「报告很好看」。

本章的扫描脚本在本机因漏洞库下载失败而未产出结果，正文如实标注。

调试能力的边界 ​

  • docker exec、docker logs、docker inspect 免费；
  • Docker Debug 属于 Desktop 订阅能力，可用性随档位变化；
  • 不要为了「方便调试」在生产镜像里装 curl、vim、tcpdump，需要时用临时调试容器共享 namespace。

最小可跑示例 ​

一、加固镜像 ​

dockerfile
# 12 章：加固镜像的最小写法。
# 三个关键点：固定非 root uid、不装多余工具、不写启动脚本。
FROM node:24-alpine

WORKDIR /app

# 只复制运行所需的文件；不要把 .git、测试、文档带进镜像
COPY app/server.mjs ./server.mjs

# 固定 uid/gid：避免不同机器上自动分配的 uid 不一致，
# 也避免用 root（uid 0）运行应用进程。
RUN addgroup -g 10001 -S app && adduser -u 10001 -S app -G app

# 切到非 root 用户；后面的 CMD 都以这个身份运行
USER 10001:10001

ENV NODE_ENV=production
EXPOSE 8080

# 直接用 node 启动，不经过 shell，减少一个可被利用的解释器层
CMD ["node", "server.mjs"]

二、加固运行时 ​

yml
# 12 章：加固姿势。每一行都对应一个可验证的攻击面收敛。
services:
  hardened:
    build:
      context: .
      dockerfile: Dockerfile
    image: docker-guide/12-security:demo
    ports:
      - '127.0.0.1:18084:8080'

    # 1. 非 root 运行（镜像里已经 USER 10001，这里再写一次，防止被覆盖）
    user: '10001:10001'

    # 2. 根文件系统只读；应用要写的地方单独挂 tmpfs
    read_only: true
    tmpfs:
      - /tmp:size=16m,mode=1777

    # 3. 丢掉所有 Linux capabilities，需要时再逐项加回
    cap_drop:
      - ALL

    # 4. 禁止通过 setuid 提权
    security_opt:
      - no-new-privileges:true

    # 5. 限制进程数与资源，降低 fork 炸弹与内存耗尽的影响
    pids_limit: 100
    mem_limit: 128m
    cpus: 0.5

    # 6. 健康检查只读接口，不依赖容器内工具
    healthcheck:
      test:
        - CMD
        - node
        - -e
        - "fetch('http://127.0.0.1:8080/').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 5s

    # 7. 日志有上限，避免磁盘被打满
    logging:
      driver: json-file
      options:
        max-size: '10m'
        max-file: '3'

三、对照实验 ​

bash
bash examples/docker/12-runtime-security/scripts/security-check.sh
bash
#!/usr/bin/env bash
# 12 章：同一镜像，两种运行时配置的对照实验。
#
# 对比项：
#   1. 容器内 uid / CapEff
#   2. 根文件系统是否可写（EROFS）
#   3. 能否读取 /etc/shadow
#   4. HostConfig 里的 ReadonlyRootfs / CapDrop / SecurityOpt
#
# 用法：bash examples/docker/12-runtime-security/scripts/security-check.sh
set -euo pipefail

here=$(cd "$(dirname "$0")/.." && pwd)
insecure="$here/compose.insecure.yml"
hardened="$here/compose.hardened.yml"

# 两个 compose 项目分开命名，避免容器名冲突
p_in='sec-insecure'
p_hard='sec-hardened'

cleanup() {
  docker compose -f "$insecure" -p "$p_in" down -v >/dev/null 2>&1 || true
  docker compose -f "$hardened" -p "$p_hard" down -v >/dev/null 2>&1 || true
}
trap cleanup EXIT

wait_url() {
  for _ in $(seq 1 40); do
    if curl -fsS "$1" >/dev/null 2>&1; then return 0; fi
    sleep 0.5
  done
  echo "等待超时: $1"
  return 1
}

echo '== 1. 构建并启动两个对照组 =='
docker compose -f "$insecure" -p "$p_in" up -d --build
docker compose -f "$hardened" -p "$p_hard" up -d --build
wait_url http://127.0.0.1:18083/
wait_url http://127.0.0.1:18084/
echo

echo '== 2. 容器内视角（同一镜像，不同运行时配置）=='
echo -n 'insecure: '
curl -s http://127.0.0.1:18083/
echo
echo -n 'hardened: '
curl -s http://127.0.0.1:18084/
echo
echo

echo '== 3. /etc/shadow 可读性 =='
if docker compose -f "$insecure" -p "$p_in" exec -T insecure sh -c 'head -1 /etc/shadow' 2>/dev/null; then
  echo 'insecure: root 可以读取 /etc/shadow'
else
  echo 'insecure: 读取失败（意外）'
fi
if docker compose -f "$hardened" -p "$p_hard" exec -T hardened sh -c 'head -1 /etc/shadow' 2>/dev/null; then
  echo 'hardened: 读取成功（意外）'
else
  echo 'hardened: 非 root 读取被拒绝（预期）'
fi
echo

echo '== 4. 运行时安全字段（来自 docker inspect）=='
c_in=$(docker compose -f "$insecure" -p "$p_in" ps -q insecure)
c_hard=$(docker compose -f "$hardened" -p "$p_hard" ps -q hardened)
echo -n 'insecure: '
docker inspect "$c_in" --format 'User={{.Config.User}} ReadonlyRootfs={{.HostConfig.ReadonlyRootfs}} CapDrop={{json .HostConfig.CapDrop}} SecurityOpt={{json .HostConfig.SecurityOpt}}'
echo -n 'hardened: '
docker inspect "$c_hard" --format 'User={{.Config.User}} ReadonlyRootfs={{.HostConfig.ReadonlyRootfs}} CapDrop={{json .HostConfig.CapDrop}} SecurityOpt={{json .HostConfig.SecurityOpt}}'
echo

echo '== 5. 只读根文件系统验证 =='
if docker compose -f "$hardened" -p "$p_hard" exec -T hardened sh -c 'echo x > /app/probe' 2>/dev/null; then
  echo 'hardened: 写 /app 成功（意外）'
else
  echo 'hardened: 写 /app 失败，根文件系统只读（预期）'
fi
if docker compose -f "$hardened" -p "$p_hard" exec -T hardened sh -c 'echo x > /tmp/probe' 2>/dev/null; then
  echo 'hardened: 写 /tmp 成功，tmpfs 可用（预期）'
else
  echo 'hardened: 写 /tmp 失败（意外）'
fi

本机真实输出（节选）：

text
== 2. 容器内视角（同一镜像，不同运行时配置）==
insecure: {"uid":0,"gid":0,"arch":"arm64","node":"v24.22.2","capEff":"00000000a80425fb","rootfsWritable":true,"tmpWritable":true}
hardened: {"uid":10001,"gid":10001,"arch":"arm64","node":"v24.22.2","capEff":"0000000000000000","rootfsWritable":"EROFS","tmpWritable":true}

root:*::0:::::
insecure: root 可以读取 /etc/shadow
hardened: 非 root 读取被拒绝（预期）

== 4. 运行时安全字段（来自 docker inspect）==
insecure: User=0:0 ReadonlyRootfs=false CapDrop=null SecurityOpt=null
hardened: User=10001:10001 ReadonlyRootfs=true CapDrop=["ALL"] SecurityOpt=["no-new-privileges:true"]

== 5. 只读根文件系统验证 ==
hardened: 写 /app 失败，根文件系统只读（预期）
hardened: 写 /tmp 成功，tmpfs 可用（预期）

同一镜像、同一份代码，只改运行时配置，四个维度全部变化。这就是「运行时安全」的价值：不需要改业务代码。

逐步拆解 ​

第 1 步：先确认镜像里是谁在跑 ​

bash
docker image inspect docker-guide/12-security:demo --format 'User={{.Config.User}}'
docker run --rm docker-guide/12-security:demo id

如果 Config.User 为空，说明镜像默认以 root 启动；docker run 里的 id 会显示 uid=0(root)。

第 2 步：固定 uid，而不是用用户名 ​

dockerfile
RUN addgroup -g 10001 -S app && adduser -u 10001 -S app -G app
USER 10001:10001

用数字 uid 的原因：

  • 不同基础镜像的用户名到 uid 映射可能不同；
  • Kubernetes 的 runAsUser、compose 的 user: 都直接用数字；
  • 文件属主排查时数字更直接。

第 3 步：只读根文件系统 + tmpfs ​

yaml
read_only: true
tmpfs:
  - /tmp:size=16m,mode=1777

启动后验证：

bash
docker compose -f examples/docker/12-runtime-security/compose.hardened.yml -p sec-hardened exec hardened \
  sh -c 'echo x > /app/probe'   # 应报 Read-only file system

第 4 步：清空 capabilities ​

yaml
cap_drop:
  - ALL

验证方式二选一：

bash
# 容器内
grep CapEff /proc/self/status

# 宿主机
docker inspect <容器> --format '{{json .HostConfig.CapDrop}}'

需要特定能力时再单独加，例如非 root 绑定 80 端口：

yaml
cap_add:
  - NET_BIND_SERVICE

第 5 步：禁止提权 ​

yaml
security_opt:
  - no-new-privileges:true

它阻止进程通过 setuid 二进制或文件 capabilities 获得更高权限。对绝大多数应用没有副作用，应该默认开启。

第 6 步：资源限制 ​

yaml
pids_limit: 100
mem_limit: 128m
cpus: 0.5
  • pids_limit 防 fork 炸弹；
  • mem_limit 防内存耗尽（超限会被 OOM Kill，退出码 137）；
  • cpus 防单容器吃满 CPU。

这些是 compose 的写法；Kubernetes 用 resources.requests/limits（第 11 章）。

第 7 步：镜像扫描 ​

bash
bash examples/docker/12-runtime-security/scripts/scan-image.sh

本机真实失败原因：

text
FATAL Fatal error init error: DB error: failed to download vulnerability DB:
OCI repository error: ... DENIED: this image is not in the allowlist.

漏洞扫描未在本机跑通

Trivy 需要下载漏洞库，当前网络访问镜像加速地址时被拒绝（不在白名单）。所以本章不提供任何 CVE 数量或等级。要得到真实结果，需要：

bash
# 能访问 ghcr.io 或自建漏洞库镜像的环境
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:0.58.2 image --scanners vuln docker-guide/12-security:demo

或者在有网环境预先 trivy image --download-db-only，把缓存目录挂进容器。

第 8 步：把检查接进 CI ​

最小门禁可以是：

bash
# 1. 静态检查 Dockerfile 是否有 USER
grep -q '^USER ' Dockerfile || exit 1

# 2. 运行时检查：不允许 root
docker run --rm <镜像> id -u | grep -qx 0 && exit 1

# 3. 漏洞扫描：高危阻断（需要可用漏洞库）
trivy image --exit-code 1 --severity HIGH,CRITICAL <镜像>

第 1、2 条在本机可以真实执行；第 3 条依赖漏洞库可达性。

常见坑与排查 ​

现象根因排查与修复
容器启动即退出，日志 EACCES非 root 用户没有目录写权限调整目录属主，或把可写目录挂卷
EROFS: read-only file system开了 read_only，应用仍写根文件系统挂 tmpfs 或命名卷到需要写的路径
容器内 id 还是 rootDockerfile 没 USER，或 compose 覆盖成 0:0两处都要检查
加了 cap_drop: ALL 后绑定 80 端口失败缺 NET_BIND_SERVICE改用 8080，或单独 cap_add
非 root 无法读挂载的配置文件宿主机文件权限 600 且属主是 root调整权限，或用 secret 挂载
pids_limit 太小导致应用 fork 失败限制低于实际并发按负载压测后调整
容器被 OOM Kill（137）mem_limit 太小看 docker stats 与 OOMKilled，调大或降内存
扫描报告一片红但不知道先修哪个没有分级门禁先修 CRITICAL / HIGH，并区分「可直接利用」与「理论风险」
生产镜像里还留着 curl / vim为了调试方便装进去用临时调试容器，不要污染运行镜像
以为 read_only 就完全不能写还有 tmpfs 与挂载卷明确列出可写路径，其余保持只读

加固的优先级

先做「非 root + 只读根文件系统 + cap_drop: ALL + no-new-privileges」这四项，它们改动小、收益大；再做资源限制与镜像瘦身；最后才是扫描门禁与策略平台。顺序反了，容易在细枝末节上耗时间。

企业级做法 ​

  1. 基础镜像统一基线：固定版本与 digest，定期重建；不要用 latest。
  2. 默认非 root：Dockerfile 写 USER，编排层再兜底一次；CI 加一条「不允许 root」检查。
  3. 运行时默认加固：只读根文件系统、cap_drop: ALL、no-new-privileges 写进团队模板（compose / Helm chart）。
  4. 最小可写路径：明确列出 tmpfs 与卷，其余只读；上传、缓存、日志各有归属。
  5. 资源限制必填：CPU / 内存 / 进程数都有上限，避免单容器拖垮节点。
  6. 扫描进流水线：镜像构建后立即扫描，CRITICAL / HIGH 阻断；Scout 的策略与持续监控按订阅评估。
  7. 日志与审计：日志驱动配轮转上限；生产集群开启审计日志与运行时检测（如 Falco），不要只依赖镜像扫描。
  8. 密钥不落镜像：延续第 09 章的做法，运行时注入；docker history 里不应出现任何密钥痕迹。

练习与验收标准 ​

练习

  1. 在 compose.hardened.yml 里加上 cap_add: [NET_BIND_SERVICE]，把应用端口改成 80，观察 capEff 的变化。
  2. 把 read_only 改成 false，重新运行对照实验，确认 rootfsWritable 从 EROFS 变回 true。
  3. 把 pids_limit 改成 10，用 docker stats 或压测观察进程创建失败的表现。
  4. 给演示服务加一个 /mem?mb=256 接口分配内存，把 mem_limit 设为 128m，观察退出码是否为 137。

验收标准（可逐条执行）

  • [ ] security-check.sh 能完整跑完并打印两组对照结果；
  • [ ] insecure 的 uid 为 0，capEff 非全 0；
  • [ ] hardened 的 uid 为 10001，capEff 为 0000000000000000；
  • [ ] hardened 的 rootfsWritable 为 EROFS，tmpWritable 为 true；
  • [ ] docker inspect 能看到 ReadonlyRootfs=true、CapDrop=["ALL"]、SecurityOpt=["no-new-privileges:true"]；
  • [ ] 能说出镜像扫描与运行时加固各自解决什么问题；
  • [ ] 能指出 Docker Scout 策略、Docker Debug 属于付费能力边界。
