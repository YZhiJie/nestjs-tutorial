10 多架构构建与镜像发布 ​

用 buildx 构建 amd64 + arm64 的 manifest list，输出 OCI 归档验证，并分清 --load / --push / --output 三种出口。

成稿正文、示例代码与验收标准均已完整，可直接跟练

本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清「一台 Apple Silicon 机器为什么能产出 amd64 镜像」，以及 QEMU 模拟的代价；
  2. 用一份 Dockerfile 构建 linux/amd64 + linux/arm64 的 manifest list；
  3. 把多架构结果输出成 OCI 归档，在没有 registry 的环境里验证内容；
  4. 用 --load 分别运行两个平台的单平台镜像，确认平台选择真的生效；
  5. 区分 --load、--push、--output 三种出口，以及 Docker Build Cloud 的付费边界。

概念与原理 ​

为什么需要多架构 ​

Apple Silicon 开发机是 arm64，生产服务器大多是 amd64，CI runner 也可能是 amd64。镜像的每个层都和指令集绑定：

text
node:24-alpine (manifest list)
├── linux/amd64  → 真正的层（x86-64 二进制）
└── linux/arm64  → 真正的层（aarch64 二进制）

docker pull node:24-alpine 时，Docker 会按当前主机架构自动挑一个。你写 -t myapp:1.0 推上去的如果只有 amd64，同事在 M 系列 Mac 上拉取会走模拟，性能差甚至直接报 exec format error。

buildx 与 manifest list ​

docker buildx 是 BuildKit 的前端。多平台构建的关键参数：

bash
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --output type=oci,dest=out.tar \
  .

一个容易误解的点：多平台构建的产物不能直接 --load 到本地镜像列表。本地 docker images 里一个 tag 只能对应一个镜像，而 manifest list 是「一组镜像的索引」。所以出口只能是：

出口用途说明
--push推到 registry保留 manifest list，生产发布用
--output type=oci落成本地归档不依赖 registry，本章用它验证
--load导入本地只能单平台

--platform 写多个平台时用 --load 会直接报错，这是很多人第一次做多架构时的困惑点。

QEMU：同一台机器构建另一个架构 ​

Docker Desktop 自带 binfmt/QEMU。构建 amd64 时，RUN 指令里的 amd64 二进制通过指令翻译执行。代价：

  • 慢，尤其是 pnpm install、编译型语言；
  • 某些依赖 CPU 特性的程序可能行为异常；
  • 只适合构建，不适合压测。

本章的镜像只有一个 server.mjs，所以 amd64 构建也很快；真实 NestJS 项目在 amd64 上构建会明显更慢，这是构建缓存与 CI 选型要考虑的。

OCI 归档里到底有什么 ​

type=oci 输出的是标准 OCI Image Layout：

text
index.json            # 顶层索引
oci-layout            # 版本声明
blobs/sha256/<digest> # 所有 manifest / config / layer，按内容寻址

本章实测发现：顶层 index.json 只有一个条目，它本身还是 index，真正的 amd64 / arm64 条目在下一层。解析脚本必须递归，否则会拿不到 platform，还会把 index 当成 image manifest 去读 config，报 Cannot read properties of undefined。

发布时的命名与 digest ​

bash
docker buildx build --platform linux/amd64,linux/arm64 \
  -t registry.example.com/acme/api:1.4.0 --push .
  • tag 用不可变版本号或 git sha，不要只用 latest；
  • 推送完成后用 digest 固定部署：api@sha256:...；
  • docker buildx imagetools inspect registry.example.com/acme/api:1.4.0 可以查看 manifest list 里包含哪些平台。

付费能力边界 ​

能力免费 / 开源付费或更高档订阅
buildx / BuildKit / QEMU 多架构构建免费—
本地构建缓存免费—
Docker Build Cloud无远程 amd64/arm64 原生构建机、共享缓存
多平台 CI 矩阵取决于 CI 平台—

Build Cloud 的价值是「不用在本机用 QEMU 慢慢翻译」，但它是独立订阅能力，可用性以官方价格页和合同为准。本章所有步骤都不依赖它。

最小可跑示例 ​

一、一份 Dockerfile，两个平台 ​

dockerfile
# 10 章多架构镜像：同一份 Dockerfile，构建 amd64 与 arm64 两个平台。
# 单平台本机构建：docker build -t docker-guide/10-multiarch:local examples/docker/10-multiarch
# 网络无法直连 Docker Hub 时，可用 --build-arg BASE_IMAGE=<可达的镜像加速地址> 覆盖。
ARG BASE_IMAGE=node:24-alpine
FROM ${BASE_IMAGE}
WORKDIR /app
COPY app/server.mjs ./server.mjs
RUN addgroup -S app && adduser -S app -G app
USER app
EXPOSE 8080
HEALTHCHECK --interval=10s --timeout=3s --start-period=3s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:8080/').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
CMD ["node", "server.mjs"]

ARG BASE_IMAGE 的作用是让基础镜像地址可覆盖：Docker Hub 不可达时，可以换成镜像加速地址，而不改文件内容。

二、构建并解析 OCI index ​

bash
# 网络无法直连 Docker Hub 时，先指定可达的基础镜像
export BASE_IMAGE=docker.m.daocloud.io/library/node:24-alpine
bash examples/docker/10-multiarch/scripts/build-multiarch.sh
bash
#!/usr/bin/env bash
# 10 章：构建带 manifest list 的多架构镜像，输出为本地 OCI 归档（不需要 registry）。
# 用法：bash examples/docker/10-multiarch/scripts/build-multiarch.sh
set -euo pipefail

here=$(cd "$(dirname "$0")/.." && pwd)
out="$here/dist/api-multi.tar"
mkdir -p "$here/dist"
rm -f "$out"

echo '== 构建 linux/amd64 + linux/arm64 =='
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --provenance=false --sbom=false \
  --build-arg BASE_IMAGE="${BASE_IMAGE:-node:24-alpine}" \
  -f "$here/Dockerfile" \
  -t docker-guide/10-multiarch:multi \
  --output "type=oci,dest=$out" \
  "$here"

echo
echo "产物: $out"
ls -lh "$out"

echo
echo '== 解包并读取 OCI index =='
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT
tar -xf "$out" -C "$tmp"
node "$here/scripts/inspect-oci.mjs" "$tmp"

三、分别运行两个平台 ​

bash
bash examples/docker/10-multiarch/scripts/run-platform.sh arm64
bash examples/docker/10-multiarch/scripts/run-platform.sh amd64
bash
#!/usr/bin/env bash
# 10 章：把单平台镜像 load 到本地并运行，验证「同一 Dockerfile 在不同架构上都能跑」。
# 用法：bash examples/docker/10-multiarch/scripts/run-platform.sh [arm64|amd64]
set -euo pipefail

here=$(cd "$(dirname "$0")/.." && pwd)
platform=${1:-arm64}
[ "$platform" = "amd64" ] || [ "$platform" = "arm64" ] || {
  echo '只支持 arm64 或 amd64'
  exit 1
}

tag="docker-guide/10-multiarch:${platform}"

echo "== 构建并 load linux/${platform} =="
docker buildx build \
  --platform "linux/${platform}" \
  --provenance=false --sbom=false \
  --build-arg BASE_IMAGE="${BASE_IMAGE:-node:24-alpine}" \
  -f "$here/Dockerfile" \
  -t "$tag" \
  --load \
  "$here"

echo
echo '== 运行并请求接口 =='
docker rm -f multiarch-demo >/dev/null 2>&1 || true
docker run -d --name multiarch-demo -p 127.0.0.1:18082:8080 --platform "linux/${platform}" "$tag" >/dev/null
sleep 2
curl -s http://127.0.0.1:18082/
echo
docker rm -f multiarch-demo >/dev/null

本机真实输出：

json
{"service":"multiarch-demo","arch":"arm64","platform":"linux","kernel":"7.0.14-linuxkit","node":"v24.22.2"}
{"service":"multiarch-demo","arch":"x64","platform":"linux","kernel":"7.0.14-linuxkit","node":"v24.22.2"}

arch 从 arm64 变成 x64，证明第二次运行的确实是 amd64 镜像，Docker Desktop 用 QEMU 做了指令翻译。

逐步拆解 ​

第 1 步：确认 buildx 可用 ​

bash
docker buildx version
docker buildx ls

docker buildx ls 会列出当前 builder 支持的平台。Docker Desktop 默认 builder 通常已包含 linux/amd64、linux/arm64；如果没有，需要 docker buildx create --use 或启用 containerd 镜像存储。

第 2 步：为什么 --load 不能配多平台 ​

bash
# 这个命令会失败
docker buildx build --platform linux/amd64,linux/arm64 --load .

报错大意是「multiple platforms feature is currently not supported for docker driver」。原因在概念部分已经说明：本地镜像列表的一个 tag 只能指向一个镜像。

正确做法二选一：

bash
# A. 推 registry
docker buildx build --platform linux/amd64,linux/arm64 -t repo/api:1.0 --push .

# B. 落 OCI 归档
docker buildx build --platform linux/amd64,linux/arm64 \
  --output type=oci,dest=api.tar .

第 3 步：读懂 OCI index 的两层结构 ​

bash
tmp=$(mktemp -d)
tar -xf examples/docker/10-multiarch/dist/api-multi.tar -C "$tmp"
cat "$tmp/index.json"

本机真实内容（节选）：

json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.index.v1+json",
  "manifests": [
    {
      "mediaType": "application/vnd.oci.image.index.v1+json",
      "digest": "sha256:61a09acb...",
      "annotations": { "org.opencontainers.image.ref.name": "multi" }
    }
  ]
}

顶层条目没有 platform，mediaType 还是 index。继续读它指向的 blob，才是带 platform 的 amd64 / arm64 条目。inspect-oci.mjs 的递归就是为此写的。

第 4 步：检查单个平台的 config ​

bash
node examples/docker/10-multiarch/scripts/inspect-oci.mjs "$tmp"

输出的 configDigest 指向镜像配置，里面有 architecture、os、created 和环境变量。排查「镜像里到底是哪个架构」时，看 config 比看 tag 可靠。

第 5 步：把归档导入另一台机器 ​

bash
# 在目标机器上
docker load -i api-multi.tar

注意：docker load 对多平台 OCI 归档的行为取决于 Docker 版本，可能只导入当前平台。跨机器发布更可靠的方式仍然是推 registry 后 docker pull --platform。

第 6 步：检查 registry 里的 manifest list ​

有 registry 时：

bash
docker buildx imagetools inspect registry.example.com/acme/api:1.4.0

会列出每个平台的 digest 和大小。这一步和本章解析本地 index.json 是同一件事，只是一个在本地、一个在远端。

第 7 步：多架构与 CI ​

  • CI 若是 amd64，构建 arm64 仍走 QEMU，慢；
  • 可以用 CI 的矩阵（amd64 runner + arm64 runner）分别构建单平台，再 docker manifest create 合并；
  • 或者用 Build Cloud 的原生多架构构建机（付费能力）。

常见坑与排查 ​

现象根因排查与修复
exec format error镜像架构与宿主不符docker image inspect --format '{{.Architecture}}'；用 --platform 构建正确架构
多平台 --load 报错本地列表一个 tag 只能一个镜像改 --push 或 --output type=oci
构建 amd64 极慢QEMU 指令翻译只构建需要的平台；CI 用原生 runner 或 Build Cloud
inspect-oci.mjs 报 undefined.digest顶层 index 套 index，没递归递归展开 mediaType 为 index 的条目
拉下来的镜像平台不对tag 只有单平台，或节点被 --platform 固定imagetools inspect 看 manifest list；docker pull --platform 显式指定
推送后同事拉取走模拟只推了 amd64推 manifest list，不是单平台 tag
no matching manifest for linux/arm64基础镜像没有 arm64 变体换基础镜像，或接受模拟运行
多架构构建把缓存冲掉两个平台共享 builder 缓存但层不同正常现象；用 --cache-to/--cache-from 管理

多架构镜像不等于「每个平台都测过」

构建成功只说明能产出制品。amd64 镜像在 arm64 机器上跑通，只是 QEMU 模拟通过，不代表在真实 amd64 服务器上没有问题。生产前至少在一个目标架构的真实环境跑一次冒烟测试。

企业级做法 ​

  1. 发布物是 manifest list，不是单平台镜像：CI 产出多架构，部署按 digest 固定。
  2. CI 用原生架构 runner 或 Build Cloud：QEMU 构建在生产规模下太慢，尤其是 Node 依赖安装与编译。
  3. 基础镜像固定版本与 digest：node:24-alpine 会漂移，生产建议 node:24.x-alpine@sha256:...。
  4. 构建参数外置：像本章的 BASE_IMAGE 一样，让镜像源可切换，适配内网与镜像加速。
  5. 多架构构建要有冒烟测试：每个平台至少启动一次并请求健康检查。
  6. 归档只用于离线搬运：docker save / OCI tar 没有访问控制与版本管理，正式发布走 registry。
  7. 记录构建元数据：--provenance、--sbom 会生成 attestation；本章为让 index 结构简单用 --provenance=false --sbom=false，生产应按合规要求开启，并知道它会多出 unknown/unknown 条目。

练习与验收标准 ​

练习

  1. 把 --platform 改成只构建 linux/arm64，用 --load 导入并运行，确认不再报错。
  2. 在 build-multiarch.sh 里去掉 --provenance=false --sbom=false，重新构建，观察 index.json 是否多出 unknown/unknown 条目。
  3. 给 server.mjs 增加一个 /arch 路由，返回 process.arch，分别请求两个平台。
  4. 用 docker image inspect --format '{{.Architecture}}/{{.Os}}' 检查本地两个单平台镜像。

验收标准（可逐条执行）

  • [ ] build-multiarch.sh 输出两行，platform 分别为 linux/amd64 与 linux/arm64；
  • [ ] 两行的 manifestDigest 不同；
  • [ ] run-platform.sh arm64 返回 "arch":"arm64"；
  • [ ] run-platform.sh amd64 返回 "arch":"x64"；
  • [ ] 能解释为什么多平台不能 --load；
  • [ ] 能说出 --push、--output type=oci、--load 三者的适用场景；
  • [ ] 能指出 Build Cloud 属于付费能力，以及不用它时的替代方案。

  • 没有在真实 amd64 服务器上运行 amd64 镜像，QEMU 模拟通过不等于原生通过；

  • Windows 容器的多架构（windows/amd64）未覆盖，本章只讨论 Linux 镜像。
