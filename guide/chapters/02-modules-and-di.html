02 模块化与依赖注入 ​

模块、Provider 与依赖注入的可见性边界，循环依赖与作用域取舍。

成稿正文、示例代码与验收标准均已完整，可直接跟练
难度
★★☆☆☆
预计课时
2 小时
最后核对
2026-11-10

本章目标 ​

  1. 掌握 Module 的三个基本组成：imports、providers、exports，并说清「谁能看见谁」；
  2. 用 Provider 的四种注册方式解决真实问题：类、useClass、useValue、useExisting；
  3. 会做共享模块（@Global() 的取舍），知道什么时候不该用全局模块；
  4. 能识别并解决模块/类的循环依赖，理解为什么 ESM 下「类互相 import」会直接崩；
  5. 知道单例、请求作用域、瞬态作用域的差别与代价。

概念与原理 ​

模块是可见性边界，不是文件夹 ​

很多教程把 Module 说成「把文件分组」，这会误导。Module 真正的语义是依赖注入的可见性边界：

动作效果
providers: [XService]在本模块内可注入 XService
exports: [XService]其他模块 imports 本模块后，才能注入 XService
没 exports本模块私有，外部注入会报 can't resolve dependencies
@Global()全局可见，任何模块无需 import（慎用）

一个 Provider 即使被两个模块各自登记，只要在不同模块，就会各自实例化一份——这是「同一个类、两个实例」最常见的原因。

注入的四种写法与适用场景 ​

ts
// 1. 类直接登记：最常见
providers: [UsersService]

// 2. 接口/类替换：测试替身、按环境切换实现
providers: [{ provide: CachePort, useClass: RedisCacheAdapter }]

// 3. 值：配置对象、第三方客户端
providers: [{ provide: 'STRIPE_CLIENT', useValue: stripeClient }]

// 4. 别名：把已有实例挂到另一个 token 上（本项目用它暴露「接口」）
providers: [{ provide: USER_DIRECTORY, useExisting: UsersService }]

第 4 种是本项目的关键技巧，下一节展开。

接口在运行时不存在，所以要 Token ​

TypeScript 的 interface 编译后会被擦除，容器无法用「接口类型」做注入依据。做法是：接口 + 一个运行时存在的 token。

最小可跑示例 ​

本项目有 users 与 audit 两个模块，它们互相需要：

  • UsersService 要写审计 → 依赖 AuditService；
  • AuditService 展示日志时要显示「操作人姓名」→ 需要查用户。

一、定义端口（接口 + Token） ​

ts
import type { PublicUser } from './user.entity.js';

/**
 * 审计模块只需要「按 id 批量查用户」这一项能力。
 * 用接口 + Symbol 令牌隔离，避免 UsersService 与 AuditService 直接类互引
 * （ESM 下装饰器元数据会在模块求值阶段就引用对方，形成初始化死锁）。
 */
export interface UserDirectory {
  findByIds(ids: string[]): Promise<PublicUser[]>;
}

export const USER_DIRECTORY = Symbol('UserDirectory');

二、在 UsersModule 里把实现挂到 Token 上 ​

ts
import { forwardRef, Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { AuditModule } from '../audit/audit.module.js';
import { USER_DIRECTORY } from './user-directory.js';
import { UserEntity } from './user.entity.js';
import { UsersController } from './users.controller.js';
import { UsersService } from './users.service.js';

/**
 * 模块是 Nest 的最小封装单元：
 * - providers 默认只在模块内部可见
 * - 只有 exports 出去的内容，别的模块 import 本模块后才能注入
 */
@Module({
  imports: [
    TypeOrmModule.forFeature([UserEntity]),
    // 模块之间存在循环依赖时，Nest 需要 forwardRef 才能延迟解析
    forwardRef(() => AuditModule),
  ],
  controllers: [UsersController],
  providers: [
    UsersService,
    // 把 UsersService 以接口令牌的形式暴露给审计模块：调用方只看到能力，不看到实现
    { provide: USER_DIRECTORY, useExisting: UsersService },
  ],
  exports: [UsersService, USER_DIRECTORY],
})
export class UsersModule {}

注意 useExisting 而不是 useClass：前者复用同一个实例，后者会新建一个。如果这里写错，会出现「用户数据在两个实例里不一致」的诡异 bug。

三、AuditModule 只依赖端口 ​

ts
import { forwardRef, Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { UsersModule } from '../users/users.module.js';
import { AuditLogEntity } from './audit-log.entity.js';
import { AuditController } from './audit.controller.js';
import { AuditService } from './audit.service.js';

/**
 * AuditModule 依赖 UsersModule 展示操作人姓名，UsersModule 依赖 AuditService 写审计。
 * 双方都用 forwardRef 导入对方，Nest 会在实例化阶段完成互相注入。
 */
@Module({
  imports: [TypeOrmModule.forFeature([AuditLogEntity]), forwardRef(() => UsersModule)],
  controllers: [AuditController],
  providers: [AuditService],
  exports: [AuditService],
})
export class AuditModule {}
ts
constructor(
  @InjectRepository(AuditLogEntity)
  private readonly logs: Repository<AuditLogEntity>,
  // 只依赖「按 id 批量查用户」这个接口，不依赖 UsersService 具体实现
  @Inject(forwardRef(() => USER_DIRECTORY))
  private readonly userDirectory: UserDirectory,
  private readonly cache: CacheService,
) {}

四、UsersService 反过来依赖 AuditService ​

ts
constructor(
  // 仓储由 TypeOrmModule.forFeature([UserEntity]) 提供，注入的是 Repository 代理，不是裸连接
  @InjectRepository(UserEntity)
  private readonly users: Repository<UserEntity>,
  // UsersService 需要写审计，AuditService 需要读用户来展示操作人姓名：
  // 两个模块互相依赖，用 forwardRef 打破加载顺序死锁（详见第 2 章）。
  @Inject(forwardRef(() => AuditService))
  private readonly auditService: AuditService,
) {}

逐步拆解 ​

1. 为什么不用「两个类互相 import」的写法 ​

最直觉的写法是 AuditService 直接 import { UsersService }。在 CommonJS 下它勉强能跑；在 ESM + emitDecoratorMetadata 下会直接崩：

text
ReferenceError: Cannot access 'UsersService' before initialization
    at dist/audit/audit.service.js:48:38

原因：编译产物里，装饰器元数据在模块求值时就执行了——

js
__metadata("design:paramtypes", [UsersService])   // 此刻 UsersService 还没初始化

users.service.js 与 audit.service.js 互相 import，谁先求值谁就拿不到对方的绑定。这就是本章最值得记住的坑：Nest 的 forwardRef 解决的是「模块依赖图」的顺序，解决不了「ESM 模块求值」的循环。

三层解法，按推荐程度排序：

做法说明适用
接口 + Token（本项目）一方依赖抽象，文件级无环首选
事件解耦用户变更发事件，审计模块订阅（第 08 章）跨领域、可异步
类直接互相 forwardRef两边都 @Inject(forwardRef(...))，仅模块级环临时方案，ESM 下仍可能触发 TDZ

2. 模块级循环依赖：forwardRef ​

users.module.ts 与 audit.module.ts 仍然互相 import（模块图有环），所以两边都用：

ts
imports: [forwardRef(() => AuditModule)]

forwardRef 的原理是把「取模块引用」延迟到解析阶段，而不是模块求值时。注意它接收的是返回引用的箭头函数，不能写成 forwardRef(AuditModule)。

3. useExisting 与 useClass 的差别 ​

ts
// 同一个实例：UsersService 的单例被复用
{ provide: USER_DIRECTORY, useExisting: UsersService }

// 新实例：容器会再 new 一个 UsersService
{ provide: USER_DIRECTORY, useClass: UsersService }

判断方法：如果你的实现内部持有状态（内存 Map、连接池、缓存），必须 useExisting，否则就是「两份状态」。

4. 共享模块与 @Global() ​

ConfigModule.forRoot({ isGlobal: true }) 就是共享模块：任何模块不必 import 就能注入 ConfigService。

判断标准：

  • 基础设施类（配置、日志、追踪、数据库连接）→ 可全局；
  • 业务领域（用户、订单、支付）→ 不要全局。全局业务模块会让依赖关系隐形，半年后没人说得清 OrderService 到底依赖谁。

5. Provider 作用域与代价 ​

作用域写法实例数代价
单例（默认）无需声明进程内 1 个无；但要求无请求级状态
请求作用域@Injectable({ scope: Scope.REQUEST })每请求 1 个依赖它的对象也变成请求级，实例化开销上升
瞬态Scope.TRANSIENT每个注入点 1 个适合有状态工具类，容易滥用

第 14 章会用一个真实场景量化请求作用域的代价。现在只需记住：默认单例，除非你有明确理由。

常见坑与排查 ​

现象根因处理
Nest can't resolve dependencies of the AuditService (?)提供方模块没 exports 该 Provider，或消费方没 imports检查 exports 与 imports 两端
Cannot access 'X' before initialization类文件互相 import（见上）改接口 + Token，或事件解耦
两个模块里的「同一个服务」状态不一致各自 providers 登记，或用了 useClass只在一个模块登记并 exports，另一方 imports；替换用 useExisting
Nest can't resolve dependencies 但 token 明明存在用了字符串 token 但大小写/拼写不一致用 Symbol 或导出的常量做 token
循环依赖加了 forwardRef 仍报错只加在 imports，没加在构造函数的 @Inject两边都要加
单元测试里 new UsersService(fakeAudit) 报类型错误构造函数参数是类而非接口测试里 as unknown as AuditService，或改为依赖端口接口

企业级做法 ​

  1. 按业务域切模块，而不是按技术层。users/ 里放 controller、service、dto、entity；不要建全局的 controllers/、services/ 大杂烩。
  2. 跨模块只暴露端口。像 USER_DIRECTORY 这样：调用方看到的是能力，不是实现，未来换成 RPC/缓存实现时调用方零改动。
  3. 循环依赖是设计味道。能用事件、能用抽取第三个模块解决的，不要用 forwardRef 糊过去——它只是让编译通过，没解决耦合。
  4. 每个模块有明确的所有者。UsersModule 拥有用户数据，其他模块想改用户只能通过它暴露的方法。
  5. 在模块里注释「为什么」。本项目的两个模块都写了为什么互相依赖，这比写「用户模块」有用得多。
  6. 测试要能脱离容器。UsersService 的单元测试直接 new UsersService(fakeAudit)，不需要启动 Nest——分层清晰的直接收益。

练习与验收标准 ​

练习

  1. 新建 notifications 模块，NotificationsService.send(email, content) 只打日志；让 UsersService.create 在创建成功后调用它。
  2. 把它改成「通过端口注入」：定义 NOTIFIER token 与 Notifier 接口，在 NotificationsModule 里提供实现并导出。
  3. 故意把 useExisting 改成 useClass，观察 /api/audits 里 actorName 是否变成 null，并解释原因。

验收标准

  • [ ] 携带 admin 令牌请求 curl -H "authorization: Bearer $TOKEN" "http://localhost:3000/api/audits?limit=2"，返回的 actorName 不为 null；
  • [ ] 把 users.module.ts 里的 exports 删掉后，应用启动报错，且你能指出报错指向哪个模块；
  • [ ] 能画出 UsersModule 与 AuditModule 的依赖关系图，并标注哪条边用了 forwardRef；
  • [ ] 能解释「为什么 AuditService 里 import type { UserDirectory } 不会引入运行时依赖」；
  • [ ] 单测 pnpm --filter @nestjs-tutorial/api test 通过，且不依赖 Nest 容器启动。
