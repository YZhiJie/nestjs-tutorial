14 精通专题：自定义装饰器与动态模块 ​

自定义装饰器、动态模块与高级元编程的落地场景。

成稿正文、示例代码与验收标准均已完整，可直接跟练
难度
★★★★★
预计课时
3 小时
最后核对
2026-11-10

框架用久了会形成两种能力：一种是把业务写进 Nest 的既有轨道，另一种是让 Nest 按你的方式工作。本章只讲后者，并且只讲仓库里真实存在的东西：参数装饰器、元数据 + 守卫、动态模块、生命周期钩子。请求作用域的代价与内部 SDK 发布属于「知道但没在本工程落地」的部分，会明确标注。

本章实现状态

自定义装饰器、元数据守卫、动态模块的使用与生命周期钩子都是仓库里的真实代码。请求作用域性能实测、内部 SDK 打包发布未实现，在文末清单标注。

本章目标 ​

  1. 用 createParamDecorator 把身份注入参数，并理解它「只取值、不校验」的边界
  2. 用 SetMetadata + Reflector 让守卫读取路由上的声明，而不是在守卫里写 if
  3. 读懂 forRootAsync 这类动态模块在解决什么问题，并能判断什么时候该自己写一个
  4. 掌握生命周期钩子的执行顺序，知道启动失败与关闭超时分别发生在哪一步
  5. 说清请求作用域的代价来源，以及为什么默认应该用单例

概念与原理 ​

1. 参数装饰器不是「拦截器」 ​

机制执行时机适合做什么
参数装饰器控制器方法调用前，由 Nest 组装参数从 request 取已解析好的值
Guard路由匹配后、进入管道前放行/拒绝（401/403）
PipeGuard 之后校验与转换 DTO
Interceptor处理器前后计时、缓存、统一包装响应

@CurrentUser() 只负责把 JwtAuthGuard 已经放进 request.user 的对象取出来。校验令牌是守卫的事，参数装饰器里再校验一次只会重复执行。

2. 元数据 + 守卫：声明与执行分离 ​

@Roles('admin') 不执行任何逻辑，它只是往路由上写一条元数据：

ts
export const Roles = (...roles: UserRole[]) => SetMetadata(ROLES_KEY, roles);

真正判断的是 RolesGuard，它通过 Reflector.getAllAndOverride 先读方法、再读类。这种「声明在执行处之外」的模式，是 Nest 里所有横切能力的共同结构：

  • 想加一个新约束（例如 @RequireScope('orders:write')），只需要新增装饰器 + 一个守卫，不改控制器；
  • 想把规则从代码移到配置，只要元数据来源可变。

顺序很重要：RolesGuard 必须排在 JwtAuthGuard 之后，否则 request.user 还不存在，角色判断只能落到 403 兜底分支。

3. 动态模块解决的是「配置在运行时才知道」 ​

普通模块的 imports / providers 在编译期就固定了。数据库连接串、缓存驱动、队列后端这些值要到运行时读环境变量才知道，forRootAsync 就是让模块在依赖注入完成之后再构造 provider：

ts
import { Module } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { TypeOrmModule } from '@nestjs/typeorm';
import type { AppConfig } from '../config/configuration.js';
import { buildTypeOrmOptions } from './database-options.js';

@Module({
  imports: [
    TypeOrmModule.forRootAsync({
      inject: [ConfigService],
      useFactory: (config: ConfigService<AppConfig, true>) => buildTypeOrmOptions(config),
    }),
  ],
})
export class DatabaseModule {}

inject: [ConfigService] 是关键：它告诉 Nest「先解析 ConfigService，再把实例传进 useFactory」。这样模块内部不需要自己去读 process.env，测试时也能换成假配置。

4. 生命周期钩子的顺序 ​

钩子时机本工程用途
onModuleInit模块依赖就绪后未使用
onApplicationBootstrap全部模块初始化完成、监听端口前注册队列定时任务、等待 Redis
onModuleDestroy收到关闭信号后未使用
onApplicationShutdown连接关闭阶段停止 BullMQ Worker、关闭连接

队列模块把「注册定时任务」放在 onApplicationBootstrap，而不是构造函数里：构造函数执行时，Redis 连接与配置可能还没就绪，抛错的位置也会变得难以定位。

ts
async onApplicationBootstrap(): Promise<void> {
  await this.jobs.start();
}

async onApplicationShutdown(): Promise<void> {
  await this.jobs.close();
}

5. 请求作用域为什么贵 ​

@Injectable({ scope: Scope.REQUEST }) 会让该 provider 每次请求创建一次，并且作用域会向上冒泡：任何注入它的单例 provider 也会被迫变成请求作用域。结果是整条依赖链每请求实例化一次，Controller 与拦截器也无法复用。

代价来源不是「new 一个对象」，而是：

  • 依赖图里每个节点都要按请求解析；
  • 无法在启动时完成实例化，DI 容器的解析工作进入热路径；
  • 与单例缓存、连接池等「启动时建立」的优化天然冲突。

经验规则：能用参数传递的，就不要用请求作用域。当前用户、追踪 ID 这类值，用参数装饰器或 AsyncLocalStorage 更便宜。

最小可跑示例 ​

1. 身份注入：@CurrentUser() ​

ts
import { createParamDecorator, ExecutionContext } from '@nestjs/common';
import type { Request } from 'express';
import type { AuthenticatedUser } from '../authenticated-user.js';

/**
 * 把 JwtAuthGuard 解析出的身份直接注入参数。
 * 这里只做「取值」，不做校验——校验是 Guard 的职责。
 */
export const CurrentUser = createParamDecorator(
  (_data: unknown, ctx: ExecutionContext): AuthenticatedUser => {
    const request = ctx.switchToHttp().getRequest<Request & { user: AuthenticatedUser }>();
    return request.user;
  },
);

2. 声明式权限：@Roles() + RolesGuard ​

ts
import { SetMetadata } from '@nestjs/common';
import type { UserRole } from '../../users/user.entity.js';

export const ROLES_KEY = 'auth:roles';

/** 声明访问该路由需要的角色。单个角色即可满足时也传数组，便于以后扩展 */
export const Roles = (...roles: UserRole[]) => SetMetadata(ROLES_KEY, roles);
ts
canActivate(context: ExecutionContext): boolean {
  const requiredRoles = this.reflector.getAllAndOverride<UserRole[]>(ROLES_KEY, [
    context.getHandler(),
    context.getClass(),
  ]);
  if (!requiredRoles || requiredRoles.length === 0) {
    return true;
  }

  const request = context
    .switchToHttp()
    .getRequest<Request & { user?: AuthenticatedUser }>();
  const user = request.user;

  if (!user) {
    // 理论上不会走到：JwtAuthGuard 已经拦过一遍。保留是为了守卫被单独复用时的安全兜底
    throw new ForbiddenException({
      code: 'FORBIDDEN_ROLE',
      message: '缺少身份信息，无法判断角色',
    });
  }

  if (!requiredRoles.includes(user.role)) {
    throw new ForbiddenException({
      code: 'FORBIDDEN_ROLE',
      message: `需要 ${requiredRoles.join(' 或 ')} 角色`,
      details: { requiredRoles, actualRole: user.role },
    });
  }

  return true;
}

3. 公开路由：@Public() ​

ts
import { SetMetadata } from '@nestjs/common';

export const IS_PUBLIC_KEY = 'auth:isPublic';

/**
 * 默认全部接口都需要登录；只有显式标记 @Public() 的才放行。
 * 「默认拒绝」比「默认放行 + 逐个加 Guard」安全得多。
 */
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);

@Public() 同样是元数据：JwtAuthGuard 读到它就跳过校验。健康检查与指标接口靠它暴露，否则探针会被 401 挡住。

逐步拆解 ​

1. 一次请求里，这些机制按什么顺序发生 ​

text
请求进入
  → requestIdMiddleware       生成/透传 x-request-id
  → httpMetricsMiddleware     记录开始时间
  → JwtAuthGuard              解析令牌，写入 request.user（@Public 则跳过）
  → RolesGuard                读 @Roles 元数据，判断角色
  → ValidationPipe            校验 DTO
  → Interceptor               缓存/日志/包装
  → Controller 方法           参数由 @CurrentUser 注入
  → 响应包装 { data, meta }

这也解释了第 11 章为什么要用中间件采指标：Guard 在拦截器之前，401 的请求根本到不了拦截器。

2. 实测：元数据守卫的两种失败 ​

bash
# 没有令牌：401，不知道你是谁
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/api/audits
# 401

# member 令牌：403，知道你是谁，但角色不够
curl -s -o /dev/null -w '%{http_code}\n' \
  http://localhost:3000/api/audits -H "authorization: Bearer $MEMBER_TOKEN"
# 403
json
{"error":{"code":"FORBIDDEN_ROLE","message":"需要 admin 角色","details":{"requiredRoles":["admin"],"actualRole":"member"}}}

两个状态码的区别不是风格问题：401 让客户端去登录，403 让客户端别再试。混用会导致前端反复跳登录页。

3. 动态模块的取舍：什么时候自己写 ​

场景建议
只是读几个环境变量ConfigService 足够，不要造模块
需要在启动时选择实现（redis / memory）用 provider 工厂，本工程的 CacheModule / QueueModule 就是这样
需要把配置作为参数传给第三方模块forRootAsync，如 TypeOrmModule
要发布给多个项目复用才值得写完整的 forRoot / forRootAsync / forFeature

forRoot 不是「高级写法」的同义词。本工程的缓存与队列模块用 useFactory 在启动时选驱动，代码量更小，行为也更直观；只有当模块需要被别人 imports 并且配置来自调用方时，动态模块才划算。

4. 生命周期钩子的真实用途：优雅关闭 ​

main.ts 调用 enableShutdownHooks() 后，SIGTERM 会触发 onApplicationShutdown：

ts
// 让 SIGTERM / SIGINT 触发 onApplicationShutdown：
// 队列 Worker 停止接新任务、TypeORM 关闭连接池都在这里完成。
// 没有这一步，容器重启时正在执行的任务会被直接切断。
app.enableShutdownHooks();
for (const signal of ['SIGTERM', 'SIGINT'] as const) {
  process.once(signal, () => Logger.log(`收到 ${signal}，开始优雅关闭`, 'Bootstrap'));
}

实测（第 13 章）：docker stop -t 15 后日志出现「收到 SIGTERM，开始优雅关闭」，容器在 15 秒内退出。如果没有关闭钩子，BullMQ Worker 会被直接切断，正在执行的任务要等锁过期才会重投。

5. 可复用 SDK 的边界 ​

把能力抽成内部包之前，先回答三个问题：

  1. 它依赖业务吗？ 依赖 User 实体的守卫不适合抽包，换成通用 Principal 接口才行。
  2. 版本怎么升？ 内部包也要 semver，破坏性改动要给迁移说明。
  3. 谁负责测试？ 抽出去之后，主仓库的 e2e 不再覆盖它，包本身必须有测试与发布流水线。

本示例是单应用仓库，没有 packages/*，所以没有真实的 SDK 发布流程。上面三条是判断标准，不是已完成的能力。

常见坑与排查 ​

报错 / 现象根因修复验证
@CurrentUser() 返回 undefined守卫没执行或执行顺序在参数装饰器之后确认 JwtAuthGuard 是全局守卫且先于角色守卫受保护路由能拿到 user.id
加了 @Roles() 但没生效守卫没注册，或 Reflector 读错了目标在 APP_GUARD 注册守卫，getAllAndOverride 同时传 handler 与 classmember 访问 admin 路由返回 403
循环依赖 Nest cannot create the module instance两个模块互相 imports用 forwardRef()，或把共享能力下沉到独立模块启动无报错
请求作用域后 QPS 明显下降作用域冒泡，整条链每请求实例化改回单例 + 参数传递/AsyncLocalStorage压测对比前后 QPS 与内存
关闭时任务被截断没启用 shutdown hooks 或超时太短enableShutdownHooks() + 合理的 stop_grace_period停止日志包含关闭记录

企业级做法 ​

  • 装饰器只做声明：校验、查询、副作用放到 Guard/Pipe/Interceptor，装饰器保持可预测。
  • 元数据 key 统一前缀：auth:roles、auth:public，避免与第三方库冲突。
  • 守卫顺序显式化：在模块里按「认证 → 授权 → 限流」注册，顺序即语义。
  • 动态模块提供同步与异步两版：forRoot 给测试与简单场景，forRootAsync 给运行时配置。
  • 关闭预算写进部署清单：应用关闭时间 < terminationGracePeriodSeconds，并留出 preStop 的缓冲。
  • 内部包先有契约再有实现：接口（Principal、Clock、IdGenerator）稳定后再抽包，否则抽一次改一次。
