日志、指标、追踪与健康检查，构建可定位问题的可观测性。

上线之后最怕的一句话是「接口有点慢」。没有数据时，只能靠猜：是数据库、缓存、还是某个下游？本章把示例工程补成「能被问出答案」的状态：结构化日志带请求 ID、健康检查分层、进程内指标端点，以及一个明确的错误上报出口。

本章实现状态

日志、请求 ID、健康检查分层、指标端点与错误日志都已实现并可 curl 验证。Prometheus 采集、OpenTelemetry 链路追踪、Sentry 上报未接入，属于「设计讲解，示例未实现」，在文末清单单独列出。

本章目标 ​

  1. 把日志从「打印」升级为「可检索的结构化事件」，并用请求 ID 串联一次请求
  2. 区分存活探针、就绪探针与依赖明细，知道每个探针该查什么、不该查什么
  3. 暴露进程内指标：请求量、状态码、延迟分位、缓存命中率、队列任务结果
  4. 定义错误上报的唯一出口，避免上报逻辑散落在业务代码里
  5. 说清这套轻量方案与 Prometheus / OpenTelemetry 的差距，以及替换路径

概念与原理 ​

1. 三根支柱，先有「关联」再谈「丰富」 ​

支柱回答的问题本章落点
日志这一次请求具体发生了什么requestId + JSON 行
指标整体趋势有没有异常GET /api/metrics
追踪一次请求慢在哪个环节仅预留 requestId，未接 OTel

很多项目一上来就引入全套 OTel，结果日志里没有请求 ID，指标没有路由标签，采样器配了但查不到具体请求。顺序应该是：先让每条日志带得上 requestId，再让每个指标有稳定标签，最后才谈跨服务追踪。

2. 请求 ID 的边界 ​

请求 ID 由入口中间件生成或透传（x-request-id），写进响应头，也写进所有日志行。

  • 生成：没有 x-request-id 时用 randomUUID()；
  • 透传：上游网关传了就用上游的，否则跨系统关联会断；
  • 边界：进程内一路靠 req.requestId 或 AsyncLocalStorage；进程外靠 HTTP 头，消息队列要靠消息属性透传（本示例未做）。

3. 健康检查为什么必须分层 ​

探针查什么失败后果
liveness /health/live事件循环能否响应编排器重启实例
readiness /health/ready数据库、缓存是否可用负载均衡摘流量，不重启
dependencies /health/dependencies逐项依赖明细只给人看，始终 200

最常见的错误是让 liveness 也去查数据库：数据库抖动 30 秒，编排器把所有实例重启一遍，抖动变成雪崩。liveness 只证明进程没死，readiness 才证明能接流量。

4. 指标的高基数陷阱 ​

指标标签的取值数量决定存储成本。把 req.originalUrl 当标签，/api/orders/3f2c... 每个订单一条时间序列，一天就能把时序库打爆。

正确做法是用路由模板：/api/orders/:id。本示例在 Express 的 req.route.path 上取模板，未匹配的 404 统一记为 unmatched。

5. 分位数为什么用桶 ​

精确 p95 需要保留每个样本（内存随流量增长）或引入 t-digest / HDR Histogram。示例用固定桶（5/10/25/50/100/250/500/1000/2500/5000ms）累计计数，取第一个达到目标的桶上界。误差是「上界 - 下界」，例如 p95 显示 250ms，真实值在 100~250ms 之间。对「有没有变慢」这个问题足够，对 SLO 结算不够。

最小可跑示例 ​

1. 请求 ID 与结构化访问日志 ​

ts
import { randomUUID } from 'node:crypto';
import type { NextFunction, Request, Response } from 'express';

declare global {
  // eslint-disable-next-line @typescript-eslint/no-namespace
  namespace Express {
    interface Request {
      requestId?: string;
    }
  }
}

export const REQUEST_ID_HEADER = 'x-request-id';

/**
 * 请求追踪 ID：优先透传上游（网关/BFF）给的 x-request-id，
 * 没有就生成一个。后续日志、错误响应、审计都带同一个 ID，串起全链路。
 */
export function requestIdMiddleware(req: Request, res: Response, next: NextFunction): void {
  const incoming = req.headers[REQUEST_ID_HEADER];
  const requestId = typeof incoming === 'string' && incoming.length > 0 ? incoming : randomUUID();
  req.requestId = requestId;
  res.setHeader(REQUEST_ID_HEADER, requestId);
  next();
}
ts
import {
  CallHandler,
  ExecutionContext,
  Injectable,
  Logger,
  NestInterceptor,
} from '@nestjs/common';
import type { Request, Response } from 'express';
import { Observable, tap } from 'rxjs';

/**
 * 访问日志拦截器：一条结构化 JSON 日志 = 方法 + 路径 + 状态码 + 耗时 + 追踪 ID。
 * 结构化（而不是拼字符串）是后面接 ELK/Loki 做检索的前提。
 */
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  private readonly logger = new Logger('HTTP');

  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const http = context.switchToHttp();
    const req = http.getRequest<Request>();
    const res = http.getResponse<Response>();
    const startedAt = Date.now();

    return next.handle().pipe(
      tap({
        next: () => this.writeLog(req, res.statusCode, startedAt),
        error: (error: { status?: number }) =>
          this.writeLog(req, error.status ?? 500, startedAt, error),
      }),
    );
  }

  private writeLog(req: Request, statusCode: number, startedAt: number, error?: unknown): void {
    const payload = {
      msg: 'request.completed',
      method: req.method,
      path: req.originalUrl,
      statusCode,
      durationMs: Date.now() - startedAt,
      requestId: req.requestId,
      ...(error ? { error: (error as Error).message } : {}),
    };
    if (statusCode >= 500) {
      this.logger.error(JSON.stringify(payload));
    } else {
      this.logger.log(JSON.stringify(payload));
    }
  }
}

每一次请求结束都会输出一行 JSON，字段固定：msg / requestId / method / path / status / durationMs。日志采集按 requestId 聚合，就能还原一次请求的全部行。

2. 指标服务 ​

ts
recordHttp(params: {
  method: string;
  route: string;
  statusCode: number;
  durationMs: number;
}): void {
  const key = `${params.method} ${params.route}`;
  let stats = this.routes.get(key);
  if (!stats) {
    stats = {
      count: 0,
      byStatus: {},
      duration: { count: 0, sumMs: 0, buckets: LATENCY_BUCKETS.map(() => 0), maxMs: 0 },
    };
    this.routes.set(key, stats);
  }

  const statusKey = String(params.statusCode);
  stats.count += 1;
  stats.byStatus[statusKey] = (stats.byStatus[statusKey] ?? 0) + 1;
  this.statusTotals[statusKey] = (this.statusTotals[statusKey] ?? 0) + 1;
  this.httpTotal += 1;

  const duration = stats.duration;
  duration.count += 1;
  duration.sumMs += params.durationMs;
  duration.maxMs = Math.max(duration.maxMs, params.durationMs);
  for (let i = 0; i < LATENCY_BUCKETS.length; i += 1) {
    if (params.durationMs <= LATENCY_BUCKETS[i]) {
      duration.buckets[i] += 1;
    }
  }
}

HTTP 指标用中间件采集，而不是拦截器：

ts
import type { Request, RequestHandler } from 'express';
import type { MetricsService } from './metrics.service.js';

/** Express 匹配到路由后挂上的路由定义，`path` 是带参数的模板 */
type RoutableRequest = Request & { route?: { path?: string } };

/**
 * HTTP 指标中间件。
 *
 * 为什么不是拦截器：Guard 在拦截器之前执行，401/403 的请求根本进不了拦截器，
 * 而「鉴权失败有多少」恰恰是最需要监控的指标之一。中间件能看到所有已完成响应。
 *
 * 路由标签取 Express 匹配到的路由模板（如 `/api/orders/:id`），
 * 而不是真实 URL——否则每个订单 id 都会变成一条时间序列。
 */
export function createHttpMetricsMiddleware(metrics: MetricsService): RequestHandler {
  return (req, res, next) => {
    const startedAt = Date.now();

    res.on('finish', () => {
      // SSE 是长连接：请求可能要挂几十分钟，记进延迟分位会把 p95 直接拉爆。
      // 实时连接的规模用 /api/realtime/stats 观察，不走 HTTP 指标。
      const contentType = res.getHeader('content-type');
      if (typeof contentType === 'string' && contentType.startsWith('text/event-stream')) {
        return;
      }

      metrics.recordHttp({
        method: req.method,
        // 未匹配到路由（404）不保留具体路径，避免扫描器把基数打爆
        route: (req as RoutableRequest).route?.path ?? 'unmatched',
        statusCode: res.statusCode,
        durationMs: Date.now() - startedAt,
      });
    });

    next();
  };
}

原因很实际：NestJS 的执行顺序是 中间件 → Guard → 拦截器 → 管道 → 控制器。放在拦截器里，被 Guard 拒绝的 401/403 根本不会进入统计，而鉴权失败率恰恰是安全监控的核心指标之一。下面这段实测里，未授权的 GET /api/orders 被计入了 401。

3. 健康检查分层 ​

ts
import { Controller, Get } from '@nestjs/common';
import { Public } from '../auth/decorators/public.decorator.js';
import { HealthService } from './health.service.js';
import type {
  CacheCheck,
  DatabaseCheck,
  HealthSnapshot,
  LivenessSnapshot,
} from './health.service.js';

/** 健康检查给探针用，必须是公开接口，且响应结构不要套业务外壳 */
@Public()
@Controller('health')
export class HealthController {
  constructor(private readonly healthService: HealthService) {}

  @Get()
  check(): Promise<HealthSnapshot> {
    return this.healthService.check();
  }

  /** 存活：不查依赖，永远 200（除非进程已经卡死到无法响应） */
  @Get('live')
  liveness(): LivenessSnapshot {
    return this.healthService.liveness();
  }

  /** 就绪：依赖不可用时 503，给负载均衡摘流量用 */
  @Get('ready')
  readiness(): Promise<{
    status: 'ok';
    checks: { database: DatabaseCheck; cache: CacheCheck };
  }> {
    return this.healthService.readiness();
  }

  /** 依赖明细：给人和排障脚本看，始终 200，状态在 body 里 */
  @Get('dependencies')
  dependencies(): Promise<HealthSnapshot> {
    return this.healthService.check();
  }
}

3. 错误上报的唯一出口 ​

所有未捕获异常都进全局过滤器，5xx 在这里输出一条结构化错误日志：

ts
if (status >= HttpStatus.INTERNAL_SERVER_ERROR) {
  const stack = exception instanceof Error ? exception.stack : String(exception);
  // 鉴权失败时 user 还未挂上，可选读取
  const user = (req as Request & { user?: { id?: string } }).user;
  // 错误上报的唯一出口：结构化一条 error 日志，带 requestId 便于和访问日志串联。
  // 接 Sentry / 自建上报平台时，在这里加一次上报调用即可，不要把上报散落到业务代码。
  this.logger.error(
    JSON.stringify({
      msg: 'request.failed',
      method: req.method,
      path: req.originalUrl,
      status,
      code: body.error.code,
      requestId: req.requestId,
      userId: user?.id ?? null,
      message: body.error.message,
    }),
    stack,
  );
}

要接 Sentry，只需要在这一个位置加一次上报调用（附带 requestId 与 userId），不必改任何业务代码。未接入是本示例的现状，不是遗漏。

常见坑与排查 ​

报错 / 现象根因修复验证
日志里查不到某次请求中间件顺序在日志拦截器之后，requestId 还没挂上app.use(requestIdMiddleware) 放在全局拦截器之前响应头有 x-request-id，日志同一 ID
指标里没有 401用拦截器采集，Guard 先于拦截器执行改用中间件监听 res.finish未授权请求后 byStatus['401'] > 0
时序库基数爆炸标签用了真实 URL用 req.route.path 路由模板，404 记 unmatchedroutes 里只有模板，没有具体 id
p95 看起来「偏大」分位数取桶上界接受误差，或引入 HDR Histogram对比 maxMs 与桶边界
liveness 失败触发重启风暴liveness 查了数据库liveness 只返回进程状态停掉 Postgres 后 /health/live 仍 200

企业级做法 ​

  • 告警只建在症状上：5xx 比例、p95 延迟、队列积压、ready 连续失败。不要为每个业务异常建告警，否则告警疲劳比没有告警更糟。
  • 日志采样：2xx 访问日志可按 1%~10% 采样，5xx 与慢请求（>1s）全量。采样发生在采集端，应用端不要随机丢日志。
  • 指标命名稳定：http_requests_total、http_request_duration_ms 这类名字一旦上线就不要改，看板和告警都绑在上面。
  • 错误上报去重：同一异常按 name + 首帧堆栈 聚合，否则一次数据库故障会打出几十万条相同事件。
  • 脱敏：日志里不出现密码、令牌、完整手机号；错误上报前统一过一遍字段白名单。

练习与验收标准 ​

  • [ ] curl -s http://localhost:3000/api/metrics | jq '.data.http.byStatus["401"]' 在未授权请求后大于 0
