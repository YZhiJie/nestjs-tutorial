08 异步与消息：队列、定时任务、Outbox ​

队列、定时任务与 Outbox：异步一致性和可重试的工程做法。

本章目标 ​

  1. 判断一件事该不该搬出请求线程，以及搬出去之后失败怎么办；
  2. 用 BullMQ + Redis 实现两个真实任务：清理过期/已吊销的刷新令牌、超时关单（取消未支付订单并回补库存）；
  3. 用 Job Scheduler 做定时执行，同时提供手动触发与任务状态查询；
  4. 说清 at-least-once、幂等、重试、死信、时区这些词在代码里的落点；
  5. 把 Outbox 讲清楚，但明确标注：设计讲解，示例未实现。

概念与原理 ​

1. 什么该进队列 ​

适合不适合
可以晚几秒/几分钟做用户正在等结果（同步查询）
失败可以重试且幂等必须与请求事务同时成功（除非用 Outbox）
耗时不稳定（外部 API、批处理）极轻量的内存计算

本章的清理任务是典型例子：每天/每小时跑一次即可，不需要用户等待，重复执行也不会出错。

2. at-least-once 与幂等 ​

几乎所有队列都只能保证「至少执行一次」：Worker 执行成功后、还没来得及 ack 就崩溃，任务会被重新投递。所以任务必须幂等——执行一次和执行三次的结果一样。

清理任务的幂等来自 SQL 本身：

sql
DELETE FROM refresh_tokens
WHERE expires_at <= now()
   OR (revoked_at IS NOT NULL AND revoked_at <= now() - interval '7 days')

第二次执行影响行数为 0，不会报错，也不需要「先查再删」。

第二个任务（超时关单）的幂等来自状态机：

sql
UPDATE orders SET status = 'cancelled'
WHERE id = $1 AND status = 'pending'

只有影响行数为 1 才回补库存。任务重复执行、或与用户的支付请求并发时，最多只有一方能把 pending 改走，另一方拿到 0 行并跳过。

3. 选型：为什么是 BullMQ ​

方案优点代价本项目结论
BullMQ延迟任务、重试/退避、Cron 调度、Node 生态成熟依赖 Redis；至少一次语义✅ 采用
pg-boss 等 Postgres 队列少一个基础设施，事务内入队调度/生态较弱，轮询有延迟备选
Kafka / RabbitMQ吞吐、跨语言、回放运维成本高，不适合当「定时清理」过重
自己用 Redis List简单重试、调度、并发、可观测都要自己写不划算

项目已经为第 07 章引入了 Redis，复用它是成本最低的选择。Redis 在 compose 里开了 AOF：缓存可以丢，队列任务不能。

为什么不用 @nestjs/bullmq？它的 @Processor 是装饰器绑定的，而本项目需要按配置在 redis / memory 两种驱动间切换，装饰器无法条件注册。直接用 bullmq 的 Queue / Worker 更透明，也少一层抽象。

4. 定时任务：Job Scheduler 而不是每个实例各跑一遍 ​

BullMQ v5 起用 upsertJobScheduler 替代旧的 repeatable jobs。调度信息存在 Redis 里：

  • 多个应用实例启动时都调用 upsertJobScheduler，同一个 id 只会更新、不会重复注册；
  • 到点后 Redis 里只产生一条待执行任务，由任意一个 Worker 领取；
  • 不需要在代码里加分布式锁，也不会出现「三个实例同时清理」。

Cron 默认按 UTC 解析。本项目是每小时整点，时区不影响；如果要做「每天北京时间 02:00」，必须显式传 tz: 'Asia/Shanghai'，否则会偏移 8 小时。

5. 失败与重试 ​

当前清理任务没有配置重试（默认 attempts: 1）。这是有意的取舍：数据库短暂不可用时，下一个整点会再跑，任务本身幂等；盲目重试只会放大故障期间的写入压力。

生产上更稳妥的配置是：

ts
{ attempts: 3, backoff: { type: 'exponential', delay: 5_000 } }

失败会记录在 worker.on('failed') 日志里，任务保留最近 50 条（removeOnFail: 50），便于排查。

3. 任务本身 ​

ts
async run(): Promise<CleanupResult> {
  const now = new Date();
  const revokedBefore = new Date(now.getTime() - this.retentionDays * DAY_MS);

  const result = await this.tokens
    .createQueryBuilder()
    .delete()
    .from(RefreshTokenEntity)
    .where('expires_at <= :now', { now })
    .orWhere('revoked_at IS NOT NULL AND revoked_at <= :revokedBefore', { revokedBefore })
    .execute();

  const summary: CleanupResult = {
    deleted: result.affected ?? 0,
    executedAt: now.toISOString(),
    policy: {
      expiredBefore: now.toISOString(),
      revokedBefore: revokedBefore.toISOString(),
      revokedRetentionDays: this.retentionDays,
    },
  };

  this.logger.log(JSON.stringify({ msg: 'refresh-tokens.cleanup', ...summary }));
  return summary;
}

第二个任务把「超时关单」也搬进队列。它只读配置与限制批次，业务规则仍留在订单模块：

ts
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import type { AppConfig, QueueConfig } from '../config/configuration.js';
import { OrdersService } from '../orders/orders.service.js';
import type { TimeoutSweepResult } from '../orders/orders.service.js';

/** 单轮最多处理多少张超时订单：控制任务时长，剩下的留给下一轮 */
const SWEEP_BATCH_SIZE = 100;

/**
 * 超时关单任务。
 *
 * 业务规则在 OrdersService 里（状态机 + CAS + 回补库存），
 * 这一层只负责读配置、限制批次，让队列模块不需要了解订单细节。
 */
@Injectable()
export class OrderTimeoutService {
  private readonly config: QueueConfig;

  constructor(
    private readonly orders: OrdersService,
    configService: ConfigService<AppConfig, true>,
  ) {
    this.config = configService.get('queue', { infer: true });
  }

  run(): Promise<TimeoutSweepResult> {
    return this.orders.cancelExpired({
      olderThanMinutes: this.config.orderPaymentTimeoutMinutes,
      limit: SWEEP_BATCH_SIZE,
    });
  }
}

7. 权限与错误路径 ​

任务接口只对 admin 开放（@Roles('admin')），普通成员返回 403；查询不存在的任务返回 404 JOB_NOT_FOUND。这两条在 e2e 里都有断言：

it('admin 可手动触发刷新令牌清理任务并查询任务状态', async () => {

超时关单任务在 e2e 里用「把订单创建时间改到 2 小时前」来复现超时，不依赖真实等待：

describe('超时关单任务', () => {
  it('超时未支付的订单被任务取消并回补库存，已支付订单不受影响', async () => {
    const productsRes = await http().get('/api/products').expect(200);
    const keyboard = (productsRes.body.data as Array<{ id: string; sku: string }>).find(
      (item) => item.sku === 'KB-MECH-01',
    )!;

    await http()
      .patch(`/api/products/${keyboard.id}/inventory`)
      .set('authorization', `Bearer ${admin.accessToken}`)
      .send({ available: 5, reason: 'e2e 超时关单前置' })
      .expect(200);

    const create = (key: string, quantity: number) =>
      http()
        .post('/api/orders')
        .set('authorization', `Bearer ${member.accessToken}`)
        .set('idempotency-key', key)
        .send({ items: [{ productId: keyboard.id, quantity }] })
        .expect(201);

    const stale = await create('e2e-timeout-stale-0001', 2);
    const staleId = (stale.body.data as { order: { id: string } }).order.id;

    const paid = await create('e2e-timeout-paid-0001', 1);
    const paidId = (paid.body.data as { order: { id: string } }).order.id;
    await http()
      .post(`/api/orders/${paidId}/pay`)
      .set('authorization', `Bearer ${member.accessToken}`)
      .expect(200);

    // 把创建时间改到 2 小时前：等待真实时间流逝会让 e2e 变得不可控
    const twoHoursAgo = new Date(Date.now() - 2 * 60 * 60 * 1000);
    const orders = app.get(DataSource).getRepository(OrderEntity);
    await orders.update({ id: staleId }, { createdAt: twoHoursAgo });
    await orders.update({ id: paidId }, { createdAt: twoHoursAgo });

    const job = await http()
      .post('/api/jobs/order-timeout-sweep')
      .set('authorization', `Bearer ${admin.accessToken}`)
      .expect(202);

    const result = job.body.data.result as {
      scanned: number;
      cancelled: string[];
      skipped: number;
      timeoutMinutes: number;
    };
    expect(job.body.data.state).toBe('completed');
    expect(result.scanned).toBe(1);
    expect(result.cancelled).toEqual([staleId]);
    expect(result.skipped).toBe(0);
    expect(result.timeoutMinutes).toBe(30);

    const after = await http()
      .get(`/api/orders/${staleId}`)
      .set('authorization', `Bearer ${member.accessToken}`)
      .expect(200);
    expect(after.body.data.status).toBe('cancelled');
    expect(after.body.data.cancelledAt).not.toBeNull();

    // 已支付订单保持 paid，库存仍被它占着：5 - 1 = 4
    const paidAfter = await http()
      .get(`/api/orders/${paidId}`)
      .set('authorization', `Bearer ${member.accessToken}`)
      .expect(200);
    expect(paidAfter.body.data.status).toBe('paid');

    const stock = await http()
      .get('/api/products')
      .expect(200)
      .then((res) =>
        (res.body.data as Array<{ id: string; available: number }>).find(
          (item) => item.id === keyboard.id,
        )!.available,
      );
    expect(stock).toBe(4);

    // 再跑一次：没有新的超时订单，取消数为 0（任务幂等）
    const again = await http()
      .post('/api/jobs/order-timeout-sweep')
      .set('authorization', `Bearer ${admin.accessToken}`)
      .expect(202);
    expect((again.body.data.result as { cancelled: string[] }).cancelled).toEqual([]);
  });
});

1. 模块与生命周期 ​

ts
import { Inject, Module } from '@nestjs/common';
import type { OnApplicationBootstrap, OnApplicationShutdown } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { TypeOrmModule } from '@nestjs/typeorm';
import { RefreshTokenEntity } from '../auth/refresh-token.entity.js';
import type { AppConfig } from '../config/configuration.js';
import { MetricsService } from '../metrics/metrics.service.js';
import { OrdersModule } from '../orders/orders.module.js';
import { BullJobsService } from './bull-jobs.service.js';
import { JobsController } from './jobs.controller.js';
import { JOBS_SERVICE } from './jobs.service.js';
import type { JobHandler, JobHandlers, JobsService } from './jobs.service.js';
import { CLEANUP_JOB, ORDER_TIMEOUT_JOB } from './jobs.service.js';
import { MemoryJobsService } from './memory-jobs.service.js';
import { OrderTimeoutService } from './order-timeout.service.js';
import { RefreshTokenCleanupService } from './refresh-token-cleanup.service.js';

/**
 * 队列模块：驱动在启动阶段选择，和缓存一样不做静默降级。
 *
 * 生命周期放在模块上而不是各驱动里，保证 main.ts 与 e2e 都走同一条路径：
 * start() 注册定时任务并等待 Redis，close() 停掉 Worker 与连接。
 *
 * 新增任务的步骤只有两步：在 jobs.service.ts 里加任务名，在下面的 handlers 里注册。
 */
@Module({
  imports: [TypeOrmModule.forFeature([RefreshTokenEntity]), OrdersModule],
  controllers: [JobsController],
  providers: [
    RefreshTokenCleanupService,
    OrderTimeoutService,
    {
      provide: JOBS_SERVICE,
      inject: [ConfigService, RefreshTokenCleanupService, OrderTimeoutService, MetricsService],
      useFactory: (
        config: ConfigService<AppConfig, true>,
        cleanup: RefreshTokenCleanupService,
        orderTimeout: OrderTimeoutService,
        metrics: MetricsService,
      ): JobsService => {
        const queue = config.get('queue', { infer: true });
        const handlers: JobHandlers = new Map<string, JobHandler>([
          [CLEANUP_JOB, () => cleanup.run()],
          [ORDER_TIMEOUT_JOB, () => orderTimeout.run()],
        ]);

        if (queue.driver === 'memory') {
          return new MemoryJobsService(handlers, metrics);
        }
        return BullJobsService.create(
          handlers,
          config.get('redis', { infer: true }),
          queue,
          metrics,
        );
      },
    },
  ],
  exports: [JOBS_SERVICE, RefreshTokenCleanupService, OrderTimeoutService],
})
export class QueueModule implements OnApplicationBootstrap, OnApplicationShutdown {
  constructor(@Inject(JOBS_SERVICE) private readonly jobs: JobsService) {}

  // #region queue-lifecycle
  async onApplicationBootstrap(): Promise<void> {
    await this.jobs.start();
  }

  async onApplicationShutdown(): Promise<void> {
    await this.jobs.close();
  }
  // #endregion queue-lifecycle
}

驱动选择发生在启动阶段：redis 走 BullMQ，memory 走进程内实现。start() 注册调度并等待 Redis 就绪，close() 关闭 Worker 与队列连接。

应用已经调用 app.enableShutdownHooks()，所以 SIGTERM 时会执行 onApplicationShutdown，不会把正在执行的任务直接切断。第 13 章会把它扩展成完整的优雅关闭。

2. BullMQ 驱动 ​

ts

import { Queue, Worker } from 'bullmq';
import type { Job } from 'bullmq';
import type { QueueConfig, RedisConfig } from '../config/configuration.js';
import type { MetricsService } from '../metrics/metrics.service.js';
import { formatRedisHint, RedisUnavailableError } from '../redis/redis-hint.js';
import type { JobHandlers, JobSummary, JobsService } from './jobs.service.js';
import {
  CLEANUP_JOB,
  CLEANUP_SCHEDULER_ID,
  MAINTENANCE_QUEUE,
  ORDER_TIMEOUT_JOB,
  ORDER_TIMEOUT_SCHEDULER_ID,
} from './jobs.service.js';

interface Schedule {
  id: string;
  pattern: string;
  name: string;
}

/**
 * BullMQ 驱动：生产者（Queue）与消费者（Worker）在同一个进程里，
 * 这是开发期最简单的形态；生产里把 Worker 单独起进程即可复用同一份代码。
 *
 * 定时任务用 BullMQ 的 Job Scheduler（v5 起替代 repeatable jobs）：
 * 调度信息存在 Redis 里，多实例只会按 cron 产生一条待执行任务，不会每个实例各跑一遍。
 *
 * 驱动只认识「任务名 → 执行函数」这张表，新增任务不需要改这里。
 */
export class BullJobsService implements JobsService {
  private readonly logger = new Logger(BullJobsService.name);
  private readonly queue: Queue;
  private readonly worker: Worker;

  private constructor(
    private readonly handlers: JobHandlers,
    private readonly redisConfig: RedisConfig,
    private readonly queueConfig: QueueConfig,
    private readonly metrics: MetricsService,
    connection: { host: string; port: number; password?: string; db: number },
  ) {
    this.queue = new Queue(MAINTENANCE_QUEUE, { connection });
    this.worker = new Worker(
      MAINTENANCE_QUEUE,
      async (job) => this.dispatch(job.name),
      { connection, concurrency: queueConfig.concurrency },
    );

    // EventEmitter 的 error 事件没有监听者会直接抛到进程级别
    this.queue.on('error', (error: Error) =>
      this.logger.error(`队列连接异常: ${error.message}`),
    );
    this.worker.on('error', (error: Error) =>
      this.logger.error(`Worker 连接异常: ${error.message}`),
    );
    this.worker.on('failed', (job, error) => {
      this.logger.error(
        JSON.stringify({ msg: 'job.failed', jobId: job?.id, name: job?.name, error: error.message }),
      );
      if (job) {
        this.metrics.recordJob(job.name, 'failed');
      }
    });
    this.worker.on('completed', (job) => this.metrics.recordJob(job.name, 'completed'));
  }

  static create(
    handlers: JobHandlers,
    redisConfig: RedisConfig,
    queueConfig: QueueConfig,
    metrics: MetricsService,
  ): BullJobsService {
    return new BullJobsService(handlers, redisConfig, queueConfig, metrics, {
      host: redisConfig.host,
      port: redisConfig.port,
      password: redisConfig.password ?? undefined,
      db: redisConfig.db,
    });
  }

  async start(): Promise<void> {
    try {
      await waitUntilReady(this.queue, 5_000);
      for (const schedule of this.schedules()) {
        await this.queue.upsertJobScheduler(
          schedule.id,
          { pattern: schedule.pattern },
          {
            name: schedule.name,
            data: {},
            // 只保留最近若干次执行记录，避免 Redis 无限增长
            opts: { removeOnComplete: 20, removeOnFail: 50 },
          },
        );
      }
      this.logger.log(
        JSON.stringify({
          msg: 'queue.ready',
          queue: MAINTENANCE_QUEUE,
          concurrency: this.queueConfig.concurrency,
          schedules: this.schedules().map(({ id, name, pattern }) => ({ id, name, pattern })),
        }),
      );
    } catch (error) {
      await this.close();
      throw new RedisUnavailableError(formatRedisHint(error, this.redisConfig));
    }
  }

  enqueueCleanup(): Promise<JobSummary> {
    return this.enqueue(CLEANUP_JOB);
  }

  enqueueOrderTimeout(): Promise<JobSummary> {
    return this.enqueue(ORDER_TIMEOUT_JOB);
  }

  async getJob(id: string): Promise<JobSummary | null> {
    const job = await this.queue.getJob(id);
    return job ? toSummary(job) : null;
  }

  async close(): Promise<void> {
    await this.worker.close().catch(() => undefined);
    await this.queue.close().catch(() => undefined);
  }

  private async enqueue(name: string): Promise<JobSummary> {
    if (!this.handlers.has(name)) {
      throw new Error(`未注册的任务: ${name}`);
    }
    const job = await this.queue.add(name, {}, { removeOnComplete: 20, removeOnFail: 50 });
    return toSummary(job);
  }

  private dispatch(name: string): Promise<unknown> {
    const handler = this.handlers.get(name);
    if (!handler) {
      throw new Error(`未知任务: ${name}`);
    }
    return handler();
  }

  private schedules(): Schedule[] {
    return [
      { id: CLEANUP_SCHEDULER_ID, pattern: this.queueConfig.cleanupCron, name: CLEANUP_JOB },
      {
        id: ORDER_TIMEOUT_SCHEDULER_ID,
        pattern: this.queueConfig.orderTimeoutCron,
        name: ORDER_TIMEOUT_JOB,
      },
    ];
  }
}

async function toSummary(job: Job): Promise<JobSummary> {
  return {
    id: String(job.id),
    name: job.name,
    state: await job.getState(),
    result: job.returnvalue,
    ...(job.failedReason ? { failedReason: job.failedReason } : {}),
    ...(job.timestamp ? { createdAt: new Date(job.timestamp).toISOString() } : {}),
    ...(job.finishedOn ? { finishedAt: new Date(job.finishedOn).toISOString() } : {}),
  };
}

async function waitUntilReady(queue: Queue, timeoutMs: number): Promise<void> {
  let timer: NodeJS.Timeout | undefined;
  try {
    await Promise.race([
      queue.waitUntilReady(),
      new Promise<never>((_, reject) => {
        timer = setTimeout(
          () => reject(new Error(`Redis 连接超时（${timeoutMs}ms）`)),
          timeoutMs,
        );
        timer.unref();
      }),
    ]);
  } finally {
    if (timer) {
      clearTimeout(timer);
    }
  }
}

几个关键点：

  • Queue 与 Worker 用同一份连接配置，但 BullMQ 会各自创建客户端；生产可以把 Worker 拆成独立进程；
  • waitUntilReady 加了 5 秒超时：Redis 不可用时快速失败，而不是无限重连；
  • worker.on('error') 与 queue.on('error') 必须监听，否则 EventEmitter 的 error 事件会掀翻进程；
  • 驱动只认识「任务名 → 执行函数」的 Map，新增任务不用改驱动；
  • 只保留最近 20 条成功、50 条失败记录，避免 Redis 被历史任务撑爆。

3. 任务定义与策略 ​

ts
import { Injectable, Logger } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import type { AppConfig } from '../config/configuration.js';
import { RefreshTokenEntity } from '../auth/refresh-token.entity.js';

export interface CleanupResult {
  deleted: number;
  executedAt: string;
  policy: {
    expiredBefore: string;
    revokedBefore: string;
    revokedRetentionDays: number;
  };
}

const DAY_MS = 24 * 60 * 60 * 1000;

/**
 * 刷新令牌清理：一个「必须做、但不该占用请求线程」的典型任务。
 *
 * 清理策略：
 * - 已过期（expires_at <= now）的令牌：立刻删，它们已经无法换发；
 * - 已吊销且超过保留期（revoked_at <= now - N 天）的令牌：延迟删除，
 *   保留一段时间的吊销记录，便于排查「用户说被强制登出」这类问题。
 *
 * 删除是幂等的：重复执行只是影响行数为 0，不会报错。
 */
@Injectable()
export class RefreshTokenCleanupService {
  private readonly logger = new Logger(RefreshTokenCleanupService.name);
  private readonly retentionDays: number;

  constructor(
    @InjectRepository(RefreshTokenEntity)
    private readonly tokens: Repository<RefreshTokenEntity>,
    configService: ConfigService<AppConfig, true>,
  ) {
    this.retentionDays = configService.get('queue', { infer: true }).revokedRetentionDays;
  }

  // #region refresh-token-cleanup-run
  async run(): Promise<CleanupResult> {
    const now = new Date();
    const revokedBefore = new Date(now.getTime() - this.retentionDays * DAY_MS);

    const result = await this.tokens
      .createQueryBuilder()
      .delete()
      .from(RefreshTokenEntity)
      .where('expires_at <= :now', { now })
      .orWhere('revoked_at IS NOT NULL AND revoked_at <= :revokedBefore', { revokedBefore })
      .execute();

    const summary: CleanupResult = {
      deleted: result.affected ?? 0,
      executedAt: now.toISOString(),
      policy: {
        expiredBefore: now.toISOString(),
        revokedBefore: revokedBefore.toISOString(),
        revokedRetentionDays: this.retentionDays,
      },
    };

    this.logger.log(JSON.stringify({ msg: 'refresh-tokens.cleanup', ...summary }));
    return summary;
  }
  // #endregion refresh-token-cleanup-run
}

清理策略有两个时间边界：

  • expires_at <= now()：已经不能换发，立刻删；
  • revoked_at <= now() - 7 天：吊销记录保留一周，方便排查「用户说被强制登出」；超过后删除。

保留期来自 REFRESH_CLEANUP_RETENTION_DAYS，不要写死在 SQL 里。

4. 手动触发与状态查询 ​

ts
import {
  Controller,
  Get,
  HttpCode,
  HttpStatus,
  Inject,
  NotFoundException,
  Param,
  Post,
} from '@nestjs/common';
import { Roles } from '../auth/decorators/roles.decorator.js';
import { JOBS_SERVICE } from './jobs.service.js';
import type { JobSummary, JobsService } from './jobs.service.js';

/**
 * 运维接口：只对 admin 开放。
 *
 * 手动触发是「定时任务」的必要补充：出了问题要能立刻跑一次，
 * 而不是等到下一个整点。返回任务 id，便于轮询执行状态。
 */
@Roles('admin')
@Controller('jobs')
export class JobsController {
  constructor(@Inject(JOBS_SERVICE) private readonly jobs: JobsService) {}

  @Post('refresh-tokens-cleanup')
  @HttpCode(HttpStatus.ACCEPTED)
  enqueueCleanup(): Promise<JobSummary> {
    return this.jobs.enqueueCleanup();
  }

  /**
   * 手动跑一次超时关单。
   *
   * 正常由 cron 每 5 分钟触发；排查「订单明明超时却没关」时
   * 需要能立刻执行一次，而不是等下一轮。
   */
  @Post('order-timeout-sweep')
  @HttpCode(HttpStatus.ACCEPTED)
  enqueueOrderTimeout(): Promise<JobSummary> {
    return this.jobs.enqueueOrderTimeout();
  }

  @Get(':id')
  async getJob(@Param('id') id: string): Promise<JobSummary> {
    const job = await this.jobs.getJob(id);
    if (!job) {
      throw new NotFoundException({
        code: 'JOB_NOT_FOUND',
        message: `任务 ${id} 不存在（可能已超出保留条数）`,
      });
    }
    return job;
  }
}

返回 202 Accepted 而不是 200：任务只是被接收，不代表已经完成。调用方拿 id 轮询 GET /api/jobs/:id。

memory 驱动下任务同步执行完，返回时状态已经是 completed；redis 驱动下通常是 waiting。e2e 在内存驱动下断言 completed，真实环境用 curl 观察状态变化。

5. 失败路径 ​

失败时 state: failed，failedReason 是错误信息。任务记录保留在 Redis 中，便于重放与排查：

bash
curl -s "http://localhost:3000/api/jobs/<id>" -H "authorization: Bearer $TOKEN" | jq '.data | {state, failedReason}'

当前没有自动重试与死信队列：失败任务只是保留，不会自动再跑。这是明确的未完成项，不是「已经做好」。

6. Outbox：设计讲解，示例未实现 ​

问题：注册成功后要发欢迎邮件，但「写用户表」和「投递消息」是两个系统，无法放进同一个事务。先发消息后写库，可能消息发了用户没创建；先写库后发消息，可能库写了消息丢了。

Outbox 的做法：

  1. 在同一个数据库事务里写业务表 + 写 outbox_events 表；
  2. 独立的 relay 进程扫描未投递事件，投递到队列；
  3. 投递成功后标记 published_at，失败则重试；
  4. 消费方按事件 id 幂等。
text
BEGIN;
  INSERT INTO users ...;
  INSERT INTO outbox_events (id, type, payload, created_at) VALUES (...);
COMMIT;
-- relay: SELECT ... FOR UPDATE SKIP LOCKED → queue.add → UPDATE published_at

本仓库没有 outbox_events 表、没有 relay、没有消费方，所以这一节只讲设计。真要实现，验收标准至少包括：事务回滚时事件不存在、relay 崩溃后能继续投递、重复投递不产生重复副作用。

本工程实际用到哪、阈值怎么定 ​

队列里跑的不是演示任务，是两个真实维护任务：

任务scheduler idcron关键参数判定依据
清理刷新令牌refresh-tokens-cleanup0 * * * *（每小时）已吊销记录保留 7 天，过期记录立即删过期令牌在鉴权时已被拒绝，清理只为释放空间，不必更频繁；7 天与 REFRESH_TOKEN_TTL_DAYS 对齐，避免刚吊销的令牌在排障时已被清掉
超时自动关单orders-timeout-sweep*/5 * * * *（每 5 分钟）ORDER_PAYMENT_TIMEOUT_MINUTES=30，每批 100 单30 分钟是「库存占用成本」与「用户支付完成率」的折中；5 分钟扫描间隔决定关单精度，最坏 35 分钟关掉，误差不超过一个扫描周期

三个数字之间的关系值得记住：

  • 超时阈值决定业务体验（用户有多少时间付款）；
  • 扫描间隔决定系统精度（库存最晚多久回补），它与阈值无关，可以独立调；
  • 批大小决定单次事务压力，100 条配合 QUEUE_CONCURRENCY=2，避免一次扫描锁住整张订单表。

三者都能用环境变量覆盖（REFRESH_CLEANUP_CRON、ORDER_TIMEOUT_CRON、ORDER_PAYMENT_TIMEOUT_MINUTES），改阈值不需要改代码。手动触发用 POST /api/jobs/order-timeout-sweep，返回本次扫描与关闭的条数。

企业级做法 ​

  1. 重试与退避：给非幂等任务加重试是灾难；给幂等任务加 attempts + exponential backoff。当前未配置，属已知缺口。
  2. 独立 Worker：Web 进程只负责入队，Worker 单独扩缩容，避免长任务拖慢接口。
  3. 死信与告警：失败任务进入死信队列并告警，而不是安静地躺在 Redis 里。
  4. 可观测性：队列深度、等待时间、失败率、任务耗时。当前只有启动日志与 failed 日志，指标在第 11 章补。
  5. 批量与限速：清理类任务按批删除（如每批 1000 行），批间 sleep，避免长事务与主从延迟。
  6. 调度治理：给 scheduler id 起稳定名字，变更 cron 时用 upsert 而不是新增，避免旧调度残留。
