05 配置与环境管理 ​

配置分层、环境校验与密钥管理：让应用在启动时就暴露配置错误。

成稿正文、示例代码与验收标准均已完整，可直接跟练

本章目标 ​

  1. 用 ConfigModule 把散落在代码里的 process.env 收敛成一个有类型、可校验的配置对象；
  2. 说清 .env.local / .env / 真实环境变量三者的优先级，并知道 CLI 脚本为什么要单独处理；
  3. 在启动阶段拦住配置错误，而不是等第一个请求进来才炸；
  4. 设计「连不上数据库」时的失败行为：清晰报错、非 0 退出、不静默降级；
  5. 区分健康检查（liveness）与就绪检查（readiness）的职责。

概念与原理 ​

1. 配置的三种来源与优先级 ​

同一个变量可能来自三个地方，必须有确定的优先级，否则「我明明改了 .env 为什么不生效」会反复出现。

本项目的约定（从高到低）：

优先级来源典型场景
1真实环境变量（process.env）容器/K8s 注入、CI 变量、命令行 PORT=3001 pnpm dev
2.env.local本机个人覆盖，不进 git
3.env团队共享的开发默认值
4代码里的默认值连 .env 都没有时也能跑

实现上有两个容易忽略的细节：

  • ConfigModule 的 envFilePath: ['.env.local', '.env']，数组中靠前的文件优先；
  • @nestjs/config 默认 override: false，即 { ...文件配置, ...process.env }，所以真实环境变量永远赢。

CLI 脚本（迁移、种子）没有 Nest 容器，用的是 Node 原生的 process.loadEnvFile。它的行为是不覆盖已存在的变量，所以加载顺序反过来写：

ts
import type { DataSourceOptions } from 'typeorm';
import { DataSource } from 'typeorm';
import { InitialSchema1750000000000 } from './migrations/1750000000000-InitialSchema.js';
import { OrdersAndInventory1750000001000 } from './migrations/1750000001000-OrdersAndInventory.js';
import { WebhookEvents1750000002000 } from './migrations/1750000002000-WebhookEvents.js';

/**
 * CLI 场景下没有 ConfigModule，手动加载 .env。
 * process.loadEnvFile 不覆盖已存在的变量，所以「先加载的优先」：
 * 与 app.module.ts 的 envFilePath 保持一致，让 .env.local 覆盖 .env。
 */
export function loadEnvFiles(): void {
  for (const file of ['.env.local', '.env']) {
    try {
      process.loadEnvFile(file);
    } catch {
      // 文件不存在时忽略：CI 里通常直接注入环境变量
    }
  }
}

/**
 * 只给迁移脚本用的 DataSource：
 * 不注册实体（迁移里都是显式 SQL），因此不需要 Nest 的 DI 上下文。
 */
export function createMigrationDataSource(): DataSource {
  loadEnvFiles();

  const options: DataSourceOptions = {
    type: 'postgres',
    host: process.env.DB_HOST ?? 'localhost',
    port: Number.parseInt(process.env.DB_PORT ?? '5432', 10),
    username: process.env.DB_USERNAME ?? 'postgres',
    password: process.env.DB_PASSWORD ?? 'postgres',
    database: process.env.DB_NAME ?? 'nestjs_tutorial',
    ssl: process.env.DB_SSL === 'true' ? { rejectUnauthorized: false } : false,
    uuidExtension: 'pgcrypto',
    entities: [],
    migrations: [
      InitialSchema1750000000000,
      OrdersAndInventory1750000001000,
      WebhookEvents1750000002000,
    ],
    synchronize: false,
    logging: process.env.DB_LOGGING === 'true' ? ['query', 'error'] : ['error'],
  };

  return new DataSource(options);
}

这两处顺序不一致看起来别扭，但原因相同：先读到的赢。process.loadEnvFile 没有「覆盖」选项，只能靠调用顺序表达优先级。

2. 配置对象的形状：AppConfig ​

业务代码不直接读 process.env，而是通过 ConfigService<AppConfig, true> 读取。true 表示「路径一定存在」，get('database', { infer: true }) 会推导出 DatabaseConfig 类型。

ts
export interface AppConfig {
  nodeEnv: 'development' | 'test' | 'production';
  port: number;
  logLevel: 'debug' | 'info' | 'warn' | 'error';
  corsOrigin: string;
  apiPrefix: string;
  database: DatabaseConfig;
  auth: AuthConfig;
  redis: RedisConfig;
  cache: CacheConfig;
  queue: QueueConfig;
  bff: BffConfig;
  realtime: RealtimeConfig;
  storage: StorageConfig;
  webhooks: WebhookConfig;
}

注意 parseInteger 和 === 'true' 这两处：环境变量永远是字符串，转换规则必须显式写出来，不能靠类型断言。

ts
/**
 * 开发环境默认密钥。生产环境若沿用它，启动期校验会直接失败（见 env.validation.ts），
 * 这样「忘了配密钥」不会静默上线成一个谁都能签 token 的服务。
 */
export const DEV_ACCESS_SECRET = 'dev-only-insecure-access-secret-change-me';

/** Webhook 签名的开发默认密钥；生产环境沿用它会在启动期被拦截 */
export const DEV_WEBHOOK_SECRET = 'dev-only-insecure-webhook-secret-change-me';

function parseInteger(raw: string | undefined, fallback: number): number {
  const parsed = Number.parseInt(raw ?? '', 10);
  return Number.isFinite(parsed) ? parsed : fallback;
}

/**
 * 项目配置的唯一出口：所有业务代码都通过 ConfigService<AppConfig, true> 读取，
 * 而不是直接读 process.env —— 这样测试里可以整体覆盖，生产里也便于做启动期校验。
 */
export default (): AppConfig => {
  const database: DatabaseConfig = {
    // 默认走 Postgres：连不上就报错退出，不会偷偷退回内存存储。
    // 只有显式设置 DB_DRIVER=sqljs 才会使用进程内数据库（测试与临时演示使用）。
    driver: (process.env.DB_DRIVER as DatabaseDriver) ?? 'postgres',
    host: process.env.DB_HOST ?? 'localhost',
    port: parseInteger(process.env.DB_PORT, 5432),
    username: process.env.DB_USERNAME ?? 'postgres',
    password: process.env.DB_PASSWORD ?? 'postgres',
    name: process.env.DB_NAME ?? 'nestjs_tutorial',
    ssl: process.env.DB_SSL === 'true',
    logging: process.env.DB_LOGGING === 'true',
  };

  // 缓存与队列的默认驱动跟随数据库：
  // - Postgres 开发环境 → Redis（docker-compose 已提供）
  // - sqljs 临时演示 / 测试 → 进程内实现，`pnpm verify` 不需要 Docker
  // 想混搭时显式设置 CACHE_DRIVER / QUEUE_DRIVER 覆盖即可。
  const localDriver = database.driver === 'sqljs' ? 'memory' : 'redis';

节选：Redis、缓存、队列等其余配置项的映射见 apps/api/src/config/configuration.ts。

3. 启动期校验：让坏配置上不了线 ​

ConfigModule.forRoot({ validate }) 会在应用初始化时调用校验函数。校验不通过就抛错，进程不会进入监听状态。

ts
/**
 * 环境变量契约。启动阶段先校验，校验不通过直接抛错退出，
 * 避免「服务起来了才发现端口/密钥是坏的」这类线上事故。
 */
export class EnvironmentVariables {
  @IsEnum(NodeEnv)
  @IsOptional()
  NODE_ENV: NodeEnv = NodeEnv.Development;

  @Type(() => Number)
  @IsInt()
  @Min(1)
  @Max(65535)
  @IsOptional()
  PORT: number = 3000;

节选：其余字段的校验规则见 apps/api/src/config/env.validation.ts。

这里有两个关键决定：

  1. 不开 enableImplicitConversion：它会把字符串 'false' 用 Boolean() 转成 true。本项目在接入 Postgres 时就踩过：DB_SSL=false 被转成 true，连接时带上 SSL，报 The server does not support SSL connections；
  2. 数字字段单独 @Type(() => Number)：只对需要的字段做转换，意图明确。

还有一条业务规则：NODE_ENV=production 时，JWT_ACCESS_SECRET 不允许等于开发默认值。否则「忘了配密钥」会静默上线成一个谁都能签 token 的服务。

ts
export function validateEnv(raw: Record<string, unknown>): EnvironmentVariables {
  // 不开 enableImplicitConversion：它会把字符串 'false' 用 Boolean() 转成 true
  // （经典的布尔环境变量陷阱）。数字字段单独用 @Type(() => Number) 显式转换。
  const config = plainToInstance(EnvironmentVariables, raw, {
    excludeExtraneousValues: false,
  });
  const errors = validateSync(config, { skipMissingProperties: false });

  if (errors.length > 0) {
    const details = errors
      .map((error) => Object.values(error.constraints ?? {}).join('; '))
      .join(' | ');
    throw new Error(`环境变量校验失败: ${details}`);
  }

  // 生产环境禁止沿用开发默认密钥：这是一个必须在启动期拦住的配置错误
  if (config.NODE_ENV === NodeEnv.Production && config.JWT_ACCESS_SECRET === DEV_ACCESS_SECRET) {
    throw new Error(
      '环境变量校验失败: 生产环境必须显式设置 JWT_ACCESS_SECRET（当前值仍是开发默认值）',
    );
  }

  // Webhook 密钥同理：沿用默认值等于任何人都能伪造回调
  if (config.NODE_ENV === NodeEnv.Production && config.WEBHOOK_SECRET === DEV_WEBHOOK_SECRET) {
    throw new Error(
      '环境变量校验失败: 生产环境必须显式设置 WEBHOOK_SECRET（当前值仍是开发默认值）',
    );
  }

  return config;
}

4. 配置校验失败长什么样 ​

bash
PORT=abc pnpm dev

真实输出（节选）：

text
[Nest] ERROR [ExceptionHandler] Error: 环境变量校验失败:
PORT must not be greater than 65535; PORT must not be less than 1; PORT must be an integer number
...
Node.js v24.17.0

进程以非 0 退出码结束。堆栈不是最友好的形式，但错误信息本身是可执行的：它直接告诉你哪个变量、违反了哪条规则。

想要更干净的错误输出

可以在 main.ts 里单独捕获「环境变量校验失败」并只打印一行。本项目没有这么做，是因为启动失败只发生一次、面向的是开发者与部署平台；数据库连接失败才是高频问题，值得单独做中文提示（见下一节）。

5. 连不上数据库：清晰失败，不静默降级 ​

NestFactory.create 默认 abortOnError: true，初始化失败会直接 process.abort()，我们自己的错误处理拿不到异常。所以 main.ts 显式关掉它：

ts
import { Logger } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { NestFactory } from '@nestjs/core';
import type { INestApplication } from '@nestjs/common';
import { AppModule } from './app.module.js';
import configuration from './config/configuration.js';
import type { AppConfig } from './config/configuration.js';
import { formatDatabaseHint, isDatabaseConnectionError } from './database/connection-hint.js';
import { createRedisClient } from './redis/redis.client.js';
import { formatRedisHint, isRedisError, RedisUnavailableError } from './redis/redis-hint.js';
import { configureApp } from './setup-app.js';

/**
 * 在创建 Nest 应用之前先确认 Redis 可用。
 *
 * 为什么不在模块工厂里做？Nest 12 的 abortOnError:false 会把初始化异常交给
 * ExceptionHandler 记录，但 create() 的 Promise 不会 settle，进程会挂住。
 * 预检放在最前面，连不上就打印排查步骤并退出，行为可预测。
 */
async function preflightRedis(): Promise<void> {
  for (const file of ['.env.local', '.env']) {
    try {
      process.loadEnvFile(file);
    } catch {
      // 文件不存在就跳过，和 ConfigModule 的行为保持一致
    }
  }

  const config = configuration();
  if (config.cache.driver !== 'redis' && config.queue.driver !== 'redis') {
    return;
  }

  try {
    const client = await createRedisClient(config.redis);
    await client.quit().catch(() => client.disconnect());
  } catch (error) {
    if (error instanceof RedisUnavailableError) {
      console.error(error.message);
      process.exit(1);
    }
    throw error;
  }
}

async function bootstrap(): Promise<void> {
  await preflightRedis();

  let app: INestApplication;

  try {
    // abortOnError: false —— 默认情况下 Nest 在初始化失败时直接 process.abort()，
    // 我们的错误处理拿不到异常；关掉它才能给出「怎么修」的提示再退出。
    // rawBody: Webhook 验签必须基于原始字节，不能被 JSON 反序列化后的对象替代
    app = await NestFactory.create(AppModule, {
      bufferLogs: true,
      abortOnError: false,
      rawBody: true,
    });
  } catch (error) {
    // 数据库连不上时给可执行提示，而不是静默降级或只甩一段堆栈
    if (isDatabaseConnectionError(error)) {
      console.error(formatDatabaseHint(error));
      process.exitCode = 1;
      return;
    }
    // Redis（缓存/队列）同理：不自动退回内存实现
    if (isRedisError(error)) {
      const message = error instanceof Error ? error.message : '';
      console.error(message.startsWith('✖ Redis 连接失败') ? message : formatRedisHint(error));
      process.exitCode = 1;
      return;
    }
    throw error;
  }

  configureApp(app);

  // #region main-shutdown
  // 让 SIGTERM / SIGINT 触发 onApplicationShutdown：
  // 队列 Worker 停止接新任务、TypeORM 关闭连接池都在这里完成。
  // 没有这一步，容器重启时正在执行的任务会被直接切断。
  app.enableShutdownHooks();
  for (const signal of ['SIGTERM', 'SIGINT'] as const) {
    process.once(signal, () => Logger.log(`收到 ${signal}，开始优雅关闭`, 'Bootstrap'));
  }
  // #endregion main-shutdown

  const config = app.get(ConfigService<AppConfig, true>);
  const port = config.get('port', { infer: true });
  const prefix = config.get('apiPrefix', { infer: true });
  const database = config.get('database', { infer: true });
  const cache = config.get('cache', { infer: true });
  const queue = config.get('queue', { infer: true });

  await app.listen(port);

  Logger.log(`API 已启动: http://localhost:${port}/${prefix}`, 'Bootstrap');
  Logger.log(
    `数据库: ${database.driver}${database.driver === 'postgres' ? ` (${database.host}:${database.port}/${database.name})` : '（进程内，重启即清空）'}`,
    'Bootstrap',
  );
  Logger.log(
    `缓存: ${cache.driver}${cache.driver === 'redis' ? ` (${config.get('redis', { infer: true }).host}:${config.get('redis', { infer: true }).port})` : '（进程内，仅测试/临时演示）'}，队列: ${queue.driver}`,
    'Bootstrap',
  );
}

await bootstrap();

连接错误由 connection-hint.ts 识别并翻译成「下一步做什么」：

ts
/** 把「连不上数据库」这类底层错误识别出来，避免和其它启动错误混在一起 */
const CONNECTION_ERROR_CODES = new Set([
  'ECONNREFUSED',
  'ENOTFOUND',
  'ETIMEDOUT',
  'EHOSTUNREACH',
  'ECONNRESET',
  '28P01', // Postgres: password authentication failed
  '3D000', // Postgres: database does not exist
]);

function collectMessages(error: unknown, depth = 0): string[] {
  if (depth > 4 || error === null || error === undefined) {
    return [];
  }

  const messages: string[] = [];
  const candidate = error as {
    message?: unknown;
    code?: unknown;
    errors?: unknown;
    driverError?: { code?: unknown; message?: unknown };
  };

  if (typeof candidate.message === 'string') {
    messages.push(candidate.message);
  }
  if (typeof candidate.code === 'string') {
    messages.push(candidate.code);
  }
  if (candidate.driverError && typeof candidate.driverError.code === 'string') {
    messages.push(candidate.driverError.code);
  }
  if (Array.isArray(candidate.errors)) {
    for (const nested of candidate.errors) {
      messages.push(...collectMessages(nested, depth + 1));
    }
  }

  return messages;
}

export function isDatabaseConnectionError(error: unknown): boolean {
  const messages = collectMessages(error);
  if (messages.some((message) => CONNECTION_ERROR_CODES.has(message))) {
    return true;
  }

  const joined = messages.join(' | ');
  return (
    joined.includes('Unable to connect to the database') ||
    joined.includes('connect ECONNREFUSED') ||
    joined.includes('password authentication failed') ||
    joined.includes('does not exist')
  );
}

/**
 * 启动失败时给「可执行」的提示，而不是甩一段堆栈。
 * 这也是「不静默降级」的另一半：连不上要让人一眼知道下一步做什么。
 */
export function formatDatabaseHint(error: unknown): string {
  const host = process.env.DB_HOST ?? 'localhost';
  const port = process.env.DB_PORT ?? '5432';
  const database = process.env.DB_NAME ?? 'nestjs_tutorial';
  const raw = collectMessages(error).find((message) => message.trim().length > 0) ?? String(error);

  return [
    '✖ 数据库连接失败，服务未启动。',
    '',
    `  配置: postgres://${process.env.DB_USERNAME ?? 'postgres'}@${host}:${port}/${database}`,
    `  原因: ${raw}`,
    '',
    '  按顺序排查：',
    '  1) 启动数据库：docker compose up -d postgres',
    "     确认健康：docker compose ps --format '{{.Name}} {{.Health}}'",
    '  2) 检查 apps/api/.env 里的 DB_HOST / DB_PORT / DB_USERNAME / DB_PASSWORD / DB_NAME',
    '  3) 首次启动建表：pnpm --filter @nestjs-tutorial/api db:migrate',
    '     （正常启动时也会自动执行未运行的迁移）',
    '  4) 只想临时跑通接口、不需要持久化：DB_DRIVER=sqljs pnpm dev',
    '',
    '  注意：服务不会自动退回内存存储——避免「以为连上了数据库，其实重启就丢数据」。',
  ].join('\n');
}

真实输出（DB_PORT=5999 node dist/main.js，退出码 1）：

text
✖ 数据库连接失败，服务未启动。

  配置: postgres://postgres@localhost:5999/nestjs_tutorial
  原因: ECONNREFUSED

  按顺序排查：
  1) 启动数据库：docker compose up -d postgres
     确认健康：docker compose ps --format '{{.Name}} {{.Health}}'
  2) 检查 apps/api/.env 里的 DB_HOST / DB_PORT / DB_USERNAME / DB_PASSWORD / DB_NAME
  3) 首次启动建表：pnpm --filter @nestjs-tutorial/api db:migrate
     （正常启动时也会自动执行未运行的迁移）
  4) 只想临时跑通接口、不需要持久化：DB_DRIVER=sqljs pnpm dev

  注意：服务不会自动退回内存存储——避免「以为连上了数据库，其实重启就丢数据」。

这段提示的设计原则：

  • 给下一步命令，而不是只给错误码；
  • 明确拒绝降级：DB_DRIVER 默认就是 postgres，只有显式设置 sqljs 才会用内存库；
  • 退出码非 0：容器编排和 CI 才能正确判定失败。

6. 健康检查与就绪检查 ​

  • GET /api/health：liveness，进程活着就返回 200，数据库挂了标记 degraded，但不赶走流量；
  • GET /api/health/ready：readiness，数据库不可用直接 503，负载均衡据此停止转发。
ts
import { Injectable, ServiceUnavailableException } from '@nestjs/common';
import { DataSource } from 'typeorm';
import { CacheService } from '../cache/cache.service.js';

export interface DatabaseCheck {
  status: 'up' | 'down';
  latencyMs: number | null;
}

export interface CacheCheck {
  status: 'up' | 'down';
  driver: 'redis' | 'memory';
  latencyMs: number | null;
}

export interface HealthSnapshot {
  status: 'ok' | 'degraded';
  uptimeSeconds: number;
  timestamp: string;
  checks: {
    memory: { rssMb: number; heapUsedMb: number };
    database: DatabaseCheck;
    cache: CacheCheck;
  };
}

export interface LivenessSnapshot {
  status: 'ok';
  uptimeSeconds: number;
  timestamp: string;
}

@Injectable()
export class HealthService {
  constructor(
    private readonly dataSource: DataSource,
    private readonly cache: CacheService,
  ) {}

  async check(): Promise<HealthSnapshot> {
    const memory = process.memoryUsage();
    const [database, cache] = await Promise.all([this.checkDatabase(), this.checkCache()]);

    return {
      status: database.status === 'up' && cache.status === 'up' ? 'ok' : 'degraded',
      uptimeSeconds: Math.round(process.uptime()),
      timestamp: new Date().toISOString(),
      checks: {
        memory: {
          rssMb: Math.round(memory.rss / 1024 / 1024),
          heapUsedMb: Math.round(memory.heapUsed / 1024 / 1024),
        },
        database,
        cache,
      },
    };
  }

  /**
   * 存活探针：只证明事件循环还能响应，不碰任何外部依赖。
   *
   * 如果 liveness 也去查数据库，数据库抖动会让编排器重启所有实例，
   * 把一次依赖故障放大成一次全量重启。
   */
  liveness(): LivenessSnapshot {
    return {
      status: 'ok',
      uptimeSeconds: Math.round(process.uptime()),
      timestamp: new Date().toISOString(),
    };
  }

  /** 就绪探针：数据库或缓存任一不可用就 503，避免把流量导进来才发现依赖缺失 */
  async readiness(): Promise<{
    status: 'ok';
    checks: { database: DatabaseCheck; cache: CacheCheck };
  }> {
    const [database, cache] = await Promise.all([this.checkDatabase(), this.checkCache()]);

    if (database.status !== 'up' || cache.status !== 'up') {
      throw new ServiceUnavailableException({
        code: 'SERVICE_NOT_READY',
        message: '依赖未就绪，服务暂不可用',
        details: { database, cache },
      });
    }
    return { status: 'ok', checks: { database, cache } };
  }

  private async checkDatabase(): Promise<DatabaseCheck> {
    const startedAt = Date.now();
    try {
      await this.dataSource.query('SELECT 1');
      return { status: 'up', latencyMs: Date.now() - startedAt };
    } catch {
      return { status: 'down', latencyMs: null };
    }
  }

  private async checkCache(): Promise<CacheCheck> {
    const startedAt = Date.now();
    const driver = this.cache.driver;
    try {
      const ok = await this.cache.ping();
      return ok
        ? { status: 'up', driver, latencyMs: Date.now() - startedAt }
        : { status: 'down', driver, latencyMs: null };
    } catch {
      return { status: 'down', driver, latencyMs: null };
    }
  }
}
ts
import { Controller, Get } from '@nestjs/common';
import { Public } from '../auth/decorators/public.decorator.js';
import { HealthService } from './health.service.js';
import type {
  CacheCheck,
  DatabaseCheck,
  HealthSnapshot,
  LivenessSnapshot,
} from './health.service.js';

/** 健康检查给探针用，必须是公开接口，且响应结构不要套业务外壳 */
@Public()
@Controller('health')
export class HealthController {
  constructor(private readonly healthService: HealthService) {}

  @Get()
  check(): Promise<HealthSnapshot> {
    return this.healthService.check();
  }

  /** 存活：不查依赖，永远 200（除非进程已经卡死到无法响应） */
  @Get('live')
  liveness(): LivenessSnapshot {
    return this.healthService.liveness();
  }

  /** 就绪：依赖不可用时 503，给负载均衡摘流量用 */
  @Get('ready')
  readiness(): Promise<{
    status: 'ok';
    checks: { database: DatabaseCheck; cache: CacheCheck };
  }> {
    return this.healthService.readiness();
  }

  /** 依赖明细：给人和排障脚本看，始终 200，状态在 body 里 */
  @Get('dependencies')
  dependencies(): Promise<HealthSnapshot> {
    return this.healthService.check();
  }
}

两者都标了 @Public()——探针不会带令牌，如果被全局守卫拦成 401，K8s 会一直认为服务没起来。

逐步拆解 ​

1. 为什么所有读取都走 configuration.ts ​

如果每个 Service 都写 process.env.DB_HOST，会带来三个问题：

  • 测试里无法整体替换配置；
  • 类型全是 string | undefined，到处要写默认值；
  • 校验只能靠人肉检查。

收敛到一个工厂函数后，ConfigService 成为唯一入口，测试可以注入假配置，启动期校验也只需要维护一处。

2. ConfigModule 的装配顺序 ​

ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';
import { AuditModule } from './audit/audit.module.js';
import { AuthModule } from './auth/auth.module.js';
import { BffModule } from './bff/bff.module.js';
import { CacheModule } from './cache/cache.module.js';
import configuration from './config/configuration.js';
import { validateEnv } from './config/env.validation.js';
import { DatabaseModule } from './database/database.module.js';
import { FilesModule } from './files/files.module.js';
import { HealthModule } from './health/health.module.js';
import { MetricsModule } from './metrics/metrics.module.js';
import { OrdersModule } from './orders/orders.module.js';
import { QueueModule } from './queue/queue.module.js';
import { RealtimeModule } from './realtime/realtime.module.js';
import { UsersModule } from './users/users.module.js';
import { WebhooksModule } from './webhooks/webhooks.module.js';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      cache: true,
      load: [configuration],
      // 启动即校验：变量缺失或类型不对，进程直接失败，不给线上留隐患
      validate: validateEnv,
      envFilePath: ['.env.local', '.env'],
    }),
    DatabaseModule,
    // 全局指标：HTTP、缓存、队列都往这里记，不引入额外组件
    MetricsModule,
    // 缓存与队列都是全局能力；驱动由配置决定（redis / memory）
    CacheModule,
    QueueModule,
    HealthModule,
    UsersModule,
    AuditModule,
    AuthModule,
    BffModule,
    RealtimeModule,
    FilesModule,
    WebhooksModule,
    OrdersModule,
  ],
})
export class AppModule {}

isGlobal: true 让其他模块不用重复 import；cache: true 避免每次 get 都重新解析；validate 在依赖注入之前执行。

3. 布尔值为什么不能靠 Boolean() ​

写法DB_SSL=false 的结果
Boolean('false')true（非空字符串都是真）
value === 'true'false
z.coerce.boolean()true（同上，坑一样）

toBoolean 只认 true 与 'true'，其余一律 false。环境变量没有布尔类型，规则必须写死。

4. 数字为什么要显式 @Type ​

PORT='3000' 在 @IsInt() 下会失败，因为它是字符串。两个解法：

  • 全局 enableImplicitConversion: true：省事，但会连同布尔值一起「猜」，本项目因此踩坑后放弃；
  • 字段级 @Type(() => Number)：只转数字字段，代价是每个字段多一行。

校验范围也要写：PORT 限制 1~65535，JWT_ACCESS_TTL 限制 60~86400，避免「TTL 配成 0」导致令牌一签发就过期。

5. .env 文件的位置与 cwd ​

envFilePath 是相对进程工作目录解析的。根目录 pnpm dev 会转发到 apps/api 执行，所以：

  • apps/api/.env 能被读到；
  • 仓库根目录放 .env 读不到（除非显式写路径）。

CI 里通常不落文件，直接把变量注入环境；此时 envFilePath 指向的文件不存在也不会报错。

6. 配置变更为什么不热更新 ​

cache: true + 启动期校验意味着：改 .env 必须重启进程。这不是缺陷，而是刻意设计——运行中悄悄换数据库地址，比启动失败更难排查。

如果确实需要「运行期可变开关」（灰度、限流阈值），应该放配置中心或功能开关服务，并与启动配置分开管理。

7. 当前示例的边界 ​

诚实标注两处：

  • LOG_LEVEL 已声明并通过校验，但尚未接入日志系统（第 11 章做分级与采样）；
  • 配置只支持「启动时读取」，没有配置中心、热更新、密钥轮换（JWT_ACCESS_SECRET 轮换会在第 06 章的延伸追问里讨论）。

常见坑与排查 ​

现象根因处理
改了 .env 没生效改的是仓库根目录，进程 cwd 是 apps/api变量写进 apps/api/.env，或显式设置 envFilePath
DB_SSL=false 却尝试 SSL 连接enableImplicitConversion 把 'false' 转成 true关闭隐式转换，用 @Transform(toBoolean)

连不上数据库却没有任何输出NestFactory 默认 abortOnError: true，直接 abort设 abortOnError: false 并捕获连接错误

探针一直 401健康检查被全局 Guard 拦住控制器加 @Public()

企业级做法 ​

  1. 12-Factor：配置放环境变量，不写进代码与镜像；同一镜像在 dev/staging/prod 通用。
  2. 启动即校验：把环境变量当成一份契约（schema），缺字段、越界、格式错误都 fail fast。
  3. 密钥分层管理：本地 .env.local；CI 用平台 Secret；生产用 KMS/Vault/云厂商 Secret Manager，并支持轮换。
  4. 不同环境不同默认值：开发可以宽容，生产必须严格（例如生产禁止默认密钥、禁止 DB_DRIVER=sqljs）。
  5. 健康检查分两种：liveness 只看进程，readiness 看依赖；不要把「数据库慢」当成「进程死了」重启服务。
  6. 启动日志打印非敏感配置：驱动、host、port、库名可以打；密码、密钥永远不打。
  7. 配置变更可审计：谁在什么时候改了哪个变量，应该能在发布记录里查到；K8s 用 ConfigMap/Secret 版本，传统部署用变更单。
  8. 功能开关与启动配置分离：需要运行期调整的阈值放开关服务，避免为了改一个数字重启整个服务。

练习与验收标准 ​

练习

  1. 给 EnvironmentVariables 增加 FEATURE_BETA_ENABLED（布尔），并在某个接口里读取它控制返回字段。
  2. 把 LOG_LEVEL 接进 Logger：debug 时输出请求体摘要，warn 时只输出错误。
  3. 为「生产环境禁止 DB_DRIVER=sqljs」加一条校验，并写一个单测。
  4. 给 formatDatabaseHint 增加一种错误（例如 3D000 数据库不存在），输出对应的修复建议。

验收标准

  • [ ] docker compose up -d postgres 后 docker compose ps 显示 healthy，pnpm dev 单命令启动成功；
  • [ ] 启动日志包含 API 已启动 与 数据库: postgres (host:port/db)；
  • [ ] PORT=abc node dist/main.js 以非 0 退出，错误信息包含 PORT；
  • [ ] DB_PORT=5999 node dist/main.js 以退出码 1 结束，并打印「✖ 数据库连接失败」及四条排查步骤；
  • [ ] 同样的命令设 DB_DRIVER=sqljs 可以启动（这是显式选择，不是自动降级）；
  • [ ] docker compose stop postgres 后 /api/health 返回 200 且 status=degraded，/api/health/ready 返回 503；
  • [ ] 恢复数据库后 /api/health/ready 回到 200，无需重启应用；
  • [ ] pnpm --filter @nestjs-tutorial/api test:e2e 在不启动 Docker的情况下也能通过（依赖 sqljs）。
