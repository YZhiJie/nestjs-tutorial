本章目标 ​

读完并动手做完本章，你应该能：

  1. 说清 NestJS 在你的进程里到底做了什么（它不是一个「新的 Node」，而是一层组织代码的框架）；
  2. 用 pnpm 起一个可运行的服务，并能读懂启动日志的每一行；
  3. 写出第一个 Controller，用 curl 打通「请求 → 处理 → 响应」；
  4. 理解 IoC 容器与依赖注入：为什么 constructor(private readonly x: XService) 能拿到实例，而不是自己 new；
  5. 知道 NestJS 12 的 ESM 约束会怎样影响你的导入写法。

概念与原理 ​

NestJS 是什么，不是什么 ​

NestJS 运行在 Node.js 之上，底层默认用 Express 处理 HTTP。它真正提供的是一套组织代码的规则：

你写的东西Nest 帮你做的
@Controller('users') + 方法注册路由、解析参数、序列化返回值
@Injectable() 的类实例化、按依赖关系组装、按作用域复用
@Module({...})划定可见性边界：谁能用谁
@Get()/@Post() 等把方法绑定到 HTTP 方法与路径

所以「学 Nest」的重点不是记装饰器，而是理解它如何组装对象和处理一次请求。

IoC 与依赖注入，一句话版本 ​

  • IoC（控制反转）：对象的创建权从「使用者」交给「容器」。
  • 依赖注入（DI）：容器创建对象时，把它需要的依赖从构造函数塞进去。

不用 DI 的写法：

ts
const usersService = new UsersService(new AuditService(...)); // 谁来 new？参数变了怎么办？

用 DI 的写法（本项目真实代码）：

ts
import {
  Body,
  Controller,
  Delete,
  ForbiddenException,
  Get,
  HttpCode,
  HttpStatus,
  Param,
  ParseUUIDPipe,
  Patch,
  Post,
  Query,
} from '@nestjs/common';
import { CurrentUser } from '../auth/decorators/current-user.decorator.js';
import { Roles } from '../auth/decorators/roles.decorator.js';
import type { AuthenticatedUser } from '../auth/authenticated-user.js';
import { CreateUserDto } from './dto/create-user.dto.js';
import { PaginationQueryDto } from './dto/pagination-query.dto.js';
import { UpdateUserDto } from './dto/update-user.dto.js';
import { UsersService } from './users.service.js';
import type { PagedResult } from './users.service.js';
import type { PublicUser } from './user.entity.js';

@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Roles('admin')
  @Post()
  create(
    @Body() dto: CreateUserDto,
    @CurrentUser() actor: AuthenticatedUser,
  ): Promise<PublicUser> {
    return this.usersService.create(dto, actor.id);
  }

  @Roles('admin')
  @Get()
  findAll(@Query() query: PaginationQueryDto): Promise<PagedResult<PublicUser>> {
    return this.usersService.findAll(query);
  }

  // #region users-controller-self-scope
  @Get(':id')
  findOne(
    @Param('id', new ParseUUIDPipe()) id: string,
    @CurrentUser() actor: AuthenticatedUser,
  ): Promise<PublicUser> {
    // 水平越权防护：不是 admin 时，只能读自己。
    // 这类判断依赖「资源归属」，放 Guard 里会很别扭，落在用例层更清楚。
    if (actor.role !== 'admin' && actor.id !== id) {
      throw new ForbiddenException({
        code: 'FORBIDDEN_SELF_SCOPE',
        message: '只能查看自己的用户信息',
        details: { allowedUserId: actor.id },
      });
    }
    return this.usersService.findOne(id);
  }
  // #endregion users-controller-self-scope

  @Roles('admin')
  @Patch(':id')
  update(
    @Param('id', new ParseUUIDPipe()) id: string,
    @Body() dto: UpdateUserDto,
    @CurrentUser() actor: AuthenticatedUser,
  ): Promise<PublicUser> {
    return this.usersService.update(id, dto, actor.id);
  }

  @Roles('admin')
  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  remove(
    @Param('id', new ParseUUIDPipe()) id: string,
    @CurrentUser() actor: AuthenticatedUser,
  ): Promise<void> {
    return this.usersService.remove(id, actor.id);
  }
}

第 06 章起写接口需要 admin 身份，所以方法上有 @Roles('admin')、参数上有 @CurrentUser()。读的时候先忽略这两个装饰器，只看「构造函数声明依赖、方法体内不 new 服务」。

UsersController 从头到尾没有 new UsersService()。它只在构造函数里声明「我需要一个 UsersService」，容器在启动时按类型（运行时的 design:paramtypes 元数据）把实例递进来。这就是为什么类上必须有 @Injectable()：emitDecoratorMetadata 会把参数类型写进元数据，容器才有据可查。

顺序很重要

「先声明依赖、再由容器注入」意味着：类必须被某个 Module 的 providers 或 controllers 登记，否则容器不知道该实例化谁。忘记登记时的报错是 Nest can't resolve dependencies of ...，本章「常见坑」有专门一节。

NestJS 12 的一个硬事实：纯 ESM ​

从 12 起 @nestjs/common 是纯 ESM 包（"type": "module"）。落在你的代码上就是三条规则：

  1. 项目的 package.json 要有 "type": "module"；
  2. 相对导入必须带 .js 后缀（写的是 .ts 文件，引用时写 .js，这是 ESM 的解析规则）；
  3. __dirname 不能用了，需要目录路径时用 import.meta.url。

官方脚手架的 tsconfig.json 里是 module: "nodenext"，它会在编译期就帮你检查这些规则。本仓库的完整配置见 apps/api/tsconfig.json。

启动入口只有几行：

ts
import { Logger } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { NestFactory } from '@nestjs/core';
import type { INestApplication } from '@nestjs/common';
import { AppModule } from './app.module.js';
import configuration from './config/configuration.js';
import type { AppConfig } from './config/configuration.js';
import { formatDatabaseHint, isDatabaseConnectionError } from './database/connection-hint.js';
import { createRedisClient } from './redis/redis.client.js';
import { formatRedisHint, isRedisError, RedisUnavailableError } from './redis/redis-hint.js';
import { configureApp } from './setup-app.js';

/**
 * 在创建 Nest 应用之前先确认 Redis 可用。
 *
 * 为什么不在模块工厂里做？Nest 12 的 abortOnError:false 会把初始化异常交给
 * ExceptionHandler 记录，但 create() 的 Promise 不会 settle，进程会挂住。
 * 预检放在最前面，连不上就打印排查步骤并退出，行为可预测。
 */
async function preflightRedis(): Promise<void> {
  for (const file of ['.env.local', '.env']) {
    try {
      process.loadEnvFile(file);
    } catch {
      // 文件不存在就跳过，和 ConfigModule 的行为保持一致
    }
  }

  const config = configuration();
  if (config.cache.driver !== 'redis' && config.queue.driver !== 'redis') {
    return;
  }

  try {
    const client = await createRedisClient(config.redis);
    await client.quit().catch(() => client.disconnect());
  } catch (error) {
    if (error instanceof RedisUnavailableError) {
      console.error(error.message);
      process.exit(1);
    }
    throw error;
  }
}

async function bootstrap(): Promise<void> {
  await preflightRedis();

  let app: INestApplication;

  try {
    // abortOnError: false —— 默认情况下 Nest 在初始化失败时直接 process.abort()，
    // 我们的错误处理拿不到异常；关掉它才能给出「怎么修」的提示再退出。
    // rawBody: Webhook 验签必须基于原始字节，不能被 JSON 反序列化后的对象替代
    app = await NestFactory.create(AppModule, {
      bufferLogs: true,
      abortOnError: false,
      rawBody: true,
    });
  } catch (error) {
    // 数据库连不上时给可执行提示，而不是静默降级或只甩一段堆栈
    if (isDatabaseConnectionError(error)) {
      console.error(formatDatabaseHint(error));
      process.exitCode = 1;
      return;
    }
    // Redis（缓存/队列）同理：不自动退回内存实现
    if (isRedisError(error)) {
      const message = error instanceof Error ? error.message : '';
      console.error(message.startsWith('✖ Redis 连接失败') ? message : formatRedisHint(error));
      process.exitCode = 1;
      return;
    }
    throw error;
  }

  configureApp(app);

  // #region main-shutdown
  // 让 SIGTERM / SIGINT 触发 onApplicationShutdown：
  // 队列 Worker 停止接新任务、TypeORM 关闭连接池都在这里完成。
  // 没有这一步，容器重启时正在执行的任务会被直接切断。
  app.enableShutdownHooks();
  for (const signal of ['SIGTERM', 'SIGINT'] as const) {
    process.once(signal, () => Logger.log(`收到 ${signal}，开始优雅关闭`, 'Bootstrap'));
  }
  // #endregion main-shutdown

  const config = app.get(ConfigService<AppConfig, true>);
  const port = config.get('port', { infer: true });
  const prefix = config.get('apiPrefix', { infer: true });
  const database = config.get('database', { infer: true });
  const cache = config.get('cache', { infer: true });
  const queue = config.get('queue', { infer: true });

  await app.listen(port);

  Logger.log(`API 已启动: http://localhost:${port}/${prefix}`, 'Bootstrap');
  Logger.log(
    `数据库: ${database.driver}${database.driver === 'postgres' ? ` (${database.host}:${database.port}/${database.name})` : '（进程内，重启即清空）'}`,
    'Bootstrap',
  );
  Logger.log(
    `缓存: ${cache.driver}${cache.driver === 'redis' ? ` (${config.get('redis', { infer: true }).host}:${config.get('redis', { infer: true }).port})` : '（进程内，仅测试/临时演示）'}，队列: ${queue.driver}`,
    'Bootstrap',
  );
}

await bootstrap();

二、第一个 Controller ​

健康检查是最小但完整的例子——有路由、有依赖、有返回值：

ts
import { Controller, Get } from '@nestjs/common';
import { Public } from '../auth/decorators/public.decorator.js';
import { HealthService } from './health.service.js';
import type {
  CacheCheck,
  DatabaseCheck,
  HealthSnapshot,
  LivenessSnapshot,
} from './health.service.js';

/** 健康检查给探针用，必须是公开接口，且响应结构不要套业务外壳 */
@Public()
@Controller('health')
export class HealthController {
  constructor(private readonly healthService: HealthService) {}

  @Get()
  check(): Promise<HealthSnapshot> {
    return this.healthService.check();
  }

  /** 存活：不查依赖，永远 200（除非进程已经卡死到无法响应） */
  @Get('live')
  liveness(): LivenessSnapshot {
    return this.healthService.liveness();
  }

  /** 就绪：依赖不可用时 503，给负载均衡摘流量用 */
  @Get('ready')
  readiness(): Promise<{
    status: 'ok';
    checks: { database: DatabaseCheck; cache: CacheCheck };
  }> {
    return this.healthService.readiness();
  }

  /** 依赖明细：给人和排障脚本看，始终 200，状态在 body 里 */
  @Get('dependencies')
  dependencies(): Promise<HealthSnapshot> {
    return this.healthService.check();
  }
}

它依赖的 HealthService 只做一件事：把进程现在的状态收集成一个对象。

ts
import { Injectable, ServiceUnavailableException } from '@nestjs/common';
import { DataSource } from 'typeorm';
import { CacheService } from '../cache/cache.service.js';

export interface DatabaseCheck {
  status: 'up' | 'down';
  latencyMs: number | null;
}

export interface CacheCheck {
  status: 'up' | 'down';
  driver: 'redis' | 'memory';
  latencyMs: number | null;
}

export interface HealthSnapshot {
  status: 'ok' | 'degraded';
  uptimeSeconds: number;
  timestamp: string;
  checks: {
    memory: { rssMb: number; heapUsedMb: number };
    database: DatabaseCheck;
    cache: CacheCheck;
  };
}

export interface LivenessSnapshot {
  status: 'ok';
  uptimeSeconds: number;
  timestamp: string;
}

@Injectable()
export class HealthService {
  constructor(
    private readonly dataSource: DataSource,
    private readonly cache: CacheService,
  ) {}

  async check(): Promise<HealthSnapshot> {
    const memory = process.memoryUsage();
    const [database, cache] = await Promise.all([this.checkDatabase(), this.checkCache()]);

    return {
      status: database.status === 'up' && cache.status === 'up' ? 'ok' : 'degraded',
      uptimeSeconds: Math.round(process.uptime()),
      timestamp: new Date().toISOString(),
      checks: {
        memory: {
          rssMb: Math.round(memory.rss / 1024 / 1024),
          heapUsedMb: Math.round(memory.heapUsed / 1024 / 1024),
        },
        database,
        cache,
      },
    };
  }

  /**
   * 存活探针：只证明事件循环还能响应，不碰任何外部依赖。
   *
   * 如果 liveness 也去查数据库，数据库抖动会让编排器重启所有实例，
   * 把一次依赖故障放大成一次全量重启。
   */
  liveness(): LivenessSnapshot {
    return {
      status: 'ok',
      uptimeSeconds: Math.round(process.uptime()),
      timestamp: new Date().toISOString(),
    };
  }

  /** 就绪探针：数据库或缓存任一不可用就 503，避免把流量导进来才发现依赖缺失 */
  async readiness(): Promise<{
    status: 'ok';
    checks: { database: DatabaseCheck; cache: CacheCheck };
  }> {
    const [database, cache] = await Promise.all([this.checkDatabase(), this.checkCache()]);

    if (database.status !== 'up' || cache.status !== 'up') {
      throw new ServiceUnavailableException({
        code: 'SERVICE_NOT_READY',
        message: '依赖未就绪，服务暂不可用',
        details: { database, cache },
      });
    }
    return { status: 'ok', checks: { database, cache } };
  }

  private async checkDatabase(): Promise<DatabaseCheck> {
    const startedAt = Date.now();
    try {
      await this.dataSource.query('SELECT 1');
      return { status: 'up', latencyMs: Date.now() - startedAt };
    } catch {
      return { status: 'down', latencyMs: null };
    }
  }

  private async checkCache(): Promise<CacheCheck> {
    const startedAt = Date.now();
    const driver = this.cache.driver;
    try {
      const ok = await this.cache.ping();
      return ok
        ? { status: 'up', driver, latencyMs: Date.now() - startedAt }
        : { status: 'down', driver, latencyMs: null };
    } catch {
      return { status: 'down', driver, latencyMs: null };
    }
  }
}

逐步拆解 ​

第 1 步：NestFactory.create(AppModule) 做了什么 ​

按时间顺序：

  1. 读取 AppModule 的 imports / controllers / providers，构建依赖图；
  2. 实例化所有单例 Provider（默认是单例，整个进程一份）；
  3. 扫描 Controller 上的路由装饰器，注册到 Express 的路由表；
  4. 返回一个 INestApplication，此时还没监听端口。

所以启动日志里的 InstanceLoader、RoutesResolver、RouterExplorer 就是这三步的痕迹。

第 2 步：configureApp 为什么单独抽一个文件 ​

ts
import { INestApplication, ValidationPipe } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { AllExceptionsFilter } from './common/all-exceptions.filter.js';
import { LoggingInterceptor } from './common/logging.interceptor.js';
import { requestIdMiddleware } from './common/request-id.middleware.js';
import { TransformInterceptor } from './common/transform.interceptor.js';
import type { AppConfig } from './config/configuration.js';
import { createHttpMetricsMiddleware } from './metrics/http-metrics.middleware.js';
import { MetricsService } from './metrics/metrics.service.js';

/**
 * 把「应用级横切配置」集中到一个函数里：
 * main.ts 用它启动真实服务，e2e 测试也用它装配测试应用，
 * 避免测试环境和生产环境行为不一致（这是很常见的踩坑点）。
 */
export function configureApp(app: INestApplication): INestApplication {
  const config = app.get(ConfigService<AppConfig, true>);

  app.setGlobalPrefix(config.get('apiPrefix', { infer: true }));
  app.use(requestIdMiddleware);
  // 指标放在路由之前：401/403 也要被统计，所以不能用拦截器
  app.use(createHttpMetricsMiddleware(app.get(MetricsService)));

  app.useGlobalPipes(
    new ValidationPipe({
      // 只保留 DTO 声明过的字段，多余字段直接报错，杜绝“偷偷传参”
      whitelist: true,
      forbidNonWhitelisted: true,
      // 让 query/param 自动转换成 DTO 里声明的类型
      transform: true,
    }),
  );
  app.useGlobalInterceptors(new TransformInterceptor(), new LoggingInterceptor());
  app.useGlobalFilters(new AllExceptionsFilter());

  const corsOrigin = config.get('corsOrigin', { infer: true });
  app.enableCors({
    origin: corsOrigin === '*' ? true : corsOrigin.split(',').map((item) => item.trim()),
  });

  // 收到 SIGTERM 时先触发 onModuleDestroy/onApplicationShutdown，再做优雅关闭
  app.enableShutdownHooks();

  return app;
}

三个理由，都是生产经验：

  • 可测试：e2e 测试调用同一个 configureApp，测试环境与线上行为不会漂移；
  • 可读：全局管道、拦截器、过滤器集中在一处，新人不必满仓库找；
  • 可演进：加一个全局 Guard 只在 main.ts 加，不会漏。

第 3 步：一次请求的生命周期（先有个大概印象） ​

text
HTTP 请求
  → 中间件（requestId 注入）
  → Guard（能不能进）
  → 拦截器前置
  → Pipe（参数校验与转换）

  → 拦截器后置（包装响应）
  → 异常时：ExceptionFilter 接管

这一整条链路是第 03 章的主线，本章只用到其中两环：中间件与 Controller。

第 4 步：容器是怎么知道 HealthController 需要 HealthService 的 ​

TypeScript 编译后，HealthController 的构造函数参数类型会被写入元数据：

ts
// 编译产物（dist/health/health.controller.js）里的等价形态
__metadata('design:paramtypes', [health_service_1.HealthService]);

前提是 tsconfig.json 里同时开启：

json
{
  "compilerOptions": {
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true
  }
}

少了任何一项，容器拿到的参数类型是 Object，就会报「无法解析依赖」。这是新手第一个高频报错，且报错信息不会告诉你根因是 tsconfig。

一个快速的自我诊断

curl 返回 404 但服务在跑 → 看启动日志里 Mapped {/api/health, GET} route 是否存在。不存在说明路由没注册（模块没被 imports 引入）；存在说明路径写错（注意全局前缀 api）。

企业级做法 ​

  1. 入口文件只做三件事：创建应用、套用统一配置、监听端口。业务逻辑一行都不放。
  2. 启动即失败优于启动后报错：环境变量在第 05 章会在启动时校验，宁可进程起不来，也不要带病上线。
  3. 健康检查接口从第一天就有：容器编排、负载均衡、监控都依赖它。本项目的 /api/health 还会返回内存占用，便于早期发现泄漏。
  4. 统一响应结构从第一天就定：等到 20 个接口后再改，前端会想打人。
  5. 配置不进代码：端口、前缀、CORS 全部走环境变量（见 apps/api/src/config/configuration.ts）。
  6. 不要为了「看起来分层」而分层：一个只有三个方法的服务不需要 Controller → Facade → Service → Repository 四层，按需生长。

练习与验收标准 ​

练习

  1. 新增 GET /api/health/live，只返回 { status: 'ok' }，不查内存。
  2. 把 /api/health 的 checks.memory 改成返回 heapTotalMb 与 externalMb。
  3. 故意删掉 HealthService 上的 @Injectable()，观察并记录报错原文。

验收标准（可逐条执行）

  • [ ] pnpm dev 启动后，curl -s localhost:3000/api/health | jq .data.status 输出 "ok"；
  • [ ] 请求头带 x-request-id: abc 时，响应头与 meta.requestId 都是 abc；
  • [ ] 访问不存在的路径返回 404，且响应体是统一错误结构（第 03 章会讲结构细节）；
  • [ ] 能不看文档，说出 main.ts 里每一行的作用；
  • [ ] 能解释「为什么删掉 @Injectable() 会报错」，并指出是哪个编译选项在起作用。
