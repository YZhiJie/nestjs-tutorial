03 请求处理全链路 ​

一次请求在 Nest 中的完整链路：中间件、守卫、拦截器、管道与异常过滤。

成稿正文、示例代码与验收标准均已完整，可直接跟练
难度
★★★☆☆
预计课时
2.5 小时
最后核对
2026-11-10

本章目标 ​

  1. 说清一个请求依次经过哪些扩展点，以及每个扩展点只能改什么；
  2. 用 DTO + ValidationPipe 把「脏数据」挡在业务代码之外；
  3. 用 Pipe 做参数级转换与校验，并知道内置管道与自定义管道的分工；
  4. 用 Interceptor 统一包装响应、记录耗时；
  5. 用 ExceptionFilter 把所有异常收敛成稳定的错误结构；
  6. 理解 Guard 的位置与职责（第 06 章落地鉴权）。

概念与原理 ​

一次请求的完整顺序 ​

Nest 的扩展点不是随便插的，顺序是固定的：

text
1. 中间件 Middleware        （Express 层，拿得到原始 req/res）
2. 守卫 Guard               （能不能进：鉴权、限流）
3. 拦截器 Interceptor 前置   （进入方法前：改参数、计时、日志）
4. 管道 Pipe                （参数校验 + 类型转换，逐参数执行）
5. Controller 方法 → Service
6. 拦截器 Interceptor 后置   （包装返回值、计算耗时）
7. 异常时：ExceptionFilter  （任意环节抛出都会被它接住）

按「能力」记比按名字记更实用：

扩展点能改什么不能做什么
Middleware原始请求/响应、挂载 req.xxx拿不到 Nest 的 DI 上下文（除非用 APP_ 系列注册）
Guard放行 / 拒绝（抛异常）改请求体本身
Interceptor请求前后的数据流（RxJS）校验参数（那是 Pipe 的活）
Pipe单个参数的转换与校验决定是否放行整个请求
Filter异常 → 响应的映射恢复正常流程

为什么校验要放在 Pipe，而不是 Service ​

  • 边界清晰：Controller 之前的数据一定是「已校验」的，Service 里不用再写 if (!email)；
  • 可复用：同一个 DTO 可以被多个接口使用；
  • 错误一致：校验失败自动变成 400，错误格式统一。

最小可跑示例 ​

一、Controller：只做「取参数 → 调服务 → 返回」 ​

ts
import {
  Body,
  Controller,
  Delete,
  ForbiddenException,
  Get,
  HttpCode,
  HttpStatus,
  Param,
  ParseUUIDPipe,
  Patch,
  Post,
  Query,
} from '@nestjs/common';
import { CurrentUser } from '../auth/decorators/current-user.decorator.js';
import { Roles } from '../auth/decorators/roles.decorator.js';
import type { AuthenticatedUser } from '../auth/authenticated-user.js';
import { CreateUserDto } from './dto/create-user.dto.js';
import { PaginationQueryDto } from './dto/pagination-query.dto.js';
import { UpdateUserDto } from './dto/update-user.dto.js';
import { UsersService } from './users.service.js';
import type { PagedResult } from './users.service.js';
import type { PublicUser } from './user.entity.js';

@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Roles('admin')
  @Post()
  create(
    @Body() dto: CreateUserDto,
    @CurrentUser() actor: AuthenticatedUser,
  ): Promise<PublicUser> {
    return this.usersService.create(dto, actor.id);
  }

  @Roles('admin')
  @Get()
  findAll(@Query() query: PaginationQueryDto): Promise<PagedResult<PublicUser>> {
    return this.usersService.findAll(query);
  }

  // #region users-controller-self-scope
  @Get(':id')
  findOne(
    @Param('id', new ParseUUIDPipe()) id: string,
    @CurrentUser() actor: AuthenticatedUser,
  ): Promise<PublicUser> {
    // 水平越权防护：不是 admin 时，只能读自己。
    // 这类判断依赖「资源归属」，放 Guard 里会很别扭，落在用例层更清楚。
    if (actor.role !== 'admin' && actor.id !== id) {
      throw new ForbiddenException({
        code: 'FORBIDDEN_SELF_SCOPE',
        message: '只能查看自己的用户信息',
        details: { allowedUserId: actor.id },
      });
    }
    return this.usersService.findOne(id);
  }
  // #endregion users-controller-self-scope

  @Roles('admin')
  @Patch(':id')
  update(
    @Param('id', new ParseUUIDPipe()) id: string,
    @Body() dto: UpdateUserDto,
    @CurrentUser() actor: AuthenticatedUser,
  ): Promise<PublicUser> {
    return this.usersService.update(id, dto, actor.id);
  }

  @Roles('admin')
  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  remove(
    @Param('id', new ParseUUIDPipe()) id: string,
    @CurrentUser() actor: AuthenticatedUser,
  ): Promise<void> {
    return this.usersService.remove(id, actor.id);
  }
}

@Roles() / @CurrentUser() 是第 06 章引入的鉴权装饰器。此处先关注「参数 → 服务 → 返回值」这条主干：写接口的请求只要没有 admin 角色，会在进入方法之前就被 Guard 拦掉。

二、DTO：声明形状与规则 ​

ts
import { IsEmail, IsEnum, IsOptional, IsString, Length, MaxLength } from 'class-validator';
import { USER_ROLES } from '../user.entity.js';
import type { UserRole } from '../user.entity.js';

/**
 * DTO 是「外部输入」与「内部代码」之间的边界。
 * 这里只声明形状与校验规则，真正的校验由全局 ValidationPipe 执行（见第 3 章）。
 */
export class CreateUserDto {
  @IsEmail({}, { message: 'email 必须是合法的邮箱地址' })
  @MaxLength(120)
  email!: string;

  @IsString()
  @Length(2, 32, { message: 'name 长度必须在 2~32 个字符之间' })
  name!: string;

  @IsOptional()
  @IsEnum(USER_ROLES, { message: `role 只能是 ${USER_ROLES.join(' / ')}` })
  role?: UserRole;

  // 第 06 章起用户必须有密码才能登录；上限 72 与 bcrypt 的输入上限保持一致的工程习惯
  @IsString()
  @Length(8, 72, { message: 'password 长度必须在 8~72 个字符之间' })
  password!: string;
}

更新接口用 PartialType 复用同一套规则：

ts
import { OmitType, PartialType } from '@nestjs/mapped-types';
import { CreateUserDto } from './create-user.dto.js';

/**
 * PartialType 会复用 CreateUserDto 的字段与校验元数据，并把它们全部变成可选，
 * 避免「更新 DTO」和「创建 DTO」两份规则各改各的、逐渐漂移。
 *
 * OmitType 去掉 password：改密码是独立动作（要校验旧密码、要吊销会话），
 * 不能藏在「改资料」的 PATCH 里。
 */
export class UpdateUserDto extends PartialType(OmitType(CreateUserDto, ['password'] as const)) {}

查询参数要额外注意类型转换：

ts
import { Type } from 'class-transformer';
import { IsInt, IsOptional, IsString, Max, Min } from 'class-validator';

/**
 * 查询参数来自 URL，天然是字符串。@Type 负责转成 number，
 * 否则 @IsInt 永远失败 —— 这是新手最常踩的坑之一。
 */
export class PaginationQueryDto {
  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  page: number = 1;

  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  @Max(100)
  pageSize: number = 20;

  @IsOptional()
  @IsString()
  search?: string;
}

三、全局装配：管道、拦截器、过滤器 ​

ts
import { INestApplication, ValidationPipe } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { AllExceptionsFilter } from './common/all-exceptions.filter.js';
import { LoggingInterceptor } from './common/logging.interceptor.js';
import { requestIdMiddleware } from './common/request-id.middleware.js';
import { TransformInterceptor } from './common/transform.interceptor.js';
import type { AppConfig } from './config/configuration.js';
import { createHttpMetricsMiddleware } from './metrics/http-metrics.middleware.js';
import { MetricsService } from './metrics/metrics.service.js';

/**
 * 把「应用级横切配置」集中到一个函数里：
 * main.ts 用它启动真实服务，e2e 测试也用它装配测试应用，
 * 避免测试环境和生产环境行为不一致（这是很常见的踩坑点）。
 */
export function configureApp(app: INestApplication): INestApplication {
  const config = app.get(ConfigService<AppConfig, true>);

  app.setGlobalPrefix(config.get('apiPrefix', { infer: true }));
  app.use(requestIdMiddleware);
  // 指标放在路由之前：401/403 也要被统计，所以不能用拦截器
  app.use(createHttpMetricsMiddleware(app.get(MetricsService)));

  app.useGlobalPipes(
    new ValidationPipe({
      // 只保留 DTO 声明过的字段，多余字段直接报错，杜绝“偷偷传参”
      whitelist: true,
      forbidNonWhitelisted: true,
      // 让 query/param 自动转换成 DTO 里声明的类型
      transform: true,
    }),
  );
  app.useGlobalInterceptors(new TransformInterceptor(), new LoggingInterceptor());
  app.useGlobalFilters(new AllExceptionsFilter());

  const corsOrigin = config.get('corsOrigin', { infer: true });
  app.enableCors({
    origin: corsOrigin === '*' ? true : corsOrigin.split(',').map((item) => item.trim()),
  });

  // 收到 SIGTERM 时先触发 onModuleDestroy/onApplicationShutdown，再做优雅关闭
  app.enableShutdownHooks();

  return app;
}

四、统一响应外壳 ​

ts
import {
  CallHandler,
  ExecutionContext,
  Injectable,
  NestInterceptor,
} from '@nestjs/common';
import type { Request } from 'express';
import { map, Observable } from 'rxjs';

export interface ApiEnvelope<T> {
  data: T;
  meta: {
    requestId?: string;
    timestamp: string;
  };
}

/**
 * 统一响应外壳：成功响应一律包成 { data, meta }。
 * 这样客户端不需要为每个接口写不同的解析逻辑，错误响应则由
 * AllExceptionsFilter 输出同构的 { error, meta }。
 */
@Injectable()
export class TransformInterceptor<T> implements NestInterceptor<T, ApiEnvelope<T>> {
  intercept(context: ExecutionContext, next: CallHandler<T>): Observable<ApiEnvelope<T>> {
    const req = context.switchToHttp().getRequest<Request>();
    return next.handle().pipe(
      map((data) => ({
        data,
        meta: {
          requestId: req.requestId,
          timestamp: new Date().toISOString(),
        },
      })),
    );
  }
}

五、统一异常 ​

ts
import {
  ArgumentsHost,
  Catch,
  ExceptionFilter,
  HttpException,
  HttpStatus,
  Logger,
} from '@nestjs/common';
import type { Request, Response } from 'express';

interface ErrorBody {
  error: {
    code: string;
    message: string;
    details?: unknown;
  };
  meta: {
    requestId?: string;
    timestamp: string;
    path: string;
  };
}

/**
 * 全局异常过滤器：把任何异常收敛成稳定、可被客户端解析的结构。
 * - HttpException 保留状态码与业务错误信息
 * - 未知异常统一 500，且不把内部堆栈泄漏给客户端（只写日志）
 */
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger('Exception');

  catch(exception: unknown, host: ArgumentsHost): void {
    const ctx = host.switchToHttp();
    const res = ctx.getResponse<Response>();
    const req = ctx.getRequest<Request>();

    const isHttpException = exception instanceof HttpException;
    const status = isHttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    const body: ErrorBody = {
      error: this.buildError(exception, isHttpException),
      meta: {
        requestId: req.requestId,
        timestamp: new Date().toISOString(),
        path: req.originalUrl,
      },
    };

    // #region all-exceptions-log
    if (status >= HttpStatus.INTERNAL_SERVER_ERROR) {
      const stack = exception instanceof Error ? exception.stack : String(exception);
      // 鉴权失败时 user 还未挂上，可选读取
      const user = (req as Request & { user?: { id?: string } }).user;
      // 错误上报的唯一出口：结构化一条 error 日志，带 requestId 便于和访问日志串联。
      // 接 Sentry / 自建上报平台时，在这里加一次上报调用即可，不要把上报散落到业务代码。
      this.logger.error(
        JSON.stringify({
          msg: 'request.failed',
          method: req.method,
          path: req.originalUrl,
          status,
          code: body.error.code,
          requestId: req.requestId,
          userId: user?.id ?? null,
          message: body.error.message,
        }),
        stack,
      );
    }
    // #endregion all-exceptions-log

    res.status(status).json(body);
  }

  private buildError(exception: unknown, isHttpException: boolean): ErrorBody['error'] {
    if (!isHttpException) {
      // 内部错误只暴露通用文案，真实原因在日志里
      return { code: 'INTERNAL_SERVER_ERROR', message: '服务器内部错误' };
    }

    const httpException = exception as HttpException;
    const payload = httpException.getResponse();
    const status = httpException.getStatus();

    if (typeof payload === 'string') {
      return { code: this.codeFromStatus(status), message: payload };
    }

    const { message, error, code, details } = payload as {
      message?: string | string[];
      error?: string;
      code?: string;
      details?: unknown;
    };

    return {
      code: code ?? this.codeFromStatus(status),
      message: Array.isArray(message) ? message.join('; ') : (message ?? error ?? '请求失败'),
      ...(details === undefined ? {} : { details }),
    };
  }

  private codeFromStatus(status: number): string {
    const map: Record<number, string> = {
      [HttpStatus.BAD_REQUEST]: 'BAD_REQUEST',
      [HttpStatus.UNAUTHORIZED]: 'UNAUTHORIZED',
      [HttpStatus.FORBIDDEN]: 'FORBIDDEN',
      [HttpStatus.NOT_FOUND]: 'NOT_FOUND',
      [HttpStatus.CONFLICT]: 'CONFLICT',
      [HttpStatus.UNPROCESSABLE_ENTITY]: 'UNPROCESSABLE_ENTITY',
    };
    return map[status] ?? 'HTTP_ERROR';
  }
}

六、访问日志与追踪 ID ​

ts
import {
  CallHandler,
  ExecutionContext,
  Injectable,
  Logger,
  NestInterceptor,
} from '@nestjs/common';
import type { Request, Response } from 'express';
import { Observable, tap } from 'rxjs';

/**
 * 访问日志拦截器：一条结构化 JSON 日志 = 方法 + 路径 + 状态码 + 耗时 + 追踪 ID。
 * 结构化（而不是拼字符串）是后面接 ELK/Loki 做检索的前提。
 */
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  private readonly logger = new Logger('HTTP');

  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const http = context.switchToHttp();
    const req = http.getRequest<Request>();
    const res = http.getResponse<Response>();
    const startedAt = Date.now();

    return next.handle().pipe(
      tap({
        next: () => this.writeLog(req, res.statusCode, startedAt),
        error: (error: { status?: number }) =>
          this.writeLog(req, error.status ?? 500, startedAt, error),
      }),
    );
  }

  private writeLog(req: Request, statusCode: number, startedAt: number, error?: unknown): void {
    const payload = {
      msg: 'request.completed',
      method: req.method,
      path: req.originalUrl,
      statusCode,
      durationMs: Date.now() - startedAt,
      requestId: req.requestId,
      ...(error ? { error: (error as Error).message } : {}),
    };
    if (statusCode >= 500) {
      this.logger.error(JSON.stringify(payload));
    } else {
      this.logger.log(JSON.stringify(payload));
    }
  }
}

追踪 ID 由中间件写入，后续日志与错误体都复用它：

ts
import { randomUUID } from 'node:crypto';
import type { NextFunction, Request, Response } from 'express';

declare global {
  // eslint-disable-next-line @typescript-eslint/no-namespace
  namespace Express {
    interface Request {
      requestId?: string;
    }
  }
}

export const REQUEST_ID_HEADER = 'x-request-id';

/**
 * 请求追踪 ID：优先透传上游（网关/BFF）给的 x-request-id，
 * 没有就生成一个。后续日志、错误响应、审计都带同一个 ID，串起全链路。
 */
export function requestIdMiddleware(req: Request, res: Response, next: NextFunction): void {
  const incoming = req.headers[REQUEST_ID_HEADER];
  const requestId = typeof incoming === 'string' && incoming.length > 0 ? incoming : randomUUID();
  req.requestId = requestId;
  res.setHeader(REQUEST_ID_HEADER, requestId);
  next();
}

逐步拆解 ​

1. whitelist 与 forbidNonWhitelisted 到底挡住了什么 ​

ts
new ValidationPipe({
  whitelist: true,              // 剥掉 DTO 没声明的字段
  forbidNonWhitelisted: true,   // 不剥，直接 400
  transform: true,              // 按 DTO 类型转换（字符串 → number）
})

没有这两项时，攻击者可以传 {"email":"a@b.com","name":"x","role":"admin"} 里 DTO 没定义但实体有的字段，一旦你写了 Object.assign(entity, dto) 就变成越权改字段。这是「批量赋值（mass assignment）」漏洞的典型成因。

本项目 e2e 里有一条专门测它：

ts
it('POST /api/users 传入未声明字段时被 whitelist 拒绝', async () => {
  const res = await http()
    .post('/api/users')
    .set('authorization', `Bearer ${admin.accessToken}`)
    .send({
      email: 'ok@example.com',
      name: 'Valid Name',
      password: 'Passw0rd!',
      isAdmin: true,
    })
    .expect(400);

  expect(res.body.error.message).toContain('isAdmin');
});

2. transform 与 @Type 的分工 ​

query 里的一切都是字符串。?pageSize=2 到 DTO 时是 "2"，@IsInt() 会失败。两个解法：

  • @Type(() => Number)：只对这一个字段做转换（推荐，意图明确）；
  • transformOptions: { enableImplicitConversion: true }：全局按 TS 类型猜着转（省事但容易出意外，比如 "false" 变成 true）。

本项目选显式 @Type。

3. ParseUUIDPipe 与自定义 Pipe 的边界 ​

@Param('id', new ParseUUIDPipe()) 在参数级生效：格式不对直接 400，根本进不到 Service。

自定义 Pipe 的典型场景是「把外部 ID 换成内部对象」：

ts
// 第 06 章之后会用到：把 token 里的 userId 换成完整的用户对象
@Injectable()
export class UserByIdPipe implements PipeTransform<string, Promise<User>> {
  constructor(private readonly users: UsersService) {}
  async transform(id: string): Promise<User> {
    return this.users.findOne(id); // 找不到会抛 404，错误处理统一交给 Filter
  }
}

什么时候不要写自定义 Pipe

如果转换逻辑只用一个接口、且只做一件事，直接写在 Controller 或 Service 里更清楚。Pipe 的价值在复用与声明式。

4. 拦截器的 RxJS 心智模型 ​

next.handle() 返回的是 Observable，不是 Promise。所以：

需求写法
改返回值map(data => ({ data }))
附加副作用（计时、日志）tap({ next, error })
加超时timeout(3000)
缓存响应rxjs 的 of(cached) 短路，或用 shareReplay

本项目用 map 做统一外壳、用 tap 做日志——两者都不改变业务返回值本身。

5. 异常过滤器为什么必须放最后 ​

任何环节抛出的异常（Guard 拒绝、Pipe 校验失败、Service 里 throw new NotFoundException()、甚至未捕获的 TypeError）都会冒泡到 Filter。所以 Filter 是唯一能保证「响应结构一致」的地方。

本项目有两条约定：

  • HTTP 异常：保留状态码与业务 code（如 USER_NOT_FOUND）；
  • 未知异常：一律 500 + 通用文案，内部堆栈只进日志，不返回给客户端。

6. Guard 的位置（第 06 章实现） ​

Guard 在 Pipe 之前执行，返回 false 或抛异常即中断请求。仓库里已经落地了两个全局守卫，执行顺序与注册顺序一致：

ts
import { CanActivate, ExecutionContext, Injectable, UnauthorizedException } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { JwtService } from '@nestjs/jwt';
import type { Request } from 'express';
import type { AuthenticatedUser } from '../authenticated-user.js';
import { IS_PUBLIC_KEY } from '../decorators/public.decorator.js';
import type { UserRole } from '../../users/user.entity.js';

export interface AccessTokenPayload {
  sub: string;
  email: string;
  role: UserRole;
}

type AuthenticatedRequest = Request & { user?: AuthenticatedUser };

function extractBearerToken(header: string | undefined): string | null {
  if (!header) {
    return null;
  }
  const [scheme, token] = header.split(' ');
  if (scheme?.toLowerCase() !== 'bearer' || !token) {
    return null;
  }
  return token;
}

/**
 * 全局守卫（在 AuthModule 里用 APP_GUARD 注册）：
 * 所有路由默认需要 Bearer Token，@Public() 例外。
 *
 * 失败路径分三类，前端据此决定「跳登录」还是「静默刷新」：
 * - 没有令牌 → AUTH_REQUIRED
 * - 令牌过期 → AUTH_TOKEN_EXPIRED
 * - 令牌非法 → AUTH_TOKEN_INVALID
 */
@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(
    private readonly jwtService: JwtService,
    private readonly reflector: Reflector,
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (isPublic) {
      return true;
    }

    const request = context.switchToHttp().getRequest<AuthenticatedRequest>();
    const token = extractBearerToken(request.headers.authorization);

    if (!token) {
      throw new UnauthorizedException({
        code: 'AUTH_REQUIRED',
        message: '缺少访问令牌，请在 Authorization 头中携带 Bearer <token>',
      });
    }

    try {
      const payload = await this.jwtService.verifyAsync<AccessTokenPayload>(token);
      request.user = { id: payload.sub, email: payload.email, role: payload.role };
      return true;
    } catch (error) {
      const expired = error instanceof Error && error.name === 'TokenExpiredError';
      throw new UnauthorizedException({
        code: expired ? 'AUTH_TOKEN_EXPIRED' : 'AUTH_TOKEN_INVALID',
        message: expired ? '访问令牌已过期，请使用刷新令牌换发' : '访问令牌无效',
      });
    }
  }
}
ts
import { CanActivate, ExecutionContext, ForbiddenException, Injectable } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import type { Request } from 'express';
import type { AuthenticatedUser } from '../authenticated-user.js';
import { ROLES_KEY } from '../decorators/roles.decorator.js';
import type { UserRole } from '../../users/user.entity.js';

/**
 * 角色守卫：只回答「身份够不够」，不负责「令牌是否有效」。
 * 因此它必须排在 JwtAuthGuard 之后（APP_GUARD 的注册顺序就是执行顺序）。
 *
 * 与 401 的区别：401 是「不知道你是谁」，403 是「知道你是谁，但你不能干这件事」。
 */
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  // #region roles-guard
  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.getAllAndOverride<UserRole[]>(ROLES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (!requiredRoles || requiredRoles.length === 0) {
      return true;
    }

    const request = context
      .switchToHttp()
      .getRequest<Request & { user?: AuthenticatedUser }>();
    const user = request.user;

    if (!user) {
      // 理论上不会走到：JwtAuthGuard 已经拦过一遍。保留是为了守卫被单独复用时的安全兜底
      throw new ForbiddenException({
        code: 'FORBIDDEN_ROLE',
        message: '缺少身份信息，无法判断角色',
      });
    }

    if (!requiredRoles.includes(user.role)) {
      throw new ForbiddenException({
        code: 'FORBIDDEN_ROLE',
        message: `需要 ${requiredRoles.join(' 或 ')} 角色`,
        details: { requiredRoles, actualRole: user.role },
      });
    }

    return true;
  }
  // #endregion roles-guard
}

这里只需要记住职责边界：Guard 只看元数据与请求上下文，不碰业务数据；身份从哪里来、令牌怎么轮换，是第 06 章的内容。

7. 顺序在代码里的实际体现 ​

看一下日志顺序就能验证：中间件先给 requestId，拦截器在方法返回后打印 statusCode 与 durationMs，异常时是 Filter 生成响应体、拦截器的 error 分支打印日志。

常见坑与排查 ​

现象根因处理
query.page 是字符串导致 @IsInt 失败缺 @Type(() => Number) 或 transform: true加 @Type，并确认全局管道 transform: true
校验一直不生效全局管道没注册，或 DTO 没用 class-validator 装饰器检查 setup-app.ts；DTO 必须是 class，不能是 interface
DTO 是 interface 时永远通过运行时类型被擦除，没有元数据用 class + 装饰器
响应被包了两层 data拦截器里又包了一次，或 Controller 自己返回了 { data }统一在拦截器包装，业务层返回裸数据
204 响应返回了 JSON拦截器无条件包装返回值204 场景在 Filter/拦截器里跳过包装，或用 @Res() 自行处理
错误信息是英文的默认文案没给校验装饰器传 message每个装饰器写中文 message
500 响应里带着堆栈Filter 把 error.message 直接返回了非 HttpException 一律返回通用文案
日志里没有 requestId中间件注册顺序晚于拦截器，或用了 app.useGlobalInterceptors 之外的注册方式确认 configureApp 中 app.use(requestIdMiddleware) 在最前

企业级做法 ​

  1. DTO 一层不落：即使只有两个字段，也建 DTO。它是文档、是校验、是类型，三合一。
  2. 错误码要机器可读：code: 'USER_NOT_FOUND' 比一句中文更能被前端和监控消费；message 给人看。
  3. 响应外壳统一在拦截器，不要让每个 Controller 自己拼 { data }。
  4. 日志结构化：一条 JSON 包含 method/path/statusCode/durationMs/requestId，直接可被 Loki/ELK 检索。第 11 章会升级为真正的日志分级与采样。
  5. 区分「用户错误」与「系统错误」：4xx 用日志 log 级别，5xx 用 error 并带堆栈，避免把正常业务失败刷成告警。
  6. 校验文案面向使用者：写「email 必须是合法的邮箱地址」，而不是「email must be an email」。
  7. 拦截器不要做重活：它包裹每次请求，放数据库查询或外部调用会成倍放大延迟。

练习与验收标准 ​

练习

  1. 给 /api/users 的 search 加长度限制（最长 64），并给出中文错误文案。
  2. 自定义一个 TrimPipe，把字符串参数首尾空格去掉，只作用于 @Body()。
  3. 给所有 5xx 响应加一个 traceId 字段（可以直接复用 requestId）。
  4. 写一个拦截器，让 GET 请求的响应带上 Cache-Control: private, max-age=5（先别管正确性，体会拦截器能干什么）。

验收标准

  • [ ] 携带 admin 令牌请求 POST /api/users -d '{"email":"bad","name":"X"}' 返回 400，error.code === 'BAD_REQUEST'，message 同时包含两个字段的错误；
  • [ ] 不带令牌请求同一接口返回 401（不是 400），说明 Guard 先于 Pipe 执行；
  • [ ] 传未声明字段 isAdmin 返回 400，且 message 里出现 isAdmin；
  • [ ] GET /api/users/not-a-uuid（带令牌）返回 400，而不是 500 或 404；
  • [ ] GET /api/users/00000000-0000-4000-8000-000000000000（带令牌）返回 404，error.code === 'USER_NOT_FOUND'；
  • [ ] 任意接口响应都带 meta.requestId，且与响应头 x-request-id 一致；
  • [ ] 服务端日志能按 requestId 检索到这次请求，并包含 durationMs；
  • [ ] pnpm --filter @nestjs-tutorial/api test 与 test:e2e 均通过。

延伸追问 ​
