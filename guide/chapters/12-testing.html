12 测试策略 ​

单元、集成与 E2E 测试策略，以及 Nest 测试容器的最佳实践。

成稿正文、示例代码与验收标准均已完整，可直接跟练

测试的价值不在数量，而在「失败时能否直接指出哪一层坏了」。本章不追求 100% 覆盖率，而是给示例工程定一条可执行的分层线：纯逻辑用单测、依赖真实装配的用 e2e、外部服务用可替换的驱动，最后把门槛写进 pnpm verify。

本章实现状态

单测、e2e、覆盖率门槛与 GitHub Actions CI 流水线都已实现：CI 按 lint → typecheck → 单测 → e2e → 构建 → 文档构建 六段执行，与本地 pnpm verify 完全一致。CI 尚未在 GitHub 上实际跑过一次，阶段耗时只有本地实测值。

本章目标 ​

  1. 划分单测、集成、e2e 的职责，避免同一逻辑写两遍
  2. 用内存驱动与可控替身替换外部依赖，让测试不依赖 Docker、端口与网络
  3. 用覆盖率门槛约束「值得覆盖的代码」，而不是全仓库一刀切
  4. 让测试跑得快且可重复：数据可重置、时间可回拨、并发可控
  5. 说清 Vitest 与 Jest 的取舍，以及测试里最容易「假绿」的地方

概念与原理 ​

1. 三层测试各管什么 ​

层跑什么依赖本示例对应
纯逻辑单测状态机、幂等指纹、密码哈希、指标聚合无test/*.spec.ts 中不启动 Nest 的部分
服务/装配单测Service + 真实依赖注入 + 内存驱动无网络bff.service.spec.ts、users.service.spec.ts
e2e完整 HTTP 栈：路由、Guard、管道、过滤器、缓存sqljs + 内存缓存/队列app.e2e-spec.ts、realtime.e2e-spec.ts、files-webhooks.e2e-spec.ts

判断标准很简单：如果一个问题用纯函数就能回答，就不要启动 Nest。状态机是否允许 pending → completed，不需要数据库；只有「非法迁移在 HTTP 层返回什么」才需要 e2e。

2. 为什么用 Vitest 而不是 Jest ​

维度VitestJest
ESM原生支持，不需要 --experimental-vm-modules需要额外开关与 ts-jest 配置
与 Vite 生态共用转换链，配置少独立体系
速度示例工程 62 个单测约 0.5s同规模通常更慢
生态成熟度略少更多历史插件

本工程是纯 ESM + TypeScript，ESM 是硬约束，所以选 Vitest。代价是少数 Jest 专属插件不可用，但本项目没有依赖它们。

3. 外部依赖的替换策略 ​

依赖测试里换成什么为什么
Postgressqljs（TypeORM 内置驱动）无需 Docker，进程内数据库，迁移与实体仍然生效
Redis 缓存MemoryCacheStore同样的 CacheStore 接口，TTL 语义一致
BullMQMemoryJobsService任务同步执行，测试能直接断言结果
下游通知服务vi.fn() 替换 NotificationsClient.fetch控制超时、5xx、返回值
当前时间直接改数据库 created_at比 fake timers 更接近真实查询路径

原则：替换的是「驱动/边界」，不是「业务逻辑」。如果为了测试把 OrdersService 的扣减 SQL 也 mock 掉，测试就只剩「调用了一个 mock」这一件事。

4. 覆盖率的正确用法 ​

覆盖率是发现盲区的工具，不是 KPI。本工程的门槛：

  • 只统计单测真正加载过的文件（all: false），不为「没被引用的控制器」背锅；
  • 排除入口、模块装配、迁移、实体与 DTO（没有分支逻辑）；
  • 门槛比实测基线低 2~3 个百分点，留出重构空间，但阻止明显回退。

把门槛无脑拉到 90%，结果通常是三种：删除断言、加 /* istanbul ignore */、或者写一堆「调用即通过」的测试。三者都比低覆盖率更糟。

2. e2e 的数据库与重置 ​

ts
import { DataSource } from 'typeorm';
import { AuditLogEntity } from '../src/audit/audit-log.entity.js';
import { RefreshTokenEntity } from '../src/auth/refresh-token.entity.js';
import { UserEntity } from '../src/users/user.entity.js';

/**
 * 单元/集成测试用的内存 Postgres 替身：
 * sql.js 是编译成 WebAssembly 的 SQLite，纯 JS 依赖，CI 里不需要 Docker，
 * 也不需要原生编译（比 better-sqlite3 省事）。
 *
 * 代价：方言与 Postgres 不完全一致。所以业务代码里避免 ILIKE、
 * 避免写死 uuid/timestamptz 类型，保证同一套实体两边都能跑。
 */
export async function createTestDataSource(): Promise<DataSource> {
  const dataSource = new DataSource({
    type: 'sqljs',
    autoSave: false,
    synchronize: true,
    entities: [UserEntity, AuditLogEntity, RefreshTokenEntity],
    logging: false,
  });

  await dataSource.initialize();
  return dataSource;
}

4. 直接构造 Service，把下游换成可控函数 ​

BFF 单测不启动 HTTP 服务，也不搭 TestingModule：构造参数都是接口，直接传入替身即可。效果等同于 overrideProvider，但少一层容器启动开销。需要验证模块装配本身时，再交给 e2e。

ts
function createHarness(options: {
  fetchImpl?: () => Promise<NotificationItem[]>;
  ordersImpl?: () => Promise<{
    items: OrderView[];
    total: number;
    page: number;
    pageSize: number;
  }>;
  productsImpl?: () => Promise<ProductView[]>;
  config?: Partial<BffConfig>;
  actorRole?: 'admin' | 'member';
} = {}): Harness {
  const config = configService(options.config);
  const cache = new CacheService(new MemoryCacheStore(), config);
  const fetchMock = vi.fn(options.fetchImpl ?? (async () => NOTIFICATIONS));
  const ordersListMock = vi.fn(
    options.ordersImpl ??
      (async () => ({ items: ORDERS, total: ORDERS.length, page: 1, pageSize: 3 })),
  );
  const productsListMock = vi.fn(options.productsImpl ?? (async () => PRODUCTS));

  const users = { findOne: async () => USER } as unknown as UsersService;
  const audits = { list: async () => [] } as unknown as AuditService;
  const orders = {
    list: ordersListMock,
    listProducts: productsListMock,
  } as unknown as OrdersService;
  const notifications = { fetch: fetchMock } as unknown as NotificationsClient;

  return {
    service: new BffService(users, audits, orders, notifications, cache, config),
    fetchMock,
    ordersListMock,
    productsListMock,
    cache,
  };
}

这张表是本章的核心结论：低覆盖率必须能说出理由。orders.service.ts 的 0.68% 与 file-storage.service.ts 的 34.54% 是同一类取舍——真正要验证的是「并发下不超卖」「越权拿不到文件」，这必须走真实数据库与文件系统，用 e2e 比 mock 更有说服力；而 users.service.ts 的 69% 没有这种理由，是单纯没写，属于欠账。

audit.service.ts、notifications.client.ts、webhooks.service.ts 的覆盖数字会在合并 e2e 覆盖率后大幅上升，这也是「e2e 覆盖率合并」还留在未完成清单里的原因：现在的数字低估了它们，但不能因此就当作已测。webhooks.service.ts 没有被单测直接 import，所以根本没有出现在表里。

3. e2e 的边界：测「装配」而不是「逻辑」 ​

只应出现在 e2e只应出现在单测
Guard 返回 401 还是 403状态机允许哪些迁移
DTO 校验失败返回 400 与字段名幂等指纹如何排序、去重
全局过滤器输出的结构分位数取哪个桶
缓存拦截器是否写了 x-cachegetOrSet 是否合并并发回源
响应外壳 { data, meta }下游超时被归为 timeout 还是 upstream_error

同一个断言写两遍不会提高信心，只会提高维护成本。

4. 时间相关逻辑怎么测 ​

超时关单不能靠 sleep(30 分钟)。e2e 的做法是：先创建订单，再把 created_at 改到 2 小时前，然后触发任务。

ts
describe('超时关单任务', () => {
  it('超时未支付的订单被任务取消并回补库存，已支付订单不受影响', async () => {
    const productsRes = await http().get('/api/products').expect(200);
    const keyboard = (productsRes.body.data as Array<{ id: string; sku: string }>).find(
      (item) => item.sku === 'KB-MECH-01',
    )!;

    await http()
      .patch(`/api/products/${keyboard.id}/inventory`)
      .set('authorization', `Bearer ${admin.accessToken}`)
      .send({ available: 5, reason: 'e2e 超时关单前置' })
      .expect(200);

    const create = (key: string, quantity: number) =>
      http()
        .post('/api/orders')
        .set('authorization', `Bearer ${member.accessToken}`)
        .set('idempotency-key', key)
        .send({ items: [{ productId: keyboard.id, quantity }] })
        .expect(201);

    const stale = await create('e2e-timeout-stale-0001', 2);
    const staleId = (stale.body.data as { order: { id: string } }).order.id;

    const paid = await create('e2e-timeout-paid-0001', 1);
    const paidId = (paid.body.data as { order: { id: string } }).order.id;
    await http()
      .post(`/api/orders/${paidId}/pay`)
      .set('authorization', `Bearer ${member.accessToken}`)
      .expect(200);

    // 把创建时间改到 2 小时前：等待真实时间流逝会让 e2e 变得不可控
    const twoHoursAgo = new Date(Date.now() - 2 * 60 * 60 * 1000);
    const orders = app.get(DataSource).getRepository(OrderEntity);
    await orders.update({ id: staleId }, { createdAt: twoHoursAgo });
    await orders.update({ id: paidId }, { createdAt: twoHoursAgo });

    const job = await http()
      .post('/api/jobs/order-timeout-sweep')
      .set('authorization', `Bearer ${admin.accessToken}`)
      .expect(202);

    const result = job.body.data.result as {
      scanned: number;
      cancelled: string[];
      skipped: number;
      timeoutMinutes: number;
    };
    expect(job.body.data.state).toBe('completed');
    expect(result.scanned).toBe(1);
    expect(result.cancelled).toEqual([staleId]);
    expect(result.skipped).toBe(0);
    expect(result.timeoutMinutes).toBe(30);

    const after = await http()
      .get(`/api/orders/${staleId}`)
      .set('authorization', `Bearer ${member.accessToken}`)
      .expect(200);
    expect(after.body.data.status).toBe('cancelled');
    expect(after.body.data.cancelledAt).not.toBeNull();

    // 已支付订单保持 paid，库存仍被它占着：5 - 1 = 4
    const paidAfter = await http()
      .get(`/api/orders/${paidId}`)
      .set('authorization', `Bearer ${member.accessToken}`)
      .expect(200);
    expect(paidAfter.body.data.status).toBe('paid');

    const stock = await http()
      .get('/api/products')
      .expect(200)
      .then((res) =>
        (res.body.data as Array<{ id: string; available: number }>).find(
          (item) => item.id === keyboard.id,
        )!.available,
      );
    expect(stock).toBe(4);

    // 再跑一次：没有新的超时订单，取消数为 0（任务幂等）
    const again = await http()
      .post('/api/jobs/order-timeout-sweep')
      .set('authorization', `Bearer ${admin.accessToken}`)
      .expect(202);
    expect((again.body.data.result as { cancelled: string[] }).cancelled).toEqual([]);
  });
});

这比 fake timers 更可信：任务执行的是真实 SQL，WHERE created_at < ? 的语义被真正验证了。

5. 数据隔离与顺序 ​

e2e 在 beforeAll 里 synchronize + seed，每个用例只创建自己需要的数据。要注意：

  • 商品库存会被多个用例消耗，所以库存相关用例先 PATCH 重置到确定值；
  • 幂等键要唯一（用 e2e- 前缀 + 序号），否则第二次下单会返回重放；
  • 任务类用例会改变全局状态（如取消超时订单），断言要基于「自己创建的订单」。

6. CI：把 pnpm verify 原样搬上去 ​

流水线不另写一套命令，六段与本地 verify 一一对应，顺序也一致：

yaml
name: CI

# 只做一件事：把本地 `pnpm verify` 的六道闸按顺序搬到 CI。
# 测试用 sqljs + 内存缓存/队列，所以不需要 Postgres / Redis service 容器。
on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 10.15.0

      - uses: actions/setup-node@v4
        with:
          node-version: 22.12.0
          cache: pnpm

      - name: 安装依赖
        run: pnpm install --frozen-lockfile

      # 前两步最便宜，失败最快，放在最前面
      - name: Lint
        run: pnpm --filter @nestjs-tutorial/api lint

      - name: 类型检查
        run: pnpm --filter @nestjs-tutorial/api typecheck

      - name: 单元测试 + 覆盖率门槛
        run: pnpm --filter @nestjs-tutorial/api test:cov

      - name: e2e 测试
        run: pnpm --filter @nestjs-tutorial/api test:e2e

      - name: 构建 API
        run: pnpm --filter @nestjs-tutorial/api build

      # 先做静态校验：章节元数据必填项、<<< 引用的文件与 region、站内死链
      - name: 文档校验
        run: pnpm docs:check

      # 文档构建会解析章节里的 <<< 代码引用：源码 region 改名而文档没跟上，这里就会失败
      - name: 构建文档
        run: pnpm docs:build

      - name: 上传覆盖率报告
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: apps/api/coverage
          retention-days: 7

几个刻意的选择：

  • 不启动 Postgres / Redis service：测试配置用 sqljs + 内存缓存/队列，只有「真 Postgres 语义」相关的验证才需要容器，而那是本地脚本的职责；
  • lint 与 typecheck 放最前：这两步最便宜，能在 1 分钟内否定一个拼写错误，不必等 e2e；
  • 文档构建放在最后但不可省：<<< 引用的 region 改名后，TypeScript 编译不会报错，只有 VitePress 构建会失败。它是「文档与代码一致性」的唯一自动检查；
  • 覆盖率报告 if: always() 上传：测试失败时也需要看哪一行没跑过。

本地实测各阶段耗时：单测 0.50s、e2e 2.61s、API 构建与文档构建各数秒；CI 上的实际耗时取决于 runner 与 pnpm 缓存，本文没有编造 CI 运行时长。

常见坑与排查 ​

报错 / 现象根因修复验证
Nest can't resolve dependencies of X单测里 TestingModule 少 import 了依赖补 imports，或 overrideProvider 提供替身测试通过且不再打印解析错误
e2e 偶发 409/库存不足前一个用例消耗了库存用例开始前重置库存到确定值单独跑与全量跑结果一致
覆盖率突然下降 10%新文件被单测间接 import，但没断言补关键分支，或确认是否该从统计中排除test:cov 输出里能找到文件与未覆盖行
测试通过但线上 500单测 mock 掉了真实 SQL / 序列化把该场景移到 e2e 或脚本在真实 Postgres 上复现一次
x-cache 断言不稳定内存缓存被前一个用例预热每个用例用独立的 key/用户，或清空缓存单独运行同一用例仍通过

企业级做法 ​

  • CI 分阶段：lint + typecheck → 单测 + 覆盖率门槛 → e2e → 构建 → 文档构建。前两步 1 分钟内失败，别让开发者等 10 分钟才知道拼写错误。本仓库的 .github/workflows/ci.yml 已按此顺序落地；测试不依赖 service 容器，需要真实 Postgres 的并发验证留给本地脚本。
  • 失败留证据：e2e 失败时上传服务日志与请求 ID；只给一句 expected 200 got 500 的流水线没人愿意排查。
  • 禁止「重试即通过」：flaky 测试要修根因（共享状态、时间、端口），retry: 2 会把真 bug 藏起来。
  • 契约测试：BFF 依赖下游 DTO 时，用 schema 校验（如 zod）固定契约，比人肉比对字段可靠。
  • 覆盖率门槛按模块：核心域（订单、认证）可以设 80%，边缘模块设 50%，全局一个数字会逼迫大家给边角料写无意义测试。
