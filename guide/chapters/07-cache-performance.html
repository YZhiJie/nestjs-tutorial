07 缓存与性能 ​

缓存策略、失效与击穿保护，用真实压测口径评估性能收益。

成稿正文、示例代码与验收标准均已完整，可直接跟练
难度
★★★★☆
预计课时
2.5 小时
最后核对
2026-11-10

本章目标 ​

  1. 判断一个接口该不该缓存，以及缓存失效应该由谁负责；
  2. 用 Redis 做分布式缓存，并把「连不上 Redis」变成启动期的明确失败；
  3. 用拦截器实现声明式响应缓存，命中时能看到 x-cache: hit；
  4. 用标签版本号解决「写完之后列表还读旧缓存」，而不是 SCAN + DEL 一片键；
  5. 处理缓存击穿，并说清本章没有实现的穿透/雪崩方案。

概念与原理 ​

1. 先判断该不该缓存 ​

不是所有接口都值得缓存。满足下面三条再考虑：

条件反例
读多写少每秒都在变的库存扣减
能容忍秒级延迟支付结果
数据可重建用户余额（丢了不能靠回源算出来）

本项目的审计列表（GET /api/audits）刚好满足：只有管理员看、写入频率低、晚 30 秒看到新记录可以接受。

2. Cache-Aside：读时回源，写时失效 ​

text
读：GET key → 命中？返回 : 查库 → SET key TTL → 返回
写：UPDATE 数据库 → 让该数据的缓存失效

这是最常用的模式，因为缓存故障不会阻塞写路径。代价是第一次读一定 miss，以及「写成功、失效失败」的短暂不一致。

3. 三个经典问题，本章各自做到哪一步 ​

问题现象本章做法
击穿热点键过期瞬间，大量请求同时查库✅ CacheService 的单一飞行：同键并发只回源一次
穿透查不存在的数据，每次都打到数据库⚠️ 设计讲解，示例未实现（空值缓存 / 布隆过滤器）
雪崩大量键同时过期，数据库瞬时压力⚠️ 部分：TTL 固定 30 秒，未加随机抖动（设计讲解）

不把没做的写成已做，是这一章的基本要求。

4. 为什么用「标签版本号」而不是删键 ​

写审计后，需要让所有 GET /api/audits?... 的缓存失效。两种做法：

方案代价
SCAN audits:* + DEL键多时阻塞 Redis；集群下要扫所有分片
标签版本号 INCR cache:tag:audits:version一次 O(1) 写入，旧键靠 TTL 自然回收

缓存键里带上版本号：

text
audits:v0:GET /api/audits?limit=3|actor=admin
audits:v1:GET /api/audits?limit=3|actor=admin

写操作把版本从 v0 推到 v1，后续请求自然读到新键。旧键没人读，30 秒后过期，不需要同步删除。

5. 一致性取舍 ​

  • 失效发生在数据库写入之后，不是之前，避免「先删缓存、再写库失败」导致长期空窗；
  • 版本号自增不参与数据库事务：即使调用方事务回滚，也只是多一次 miss，不会出现「新数据读不到、旧缓存还在」；
  • 最坏情况是写成功、INCR 失败：缓存最多再脏 30 秒，这是 TTL 兜底的价值。

3. 给路由加缓存 ​

ts
// 审计列表是典型的「读多写少、允许秒级延迟」数据：
// 加一层响应缓存，命中时响应头会带 x-cache: hit。
// 写审计时通过标签版本号让缓存失效（见 AuditService.record）。
@UseInterceptors(CacheResponseInterceptor)
@CacheResponse({ tag: 'audits' })
@Get()
list(@Query() query: ListAuditsQueryDto): Promise<AuditRecordView[]> {
  return this.auditService.list(query.limit);
}

@CacheResponse 只是元数据，真正干活的是 CacheResponseInterceptor：

ts
// 缓存键包含角色（以及可选的用户 id）：
// 同一路径在不同身份下可能返回不同数据，漏掉这一维就是越权读取缓存。
const actor = options.varyByActor
  ? `${req.user?.role ?? 'anonymous'}:${req.user?.id ?? 'anonymous'}`
  : (req.user?.role ?? 'anonymous');

const version = await this.cache.tagVersion(options.tag);
const key = this.cache.buildTaggedKey(
  options.tag,
  version,
  `${req.method} ${req.originalUrl}|actor=${actor}`,
);

const result = await this.cache.getOrSet(
  key,
  () => lastValueFrom(next.handle()),
  options.ttlSeconds,
);

逐步拆解 ​

1. 抽象存储：业务不直接依赖 Redis ​

ts
/**
 * 缓存存储的最小接口。
 *
 * 业务代码只依赖这个接口，不直接依赖 Redis：
 * - 开发/生产用 Redis（多实例共享）；
 * - 测试与 `DB_DRIVER=sqljs` 的临时演示用内存实现，`pnpm verify` 不需要 Docker。
 *
 * 接口刻意保持很小：缓存不是数据库，不需要事务、扫描、复杂数据结构。
 */
export const CACHE_STORE = Symbol('CACHE_STORE');

export interface CacheStore {
  readonly driver: 'redis' | 'memory';
  get(key: string): Promise<string | null>;
  set(key: string, value: string, ttlSeconds: number): Promise<void>;
  delete(key: string): Promise<void>;
  /** 用于「标签版本号」：自增即让该标签下的所有旧键失效，不必逐个删除 */
  increment(key: string): Promise<number>;
  ping(): Promise<boolean>;
  close(): Promise<void>;
}

两个实现：

  • RedisCacheStore：SET key value EX ttl 一条命令完成写入和过期，避免两条命令之间进程挂掉留下永不过期的键；
  • MemoryCacheStore：测试与 DB_DRIVER=sqljs 临时演示用，带容量上限与惰性过期。

在 cache.module.ts 里按配置选择实现，并用 @Global() 导出。业务代码注入 CacheService，不感知驱动。

2. 连不上 Redis 就启动失败 ​

ts
import { Redis } from 'ioredis';
import type { RedisConfig } from '../config/configuration.js';
import { formatRedisHint, RedisUnavailableError } from './redis-hint.js';

/**
 * 缓存用的 Redis 连接。
 *
 * 两个关键选择：
 * - lazyConnect + 手动 ping：把「连不上」暴露在启动阶段，而不是等第一个请求；
 * - maxRetriesPerRequest 限制重试次数：缓存是「可选依赖」，不能在 Redis 抖动时
 *   把请求线程一直挂住（超时预算见第 07 章）。
 */
export async function createRedisClient(config: RedisConfig): Promise<Redis> {
  const client = new Redis({
    host: config.host,
    port: config.port,
    password: config.password ?? undefined,
    db: config.db,
    keyPrefix: config.keyPrefix,
    lazyConnect: true,
    maxRetriesPerRequest: 1,
    // 未连接时不要排队命令，直接失败；由上层决定回源还是报错
    enableOfflineQueue: false,
  });

  // ioredis 的 error 事件必须有监听者，否则 Node 会当成未捕获异常
  client.on('error', () => {
    // 具体错误在 connect/ping 的 catch 里统一处理
  });

  try {
    await client.connect();
    await client.ping();
    return client;
  } catch (error) {
    client.disconnect();
    throw new RedisUnavailableError(formatRedisHint(error, config));
  }
}
text
✖ Redis 连接失败，服务未启动。

  配置: redis://localhost:6379/0
  原因: Connection is closed.

  按顺序排查：
  1) 启动 Redis：docker compose up -d redis
     确认健康：docker compose ps --format '{{.Name}} {{.Health}}'
  2) 检查 apps/api/.env 里的 REDIS_HOST / REDIS_PORT / REDIS_PASSWORD
  3) 只想跑接口、不需要分布式缓存与队列：
     CACHE_DRIVER=memory QUEUE_DRIVER=memory pnpm dev

  注意：服务不会自动退回内存实现——单机看着能用，多实例时缓存与任务都不共享。

这段实测的退出码是 1。为什么不自动退回内存？因为那种「本机一切正常」的假象，会在多实例部署时变成缓存不一致与任务重复执行。

实现细节：main.ts 在创建 Nest 应用之前做 Redis 预检。Nest 12 在 abortOnError: false 时会把初始化异常交给 ExceptionHandler，但 create() 的 Promise 不会 settle，进程会挂住；预检让失败路径可预测。

3. 防击穿：同一键并发只回源一次 ​

ts
async getOrSet<T>(
  key: string,
  loader: () => Promise<T>,
  ttlSeconds: number = this.config.ttlSeconds,
): Promise<CacheResult<T>> {
  const cached = await this.store.get(key);
  if (cached !== null) {
    this.metrics?.recordCache(true);
    return { value: JSON.parse(cached) as T, hit: true };
  }

  const pending = this.inFlight.get(key) as Promise<T> | undefined;
  if (pending) {
    // 合并到已有回源请求：这次算 miss，但不重复查库
    this.metrics?.recordCache(false);
    return { value: await pending, hit: false };
  }

  const task = loader()
    .then(async (value) => {
      await this.store.set(key, JSON.stringify(value), ttlSeconds);
      return value;
    })
    .finally(() => this.inFlight.delete(key));

  this.inFlight.set(key, task);
  this.metrics?.recordCache(false);
  return { value: await task, hit: false };
}

注意第二个请求拿到 hit: false：它确实没有命中缓存，只是复用了第一个请求的回源结果。所以 x-cache 只能表达「是否命中」，不能表达「是否查了库」。

4. 键里必须带身份维度 ​

GET /api/audits 目前只对 admin 开放，但键里仍然写入 actor=admin。这是一个便宜的防御：将来同一路径开放给多种角色时，不会因为漏掉维度而互相读到对方的数据。

如果接口返回「当前用户自己的数据」，要打开 varyByActor，让键包含用户 id：

ts
@CacheResponse({ tag: 'me', varyByActor: true })

5. 失效：写路径只做一次 INCR ​

ts
/**
 * manager 参数用于参与调用方的事务：
 * 用户创建失败时，对应的审计记录也必须一起回滚。
 */
async record(input: AuditEntryInput, manager?: EntityManager): Promise<void> {
  const repository = manager ? manager.getRepository(AuditLogEntity) : this.logs;
  await repository.save(
    repository.create({
      action: input.action,
      actorId: input.actorId,
      targetId: input.targetId ?? null,
      summary: input.summary,
    }),
  );

  // 版本号自增不参与数据库事务：即使调用方事务回滚，也只是多一次 miss，
  // 不会出现「写出了新数据、列表却还读旧缓存」的脏读。
  await this.cache.invalidateTag('audits');
}

record() 同时被「创建用户」「更新用户」等写路径调用，所以只需要在这一处失效，不会漏掉某个写接口。

6. N+1：缓存之外的性能问题 ​

审计列表要把 actorId 换成姓名。如果每条记录都查一次用户表，20 条记录就是 21 次查询。本项目的做法是一次 IN (ids) 批量查询后在内存里拼接：

ts
import { forwardRef, Inject, Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import type { EntityManager } from 'typeorm';
import { CacheService } from '../cache/cache.service.js';
import { USER_DIRECTORY } from '../users/user-directory.js';
import type { UserDirectory } from '../users/user-directory.js';
import { AuditLogEntity } from './audit-log.entity.js';

export interface AuditEntryInput {
  action: string;
  actorId: string | null;
  targetId?: string | null;
  summary: string;
}

export interface AuditRecordView extends AuditEntryInput {
  id: string;
  createdAt: string;
  actorName: string | null;
}

@Injectable()
export class AuditService {
  // #region audit-service-constructor
  constructor(
    @InjectRepository(AuditLogEntity)
    private readonly logs: Repository<AuditLogEntity>,
    // 只依赖「按 id 批量查用户」这个接口，不依赖 UsersService 具体实现
    @Inject(forwardRef(() => USER_DIRECTORY))
    private readonly userDirectory: UserDirectory,
    private readonly cache: CacheService,
  ) {}
  // #endregion audit-service-constructor

  // #region audit-record
  /**
   * manager 参数用于参与调用方的事务：
   * 用户创建失败时，对应的审计记录也必须一起回滚。
   */
  async record(input: AuditEntryInput, manager?: EntityManager): Promise<void> {
    const repository = manager ? manager.getRepository(AuditLogEntity) : this.logs;
    await repository.save(
      repository.create({
        action: input.action,
        actorId: input.actorId,
        targetId: input.targetId ?? null,
        summary: input.summary,
      }),
    );

    // 版本号自增不参与数据库事务：即使调用方事务回滚，也只是多一次 miss，
    // 不会出现「写出了新数据、列表却还读旧缓存」的脏读。
    await this.cache.invalidateTag('audits');
  }
  // #endregion audit-record

  async list(limit: number): Promise<AuditRecordView[]> {
    const records = await this.logs.find({ order: { createdAt: 'DESC' }, take: limit });

    // 一次性批量取回操作人，避免逐条查询造成 N+1
    const actors = await this.userDirectory.findByIds(
      records.map((record) => record.actorId).filter((id): id is string => Boolean(id)),
    );
    const nameById = new Map(actors.map((user) => [user.id, user.name]));

    return records.map((record) => ({
      id: record.id,
      action: record.action,
      actorId: record.actorId,
      targetId: record.targetId,
      summary: record.summary,
      createdAt: record.createdAt.toISOString(),
      actorName: record.actorId ? (nameById.get(record.actorId) ?? null) : null,
    }));
  }
}

缓存不能掩盖 N+1：命中时快，miss 时依然慢。先修查询，再谈缓存。

常见坑与排查 ​

现象根因修复验证
启动即退出，提示 Redis 连接失败Redis 没起 / 端口不对docker compose up -d redis，核对 .envdocker compose ps 显示 healthy
两个角色读到同一份数据缓存键漏了身份维度键加入角色或用户 id用两个账号请求同一路径，对比 x-cache 与响应体
写完立刻读还是旧值只设了 TTL，没有主动失效写路径调用 invalidateTag写后第一次请求应为 x-cache: miss
测试环境连不上 Redis.env 里的 CACHE_DRIVER=redis 覆盖了默认值测试配置显式设为 memorypnpm verify 不依赖 Docker
内存缓存越跑越大没有容量上限MemoryCacheStore 的 maxEntries 淘汰压测或单测观察 Map 大小
缓存里出现 undefined把 undefined 序列化后写回只缓存可 JSON 化的值，或先判空单测覆盖空值分支

本工程实际用到哪、阈值怎么定 ​

缓存不是「全站加一层」，只在两处开启，且 TTL 不同：

位置键TTL失效方式为什么是这个数
GET /api/auditsaudits:v{n}:GET /api/audits|actor={role}30s（CACHE_TTL_SECONDS）写审计时 INCR cache:tag:audits:version全站只读列表，脏 30 秒无人感知；写路径已主动换版本号，TTL 只是兜底
GET /api/bff/dashboardbff:dashboard:{client}:{userId}:{simulate}10s（BFF_CACHE_TTL_SECONDS）只靠 TTL含当前用户订单状态，用户刚下单刷新就要看到，10s 是「可接受的最长滞后」

两个数字都不是拍脑袋定的，而是从「脏读多久会被当成 bug」倒推：审计列表 30 秒没人注意；订单状态超过 10 秒，用户就会重复下单或质疑系统丢了订单。

第三处是负缓存：BFF 的降级结果同样写 10 秒。下游故障期间重复请求不该反复打下游，代价是故障恢复后最多多等一个 TTL（见第 11 章的企业页）。

还有一处没有缓存：库存扣减与订单状态读取一律直连数据库。库存是强一致数据，缓存它等于把超卖风险引进系统——能缓存的判断依据是「脏一会儿会不会造成资损」，不是「读得多不多」。

企业级做法 ​

本章实现的是「能跑、可验证」的骨架，生产还需要补：

  1. TTL 抖动：30s + random(0~5s)，避免同批键同时过期。当前固定 30 秒，属已知缺口。
  2. 穿透保护：对不存在的数据缓存短 TTL 的空值，或在入口加布隆过滤器。当前未实现。
  3. 超时预算：缓存读应该设置几十毫秒的超时，超时直接回源；maxRetriesPerRequest: 1 只是限制重试，不是超时。当前未做单独超时。
  4. 降级开关：Redis 故障时是否允许「跳过缓存直接查库」，要按业务决定。本项目选择启动期失败，而不是运行期静默降级。
  5. 指标：命中率、回源 QPS、Redis 延迟、键数量。当前只有健康检查，指标在第 11 章补。
  6. 容量与淘汰：生产 Redis 要设置 maxmemory-policy，并给不同业务分配不同 DB 或前缀。本项目用 REDIS_KEY_PREFIX 做前缀隔离。

延伸追问 ​

  • 你的业务里哪个接口满足「读多写少、可容忍延迟、可重建」？先给它加缓存，还是先修 N+1？
  • 如果缓存失效失败，业务能接受多长时间的脏读？这个数字决定 TTL，而不是反过来。
  • 多实例部署时，MemoryCacheStore 会带来哪些具体问题？为什么测试可以用、生产不能用？
