13 部署与运维 ​

构建产物、部署、优雅退出与运维清单。

成稿正文、示例代码与验收标准均已完整，可直接跟练

把应用跑在开发机上和跑在容器里，差别不在 node dist/main.js，而在四件事：镜像里有没有多余的东西、进程能不能优雅退出、依赖没起来时会不会误导流量、出问题后靠什么判断。本章把这四件事落到真实的 Dockerfile、compose 配置与实测输出上。

本章实现状态

多阶段 Dockerfile、compose 的 api 服务、健康探针、优雅关闭都已实现并实际构建运行验证；GitHub Actions CI 流水线已落地（六段与 pnpm verify 一致，但尚未在 GitHub 上实跑）。Kubernetes 清单、独立迁移 Job、镜像扫描未实现，属于「设计讲解，示例未实现」。

本章目标 ​

  1. 用多阶段构建把「编译环境」和「运行环境」分开，并看清这份镜像还差在哪
  2. 让 SIGTERM 真正走完关闭流程：停止接流量、关闭队列 Worker、释放数据库连接
  3. 用健康探针区分「进程活着」与「能接流量」，避免滚动更新时把请求打到半启动的实例
  4. 把配置与密钥从镜像里赶出去：镜像不读 .env，只读环境变量
  5. 说清当前镜像的体积问题与生产裁剪路径
  6. 用 CI 把「能构建」变成「每次提交都验证过能构建」

概念与原理 ​

1. 多阶段构建解决的不是「分层」，是「隔离」 ​

三层职责：

阶段内容是否进入最终镜像
deps清单文件 + pnpm install只保留 node_modules
build源码 + TypeScript 编译不进入
runtime产物、运行依赖、非 root 用户是

把 deps 单独拆出来是为了缓存：源码改一百次，pnpm install 只跑一次（前提是清单文件没变）。

2. ESM 产物为什么用 node 直接启动 ​

本工程是纯 ESM，编译产物是 dist/main.js（不是 dist/src/main.js）。启动命令必须直接指向入口：

bash
node apps/api/dist/main.js

镜像里的工作目录是 /app，所以 CMD 写的是 node dist/main.js；两者指向同一个文件。

不要写成 pnpm start。多一层包管理器转发，SIGTERM 先到 pnpm，再由它转发给 node，容器停止时会多出不确定的延迟，甚至出现「pnpm 退了，node 还活着」。

3. 优雅关闭到底关了什么 ​

app.enableShutdownHooks() 让 SIGTERM / SIGINT 触发 Nest 的生命周期钩子：

  1. HTTP server 停止接收新连接（在途请求继续完成）；
  2. QueueModule.onApplicationShutdown() 关闭 BullMQ Worker 与连接；
  3. TypeORM 关闭连接池。

没有第 1 步，滚动更新时用户会看到连接被重置；没有第 2 步，正在执行的任务会被硬截断，而 BullMQ 要等到锁过期才会重新投递。

4. 探针与滚动更新的配合 ​

阶段探针行为
启动中start_period 20s 内不判定失败容器不会因为「还没起来」被反复重启
启动完成/api/health/ready 成功编排器/负载均衡开始导流量
运行中liveness 成功不重启
停止中收到 SIGTERM先从端点摘除，再等在途请求结束

stop_grace_period: 15s 给关闭流程留时间。超过这个时间，Docker 会 SIGKILL，等于前面的优雅关闭白做。

5. 镜像里不放密钥 ​

镜像应该「在哪都能跑，但离开环境就起不来」。JWT_ACCESS_SECRET 这类值由运行时注入；本工程的配置校验在 NODE_ENV=production 时会拒绝开发默认密钥，直接启动失败：

text
Error: 环境变量校验失败: 生产环境必须显式设置 JWT_ACCESS_SECRET（当前值仍是开发默认值）

这不是麻烦，而是把「误用默认密钥上线」变成一次启动失败，而不是一次安全事故。

最小可跑示例 ​

1. 多阶段 Dockerfile ​

plain
# 依赖层
# 只复制清单文件，源码变化不会让 pnpm install 缓存失效
FROM node:24-alpine AS deps
ENV PNPM_HOME=/pnpm
ENV PATH=$PNPM_HOME:$PATH
RUN corepack enable
WORKDIR /repo
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/api/package.json apps/api/package.json
RUN pnpm install --frozen-lockfile

# ---------- 构建层 ----------
FROM deps AS build
WORKDIR /repo
COPY . .
RUN pnpm --filter @nestjs-tutorial/api build
# 只把生产依赖「展开」到一个独立目录：deploy 会按 dependencies 重新解析，
# TypeScript、Vitest、VitePress 这些 devDependencies 不会进来。
RUN pnpm --filter @nestjs-tutorial/api deploy --prod --legacy /prod/api

# ---------- 运行层 ----------
# 不带源码、不带 devDependencies 的编译工具链；只保留运行所需文件
FROM node:24-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app

# 先建非 root 用户，再用 COPY --chown 落文件：
# 事后 chown -R 会把 150MB 依赖整层复制一遍，镜像直接胖一倍。
RUN addgroup -S app && adduser -S app -G app

# deploy 产物已经是扁平的真实目录，不再依赖 pnpm store 的符号链接
COPY --chown=app:app --from=build /prod/api/node_modules ./node_modules
COPY --chown=app:app --from=build /prod/api/package.json ./package.json
COPY --chown=app:app --from=build /repo/apps/api/dist ./dist

# 迁移随应用启动执行（migrationsRun: true），所以镜像里必须带 migrations
USER app

EXPOSE 3000

# 就绪探针而不是存活探针：依赖没起来时容器不应接流量
HEALTHCHECK --interval=10s --timeout=3s --start-period=20s --retries=5 \
  CMD node -e "fetch('http://127.0.0.1:3000/api/health/ready').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

# 用 node 直接启动，让 SIGTERM 直达进程，而不是经过 pnpm 多一层转发
CMD ["node", "dist/main.js"]

几个刻意的选择：

  • COPY package.json pnpm-lock.yaml pnpm-workspace.yaml 再安装，源码变化不会击穿依赖缓存；
  • 构建层用 pnpm deploy --prod 把生产依赖展开到 /prod/api，运行层只复制这一个目录，TypeScript、Vitest、VitePress 都进不来；
  • 运行层先建用户、再用 COPY --chown 落文件：如果反过来写 COPY 再 chown -R，150MB 的依赖会被整层复制一遍，镜像体积近乎翻倍（实测 594MB → 407MB）；
  • 非 root 用户运行（adduser app），容器逃逸的成本更高；
  • HEALTHCHECK 用 node -e fetch(...) 而不是 curl，镜像里不需要额外装工具。

2. compose 里的 api 服务 ​

yml
api:
  profiles: ['container']
  build:
    context: .
    dockerfile: apps/api/Dockerfile
  container_name: nestjs-tutorial-api
  restart: unless-stopped
  environment:
    NODE_ENV: production
    PORT: 3000
    DB_DRIVER: postgres
    DB_HOST: postgres
    DB_PORT: 5432
    DB_USERNAME: ${DB_USERNAME:-postgres}
    DB_PASSWORD: ${DB_PASSWORD:-postgres}
    DB_NAME: ${DB_NAME:-nestjs_tutorial}
    CACHE_DRIVER: redis
    QUEUE_DRIVER: redis
    REDIS_HOST: redis
    REDIS_PORT: 6379
    # 本地验证用的默认值；任何共享环境都必须通过环境变量覆盖
    JWT_ACCESS_SECRET: ${JWT_ACCESS_SECRET:-local-container-only-change-me}
    ORDER_PAYMENT_TIMEOUT_MINUTES: ${ORDER_PAYMENT_TIMEOUT_MINUTES:-30}
  ports:
    - '${API_PORT:-3000}:3000'
  depends_on:
    postgres:
      condition: service_healthy
    redis:
      condition: service_healthy
  # 镜像内已有 HEALTHCHECK，这里显式声明让 `docker compose ps` 显示状态
  healthcheck:
    test:
      [
        'CMD',
        'node',
        '-e',
        "fetch('http://127.0.0.1:3000/api/health/ready').then((r)=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))",
      ]
    interval: 10s
    timeout: 3s
    retries: 5
    start_period: 20s
  # 给队列任务与连接池留出关闭时间；超过 15s 才强杀
  stop_grace_period: 15s

用 profiles: ['container'] 而不是删掉注释：默认 docker compose up 只起 Postgres 与 Redis，日常开发仍然 pnpm dev 热重载；要验证生产镜像时显式加 --profile container。

3. 优雅关闭 ​

ts
// 让 SIGTERM / SIGINT 触发 onApplicationShutdown：
// 队列 Worker 停止接新任务、TypeORM 关闭连接池都在这里完成。
// 没有这一步，容器重启时正在执行的任务会被直接切断。
app.enableShutdownHooks();
for (const signal of ['SIGTERM', 'SIGINT'] as const) {
  process.once(signal, () => Logger.log(`收到 ${signal}，开始优雅关闭`, 'Bootstrap'));
}

5. 迁移与种子 ​

应用启动时 migrationsRun: true 自动执行迁移，所以容器起来就有表结构。种子数据不会自动执行（避免生产误插演示账号），需要时手动：

bash
docker compose --profile container exec api node dist/database/cli/seed.js

6. CI：发布前的六道闸 ​

部署文档最容易漏掉的一环是「这个镜像在构建前验证过什么」。仓库的 GitHub Actions 流水线把本地 pnpm verify 原样搬了上去：

yaml
name: CI

# 只做一件事：把本地 `pnpm verify` 的六道闸按顺序搬到 CI。
# 测试用 sqljs + 内存缓存/队列，所以不需要 Postgres / Redis service 容器。
on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 10.15.0

      - uses: actions/setup-node@v4
        with:
          node-version: 22.12.0
          cache: pnpm

      - name: 安装依赖
        run: pnpm install --frozen-lockfile

      # 前两步最便宜，失败最快，放在最前面
      - name: Lint
        run: pnpm --filter @nestjs-tutorial/api lint

      - name: 类型检查
        run: pnpm --filter @nestjs-tutorial/api typecheck

      - name: 单元测试 + 覆盖率门槛
        run: pnpm --filter @nestjs-tutorial/api test:cov

      - name: e2e 测试
        run: pnpm --filter @nestjs-tutorial/api test:e2e

      - name: 构建 API
        run: pnpm --filter @nestjs-tutorial/api build

      # 先做静态校验：章节元数据必填项、<<< 引用的文件与 region、站内死链
      - name: 文档校验
        run: pnpm docs:check

      # 文档构建会解析章节里的 <<< 代码引用：源码 region 改名而文档没跟上，这里就会失败
      - name: 构建文档
        run: pnpm docs:build

      - name: 上传覆盖率报告
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: apps/api/coverage
          retention-days: 7

顺序不能随便换：

阶段为什么在这个位置失败意味着什么
lint最便宜，秒级代码风格/可疑写法，通常改一行
typecheck不跑代码就能发现签名不匹配接口改动漏改调用方
单测 + 覆盖率0.5s，覆盖纯逻辑业务规则被改坏
e2e2.6s，覆盖装配与真实数据库语义Guard、管道、迁移、事务出问题
构建验证 ESM 产物路径与 pnpm deploy 可用运行镜像起不来
文档构建解析章节里的 <<< 代码引用源码 region 改名但文档没跟上

流水线不启动 Postgres/Redis service：vitest 配置用 sqljs 与内存缓存/队列，这是刻意的取舍——需要真实 Postgres 的并发不超卖验证由本地脚本承担，CI 只保证「每次提交都可构建、可测试」。

未实跑

CI 配置文件已通过本地 YAML 检查，六段命令也都在本地逐条执行过（实测单测 0.50s、e2e 2.61s、文档构建约 3.6s），但尚未在 GitHub Actions runner 上真正触发。因此本章不给出 CI 总时长，也不声称「CI 已通过」。

镜像扫描没有放进这条流水线：Trivy 之类的工具需要额外权限与基线策略，属于未完成项。

常见坑与排查 ​

报错 / 现象根因修复验证
容器起来就退出，日志说 JWT_ACCESS_SECRET 仍是默认值生产环境校验拒绝了开发密钥通过 compose environment 或 secret 注入启动日志出现 API 已启动
Cannot find module '/app/dist/main.js'镜像内工作目录是 /app，产物在 /app/distCMD 写 node dist/main.jsdocker run 后进程保持运行

企业级做法 ​

  • 镜像不可变：用 commit sha 打标签（api:${GIT_SHA}），不要用 latest 部署，否则回滚时不知道回滚到哪一版。
  • 密钥走 Secret 而不是 env 文件：K8s Secret / 云厂商参数服务；环境变量在 docker inspect 里可见，属于「够用但不安全」。
  • 滚动更新配合 readiness：maxUnavailable: 0，先起新实例并通过 readiness，再摘旧实例，避免容量瞬时下降。
  • 优雅关闭预算：preStop sleep 5s + 应用关闭 < terminationGracePeriodSeconds，否则请求仍会被切断。
  • 启动即迁移的风险：多实例同时启动会并发跑迁移。生产更稳的是单独的 migrate Job，应用只校验 schema 版本。
  • 镜像扫描：CI 里跑 Trivy 之类的扫描，高危漏洞阻断发布；基础镜像固定小版本并及时更新。

练习与验收标准 ​

  • [ ] docker build 成功，docker images 能看到 nestjs-tutorial-api:trimmed，且体积小于 500MB
  • [ ] docker compose --profile container ps 中 api 状态为 healthy
  • [ ] curl localhost:3100/api/health/ready 返回 200 且 database、cache 都是 up
  • [ ] docker stop -t 15 nestjs-tutorial-api 后日志包含「收到 SIGTERM」，且停止耗时小于 15 秒
  • [ ] 不设置 JWT_ACCESS_SECRET 时容器启动失败并打印明确原因（验证生产校验生效）
  • [ ] 本地按 CI 顺序跑一遍 lint → typecheck → test:cov → test:e2e → build → docs:build，全部通过
