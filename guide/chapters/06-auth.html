06 认证授权：JWT 与 RBAC ​

JWT 认证、刷新令牌与 RBAC 权限模型，含守卫与安全边界。

成稿正文、示例代码与验收标准均已完整，可直接跟练

★★★★☆
预计课时

最后核对

本章目标 ​

  1. 实现登录 → 访问令牌 → 刷新令牌轮换 → 登出的完整闭环；
  2. 说清密码、访问令牌、刷新令牌三类凭证各自的存储方式与过期策略；
  3. 用全局 Guard + 装饰器实现「默认拒绝、按角色放行」，并区分未授权 401 与越权 403；
  4. 处理刷新令牌重放、并发轮换、登出吊销这些真实工程细节；
  5. 识别垂直越权与水平越权，知道 RBAC 管不了什么。

概念与原理 ​

1. 认证与授权是两件事 ​

认证 Authentication授权 Authorization
回答的问题你是谁？你能做什么？
失败状态码401 Unauthorized403 Forbidden
本项目的实现JwtAuthGuard：校验 Bearer TokenRolesGuard + 用例内归属判断
前端该怎么做跳登录页 / 用 refresh 换新令牌提示无权限，不要跳登录

把两者混在一起，最常见的后果是：前端收到 403 也去跳登录，用户反复登录却始终进不去。

2. 三类凭证，三种策略 ​

凭证形态存放位置有效期能否即时吊销
密码用户输入数据库存 scrypt$salt$hash长期改密码即可
访问令牌JWT（HS256）客户端内存/存储15 分钟（JWT_ACCESS_TTL=900）不能，只能等过期
刷新令牌32 字节随机串数据库存 sha2567 天（REFRESH_TOKEN_TTL_DAYS=7）能，删/吊销数据库行

JWT 是自包含的：服务端只验签名与过期时间，不查库，所以快；代价是签发后无法撤回。这就是必须搭配短期 TTL + 可吊销刷新令牌的原因。

3. 密码存储：scrypt 的取舍 ​

本项目用 Node 内置 node:crypto 的 scrypt，格式是 scrypt$<salt>$<hash>：

  • 每个用户独立随机盐，同样的密码两次哈希结果不同；
  • 校验用 timingSafeEqual，避免逐字节比较泄露时间信息；
  • 用户不存在时也跑一次哈希（dummy hash），避免通过响应时间枚举邮箱。

为什么不用 bcrypt/argon2？它们需要原生编译，在 CI、Docker 多平台构建时是额外的失败源。真要上生产，argon2id 是更主流的选择，本项目在「零依赖可跑」与「生产最佳实践」之间选择了前者，并在文档里标明。

4. JWT 载荷设计 ​

json
{ "sub": "<userId>", "email": "ada@example.com", "role": "admin", "iss": "nestjs-tutorial", "iat": 1762757629, "exp": 1762758529 }

原则：

  • 只放鉴权需要的最小信息，JWT 是 Base64URL 编码，不是加密，任何人都能解开看；
  • 不放密码、手机号、身份证等敏感数据；
  • role 放进去的代价是：管理员改了某人角色，旧令牌在过期前仍是旧角色（最长 15 分钟）。这是可接受的窗口，但要知道它的存在。

5. 刷新令牌轮换与重放检测 ​

一次登录创建一个 family（会话链）。每次刷新：

text
旧令牌（未吊销） --条件更新为已吊销--> 新令牌（同一 family）

如果已吊销的旧令牌再次出现，只有两种可能：客户端重试了，或者令牌被偷了。服务端无法区分，只能按最坏情况处理：吊销整个 family，强制重新登录。

状态机：

数据库中的状态再次使用时响应码
未吊销、未过期正常轮换200，返回新令牌对
未吊销、已过期拒绝AUTH_REFRESH_EXPIRED
已吊销，且 replaced_by_token_id 有值判定为重放，吊销 familyAUTH_REFRESH_REUSED
已吊销，replaced_by_token_id 为空登出导致的失效AUTH_REFRESH_INVALID
查不到伪造或已清理AUTH_REFRESH_INVALID

6. 401 与 403 的错误码分工 ​

HTTPerror.code含义前端动作
401AUTH_REQUIRED没带令牌跳登录
401AUTH_TOKEN_EXPIRED访问令牌过期用 refresh 换新令牌
401AUTH_TOKEN_INVALID签名错/格式错清空本地令牌，跳登录
401AUTH_INVALID_CREDENTIALS邮箱或密码错提示重试
401AUTH_REFRESH_REUSED刷新令牌重放清空会话，跳登录并提示「会话异常」
401AUTH_REFRESH_INVALID / AUTH_REFRESH_EXPIRED刷新令牌失效/过期跳登录
403FORBIDDEN_ROLE角色不够（垂直越权）提示无权限
403FORBIDDEN_SELF_SCOPE访问了不属于自己的资源（水平越权）提示无权限

错误码是给机器读的，message 是给人读的。前端只根据 code 做分支，不要解析中文文案。

最小可跑示例 ​

一、密码与刷新令牌工具 ​

ts
import { randomBytes, scrypt as scryptCallback, timingSafeEqual } from 'node:crypto';
import { promisify } from 'node:util';

const scrypt = promisify(scryptCallback);
const KEY_LENGTH = 64;
const SALT_LENGTH = 16;
const ALGORITHM = 'scrypt';

/**
 * 密码存储格式：scrypt$<salt-base64url>$<hash-base64url>
 * 每个用户独立随机盐；校验用 timingSafeEqual，避免逐字节比较泄露信息。
 *
 * 用 node:crypto 而不是 bcrypt/argon2：后两者需要原生编译，
 * 在 CI 与不同平台上是额外的失败源。真要上生产，argon2id 是更主流的选择。
 */
export async function hashPassword(plain: string): Promise<string> {
  const salt = randomBytes(SALT_LENGTH);
  const derived = (await scrypt(plain, salt, KEY_LENGTH)) as Buffer;
  return `${ALGORITHM}$${salt.toString('base64url')}$${derived.toString('base64url')}`;
}

export async function verifyPassword(plain: string, stored: string): Promise<boolean> {
  const [algorithm, saltPart, hashPart] = stored.split('$');
  if (algorithm !== ALGORITHM || !saltPart || !hashPart) {
    return false;
  }

  const salt = Buffer.from(saltPart, 'base64url');
  const expected = Buffer.from(hashPart, 'base64url');
  const actual = (await scrypt(plain, salt, expected.length)) as Buffer;

  return expected.length === actual.length && timingSafeEqual(expected, actual);
}

/** 用户不存在时也跑一遍哈希，避免用响应时间探测「邮箱是否注册过」 */
let dummyHash: Promise<string> | undefined;
export function getDummyPasswordHash(): Promise<string> {
  dummyHash ??= hashPassword(randomBytes(16).toString('hex'));
  return dummyHash;
}
ts
import { createHash, randomBytes } from 'node:crypto';

/** 刷新令牌本身是 32 字节随机串；数据库只存它的 sha256 */
export function createRefreshTokenValue(): string {
  return randomBytes(32).toString('base64url');
}

export function hashRefreshToken(rawToken: string): string {
  return createHash('sha256').update(rawToken).digest('hex');
}

刷新令牌只把哈希存库：数据库泄露时，攻击者拿到 sha256 也无法当令牌用（令牌本身是 256 位随机数，不存在被猜中的可能）。

二、刷新令牌表 ​

ts
import { Column, CreateDateColumn, Entity, Index, PrimaryGeneratedColumn } from 'typeorm';

/**
 * 刷新令牌表。这里存的是随机串的 sha256，不是令牌本身：
 * 数据库泄露时攻击者拿到的哈希无法直接当令牌用。
 *
 * 一次登录对应一个 family（会话链）；每次刷新在同一 family 内换发新令牌，
 * 旧令牌立即置 revoked_at。若已吊销的令牌再次出现，说明可能被盗用，
 * 服务端会吊销整个 family（见 AuthService.refresh）。
 */
@Entity('refresh_tokens')
export class RefreshTokenEntity {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Index('idx_refresh_tokens_user_id')
  @Column({ name: 'user_id', type: 'uuid' })
  userId: string;

  @Index('idx_refresh_tokens_family_id')
  @Column({ name: 'family_id', type: 'uuid' })
  familyId: string;

  @Index('uq_refresh_tokens_token_hash', { unique: true })
  @Column({ name: 'token_hash', type: 'varchar', length: 64 })
  tokenHash: string;

  @Column({ name: 'expires_at' })
  expiresAt: Date;

  /**
   * 数据库里可为空；TS 类型故意写成 Date 而不是 Date | null：
   * 联合类型会让反射元数据变成 Object，TypeORM 就无法推断列类型
   * （Postgres 与 sqljs 需要的类型名还不一样，写死 type 反而不可移植）。
   */
  @Column({ name: 'revoked_at', nullable: true })
  revokedAt: Date;

  @Column({ name: 'replaced_by_token_id', type: 'uuid', nullable: true })
  replacedByTokenId: string | null;

  @Column({ name: 'user_agent', type: 'varchar', length: 255, nullable: true })
  userAgent: string | null;

  @CreateDateColumn({ name: 'created_at' })
  createdAt: Date;
}

字段分工：

  • token_hash：sha256，唯一索引，按它查令牌；
  • family_id：一次登录的所有令牌共享，用于「连坐吊销」；
  • expires_at：绝对过期时间，不依赖 JWT；
  • revoked_at：吊销时间，空表示有效；
  • replaced_by_token_id：轮换后指向新令牌，用来区分「重放」与「登出失效」；
  • user_agent：排障与会话管理用，不参与鉴权。

表结构在初始迁移里创建（见第 04 章），外键 ON DELETE CASCADE：用户被硬删除时，令牌一并清理。

三、登录 ​

ts
async login(dto: LoginDto, userAgent?: string): Promise<LoginResult> {
  const user = await this.users.findForLogin(dto.email);

  // 用户不存在时也跑一次哈希校验，避免通过响应时间判断邮箱是否注册过
  const passwordOk = await verifyPassword(
    dto.password,
    user?.passwordHash ?? (await getDummyPasswordHash()),
  );

  if (!user || !passwordOk) {
    throw new UnauthorizedException({
      code: 'AUTH_INVALID_CREDENTIALS',
      message: '邮箱或密码不正确',
    });
  }

  const session = await this.issueSession(
    this.refreshTokens.manager,
    user,
    randomUUID(),
    userAgent,
  );

  return { ...session.tokens, user: toPublicUser(user) };
}

两个安全细节：

  1. user?.passwordHash ?? await getDummyPasswordHash()：用户不存在时也做一次等价耗时的哈希；
  2. 失败统一返回 AUTH_INVALID_CREDENTIALS，不区分「邮箱不存在」与「密码错误」。

四、刷新与轮换 ​

ts
async refresh(rawToken: string, userAgent?: string): Promise<TokenPair> {
  const tokenHash = hashRefreshToken(rawToken);

  const outcome = await this.dataSource.transaction(
    async (manager): Promise<RefreshOutcome> => {
      const repository = manager.getRepository(RefreshTokenEntity);
      const existing = await repository.findOne({ where: { tokenHash } });

      if (!existing) {
        return {
          status: 'rejected',
          code: 'AUTH_REFRESH_INVALID',
          message: '刷新令牌无效，请重新登录',
        };
      }

      if (existing.revokedAt) {
        // 有 replaced_by_token_id 说明它是「轮换后作废」的旧令牌，再次出现＝重放；
        // 没有则说明是登出时整族吊销的，属于正常失效，不必再吊销一次。
        if (existing.replacedByTokenId) {
          await this.revokeFamily(repository, existing.familyId);
          return {
            status: 'rejected',
            code: 'AUTH_REFRESH_REUSED',
            message: '该刷新令牌已被使用过，已吊销本次登录的全部令牌，请重新登录',
          };
        }
        return {
          status: 'rejected',
          code: 'AUTH_REFRESH_INVALID',
          message: '该刷新令牌已失效（会话已登出），请重新登录',
        };
      }

      if (existing.expiresAt.getTime() <= Date.now()) {
        return {
          status: 'rejected',
          code: 'AUTH_REFRESH_EXPIRED',
          message: '刷新令牌已过期，请重新登录',
        };
      }

      const rotated = await repository
        .createQueryBuilder()
        .update(RefreshTokenEntity)
        .set({ revokedAt: new Date() })
        .where('id = :id AND revoked_at IS NULL', { id: existing.id })
        .execute();

      if (!rotated.affected) {
        // 另一个并发请求刚刚用掉了它，同样按重放处理
        await this.revokeFamily(repository, existing.familyId);
        return {
          status: 'rejected',
          code: 'AUTH_REFRESH_REUSED',
          message: '该刷新令牌已被使用过，已吊销本次登录的全部令牌，请重新登录',
        };
      }

      const user = await manager
        .getRepository(UserEntity)
        .findOne({ where: { id: existing.userId } });

      if (!user) {
        return {
          status: 'rejected',
          code: 'AUTH_REFRESH_INVALID',
          message: '令牌对应的用户不存在或已停用',
        };
      }

      const session = await this.issueSession(manager, user, existing.familyId, userAgent);
      await repository.update({ id: existing.id }, { replacedByTokenId: session.refreshEntityId });

      return { status: 'ok', tokens: session.tokens };
    },
  );

  if (outcome.status === 'rejected') {
    throw new UnauthorizedException({ code: outcome.code, message: outcome.message });
  }

  return outcome.tokens;
}

这段代码有一个必须讲清楚的设计：事务内不抛异常。

最初实现是在检测到重放时直接 throw new UnauthorizedException()，结果「吊销 family」的 UPDATE 跟着事务一起回滚——攻击者重放旧令牌，服务端看起来拒绝了，实际上整条链仍然有效。

现在的做法是：事务只负责「得出结论 + 落库」，返回一个判别联合 RefreshOutcome；事务提交之后再抛 401。

并发也在这里处理：where('id = :id AND revoked_at IS NULL') + 检查 affected，两个请求同时刷新时只有一个能把旧令牌「占住」，另一个按重放处理。

五、登出 ​

ts
async logout(userId: string, rawToken: string): Promise<void> {
  const existing = await this.refreshTokens.findOne({
    where: { tokenHash: hashRefreshToken(rawToken), userId },
  });
  if (!existing) {
    return; // 幂等：令牌不存在也返回成功
  }
  await this.revokeFamily(this.refreshTokens, existing.familyId);
}

登出返回 204，不返回 body。它吊销的是「该刷新令牌所在的整个 family」，也就是同一台设备上的会话链。

注意：登出不能让已经签发的访问令牌立刻失效，它最多再活 15 分钟。要彻底即时失效，需要引入令牌黑名单或把会话状态放到 Redis（第 07 章的延伸话题）。

六、控制器与 Guard 装配 ​

import {
  Body,
  Controller,
  Get,
  Headers,
  HttpCode,
  HttpStatus,
  Post,
} from '@nestjs/common';
import { AuthService } from './auth.service.js';
import type { LoginResult, TokenPair } from './auth.service.js';
import type { AuthenticatedUser } from './authenticated-user.js';
import { CurrentUser } from './decorators/current-user.decorator.js';
import { Public } from './decorators/public.decorator.js';
import { LoginDto } from './dto/login.dto.js';
import { RefreshTokenDto } from './dto/refresh-token.dto.js';
import type { PublicUser } from '../users/user.entity.js';

@Controller('auth')
export class AuthController {
  constructor(private readonly authService: AuthService) {}

  @Public()
  @Post('login')
  @HttpCode(HttpStatus.OK)
  login(@Body() dto: LoginDto, @Headers('user-agent') userAgent?: string): Promise<LoginResult> {
    return this.authService.login(dto, userAgent);
  }

  @Public()
  @Post('refresh')
  @HttpCode(HttpStatus.OK)
  refresh(
    @Body() dto: RefreshTokenDto,
    @Headers('user-agent') userAgent?: string,
  ): Promise<TokenPair> {
    return this.authService.refresh(dto.refreshToken, userAgent);
  }

  @Post('logout')
  @HttpCode(HttpStatus.NO_CONTENT)
  logout(@CurrentUser() user: AuthenticatedUser, @Body() dto: RefreshTokenDto): Promise<void> {
    return this.authService.logout(user.id, dto.refreshToken);
  }

  @Get('me')
  me(@CurrentUser() user: AuthenticatedUser): Promise<PublicUser> {
    return this.authService.me(user.id);
  }
}

@Public() 只加在 login 与 refresh 上；logout 与 me 需要有效访问令牌。

全局守卫在 AuthModule 里注册：

ts
import { Module } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { APP_GUARD } from '@nestjs/core';
import { JwtModule } from '@nestjs/jwt';
import { TypeOrmModule } from '@nestjs/typeorm';
import type { AppConfig } from '../config/configuration.js';
import { UsersModule } from '../users/users.module.js';
import { AuthController } from './auth.controller.js';

import { RolesGuard } from './guards/roles.guard.js';

@Module({
  imports: [
    UsersModule,
    TypeOrmModule.forFeature([RefreshTokenEntity]),
    JwtModule.registerAsync({
      inject: [ConfigService],
      useFactory: (config: ConfigService<AppConfig, true>) => {
        const auth = config.get('auth', { infer: true });
        return {
          secret: auth.accessSecret,
          signOptions: { expiresIn: auth.accessTtlSeconds, issuer: auth.issuer },
        };
      },
    }),
  ],
  controllers: [AuthController],
  providers: [
    AuthService,
    // APP_GUARD 的注册顺序 = 执行顺序：先确认身份，再判断角色
    { provide: APP_GUARD, useClass: JwtAuthGuard },
    { provide: APP_GUARD, useClass: RolesGuard },
  ],
  exports: [AuthService],
})
export class AuthModule {}

APP_GUARD 的注册顺序就是执行顺序：先 JwtAuthGuard 确认身份，再 RolesGuard 判断角色。

ts
import { CanActivate, ExecutionContext, Injectable, UnauthorizedException } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { JwtService } from '@nestjs/jwt';
import type { Request } from 'express';
import type { AuthenticatedUser } from '../authenticated-user.js';
import { IS_PUBLIC_KEY } from '../decorators/public.decorator.js';
import type { UserRole } from '../../users/user.entity.js';

export interface AccessTokenPayload {
  sub: string;
  email: string;
  role: UserRole;
}

type AuthenticatedRequest = Request & { user?: AuthenticatedUser };

function extractBearerToken(header: string | undefined): string | null {
  if (!header) {
    return null;
  }
  const [scheme, token] = header.split(' ');
  if (scheme?.toLowerCase() !== 'bearer' || !token) {
    return null;
  }
  return token;
}

/**
 * 全局守卫（在 AuthModule 里用 APP_GUARD 注册）：
 * 所有路由默认需要 Bearer Token，@Public() 例外。
 *
 * 失败路径分三类，前端据此决定「跳登录」还是「静默刷新」：
 * - 没有令牌 → AUTH_REQUIRED
 * - 令牌过期 → AUTH_TOKEN_EXPIRED
 * - 令牌非法 → AUTH_TOKEN_INVALID
 */
@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(
    private readonly jwtService: JwtService,
    private readonly reflector: Reflector,
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (isPublic) {
      return true;
    }

    const request = context.switchToHttp().getRequest<AuthenticatedRequest>();
    const token = extractBearerToken(request.headers.authorization);

    if (!token) {
      throw new UnauthorizedException({
        code: 'AUTH_REQUIRED',
        message: '缺少访问令牌，请在 Authorization 头中携带 Bearer <token>',
      });
    }

    try {
      const payload = await this.jwtService.verifyAsync<AccessTokenPayload>(token);
      request.user = { id: payload.sub, email: payload.email, role: payload.role };
      return true;
    } catch (error) {
      const expired = error instanceof Error && error.name === 'TokenExpiredError';
      throw new UnauthorizedException({
        code: expired ? 'AUTH_TOKEN_EXPIRED' : 'AUTH_TOKEN_INVALID',
        message: expired ? '访问令牌已过期，请使用刷新令牌换发' : '访问令牌无效',
      });
    }
  }
}
ts
import { CanActivate, ExecutionContext, ForbiddenException, Injectable } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import type { Request } from 'express';
import type { AuthenticatedUser } from '../authenticated-user.js';
import { ROLES_KEY } from '../decorators/roles.decorator.js';
import type { UserRole } from '../../users/user.entity.js';

/**
 * 角色守卫：只回答「身份够不够」，不负责「令牌是否有效」。
 * 因此它必须排在 JwtAuthGuard 之后（APP_GUARD 的注册顺序就是执行顺序）。
 *
 * 与 401 的区别：401 是「不知道你是谁」，403 是「知道你是谁，但你不能干这件事」。
 */
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  // #region roles-guard
  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.getAllAndOverride<UserRole[]>(ROLES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (!requiredRoles || requiredRoles.length === 0) {
      return true;
    }

    const request = context
      .switchToHttp()
      .getRequest<Request & { user?: AuthenticatedUser }>();
    const user = request.user;

    if (!user) {
      // 理论上不会走到：JwtAuthGuard 已经拦过一遍。保留是为了守卫被单独复用时的安全兜底
      throw new ForbiddenException({
        code: 'FORBIDDEN_ROLE',
        message: '缺少身份信息，无法判断角色',
      });
    }

    if (!requiredRoles.includes(user.role)) {
      throw new ForbiddenException({
        code: 'FORBIDDEN_ROLE',
        message: `需要 ${requiredRoles.join(' 或 ')} 角色`,
        details: { requiredRoles, actualRole: user.role },
      });
    }

    return true;
  }
  // #endregion roles-guard
}

export const CurrentUser = createParamDecorator(

七、水平越权：Guard 管不了的那一半 ​

@Roles('admin') 能挡住「member 调 admin 接口」，但挡不住「member 读别人的资料」——因为请求者在角色上是合法的。这类资源归属判断必须落到用例层：

ts
@Get(':id')
findOne(
  @Param('id', new ParseUUIDPipe()) id: string,
  @CurrentUser() actor: AuthenticatedUser,
): Promise<PublicUser> {
  // 水平越权防护：不是 admin 时，只能读自己。
  // 这类判断依赖「资源归属」，放 Guard 里会很别扭，落在用例层更清楚。
  if (actor.role !== 'admin' && actor.id !== id) {
    throw new ForbiddenException({
      code: 'FORBIDDEN_SELF_SCOPE',
      message: '只能查看自己的用户信息',
      details: { allowedUserId: actor.id },
    });
  }
  return this.usersService.findOne(id);
}

先判归属、再查数据，还有一个副作用：非 admin 请求别人的 ID 时返回 403 而不是 404，不会泄露「这个 ID 是否存在」。

九、把关键路径固化成测试 ​

令牌轮换、重放连坐、登出失效这些路径，手工 curl 只够验证一次；真正的回归保障是 e2e：

ts
it('刷新令牌轮换：旧令牌立即失效，重放会吊销整个 family', async () => {
  const session = await login('linus@example.com');

  const refreshed = await http()
    .post('/api/auth/refresh')
    .send({ refreshToken: session.refreshToken })
    .expect(200);

  const nextRefreshToken = refreshed.body.data.refreshToken as string;
  expect(nextRefreshToken).not.toBe(session.refreshToken);

  const replay = await http()
    .post('/api/auth/refresh')
    .send({ refreshToken: session.refreshToken })
    .expect(401);
  expect(replay.body.error.code).toBe('AUTH_REFRESH_REUSED');

  // 重放后整条令牌链被吊销：新令牌也不能再换发
  // （它不是「被轮换掉的旧令牌」，所以报 AUTH_REFRESH_INVALID 而不是 REUSED）
  const revoked = await http()
    .post('/api/auth/refresh')
    .send({ refreshToken: nextRefreshToken })
    .expect(401);
  expect(revoked.body.error.code).toBe('AUTH_REFRESH_INVALID');
});

it('登出后刷新令牌失效（204）', async () => {
  const session = await login('linus@example.com');

  await http()
    .post('/api/auth/logout')
    .set('authorization', `Bearer ${session.accessToken}`)
    .send({ refreshToken: session.refreshToken })
    .expect(204);

  const afterLogout = await http()
    .post('/api/auth/refresh')
    .send({ refreshToken: session.refreshToken })
    .expect(401);

  // 登出导致的失效与「轮换重放」区分开：前者不需要再吊销整族
  expect(afterLogout.body.error.code).toBe('AUTH_REFRESH_INVALID');
});

访问令牌过期不用等 15 分钟，AUTH_TOKEN_EXPIRED 的用例在同文件里用 signAsync(..., { expiresIn: '-5s' }) 直接签一个已过期的令牌。

逐步拆解 ​

1. 为什么 access token 要短、refresh token 要长 ​

  • access token 无状态、验签即用，性能好，但无法撤销；TTL 越短，泄露后的窗口越小；
  • refresh token 要查库，能撤销，所以承担「长期会话」的职责；
  • 两者组合的结果：15 分钟的暴露窗口 + 7 天的可控会话。

如果把 access token 也做成 7 天，等于放弃了撤销能力；如果把 refresh token 做成 15 分钟，用户会频繁被踢回登录页。

2. 为什么刷新要用「条件更新」 ​

ts
.update(RefreshTokenEntity)
.set({ revokedAt: new Date() })
.where('id = :id AND revoked_at IS NULL', { id: existing.id })

两个并发请求都读到了「未吊销」，如果直接 save，两个都会成功，签出两条新链。条件更新把「判断 + 占用」合成一条原子 SQL，affected === 0 的那个请求就知道自己输了。

这是「先查再写」的通用解法：把状态判断放进 WHERE。

3. 事务内抛异常为什么会回滚吊销 ​

dataSource.transaction(async (manager) => { ... }) 的回调抛出异常时，TypeORM 会 ROLLBACK。所以：

  • 「写吊销记录」和「抛 401」不能放在同一个事务回调里；
  • 正确顺序是：事务内返回结果 → 事务提交 → 根据结果抛异常。

这个坑不只出现在认证里。任何「失败时要留下痕迹」的场景（审计、补偿、告警）都要注意。

4. 登出为什么是幂等 + 204 ​

  • 令牌不存在、已吊销、已过期，都返回成功：登出不应该成为一个「探测令牌是否存在」的接口；
  • 204 表示「成功且没有响应体」，前端不需要解析；
  • 只吊销 refresh family，不尝试吊销 access token（做不到，见下一节）。

5. JWT 的「不可撤销」怎么缓解 ​

方案代价适用场景
短 TTL（本项目）最长 15 分钟窗口大多数业务
令牌黑名单（Redis）每次请求多一次查询高风险操作、强制下线
会话表/版本号每请求查库或缓存需要「立即踢人」
双向 TLS / 短期证书运维复杂服务间通信

本项目的选择是短 TTL + 可吊销 refresh token，并把「强制下线」留作第 07 章的练习。

6. Guard 顺序与 @Public() 的组合规则 ​

  • 全局守卫先于控制器级守卫；APP_GUARD 之间按注册顺序执行；
  • JwtAuthGuard 查 IS_PUBLIC_KEY，命中就放行；
  • RolesGuard 只查 ROLES_KEY，没有声明就放行；
  • 所以 @Public() + @Roles() 同时出现时，角色检查仍会执行——但此时 request.user 为空，会得到 403。不要这样组合。

7. 密码与令牌的日志红线 ​

  • 请求日志里不能出现 password、authorization、refreshToken；
  • 错误响应里不能回显用户输入的原密码；
  • 数据库慢查询日志会打印参数，登录相关查询要特别小心（password_hash 出现在 addSelect 里）。

企业级做法 ​

  1. 密码哈希用 argon2id：内存硬，抗 GPU；scrypt 是可接受的零依赖替代，md5/sha1/明文绝对不行。
  2. 刷新令牌轮换 + 重放检测是默认配置：OAuth 2.1 已把「公开客户端必须轮换」写成要求。
  3. 令牌只通过 HTTPS 传输：Bearer Token 等价于密码，明文 HTTP 下没有任何安全性可言。
  4. 区分设备会话：family_id + user_agent 是最小实现；完整做法是「会话管理」页面，可单独踢掉某台设备。
  5. 密钥轮换：JWT_ACCESS_SECRET 要支持双密钥（kid 标识），旧密钥只验不签，过渡期后再删。
  6. 登录限流与告警：同一 IP/账号的失败次数要限流；连续失败、异常地域登录要触发风控（第 10/11 章）。
  7. 权限模型要能演进：RBAC 适合「角色少、边界清晰」；出现「同角色但只能看自己部门」时，需要 ABAC/ReBAC 或把数据权限下沉到查询条件。
  8. 审计与合规：登录成功/失败、刷新重放、登出、角色变更都应留痕；审计日志本身要防篡改（第 04 章的审计表）。
  9. 前端令牌存储：localStorage 易受 XSS；HttpOnly Cookie 易受 CSRF。选哪个取决于威胁模型，本项目用 Authorization 头 + 不做 Cookie，因此不涉及 CSRF，但要求严格防 XSS。
  10. 不要自己造协议：内部系统可以照本章做；面向第三方或需要 SSO 时，直接上 OIDC（Keycloak/Auth0/云厂商 IAM）。

练习与验收标准 ​

练习

  1. 给登录接口加限流：同一邮箱 1 分钟内失败 5 次后返回 429（可先用内存 Map 实现）。
  2. 实现「刷新令牌复用宽限期」：允许旧令牌在轮换后 10 秒内重试一次，避免弱网导致误判（想清楚它如何削弱重放检测）。
  3. 增加 GET /api/auth/sessions：列出当前用户所有未吊销的 family，并支持 DELETE /api/auth/sessions/:familyId。
  4. 把 role 从 JWT 里拿掉，改成每次请求查缓存中的用户角色，比较两种方案的延迟与「改角色立即生效」的差异。
  5. 写一个 e2e：并发两次刷新同一令牌，断言只有一次 200、另一次是 AUTH_REFRESH_REUSED。

验收标准

  • [ ] POST /api/auth/login 正确账号返回 200，含 accessToken、refreshToken、expiresIn: 900、user；
  • [ ] 错误密码返回 401 AUTH_INVALID_CREDENTIALS，且与「邮箱不存在」的响应完全一致；
  • [ ] 不带令牌访问 /api/users 返回 401 AUTH_REQUIRED；
  • [ ] member 访问 /api/users 返回 403 FORBIDDEN_ROLE，details.actualRole === 'member'；
  • [ ] member 读他人资料返回 403 FORBIDDEN_SELF_SCOPE，读自己返回 200；
  • [ ] 刷新一次后旧 refresh token 再用返回 401 AUTH_REFRESH_REUSED，且新令牌也随之为 401 AUTH_REFRESH_INVALID；
  • [ ] 登出返回 204，随后用同一 refresh token 刷新返回 401 AUTH_REFRESH_INVALID；
  • [ ] 过期访问令牌返回 401 AUTH_TOKEN_EXPIRED（e2e 用 expiresIn: '-5s' 验证）；
  • [ ] 数据库里 refresh_tokens 只能看到 64 位十六进制哈希，看不到原始令牌；
  • [ ] pnpm --filter @nestjs-tutorial/api test:e2e 中认证相关用例全部通过。
