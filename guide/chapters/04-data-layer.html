04 数据层：TypeORM、迁移与事务 ​

TypeORM 实体、迁移、事务与查询边界，避免 ORM 带来的隐性 N+1。

成稿正文、示例代码与验收标准均已完整，可直接跟练

本章目标 ​

  1. 在 TypeORM 与 Prisma 之间做出有理由、也知道代价的选择；
  2. 用实体描述表结构，用显式 SQL 迁移管理 schema 变更，而不是依赖 synchronize；
  3. 用事务保证「写业务数据 + 写审计」的原子性，并验证回滚真的生效；
  4. 用 QueryBuilder 写出跨方言可跑的分页与搜索；
  5. 把第 03 章还在内存里的用户存储，替换成真实的 Postgres 仓储。

概念与原理 ​

1. 选型：TypeORM 还是 Prisma ​

先把结论放前面：本项目选 TypeORM。不是因为 Prisma 不好，而是两者优化的是不同的东西。

维度TypeORMPrisma对本教程的影响
数据模型装饰器实体类，就是普通 TS 类独立 schema.prisma DSLTypeORM 的实体可直接参与 Nest DI 与类型推导
生成步骤无，改完实体直接跑必须 prisma generate，产物进 node_modules少一个「忘了 generate 导致类型对不上」的失败源
查询方式Repository / QueryBuilder / 原生 SQL 三种粒度以 prisma.xxx 为主，复杂查询用 $queryRaw复杂报表、动态条件用 QueryBuilder 更顺手
迁移自己写 SQL 或用 CLI 生成后审阅prisma migrate 生成 SQL 并托管迁移表两者都能回滚，TypeORM 更容易写「手写 DDL」
事务manager.transaction，可把 EntityManager 传下去$transaction 回调 / 数组TypeORM 的「事务管理器传递」对跨 Service 的组合更自然
测试替身可换 sql.js（纯 JS 的 SQLite）需要真实数据库或额外 mock本仓库 pnpm verify 不依赖 Docker
类型安全依赖 TS 类型，运行时仍可能拿到 any生成类型非常强Prisma 在这一点确实更好
学习成本装饰器 + 元数据，坑更分散DSL 简单，边界清晰教程面向「理解 ORM 在做什么」，TypeORM 的透明度更高

选 TypeORM 的五条具体理由

  1. 实体即类：UserEntity 既能被 TypeORM 映射，也能被 Nest 的 TypeOrmModule.forFeature([UserEntity]) 直接消费，不需要在 schema 文件与 TS 类型之间来回同步。
  2. 没有 codegen 环节：CI 里少一步 prisma generate，也就少一类「本地能跑、流水线报类型缺失」的问题。
  3. QueryBuilder 可控：分页、动态搜索条件、条件更新（where('id = :id AND revoked_at IS NULL')）都能落到 SQL 级别；第 06 章的并发轮换就依赖这个能力。
  4. 事务管理器可传递：manager.transaction(async (manager) => ...) 拿到的 manager 可以继续传给其他 Service，保证它们在同一事务里（本章第 3 节会演示）。
  5. 测试可以不用 Docker：sql.js 是编译成 WebAssembly 的 SQLite，纯 JS 依赖，pnpm verify 在任何机器上都能跑。

代价也要写清楚

  • TypeORM 的类型安全弱于 Prisma，运行时字段仍可能是 any，要靠 DTO、实体约束和测试兜底；
  • synchronize: true 很诱人，但它会在启动时按实体改表，生产环境必须关闭；
  • 方言差异需要自己处理（本项目用 LOWER(...) LIKE 而不是 ILIKE，就是为了同一套代码在 Postgres 与 sqljs 上都能跑）。

什么时候该选 Prisma

团队更看重「schema 单一事实来源 + 生成类型」，业务以 CRUD 为主、复杂 SQL 少，且能接受 codegen 步骤时，Prisma 的体验更好。选型没有唯一答案，关键是能把取舍写进 ADR（架构决策记录）。

2. 实体、对外形状与 DTO 是三样东西 ​

初学者最容易把三者混成一个。本项目明确分开：

形状例子谁用是否含敏感字段
实体 EntityUserEntity仓储、事务有 passwordHash、deletedAt
对外形状PublicUserController 返回值只有 id/email/name/role/createdAt
入参 DTOCreateUserDto请求体校验有 password，没有 id

转换只允许在一个地方发生：toPublicUser()。这样即使某个接口不小心 return user，类型层面也会提醒你「这不是 PublicUser」。

3. 迁移与 synchronize 的分工 ​

  • 迁移：一次 schema 变更 = 一个带时间戳的类，up 建、down 拆，进 git、可评审、可回滚；
  • synchronize：按实体差异自动改表，开发期爽，生产期危险（改列类型、丢数据都可能无声发生）。

本项目的选择是：Postgres 永远 synchronize: false + migrationsRun: true；测试用的 sqljs 才开 synchronize: true。这样「本地改实体就自动改表」的便利只存在于测试库，生产 schema 只能由迁移推进。

4. 事务的边界：管理器必须传下去 ​

this.users.manager.transaction(cb) 里的 cb(manager) 才是事务内的管理器。常见错误是：

ts
await this.users.manager.transaction(async () => {
  await this.users.save(user);      // 用的是仓储自带的 manager，可能另开连接
  await this.audit.record(log);     // 不在同一事务里
});

正确做法是把 manager 一路传下去，让所有写操作共用同一个事务连接。

5. 分页的三件事 ​

  1. 总数与列表是两条 SQL：getManyAndCount() 会额外跑一次 COUNT，这是分页的常规代价；
  2. 排序必须稳定：只按 createdAt 排，时间相同的记录在翻页时可能重复或漏掉，所以追加 id；
  3. 搜索条件要跨方言：ILIKE 只有 Postgres 有，LOWER(col) LIKE :kw 两边都能跑。

二、ORM 配置的唯一入口 ​

ts
import type { TypeOrmModuleOptions } from '@nestjs/typeorm';
import type { ConfigService } from '@nestjs/config';
import type { AppConfig } from '../config/configuration.js';
import { InitialSchema1750000000000 } from './migrations/1750000000000-InitialSchema.js';
import { OrdersAndInventory1750000001000 } from './migrations/1750000001000-OrdersAndInventory.js';
import { WebhookEvents1750000002000 } from './migrations/1750000002000-WebhookEvents.js';

/**
 * 应用与 CLI 之外的唯一 ORM 配置入口。
 *
 * 两种驱动，职责严格分开：
 * - postgres：开发与生产。schema 由迁移文件管理（synchronize 永久关闭）。
 * - sqljs：仅测试。内存库 + synchronize，让 `pnpm verify` 不需要 Docker 也能跑。
 *
 * 注意这里没有「postgres 连不上就退回 sqljs」的分支：
 * 静默降级会让人以为数据落库了，实际上重启就没了。
 */
export function buildTypeOrmOptions(config: ConfigService<AppConfig, true>): TypeOrmModuleOptions {
  const database = config.get('database', { infer: true });

  if (database.driver === 'sqljs') {
    return {
      type: 'sqljs',
      autoSave: false,
      synchronize: true,
      migrationsRun: false,
      logging: ['error'],
      autoLoadEntities: true,
    };
  }

  return {
    type: 'postgres',
    host: database.host,
    port: database.port,
    username: database.username,
    password: database.password,
    database: database.name,
    ssl: database.ssl ? { rejectUnauthorized: false } : false,
    // 让 @PrimaryGeneratedColumn('uuid') 使用 gen_random_uuid()（PG13+ 内置）
    uuidExtension: 'pgcrypto',
    synchronize: false,
    migrationsRun: true,
    migrations: [
      InitialSchema1750000000000,
      OrdersAndInventory1750000001000,
      WebhookEvents1750000002000,
    ],
    logging: database.logging ? ['query', 'error'] : ['error'],
    autoLoadEntities: true,
    // 默认会重试 10 次（约 30 秒）才报错；开发期希望快速失败并给出可执行提示
    retryAttempts: 1,
  };
}

这段代码有两个刻意设计：

  • sqljs 分支只给测试用，synchronize: true、migrationsRun: false；
  • Postgres 分支没有「连不上就退回 sqljs」的分支。静默降级会让人以为数据落库了，实际上重启就没了；
  • retryAttempts: 1：默认会重试约 10 次、拖半分钟才报错，开发期希望快速失败。

三、实体：用元数据描述表 ​

ts
import {
  Column,
  CreateDateColumn,
  DeleteDateColumn,
  Entity,
  Index,
  PrimaryGeneratedColumn,
  UpdateDateColumn,
} from 'typeorm';

export const USER_ROLES = ['admin', 'member'] as const;
export type UserRole = (typeof USER_ROLES)[number];

/**
 * 对外暴露的用户形状：永远不要把实体直接返回给客户端。
 * 实体上有 passwordHash、deletedAt 这类不该出门的字段。
 */
export interface PublicUser {
  id: string;
  email: string;
  name: string;
  role: UserRole;
  createdAt: string;
}

@Entity('users')
export class UserEntity {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Index('uq_users_email', { unique: true })
  @Column({ type: 'varchar', length: 254 })
  email: string;

  @Column({ type: 'varchar', length: 80 })
  name: string;

  @Column({ type: 'varchar', length: 16, default: 'member' })
  role: UserRole;

  /**
   * select: false —— 默认查询不带出哈希，登录时再显式 addSelect。
   * 这样即使某个接口不小心 `return user`，也不会把密码哈希漏出去。
   */
  @Column({ name: 'password_hash', type: 'varchar', length: 255, select: false })
  passwordHash: string;

  @CreateDateColumn({ name: 'created_at' })
  createdAt: Date;

  @UpdateDateColumn({ name: 'updated_at' })
  updatedAt: Date;

  @DeleteDateColumn({ name: 'deleted_at' })
  deletedAt: Date | null;
}

/** 实体 → 对外形状的唯一转换点 */
export function toPublicUser(user: UserEntity): PublicUser {
  return {
    id: user.id,
    email: user.email,
    name: user.name,
    role: user.role,
    createdAt: user.createdAt.toISOString(),
  };
}

三个细节值得单独看：

  • @PrimaryGeneratedColumn('uuid') 不写死数据库类型，Postgres 与 sqljs 都能生成；
  • passwordHash 标记 select: false，普通查询拿不到哈希，登录时再显式 addSelect；
  • @DeleteDateColumn 让 remove 变成软删除：行还在，deleted_at 有值，普通查询默认过滤掉。

审计表同理，索引都写在实体上，便于和迁移对照：

ts
import { Column, CreateDateColumn, Entity, Index, PrimaryGeneratedColumn } from 'typeorm';

/**
 * 审计日志：只追加、不修改。
 * 真实项目里还会加「只允许 INSERT 的数据库账号」与归档策略，第 11 章展开。
 */

}

四、迁移：显式 SQL，可回滚 ​

ts
import type { MigrationInterface, QueryRunner } from 'typeorm';

/**
 * 初始 schema。迁移全部用显式 SQL，而不是让 TypeORM 根据实体「猜」：
 * - 团队评审迁移时看到的是可执行的 DDL，不是一段框架内部逻辑；
 * - 索引名、默认值、外键行为都由我们决定，回滚也有明确语义。
 *
 * 时间字段统一用 timestamptz（Postgres 推荐做法），
 * 实体侧不写死 type，是为了让同一套实体也能跑在测试用的 sqljs 上。
 */
export class InitialSchema1750000000000 implements MigrationInterface {
  name = 'InitialSchema1750000000000';

  async up(queryRunner: QueryRunner): Promise<void> {
    // gen_random_uuid() 在 Postgres 13+ 内置，无需额外安装 uuid-ossp 扩展
    await queryRunner.query(`
      CREATE TABLE "users" (
        "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
        "email" varchar(254) NOT NULL,
        "name" varchar(80) NOT NULL,
        "role" varchar(16) NOT NULL DEFAULT 'member',
        "password_hash" varchar(255) NOT NULL,
        "created_at" timestamptz NOT NULL DEFAULT now(),
        "updated_at" timestamptz NOT NULL DEFAULT now(),
        "deleted_at" timestamptz
      )
    `);
    await queryRunner.query(`CREATE UNIQUE INDEX "uq_users_email" ON "users" ("email")`);

    await queryRunner.query(`
      CREATE TABLE "audit_logs" (
        "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
        "action" varchar(64) NOT NULL,
        "actor_id" uuid,
        "target_id" varchar(64),
        "summary" varchar(500) NOT NULL,
        "created_at" timestamptz NOT NULL DEFAULT now()
      )
    `);
    await queryRunner.query(`CREATE INDEX "idx_audit_logs_actor_id" ON "audit_logs" ("actor_id")`);
    await queryRunner.query(
      `CREATE INDEX "idx_audit_logs_created_at" ON "audit_logs" ("created_at")`,
    );

    await queryRunner.query(`
      CREATE TABLE "refresh_tokens" (
        "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
        "user_id" uuid NOT NULL REFERENCES "users" ("id") ON DELETE CASCADE,
        "family_id" uuid NOT NULL,
        "token_hash" varchar(64) NOT NULL,
        "expires_at" timestamptz NOT NULL,
        "revoked_at" timestamptz,
        "replaced_by_token_id" uuid,
        "user_agent" varchar(255),
        "created_at" timestamptz NOT NULL DEFAULT now()
      )
    `);
    await queryRunner.query(
      `CREATE UNIQUE INDEX "uq_refresh_tokens_token_hash" ON "refresh_tokens" ("token_hash")`,
    );
    await queryRunner.query(
      `CREATE INDEX "idx_refresh_tokens_user_id" ON "refresh_tokens" ("user_id")`,
    );
    await queryRunner.query(
      `CREATE INDEX "idx_refresh_tokens_family_id" ON "refresh_tokens" ("family_id")`,
    );
  }

  async down(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`DROP TABLE "refresh_tokens"`);
    await queryRunner.query(`DROP TABLE "audit_logs"`);
    await queryRunner.query(`DROP TABLE "users"`);
  }
}

为什么不直接用 CLI 根据实体生成？因为生成结果需要人审，而审一段可执行 DDL 比审「框架内部逻辑」可靠。索引名、外键行为、默认值都在这里定死，down 也有明确语义。

迁移的执行有两条路径：

  • 应用启动时自动跑未执行的迁移（migrationsRun: true）；
  • 需要单独建表（CI、排障）时用 CLI：
bash
pnpm --filter @nestjs-tutorial/api db:migrate

真实输出（迁移已执行过时）：

text
没有待执行的迁移。

五、Repository 替换内存存储 ​

第 03 章的 UsersService 用的是进程内 Map。现在换成仓储：

ts
constructor(
  // 仓储由 TypeOrmModule.forFeature([UserEntity]) 提供，注入的是 Repository 代理，不是裸连接
  @InjectRepository(UserEntity)
  private readonly users: Repository<UserEntity>,
  // UsersService 需要写审计，AuditService 需要读用户来展示操作人姓名：
  // 两个模块互相依赖，用 forwardRef 打破加载顺序死锁（详见第 2 章）。
  @Inject(forwardRef(() => AuditService))
  private readonly auditService: AuditService,
) {}

TypeOrmModule.forFeature([UserEntity]) 负责提供 Repository<UserEntity>；UsersService 本身不需要 new 任何东西。

六、事务：用户与审计一起成功或一起失败 ​

ts
async create(dto: CreateUserDto, actorId: string | null = null): Promise<PublicUser> {
  const email = dto.email.trim().toLowerCase();
  // 哈希是 CPU 密集操作，放在事务外，避免占着连接等计算
  const passwordHash = await hashPassword(dto.password);

  try {
    return await this.users.manager.transaction(async (manager) => {
      const saved = await manager.save(
        manager.create(UserEntity, {
          email,
          name: dto.name,
          role: dto.role ?? 'member',
          passwordHash,
        }),
      );

      await this.auditService.record(
        {
          action: 'user.created',
          actorId: actorId ?? saved.id,
          targetId: saved.id,
          summary: `用户 ${saved.email} 注册成功`,
        },
        manager,
      );

      return toPublicUser(saved);
    });
  } catch (error) {
    if (isUniqueViolation(error)) {
      throw new ConflictException({
        code: 'EMAIL_TAKEN',
        message: '该邮箱已被注册',
        details: { email },
      });
    }
    throw error;
  }
}

三处关键点：

  1. hashPassword 放在事务外——scrypt 是 CPU 密集操作，占着连接等计算会拖慢整个池；
  2. auditService.record(..., manager) 把事务管理器传下去，审计和用户写入同一个事务；
  3. 唯一约束冲突（Postgres 23505）翻译成 409 EMAIL_TAKEN，而不是把数据库错误原样抛给客户端。

「回滚真的生效」不是靠读代码确认的，而是有一条测试专门制造失败：

ts
it('事务回滚：审计写入失败时用户不会残留', async () => {
  auditRecord.mockRejectedValueOnce(new Error('审计写入失败'));

  await expect(service.create(DEMO)).rejects.toThrow('审计写入失败');
  expect(await dataSource.getRepository(UserEntity).count()).toBe(0);
});

七、分页与搜索 ​

ts
async findAll(query: PaginationQueryDto): Promise<PagedResult<PublicUser>> {
  const keyword = query.search?.trim().toLowerCase();

  const qb = this.users.createQueryBuilder('user');
  if (keyword) {
    qb.where('(LOWER(user.email) LIKE :keyword OR LOWER(user.name) LIKE :keyword)', {
      keyword: `%${keyword}%`,
    });
  }
  qb.orderBy('user.createdAt', 'DESC')
    .addOrderBy('user.id', 'DESC')
    .skip((query.page - 1) * query.pageSize)
    .take(query.pageSize);

  const [items, total] = await qb.getManyAndCount();

  return {
    items: items.map(toPublicUser),
    total,
    page: query.page,
    pageSize: query.pageSize,
  };
}

skip/take 会被 TypeORM 翻译成 OFFSET/LIMIT；getManyAndCount() 同时返回当页数据与总数。排序追加 id 是为了翻页稳定。

八、软删除 ​

ts
async remove(id: string, actorId: string): Promise<void> {
  const user = await this.findOne(id);

  await this.users.manager.transaction(async (manager) => {
    const result = await manager.softDelete(UserEntity, { id });
    if (result.affected === 0) {
      throw new NotFoundException({ code: 'USER_NOT_FOUND', message: `用户 ${id} 不存在` });
    }
    await this.auditService.record(
      {
        action: 'user.deleted',
        actorId,
        targetId: id,
        summary: `用户 ${user.email} 被删除（软删除）`,
      },
      manager,
    );
  });
}

softDelete 只更新 deleted_at，所以「删除」之后审计仍然能追溯到这个人；需要看已删除数据时，查询要显式 withDeleted: true。

逐步拆解 ​

1. 为什么迁移要手写 SQL ​

「实体改了，迁移自动生成」听起来省事，但自动生成的迁移经常有三个问题：

  • 改列类型时可能先 DROP 再加，数据没了；
  • 索引/约束名是随机的，回滚时对不上；
  • 团队评审时看不懂它到底改了什么。

手写 SQL 的代价是要自己保证 up 与 down 对称。本项目的约定是：一个迁移只做一件事，down 按 up 的逆序写。

2. 事务里最容易犯的错 ​

写法后果
事务内用 this.repo.save()可能另开连接，写操作跑到事务外
事务内做耗时计算（哈希、HTTP 调用）长时间占用连接，池被拖垮
事务内 throw 后还想保留已写入的数据异常会回滚整个事务（第 06 章的令牌轮换就踩过这个坑）
事务里再嵌套 manager.transaction默认不会产生新事务，但语义容易误解

3. 唯一约束是最终防线 ​

先查再插在并发下一定会漏：两个请求同时查到「邮箱不存在」，然后都插入。数据库唯一索引才是最终防线，所以代码里要做的不是「避免冲突」，而是把冲突翻译成业务错误：

ts
/**
 * 唯一约束冲突的识别。并发场景下「先查再插」一定会漏，
 * 数据库唯一索引才是最终防线，所以要把它的报错翻译成业务错误。
 */
export function isUniqueViolation(error: unknown): boolean {
  const candidate = error as {
    driverError?: { code?: string; message?: string };
    code?: string;
    message?: string;
  };

  const code = candidate.driverError?.code ?? candidate.code;
  if (code === '23505' || code === 'SQLITE_CONSTRAINT') {
    return true;
  }

  const message = `${candidate.message ?? ''} ${candidate.driverError?.message ?? ''}`;
  return (
    message.includes('duplicate key value violates unique constraint') ||
    message.includes('UNIQUE constraint failed')
  );
}

SQLITE_CONSTRAINT 分支不是凑数——单元测试跑在 sqljs 上，不识别它，测试就会漏掉 409 这条路径。

4. select: false 与登录查询 ​

passwordHash 默认不返回，登录时需要显式取出：

ts
this.users
  .createQueryBuilder('user')
  .addSelect('user.passwordHash')
  .where('LOWER(user.email) = :email', { email })
  .getOne();

这样「普通接口不小心返回实体」也不会泄露哈希。单元测试里有一条专门验证这个行为。

5. 软删除与唯一索引的冲突 ​

当前迁移里 uq_users_email 是全表唯一，不区分 deleted_at。后果是：软删除一个用户后，同一邮箱无法再注册。

这是有意的取舍：演示项目需要审计可追溯，不希望「同邮箱出现两个历史用户」。如果业务要求「删除后可重新注册」，迁移需要改成部分唯一索引：

sql
DROP INDEX "uq_users_email";
CREATE UNIQUE INDEX "uq_users_email" ON "users" ("email") WHERE "deleted_at" IS NULL;

示例未实现

上面的部分唯一索引是设计讲解，示例未实现。TypeORM 的 @Index 装饰器表达不了 WHERE 条件，需要写在迁移里，并且实体上的索引声明要同步删掉，否则 synchronize 的测试库会建出另一套索引。

6. N+1 与批量查询 ​

审计列表要展示「操作人姓名」。如果每条审计都查一次用户，就是典型的 N+1。本项目的做法是先收集 actorId，再用 In(...) 一次取回：

ts
async findByIds(ids: string[]): Promise<PublicUser[]> {
  const uniqueIds = [...new Set(ids)];
  if (uniqueIds.length === 0) {
    return [];
  }
  const users = await this.users.find({ where: { id: In(uniqueIds) } });
  return users.map(toPublicUser);
}

In(...) 只发一条 WHERE id IN (...)，配合 new Set() 去重，避免重复 ID 放大参数。第 07 章会用它做 N+1 的对照实验。

7. 连接失败时不静默降级 ​

database-options.ts 里没有 fallback 分支，main.ts 会把连接错误翻译成中文提示并以退出码 1 结束。这部分属于第 05 章的「配置与启动」主题，这里只强调设计原则：数据层不允许「看起来成功了，其实写到了内存」。

常见坑与排查 ​

现象根因处理
Data type "Object" in "X.y" is not supported属性写成 Date | null 这类联合类型，反射元数据只剩 Object改成单类型（如 Date），列上标 nullable: true，见 RefreshTokenEntity.revokedAt
启动时报 ECONNREFUSED 127.0.0.1:5432Postgres 没起，或 DB_HOST/DB_PORT 不对docker compose up -d postgres，再用 docker compose ps 看健康状态
改了实体但表结构没变Postgres 关闭了 synchronize，又没写迁移新建迁移并执行 pnpm db:migrate，不要打开 synchronize
插入重复邮箱返回 500只做了「先查再插」，没接住唯一约束错误用 isUniqueViolation 翻译成 409 EMAIL_TAKEN
sqljs 测试通过、Postgres 报错用了 ILIKE、uuid、timestamptz 等方言特性查询用 LOWER(...) LIKE；实体不写死类型
分页第二页出现重复数据排序字段不唯一orderBy(createdAt).addOrderBy(id)
软删除后列表还能查到用了原生 SQL，或显式 withDeleted普通查询交给 Repository；需要包含已删除时明确写 withDeleted: true
事务里写审计失败，用户却还在审计用了 this.repo 而不是事务 manager把 manager 作为参数传进 record()
updated_at 不更新用了 repository.update() 但没触发 @UpdateDateColumn 的场景差异确认走的是 ORM 更新而非原生 SQL；必要时显式设置时间
迁移执行到一半失败迁移里多条 DDL 没有事务保护（Postgres 多数 DDL 可事务）单个迁移保持原子、可重跑；失败后先 db:revert 再修

企业级做法 ​

  1. 迁移只前进，不回滚生产：down 用于本地与预发；生产出问题用「新迁移修复」而不是回滚，避免数据丢失。
  2. 大表变更拆成 expand/contract：先加可空列 → 双写 → 回填 → 切读 → 删旧列，避免长锁表。
  3. 唯一约束 + 幂等键：数据库约束是最终防线，业务层只负责把冲突翻译成可理解的错误。
  4. 事务要短：事务里只放必要的写操作；哈希、外部调用、文件 IO 都放外面。
  5. 连接池要有上限与超时：pg 默认池大小有限，慢查询会拖垮整个服务；生产要配 statement_timeout，并用慢查询日志定位。
  6. 读写分离与分库分表不是第一天的事：先把索引、分页、N+1 解决掉，再谈更复杂的架构。
  7. 测试策略分层：单元/集成测试用 sqljs 保证速度；发布前用真实 Postgres 跑一遍关键链路（本仓库的 pnpm dev + curl 清单就是这条链路）。
  8. 审计表只追加：不给应用账号 UPDATE/DELETE 权限，归档走独立任务（第 11 章展开）。

练习与验收标准 ​

练习

  1. 给 users 加一个 lastLoginAt 字段：写迁移、改实体、在登录成功时更新，并确认普通查询能看到它。
  2. 把 findAll 的搜索改成「邮箱前缀匹配」，比较 LIKE 'kw%' 与 LIKE '%kw%' 在索引使用上的差异（用 EXPLAIN 看）。
  3. 写一个事务用例：先创建用户，再故意让审计写入失败，断言用户表没有新增行。
