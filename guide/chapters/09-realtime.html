09 实时能力：WebSocket 与 SSE ​

WebSocket 与 SSE 的选型、鉴权、广播与断线重连。

成稿正文、示例代码与验收标准均已完整，可直接跟练
难度
★★★★☆
预计课时
2 小时
最后核对
2026-11-10

订单支付成功后，用户页面不该靠每 3 秒轮询一次接口才知道状态变了。实时推送要解决的就是这件事，但「选 WebSocket 还是 SSE」「断线了补不补」「谁能订阅哪个房间」这三个问题，比写一个 @SubscribeMessage 更值得先想清楚。

本章实现状态

本章以 SSE 落地了完整链路：复用全局 JWT 鉴权、15 秒心跳、Last-Event-ID 断线重连回放、按用户/角色的房间隔离，下单与状态变更会真实推送。单测 9 个用例、e2e 4 个用例覆盖上述行为。WebSocket 网关与多实例 Redis 扩散未实现，在文末明确标注。

本章目标 ​

  1. 用一张表说清 WebSocket 与 SSE 的取舍，而不是「WebSocket 更实时」一句话带过；
  2. 让实时连接的鉴权复用 HTTP 的 JWT Guard，不另造一套 token；
  3. 实现心跳、retry 与 Last-Event-ID 断线重连，并说清回放窗口的边界；
  4. 用「个人房间由令牌推导 + 共享房间按角色校验」做订阅隔离；
  5. 让订单事件成为真实触发源，并给出可复现的 curl 与 e2e 验证方式。

概念与原理 ​

1. WebSocket 与 SSE 的取舍 ​

维度WebSocketSSE
方向双向仅服务端 → 客户端
协议独立握手（Upgrade），不是普通 HTTP 响应普通 HTTP 响应，Content-Type: text/event-stream
浏览器 APIWebSocketEventSource（自动重连、自动带 Last-Event-ID）
鉴权握手时带 Cookie / query / 首帧消息普通请求，可带 Authorization 头（EventSource 除外）
代理与网关需要支持 Upgrade、可能被中间层断开与普通 HTTP 一致，注意关闭响应缓冲即可
重连自己实现（退避、补偿）协议内置，配合事件 ID 补发
二进制原生支持只能传文本（二进制需 Base64）
额外依赖@nestjs/websockets + adapter无，直接用 @Res() 写响应

本项目的实时需求是「订单状态变了，通知当事人和管理看板」——单向、低频、文本，SSE 的每一项都更省事：不需要新依赖、不需要处理握手鉴权、断线重连有协议支持。反过来，如果要做协同编辑、在线游戏、客户端频繁上发指令，就该选 WebSocket。

2. 鉴权复用：为什么不在 SSE 里另造一套认证 ​

全局 JwtAuthGuard 只从 Authorization 头取令牌。SSE 端点没有加 @Public()，所以它天然走同一套判断：

text
没有令牌 → 401 AUTH_REQUIRED
令牌过期 → 401 AUTH_TOKEN_EXPIRED
角色不足 → 403（在控制器里判断）

代价是浏览器原生 EventSource 不能设置请求头。三种绕法：

方案问题
把令牌放 query（?access_token=）令牌进入访问日志、浏览器历史、Referer，等于泄露
改成 Cookie 会话需要把现有 Bearer 体系推倒重来，还要处理 CSRF
用 fetch 消费 SSE 流需要自己实现重连与 Last-Event-ID，但令牌仍在头里

示例选择第三种。客户端大致这样写：

ts
let lastEventId: string | null = null;

async function connect(token: string): Promise<void> {
  const response = await fetch('/api/realtime/events', {
    headers: {
      authorization: `Bearer ${token}`,
      ...(lastEventId ? { 'last-event-id': lastEventId } : {}),
    },
  });
  const reader = response.body!.getReader();
  // 解析 \n\n 分隔的帧：id / event / data；断线后带着 lastEventId 重新 connect
}

EventSource 能自动带 Last-Event-ID，fetch 版本需要自己记住最后一帧的 id。这一点在「常见坑」里会再提一次：两者只能选一个，不能既想要自定义头又想要协议自动重连。

3. 事件 ID 是「回放游标」，不是业务编号 ​

每发布一条事件，RealtimeService 自增一个进程内序号：

text
id: 1
event: order.created
data: {"orderId":"...","status":"pending","totalCents":49900}
  • id 只用于断线重连时比较「我收到哪了」，不承担业务含义；
  • 同一次业务变化会向两个房间各发一次，因此两个房间看到的事件 id 不同，这是正常的；
  • 服务端保留最近 REALTIME_HISTORY_SIZE（默认 200）条事件，重连时把 id > Last-Event-ID 且属于该连接房间的事件补发；
  • 超出窗口的事件补不回来——这是有意的取舍：实时通道只保证「短暂断线不丢」，长期离线应该重新拉一次列表接口。

4. 心跳解决的是「中间层以为你死了」 ​

SSE 连接空闲时没有任何字节流动。Nginx 的 proxy_read_timeout、云负载均衡的 idle timeout 通常是 60 秒，到点直接断。心跳就是一个注释帧：

text
: ping

以冒号开头的行是 SSE 注释，客户端不会触发 onmessage，但连接上有字节流动，代理会重置空闲计时。默认 15 秒一次，低于常见的 60 秒阈值，又不会产生明显流量。

还有两个配套设置：

  • X-Accel-Buffering: no：Nginx 默认缓冲 upstream 响应，不关掉的话事件会攒在缓冲区里，表现为「本地 curl 能收到，经过网关就延迟几十秒」；
  • retry: 3000：告诉客户端断线后 3 秒再重连，避免断网恢复瞬间所有客户端同时重连。

5. 房间模型：个人房间推导，共享房间校验 ​

房间谁能订阅谁往里发
user:<id>只有该用户本人，id 从令牌的 sub 取，不接受客户端传参订单服务在下单/状态变更后
orders只有 admin，在控制器里判断角色同一处发布，供管理看板订阅

关键点：

  1. 查询参数只允许 room=orders（class-validator 的 @IsIn），传别的值直接 400；
  2. 即使传了 orders，非 admin 也是 403 REALTIME_ROOM_FORBIDDEN；
  3. 个人房间永远由服务端根据令牌拼接，客户端无法通过改参数订阅别人的订单事件。

发布端不按角色裁剪字段，而是按房间决定发给谁。订单摘要里没有敏感信息，但如果以后要推手机号、地址，正确做法是拆成更细的事件或单独的房间，而不是在订阅端过滤。

6. 进程内订阅表的天花板 ​

RealtimeService 用 Map<clientId, Subscriber> 保存连接。单实例下没问题，多副本部署时：

  • 用户 A 连在实例 1，订单请求落在实例 2；
  • 实例 2 发布事件时，实例 1 的订阅表里没有这条连接，事件丢失。

正确做法是 Redis Pub/Sub（或 NATS/Kafka）：每个实例订阅同一个频道，收到后只投递给本实例的连接。本章没有实现，列在未完成清单里；但服务接口已经按「发布/订阅」拆开，替换扩散层时不需要改订单模块。

逐步拆解 ​

1. 帧格式：单独抽出来，因为错一个字符就静默丢帧 ​

ts
export function formatSseFrame(input: SseFrameInput): string {
  const lines: string[] = [];
  if (input.id !== undefined) {
    lines.push(`id: ${input.id}`);
  }
  if (input.event) {
    lines.push(`event: ${input.event}`);
  }
  if (input.data !== undefined) {
    // JSON.stringify 不会产生裸换行，所以 data 永远是单行，不需要拆成多个 data: 行
    lines.push(`data: ${JSON.stringify(input.data)}`);
  }
  return `${lines.join('\n')}\n\n`;
}

/** 注释帧（以冒号开头）不会触发客户端 onmessage，只用于心跳保活 */
export function formatSseComment(text: string): string {
  return `: ${text.replace(/[\r\n]+/g, ' ')}\n\n`;
}

data 用 JSON.stringify，所以永远不会出现裸换行，不需要拆成多个 data: 行。注释帧会把换行压平，防止调用方传入的文本「注入」出额外的 id: / event: 字段。这两个函数有 4 个单测。

2. 订阅、回放与发布 ​

ts
subscribe(options: SubscribeOptions): Subscription {
  const clientId = randomUUID();
  const rooms = new Set<string>([userRoom(options.userId), ...(options.rooms ?? [])]);

  const lastEventId = options.lastEventId;
  const replay =
    lastEventId === undefined
      ? []
      : this.history.filter((event) => event.id > lastEventId && rooms.has(event.room));

  const subscriber: Subscriber = {
    clientId,
    rooms,
    listener: () => undefined,
  };
  this.subscribers.set(clientId, subscriber);

  this.logger.log(
    JSON.stringify({
      msg: 'realtime.subscribed',
      clientId,
      userId: options.userId,
      rooms: [...rooms],
      replayed: replay.length,
    }),
  );

  return {
    clientId,
    rooms: [...rooms],
    replay,
    unsubscribe: () => {
      if (this.subscribers.delete(clientId)) {
        this.logger.log(JSON.stringify({ msg: 'realtime.unsubscribed', clientId }));
      }
    },
  };
}

subscribe 只做登记与筛选，不认识 HTTP。replay 是返回值而不是回调，控制器可以先补发历史，再绑定实时写入：

ts
bind(clientId: string, listener: (event: RealtimeEvent) => void): void {
  const subscriber = this.subscribers.get(clientId);
  if (!subscriber) {
    // 订阅后立刻断开（客户端秒退）是正常现象，不报错
    return;
  }
  subscriber.listener = listener;
}
ts
publish(room: string, event: string, data: unknown): RealtimeEvent {
  this.sequence += 1;
  const envelope: RealtimeEvent = { id: this.sequence, room, event, data };

  this.history.push(envelope);
  if (this.history.length > this.historySize) {
    this.history.splice(0, this.history.length - this.historySize);
  }

  let delivered = 0;
  for (const subscriber of this.subscribers.values()) {
    if (!subscriber.rooms.has(room)) {
      continue;
    }
    subscriber.listener(envelope);
    delivered += 1;
  }

  this.logger.log(
    JSON.stringify({ msg: 'realtime.published', id: envelope.id, room, event, delivered }),
  );
  return envelope;
}

发布时遍历所有订阅者，只有 rooms.has(room) 的连接才会收到。历史队列是简单的数组裁剪，超过 historySize 从头部删除。

3. 控制器：把「谁可以订阅」写死在这里 ​

ts
/**
 * SSE 入口。鉴权走全局 JwtAuthGuard——它只从 Authorization 头取令牌，
 * SSE 在这里没有另起一套认证：谁能连上，与谁能调 HTTP 接口是同一个判断。
 *
 * 用 @Res() 直接写原始响应，而不是 @Sse() + Observable：
 * 心跳、Last-Event-ID 补发、连接关闭清理都需要精确控制写入时机。
 */
@Get('events')
events(
  @Query() query: RealtimeQueryDto,
  @Headers('last-event-id') lastEventIdHeader: string | undefined,
  @CurrentUser() user: AuthenticatedUser,
  @Res() response: Response,
): void {
  const extraRooms: string[] = [];
  if (query.room === ORDERS_ROOM) {
    if (user.role !== 'admin') {
      throw new ForbiddenException({
        code: 'REALTIME_ROOM_FORBIDDEN',
        message: 'orders 房间只对 admin 开放',
        details: { room: ORDERS_ROOM, actualRole: user.role },
      });
    }
    extraRooms.push(ORDERS_ROOM);
  }

  const parsedLastEventId = Number.parseInt(lastEventIdHeader ?? '', 10);
  const lastEventId =
    Number.isFinite(parsedLastEventId) && parsedLastEventId > 0 ? parsedLastEventId : undefined;

  const subscription = this.realtime.subscribe({
    userId: user.id,
    rooms: extraRooms,
    lastEventId,
  });

  response.status(HttpStatus.OK);
  response.setHeader('content-type', 'text/event-stream; charset=utf-8');
  response.setHeader('cache-control', 'no-cache, no-transform');
  response.setHeader('connection', 'keep-alive');
  // Nginx 默认缓冲 upstream 响应，事件会攒到缓冲区满才下发，必须显式关掉
  response.setHeader('x-accel-buffering', 'no');
  response.flushHeaders();

  // retry 告诉浏览器断线后等多久重连；放在第一帧，客户端拿到就能用
  response.write('retry: 3000\n\n');
  for (const event of subscription.replay) {
    response.write(formatSseFrame({ id: event.id, event: event.event, data: event.data }));
  }
  response.write(
    formatSseComment(
      `connected client=${subscription.clientId} rooms=${subscription.rooms.join(',')}`,
    ),
  );

  this.realtime.bind(subscription.clientId, (event) => {
    response.write(formatSseFrame({ id: event.id, event: event.event, data: event.data }));
  });

  // 心跳只发注释帧：不产生事件、不占 id，中间的代理也能据此判断连接还活着
  const heartbeat = setInterval(() => {
    response.write(formatSseComment('ping'));
  }, this.heartbeatMs);
  heartbeat.unref();

  const cleanup = () => {
    clearInterval(heartbeat);
    subscription.unsubscribe();
  };
  response.on('close', cleanup);
  response.on('error', cleanup);
}

几个细节值得单独说：

  • @Res() 直接写响应，而不是 @Sse() + Observable。心跳定时器、重连补发、连接关闭清理都需要精确控制写入时机，Observable 的生命周期反而更难对齐；
  • response.on('close') 同时清理定时器与订阅表。漏掉这一步，客户端关页面后订阅表会一直增长，心跳还会往已关闭的流里写；
  • heartbeat.unref() 让心跳定时器不阻止进程退出，优雅关闭时不会卡住。

4. 事件来源：订单服务发布，实时模块不反向依赖订单 ​

ts
/**
 * 订单事件只推摘要，不推整张订单：
 * - `user:<id>` 是当事人房间，只有订单所属用户能订阅；
 * - `orders` 是管理端看板房间，订阅时的角色校验在网关层完成。
 *
 * 两个房间各发布一次，得到两个不同的事件 id——事件 id 是「每条连接的回放游标」，
 * 不是全局业务编号，所以同一次业务变化在不同房间里有独立序号是正常的。
 */
private publishOrderEvent(
  order: Pick<OrderView, 'id' | 'userId' | 'status' | 'totalCents'>,
  event: 'order.created' | 'order.updated',
): void {
  const payload = {
    orderId: order.id,
    status: order.status,
    totalCents: order.totalCents,
  };
  this.realtime.publish(userRoom(order.userId), event, payload);
  this.realtime.publish(ORDERS_ROOM, event, payload);
}

发布发生在事务提交之后（下单、状态迁移、超时关单三处调用），避免事务回滚后客户端已经收到「下单成功」的通知。

5. 长连接不进 HTTP 延迟指标 ​

SSE 请求可能挂几十分钟，res.on('finish') 时才记录耗时会直接把 p95 拉爆。指标中间件会在 finish 时检查 Content-Type，是事件流就跳过：

ts
import type { Request, RequestHandler } from 'express';
import type { MetricsService } from './metrics.service.js';

/** Express 匹配到路由后挂上的路由定义，`path` 是带参数的模板 */
type RoutableRequest = Request & { route?: { path?: string } };

/**
 * HTTP 指标中间件。
 *
 * 为什么不是拦截器：Guard 在拦截器之前执行，401/403 的请求根本进不了拦截器，
 * 而「鉴权失败有多少」恰恰是最需要监控的指标之一。中间件能看到所有已完成响应。
 *
 * 路由标签取 Express 匹配到的路由模板（如 `/api/orders/:id`），
 * 而不是真实 URL——否则每个订单 id 都会变成一条时间序列。
 */
export function createHttpMetricsMiddleware(metrics: MetricsService): RequestHandler {
  return (req, res, next) => {
    const startedAt = Date.now();

    res.on('finish', () => {
      // SSE 是长连接：请求可能要挂几十分钟，记进延迟分位会把 p95 直接拉爆。
      // 实时连接的规模用 /api/realtime/stats 观察，不走 HTTP 指标。
      const contentType = res.getHeader('content-type');
      if (typeof contentType === 'string' && contentType.startsWith('text/event-stream')) {
        return;
      }

      metrics.recordHttp({
        method: req.method,
        // 未匹配到路由（404）不保留具体路径，避免扫描器把基数打爆
        route: (req as RoutableRequest).route?.path ?? 'unmatched',
        statusCode: res.statusCode,
        durationMs: Date.now() - startedAt,
      });
    });

    next();
  };
}

实时连接的规模改用 GET /api/realtime/stats 观察（当前连接数、各房间连接数、事件序号）。它只是一个进程内快照，不是 Prometheus 指标。

企业级做法 ​

  • 连接数配额：按用户限制并发连接（例如 3 条），防止一个页面反复重连把订阅表撑爆；本章只有全局统计，没有限额。
  • 多实例扩散：Redis Pub/Sub 是成本最低的方案；要求「断线后仍能补历史」时，事件必须先落库（Outbox）再推，实时通道只做「通知有新事件」，客户端凭游标回拉。
  • 慢客户端背压：response.write() 返回 false 表示内核缓冲区已满。本章没有处理，持续慢的客户端会让 Node 内存增长；生产应设置写缓冲上限，超限主动断开并让客户端重连补发。
  • 鉴权时效：长连接建立后 JWT 过期不会自动断开。可以给连接设置最长存活时间（例如 30 分钟），到期发一个 reauth 事件并关闭，让客户端带新令牌重连。
  • 可观测性：至少要有「当前连接数、按房间分布、断连原因、补发条数」四个指标；验签失败、鉴权失败要能告警，否则攻击面不可见。
