10 文件与第三方集成 ​

文件上传、对象存储与第三方集成：超时、重试、幂等与安全边界。

成稿正文、示例代码与验收标准均已完整，可直接跟练

文件上传和第三方回调是两类最容易被「先跑通再说」的功能：上传只要 multer 一挂就能用，回调只要收得到 JSON 就算接通。但真正上线后会遇到的是——用户把 .exe 改名成 .png、文件名里带 ../../、支付平台重试了 5 次同一个回调、攻击者把昨天的合法请求原样重放。

本章实现状态

本地磁盘存储的上传/下载已实现：大小与类型双重校验、文件头魔数校验、UUID 落盘、归属鉴权、Content-Disposition: attachment。支付回调已实现：HMAC-SHA256 验签、300 秒时间窗、事件 ID 幂等表（唯一索引兜底并发）。对象存储直传、病毒扫描、回调异步化、密钥轮换未实现，文末逐项标注。

本章目标 ​

  1. 说清「服务端转发」与「客户端直传对象存储」的取舍，并给出可替换的存储边界；
  2. 上传链路做三层校验：大小、类型（声明 + 魔数）、文件名与落盘路径；
  3. 下载链路做归属鉴权，并让浏览器只能下载、不能渲染；
  4. 用 HMAC + 时间戳 + 事件 ID 幂等表，同时挡住伪造、重放与重复处理；
  5. 用可复现的 curl 与 e2e 证明上述每一条，而不是只写在文档里。

概念与原理 ​

1. 直传还是转发 ​

方案链路优点代价
服务端转发浏览器 → API → 对象存储鉴权、校验、审计都在一个地方；密钥不出服务端文件过一次应用，占带宽与内存；大文件要流式处理
客户端直传浏览器 → 对象存储（预签名 URL）应用不承载文件流量；天然支持分片与断点续传校验只能做「事前声明 + 事后回调」；密钥/签名管理更复杂

本示例选转发，因为本章的重点是「在服务端把住安全边界」，而且本地磁盘适配器不需要任何外部服务就能跑。存储被抽成 FileStorageService：换成 S3/MinIO 时，save 与 getForDownload 的签名不变，控制器不用改。直传方案是设计讲解，未实现。

2. 上传的三层校验 ​

层拦什么本示例的位置
传输层超大文件、多文件字段FileInterceptor 的 limits（5MB / 1 个文件）
业务层配置上限、空文件、类型白名单FileStorageService.save（默认 2MB）
内容层声明类型与真实内容不符sniffContentType 读文件头魔数

只信 Content-Type 是不够的：它由客户端填写，改成 image/png 零成本。真正的防线是文件头：

类型魔数
PNG89 50 4E 47 0D 0A 1A 0A
JPEGFF D8 FF
PDF%PDF-
text/plain无魔数；要求无 NUL 字节且可按 UTF-8 解码

声明 image/png 但内容是文本，会得到 FILE_TYPE_MISMATCH；未知二进制（例如 MZ 开头的可执行文件）直接 FILE_TYPE_NOT_ALLOWED。

3. 文件名不是路径 ​

客户端传来的 filename 只用于展示与下载时的文件名，永远不参与落盘路径。落盘名是服务端生成的 UUID：

text
storage/uploads/
├── 27ff9cca-882f-4fed-a25a-0e7836a9169e.blob   # 原始字节
└── 27ff9cca-882f-4fed-a25a-0e7836a9169e.json   # 元数据：原名、类型、大小、sha256、ownerId

这样 ../../etc/passwd 最多变成一个显示名，无法穿越目录。清洗函数还会去掉路径分隔符、控制字符、引号——不是为了防止落盘（落盘不用它），而是为了防止下载响应头被注入。

元数据放在侧车 JSON 而不是数据库，是为了让示例不依赖新表；代价是无法按用户分页列出文件、无法做配额统计。生产环境应该把元数据入库，blob 放对象存储，见未完成清单。

4. 下载：鉴权 + 不可渲染 ​

下载接口与普通接口共用全局 JWT，然后做归属校验：非 admin 只能下载 ownerId === 当前用户 的文件。

响应头有三个必须项：

text
Content-Type: image/png
Content-Disposition: attachment; filename="pixel.png"; filename*=UTF-8''pixel.png
X-Content-Type-Options: nosniff
X-Content-SHA256: c414cd0e...
  • attachment 强制下载。如果上传的是 HTML 且内联展示，同源下就能执行脚本（存储型 XSS）；
  • nosniff 禁止浏览器猜类型；
  • X-Content-SHA256 让客户端校验内容完整性；中文文件名走 RFC 5987 的 filename*，避免乱码。

5. 回调的认证模型：为什么不是 JWT ​

回调方是支付平台，不是用户，没有用户身份可以签发令牌。它证明「我是我」的方式是共享密钥 + 报文签名：

text
signature = HMAC-SHA256(secret, `${timestamp}.${rawBody}`)

三个设计点：

  1. 签原始字节，不是反序列化后的对象。JSON 重新序列化会改变字段顺序、空格、数字格式，签名必然对不上；
  2. 时间戳进签名：攻击者改 timestamp 就必须重算签名，拿不到密钥就改不动；
  3. timingSafeEqual 比较：普通 === 在首个不同字节就返回，理论上可被逐字节探测。

6. 重放防护分三层 ​

层挡住什么实现
时间窗昨天抓包、今天重放x-webhook-timestamp 与服务器时间偏差 ≤ 300 秒
事件幂等表同一个事件被重复投递（平台重试、网络重发）webhook_events.event_id 唯一索引
先查后插 + 捕获唯一冲突两个相同事件并发到达快路径 findOne，慢路径靠数据库唯一约束兜底

处理顺序必须是「验签 → 查幂等 → 执行业务」。如果把业务放在前面，一次重放就可能重复发货。示例里的业务副作用是一条审计记录，重复回调时审计数仍为 1，这一点有 e2e 断言。

回调成功统一返回 200（首次 duplicate: false，重复 duplicate: true）。不要对重复回调返回 4xx/5xx：平台会认为失败并继续重试，形成死循环。

逐步拆解 ​

1. 类型识别与文件名清洗 ​

ts
export function sniffContentType(buffer: Buffer): string | null {
  if (buffer.length >= 8 && buffer.subarray(0, 8).equals(PNG_SIGNATURE)) {
    return 'image/png';
  }
  if (buffer.length >= 3 && buffer[0] === 0xff && buffer[1] === 0xd8 && buffer[2] === 0xff) {
    return 'image/jpeg';
  }
  if (buffer.length >= 5 && buffer.subarray(0, 5).toString('ascii') === '%PDF-') {
    return 'application/pdf';
  }
  // 纯文本没有魔数：没有 NUL 字节且能按 UTF-8 解码，才当作文本
  if (!buffer.includes(0)) {
    try {
      new TextDecoder('utf-8', { fatal: true }).decode(buffer);
      return 'text/plain';
    } catch {
      return null;
    }
  }
  return null;
}
ts
export function sanitizeFileName(original: string): string {
  const base = Array.from(basename(original))
    // 控制字符（\x00-\x1f、\x7f）会让响应头与日志出现不可见字符，直接剔除
    .filter((char) => char.charCodeAt(0) > 31 && char.charCodeAt(0) !== 127)
    .join('');
  const cleaned = base.replace(/[^\w.\-\u4e00-\u9fa5]+/g, '_').replace(/^\.+/, '');
  return cleaned.slice(0, 120) || 'unnamed';
}

2. 保存：校验顺序就是失败时的可读性 ​

ts
async save(actor: AuthenticatedUser, file: UploadedFileLike | undefined): Promise<StoredFileView> {
  if (!file) {
    throw new BadRequestException({
      code: 'FILE_REQUIRED',
      message: '请在 multipart/form-data 的 file 字段上传文件',
    });
  }
  if (file.size === 0) {
    throw new BadRequestException({ code: 'FILE_EMPTY', message: '不能上传空文件' });
  }
  if (file.size > this.maxSizeBytes) {
    throw new PayloadTooLargeException({
      code: 'FILE_TOO_LARGE',
      message: `文件超过 ${this.maxSizeBytes} 字节上限`,
      details: { size: file.size, maxSize: this.maxSizeBytes },
    });
  }

  const sniffed = sniffContentType(file.buffer);
  const declared = file.mimetype;
  if (!sniffed || !ALLOWED_CONTENT_TYPES.includes(sniffed as (typeof ALLOWED_CONTENT_TYPES)[number])) {
    throw new BadRequestException({
      code: 'FILE_TYPE_NOT_ALLOWED',
      message: `不支持的文件类型：${declared}`,
      details: { declared, sniffed, allowed: ALLOWED_CONTENT_TYPES },
    });
  }
  // 声明类型与真实内容必须一致：否则「改名攻击」会绕过白名单
  if (sniffed !== declared) {
    throw new BadRequestException({
      code: 'FILE_TYPE_MISMATCH',
      message: '文件内容与声明的 Content-Type 不一致',
      details: { declared, sniffed },
    });
  }

  const id = randomUUID();
  const name = sanitizeFileName(file.originalname);
  const meta: StoredFileMeta = {
    id,
    name,
    contentType: sniffed,
    size: file.size,
    sha256: createHash('sha256').update(file.buffer).digest('hex'),
    ownerId: actor.id,
    createdAt: new Date().toISOString(),
  };

  await mkdir(this.root, { recursive: true });
  await writeFile(join(this.root, `${id}.blob`), file.buffer);
  await writeFile(join(this.root, `${id}.json`), JSON.stringify(meta), 'utf8');

  this.logger.log(
    JSON.stringify({ msg: 'file.stored', id, ownerId: actor.id, size: meta.size, contentType: sniffed }),
  );
  return this.toView(meta);
}

空文件、超限、类型不符、类型撒谎分别抛不同的错误码，客户端不需要解析自然语言。

3. 读取与归属校验 ​

ts
async getForDownload(
  id: string,
  actor: AuthenticatedUser,
): Promise<{ meta: StoredFileMeta; absolutePath: string }> {
  const meta = await this.readMeta(id);
  if (!meta) {
    throw new NotFoundException({ code: 'FILE_NOT_FOUND', message: `文件 ${id} 不存在` });
  }
  if (actor.role !== 'admin' && meta.ownerId !== actor.id) {
    throw new ForbiddenException({
      code: 'FILE_FORBIDDEN',
      message: '只能下载自己上传的文件',
      details: { ownerId: meta.ownerId },
    });
  }
  return { meta, absolutePath: join(this.root, `${meta.id}.blob`) };
}

private async readMeta(id: string): Promise<StoredFileMeta | null> {
  try {
    const raw = await readFile(join(this.root, `${id}.json`), 'utf8');
    return JSON.parse(raw) as StoredFileMeta;
  } catch {
    return null;
  }
}

private toView(meta: StoredFileMeta): StoredFileView {
  return { ...meta, downloadUrl: `/api/files/${meta.id}` };
}

4. 控制器：上传与下载 ​

ts
/**
 * 上传接口。multer 用内存存储：
 * - 大小上限在进入业务代码前就由 multer 拦住（limits），避免大文件把磁盘写满；
 * - 业务层再按配置校验一次，并检查文件头与声明类型是否一致；
 * - 写盘用的是服务端生成的 UUID 文件名，客户端的 filename 从不参与路径拼接。
 */
@Post()
@UseInterceptors(
  FileInterceptor('file', {
    // 这是第一道闸；业务层还有可配置的更严格上限（默认 2MB）
    limits: { fileSize: 5 * 1024 * 1024, files: 1 },
  }),
)
upload(
  @UploadedFile() file: UploadedFileLike | undefined,
  @CurrentUser() actor: AuthenticatedUser,
): Promise<StoredFileView> {
  return this.storage.save(actor, file);
}
ts
/**
 * 下载接口：鉴权与列表接口同一套（全局 JWT + 归属校验）。
 * 响应头里的 `x-content-sha256` 让客户端可以校验下载内容未被篡改。
 */
@Get(':id')
async download(
  @Param('id', new ParseUUIDPipe()) id: string,
  @CurrentUser() actor: AuthenticatedUser,
  @Res() response: Response,
): Promise<void> {
  const { meta, absolutePath } = await this.storage.getForDownload(id, actor);

  response.setHeader('content-type', meta.contentType);
  response.setHeader('content-length', String(meta.size));
  response.setHeader('x-content-sha256', meta.sha256);
  // 永远作为附件下载：即使上传的是 HTML/JS，也不会在同源下被浏览器渲染执行
  response.setHeader(
    'content-disposition',
    `attachment; filename="${asciiFallback(meta.name)}"; filename*=UTF-8''${encodeURIComponent(meta.name)}`,
  );
  response.setHeader('x-content-type-options', 'nosniff');

  createReadStream(absolutePath).pipe(response);
}

5. 验签是纯函数，因此可以单测穷举 ​

ts
export function signWebhook(secret: string, timestamp: string, rawBody: string): string {
  return `sha256=${createHmac('sha256', secret).update(`${timestamp}.${rawBody}`).digest('hex')}`;
}

export function verifyWebhookSignature(input: SignatureInput): SignatureRejection | null {
  const nowSeconds = Math.floor((input.nowMs ?? Date.now()) / 1000);
  const timestamp = Number.parseInt(input.timestamp ?? '', 10);

  if (!Number.isFinite(timestamp) || Math.abs(nowSeconds - timestamp) > input.toleranceSeconds) {
    return 'timestamp_invalid';
  }

  const expected = Buffer.from(signWebhook(input.secret, String(timestamp), input.rawBody));
  const provided = Buffer.from(input.signature ?? '');
  if (provided.length !== expected.length || !timingSafeEqual(provided, expected)) {
    return 'signature_invalid';
  }

  return null;
}

5 个单测覆盖：正确签名、篡改一个字节、时间戳过期、缺字段、长度不同的签名。

6. 回调处理：顺序不可换 ​

ts
async handle(
  headers: WebhookHeaders,
  rawBody: string | undefined,
  payload: PaymentWebhookDto,
): Promise<WebhookResult> {
  if (!rawBody) {
    throw new BadRequestException({
      code: 'WEBHOOK_RAW_BODY_MISSING',
      message: '缺少原始请求体，无法验签（需要在 NestFactory 中开启 rawBody）',
    });
  }

  const rejection = verifyWebhookSignature({
    rawBody,
    timestamp: headers.timestamp,
    signature: headers.signature,
    secret: this.secret,
    toleranceSeconds: this.toleranceSeconds,
  });
  if (rejection) {
    this.logger.warn(
      JSON.stringify({ msg: 'webhook.rejected', reason: rejection, eventId: payload.id }),
    );
    throw new UnauthorizedException({
      code:
        rejection === 'timestamp_invalid'
          ? 'WEBHOOK_TIMESTAMP_INVALID'
          : 'WEBHOOK_SIGNATURE_INVALID',
      message:
        rejection === 'timestamp_invalid'
          ? `时间戳缺失或偏移超过 ${this.toleranceSeconds} 秒，按重放拒绝`
          : '签名校验失败',
    });
  }

  const existing = await this.events.findOne({ where: { eventId: payload.id } });
  if (existing) {
    this.logger.log(JSON.stringify({ msg: 'webhook.duplicate', eventId: payload.id }));
    return { received: true, duplicate: true, eventId: payload.id, type: payload.type };
  }

  try {
    await this.events.save(
      this.events.create({
        eventId: payload.id,
        type: payload.type,
        payload: payload.data,
      }),
    );
  } catch (error) {
    // 并发重复：唯一索引拒绝第二条，说明另一个请求已经处理过
    if (isUniqueViolation(error)) {
      return { received: true, duplicate: true, eventId: payload.id, type: payload.type };
    }
    throw error;
  }

  await this.audit.record({
    action: `webhook.${payload.type}`,
    actorId: null,
    targetId: payload.id,
    summary: `收到支付平台回调 ${payload.id}（${payload.type}）`,
  });

  this.logger.log(JSON.stringify({ msg: 'webhook.processed', eventId: payload.id }));
  return { received: true, duplicate: false, eventId: payload.id, type: payload.type };
}

数据库层面的幂等靠实体上的唯一索引：

ts
import { Column, CreateDateColumn, Entity, Index, PrimaryGeneratedColumn } from 'typeorm';

/**
 * 回调事件表。
 *
 * `event_id` 上的唯一索引是幂等的最终防线：
 * 两个完全相同的回调并发到达时，先查后插会同时通过，只有数据库能挡住第二个。
 * 表里的记录本身就是「已处理」的凭证，重复回调直接返回成功，不再执行业务副作用。
 */
@Entity('webhook_events')
@Index('uq_webhook_events_event_id', ['eventId'], { unique: true })
export class WebhookEventEntity {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column({ name: 'event_id', type: 'varchar', length: 128 })
  eventId: string;

  @Column({ type: 'varchar', length: 128 })
  type: string;

  /** simple-json 在 Postgres 与 sqljs 下都能用，测试不需要单独改类型 */
  @Column({ type: 'simple-json' })
  payload: Record<string, unknown>;

  @CreateDateColumn({ name: 'created_at' })
  createdAt: Date;
}

7. 控制器与 rawBody ​

ts
/**
 * 支付平台回调。
 *
 * `@Public()` 只是跳过 JWT：这个接口的认证手段是 HMAC 签名，
 * 而不是用户令牌——回调方是第三方服务，没有用户身份。
 */
@Public()
@Post('payments')
@HttpCode(HttpStatus.OK)
payments(
  @Headers('x-webhook-signature') signature: string | undefined,
  @Headers('x-webhook-timestamp') timestamp: string | undefined,
  @Req() request: RawBodyRequest<Request>,
  @Body() body: PaymentWebhookDto,
): Promise<WebhookResult> {
  return this.webhooks.handle(
    { signature, timestamp },
    request.rawBody?.toString('utf8'),
    body,
  );
}

request.rawBody 必须在创建应用时开启 rawBody: true（main.ts 与 e2e 都显式传了这个选项）。否则 @Body() 已经把 JSON 解析成对象，拿不到原始字节，验签必然失败——错误码是 WEBHOOK_RAW_BODY_MISSING，不是签名错误。

企业级做法 ​

  • 对象存储 + 预签名直传：API 只负责签发短时效 URL 与记录元数据，文件不经过应用；上传完成后由对象存储回调或客户端确认来落库。要额外考虑分片上传、断点续传、跨域与桶策略。
  • 回调异步化：验签与幂等落库后立刻 200，把业务处理丢进队列（第 08 章的 BullMQ）。本章是同步写一条审计，生产里「发货、加余额」这类副作用不应占用回调请求的 RT。
  • 密钥轮换：支持同时配置新旧两个密钥，新密钥先用于验签、旧密钥保留一个重试周期，避免切换瞬间全量 401。本章只有单密钥。
  • 乱序与补偿：支付平台可能先发 refunded 再发 succeeded。要有事件序号或业务版本号，并提供「按事件 id 拉取详情」的补偿接口；本章只做幂等，不保证顺序。
  • 内容安全：接入病毒扫描、图片转码（去 EXIF）、PDF 沙箱预览；对上传目录做容量与数量配额。本章均未实现。
  • 可观测性：验签失败率、重复回调率、上传失败按错误码分桶，任一异常升高都应告警。

延伸追问 ​

  • 直传方案里，服务端已经签发了 URL，如何防止客户端上传「声明是图片、实际是脚本」的文件？
  • 回调处理已经做了幂等，为什么还需要时间窗？只用事件 id 唯一索引不够吗？
  • 如果把回调业务放进队列，duplicate: true 应该在入队前返回还是入队后返回？两种顺序各有什么风险？
  • 上传文件的 sha256 除了校验下载，还能用来做什么？（提示：秒传、去重、审计取证）
