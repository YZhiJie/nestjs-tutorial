# EP.01 初识 NestJS

> 对应正文：[01. 介绍](../docs/01-introduction/index.md)

## 剧情回顾

- **第 1 格**：标签君接手 Express 老项目——路由、业务、数据库调用搅在一个回调里，百人项目十种目录结构。
- **第 2 格**：码叔揭开 Nest 的组织方式：模块装配控制器与提供者，各构件职责分明。
- **第 3 格**：像素酱实测请求处理管线：中间件、守卫、拦截器、管道、过滤器各司其职。
- **第 4 格**：码叔结案：中大型服务端首选 Nest，结构即文档。

## 知识点拆解

### 第 1 格 · 为什么需要框架

Express 的自由度是把双刃剑：没有强制约束，项目结构完全取决于开发者素养。路由、校验、业务、持久化混在一个回调里：

```ts
app.get('/users', (req, res) => {
  // 校验、鉴权、业务、持久化全部混在一起
});
```

大项目的真实痛点不是「能不能实现」，而是「三个月后还敢不敢改」。Nest 用「约定优于配置」解决它。

### 第 2 格 · 三大构件

Nest 应用的基本单位是模块（`@Module()`），模块里装配两类东西：接收流量的控制器（`@Controller()`）与承载业务的提供者（`@Injectable()`）。这套模型直接来自 Angular——依赖注入、装饰器、模块化三大件在 Node 服务端原样复用，同时以 RxJS 为一等公民支持函数响应式编程。

### 第 3 格 · 请求处理管线

一个请求进站后按固定顺序穿越五道关卡：中间件最先拿到原始请求；守卫决定请求资格；拦截器在控制器前后插入横切逻辑；管道负责参数转换与校验；任何一层抛出的异常最终由异常过滤器统一兜底。口诀：「中守拦管，控服拦异」。

### 第 4 格 · 什么场景选 Nest

- 团队 3 人以上、接口 20 个以上的中大型服务端项目，收益最大；
- 几十行的小脚本用 Nest 是牛刀杀鸡，直接 Express 更轻；
- 入门门槛在装饰器与依赖注入，用前确认 tsconfig 开启 `experimentalDecorators` 与 `emitDecoratorMetadata`。

## 坑点清单

1. `reflect-metadata` 必须在入口文件第一行导入，否则依赖注入元数据缺失；
2. 忘开装饰器编译开关时报错信息晦涩，先查 tsconfig 再查代码；
3. Nest 不是银弹：结构约束换来的是前期样板代码，小项目慎选。

## 自测 3 题（含答案）

1. Nest 默认基于哪个 HTTP 平台？——**答案**：Express，可通过适配器切换 Fastify。
2. 请求处理管线按顺序是什么？——**答案**：中间件 → 守卫 → 拦截器（前）→ 管道 → 控制器 → 拦截器（后），异常过滤器全程兜底。
3. `reflect-metadata` 的作用是什么？——**答案**：提供装饰器元数据 API，DI 容器靠它在运行时读取构造函数参数类型完成注入。
